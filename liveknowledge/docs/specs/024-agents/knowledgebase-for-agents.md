# Knowledgebase for agents

Status: **built** ([Build plan](../005-project-roadmap/build-plan.md) step 13), but for what
[What is built, and where it differs](#what-is-built-and-where-it-differs) lists.

The knowledgebase as agents use it: the MCP server and the CLI speak in pages, and every answer carries how far it
can be trusted.

## MCP tools

The platform tools every app has stay (find, create, rename, share, archive, delete and restore, with "knowledgebase" in their
words). The page tools replace livedocuments' element and page-layout tools:

| Tool           | Does                                                                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `get_context`  | The knowledgebase's Always in Context pages as Markdown, in tree order, within the budget, with its Review Period (`review_period`). Call it first.     |
| `list_pages`   | The page tree: ids, titles, depth, verified state, owner, review date, and once for them all the knowledgebase's Review Period (`review_period`). A connected file in the sidebar is a row with `kind: "connected"` and its `app`, no trust; `read_page` does not read it. |
| `search_pages` | Passages matching a query, each with its page, heading, verified state and date, `stale` and any `conflicts_with`.                                      |
| `read_page`    | One page as Markdown with the same trust fields, its backlinks, its subpages and its cover.                                                             |
| `create_page`  | A new page from Markdown under a parent. Never Verified.                                                                                                |
| `suggest_edit` | A change to a page (replace a passage, or append) with a reason. Lands as a suggestion for a person to accept.                                          |
| `write_page`   | Replaces a page's writing directly, and sets or removes its cover. Only with the `write` scope; never rewrites a Verified or Review Due page's writing. |
| `report_gap`   | Records a question the knowledgebase could not answer.                                                                                                  |
| `move_page`    | Moves a page in the tree.                                                                                                                               |
| `request_approval` | Puts a page Pending Approval for a person to approve or reject, or (`withdraw`) takes the request back ([Approval](../030-knowledgebase/approval.md)). Never approves. |
| `list_page_comments` | The comment threads at a page's foot, open by default ([Comments on a Page](../030-knowledgebase/page-comments.md)).                               |
| `change_page_comments` | Starts, replies to, resolves and reopens a page's threads, and edits or deletes the agent's own comments, each marked Generated by AI.             |

- Scopes: `read` (get, list, search, read, report, list comments), `suggest` (plus create, suggest, request
  approval and change comments), `write` (plus write and move). A token or OAuth grant names its scopes; the default for a new connection is `read` and `suggest`.
- Every read is counted for [AI Knowledge](../030-knowledgebase/ai-knowledge.md) under the client's name.
- Tool results are small by default (a passage, not a page) and name the next tool to call for more.

## CLI

`liveknowledge` mirrors the tools: `pages`, `search`, `read`, `new`, `suggest`, `write`, `move`, `context`, `gap`,
`approval` (request_approval), `comments` (list_page_comments), `discuss` (change_page_comments),
and `import <folder|zip>` and `export <dir>` (a knowledgebase as a folder of Markdown, links relative), so a knowledgebase can be kept
beside a repository.

## Share roles

An agent has the role of the person or token it acts for, narrowed by its scopes: a Viewer's agent can never suggest;
only an Editor's agent can hold `write`. A Participant writes pages in person
([Knowledgebases and pages](../030-knowledgebase/knowledgebases-and-pages.md#share-roles), owner 2026-11-21), but
the scopes are unchanged: a token below `write`, and every token of a Participant, suggests and never writes, as
before.

## What is built, and where it differs

Built in step 13: the api's suggestions, scopes and agent routes, the MCP's tools, the CLI's commands. The detail is
the [blueprint](blueprints/knowledgebase-for-agents.md).

- **`report_gap` is registered with the tools that read**, after `read_page`: a read-only connection may call it.
- **A page is named by its id or its title** (where one page alone has that title), in every tool and command, and
  the api resolves it: no tool looks a page up first. `suggest_edit` names the passage as `old_text` and what
  replaces it as `new_text`; `read_page` takes `heading` or `max_chars` and sends the first 6,000 characters unless
  asked.
- **Every page and passage answer carries the trust fields**: `verified` (`verified`, `review-due`,
  `never-verified`), `verified_at`, `verified_by` (the verifier's name, on `read_page`, where the accounts service
  has one), `review_due`, `stale` (the review is due) and `conflicts_with` (the pages an open conflict names).
- **The Review Period is the knowledgebase's, and no tool sets it.** `review_due` and `stale` are worked out from
  the knowledgebase's one period ([Verification](../030-knowledgebase/verification.md) "The Review Period") when an
  answer is made. `get_context` and `list_pages` (the CLI's `context` and `pages`) state it once as
  `review_period`: `30 days`, `90 days`, `180 days`, `365 days` or `never`, under which no page is `review-due` and
  none has a `review_due`. No tool or command takes a per-page interval; an Editor changes the period in
  Knowledgebase Settings (a token granted `write` may `PUT knowledge-settings`, which no tool wraps).
- **Scopes sit on the platform's tokens, which are read-only or full and nothing between.** A read-only token (the
  consent screen's choice, as before) holds `read`. A full token holds `read` and `suggest`, the default for a new
  connection. `write` is granted to one token in one knowledgebase by an Editor, in person
  (`PUT /api/documents/<id>/agents/<token>/scopes`, from the connection's card in AI Knowledge: **Allow Writing**
  and **Stop Writing**, each behind a confirmation), and is kept in that knowledgebase's room: the platform's token
  has no place for it, and the accounts service was not changed. The scopes narrow the role the token's person
  holds before any route runs, so a token without `write` acts as a Participant at most in every route of the
  knowledgebase (it cannot rename it, delete a page or restore a version either), and one with `read` alone as a
  Viewer. Sharing, archiving and deleting a whole knowledgebase are the index's, and take a full token as before.
- **A person's role still bounds the agent**: creating a page needs an Editor's agent holding `suggest`;
  suggesting needs a Participant's or an Editor's; a Viewer's agent only reads, whatever is granted.
- **`write_page`'s `cover`** ([The page surface](../030-knowledgebase/page-surface.md) "The cover") names its kind:
  a picture (`{ kind: "image", imageId, focus? }`), a theme gradient (`{ kind: "gradient", preset }`), an animated
  background (`{ kind: "animated", preset, colouring?, speed? }`) or `null`, with or without `markdown`; `read_page`
  answers the same shape. A cover alone is
  taken on any page; with `markdown`, the writing's rule below holds for the whole write. A cover it cannot take is
  refused (`invalid_cover`), naming what was wrong, and nothing is written. Every write here stamps the page as an
  agent's ([Verification](../030-knowledgebase/verification.md) "Made by a person or an agent").
- **`write_page` is refused on a page whose state is Verified** (`page_verified`) **or Review Due**
  (`page_review_due`), whatever the connection holds. A page whose review is due is the one most likely to need a
  person's eye, and an agent's rewrite would bury what the review was for: the agent suggests the edit
  (`suggest_edit` stays allowed on both), and a person reviews, verifies or rewrites the page. Only a page never
  verified is written directly.
- **The room knows its connections by token** (`agent_seen`): each API token that calls a knowledge route is
  noted with the name it is counted under, how it connects (the MCP server, the CLI or the token directly),
  whether it is read-only, the role of its person and when it was last seen (to the hour). `GET knowledge` answers
  each with the scopes it holds now. The token's id (never the token) is sent only to an Editor in person, the one
  caller the scopes route takes.
- **The agent's name** is the MCP client's `clientInfo.name` from the `initialize` handshake, cut to printable
  ASCII and 60 characters. The transport is stateless, so the name is remembered against the SHA-256 of the
  caller's token in the MCP's OAuth KV (200 days) and read back by each knowledgebase tool. The CLI's reads are
  counted under "CLI".
- **The tool descriptions tell an agent what to do** ("Call this first", "Prefer a verified passage"), as this spec
  asks, where the [MCP server](../015-api/mcp-server.md) spec's §4.15 has descriptions state facts only. A
  connector directory may flag them; the same guidance is in the server's instructions.
- **CLI**: `export <knowledgebase> <dir>` and `import <folder|zip>` take the knowledgebase and the folder as
  written here; `export --all --to <dir>` stays for a backup of every knowledgebase. `import` reads a Markdown
  folder and a Notion export. It refuses a Confluence export, which is HTML read through an inert DOM the CLI's
  runtime does not have, and leaves each picture as its caption, since the article Markdown the api takes has no
  picture form: both are imported in the app. `export` writes pictures as files under `pictures/`.
- **Not built**: scopes on the OAuth consent screen beyond read-only or full; a suggestion's diff as removed and added lines (the card has `before` and
  `after`); the pages view of `@liveknowledge/document-views` still prints a page link's stored text, where
  `read_page` and `GET pages/<page>` print the linked page's current title.
