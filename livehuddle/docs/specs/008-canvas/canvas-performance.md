# Canvas performance

A board of a thousand elements feels like a board of ten: panning, zooming, selecting, dragging and
drawing stay fluid, and a canvas at rest costs nothing. This spec states the budget, the reference
board it is measured on, and the rules every canvas feature keeps so the cost of a gesture follows
what the gesture touches, not the size of the board. The measurements behind it are in
[Canvas performance on large boards](../../research/canvas-performance.md).

## The reference board

- **One synthetic board, generated by a seeded builder**, so every run measures the same thing and
  no user content is involved: 1,000 elements in the mix real boards have (40% shapes, 30% arrows
  between them, 10% freehand strokes, 10% text, 5% paths, 5% stickies), spread over an area four
  screens wide and three high, with arrows routed behind boxes by default as drawn. As in real
  diagrams, an arrow joins a shape to one of its nearest neighbours, not to any shape on the board.
- It is opened twice: as a **whiteboard** tab and as a **diagram** tab, since the two render
  differently (ink projection, the dock, the Quick Style panel).

## The budget

Measured on the reference board in Chromium at 1440 × 900, at two zooms: **fit** (the whole board on
screen) and **100%**, with the CPU at the **reference speed**: the machine the budget was set on (a
fast desktop) throttled 4×, standing in for an ordinary laptop under load. Every measuring machine is
brought to that speed: it benchmarks itself, and Chrome's CPU throttle is set so the benchmark
takes as long as on the reference at 4×. A machine slower than the reference speed runs
unthrottled, and its report says its numbers read harsher than the budget. Every report states the
throttle it ran at.

| Moment                     | Budget                                                                                   |
| -------------------------- | ---------------------------------------------------------------------------------------- |
| At rest                    | No main-thread work in any frame: no animation-frame loop, no observer that feeds itself |
| Pan and zoom               | No task over 50 ms; no element view re-renders on a pan                                  |
| Dragging a selection       | No task over 50 ms; the median frame within 33 ms                                        |
| Marquee, pen stroke, hover | No task over 50 ms                                                                       |
| Selecting or deselecting   | One task, within 100 ms                                                                  |
| Opening the board          | Interactive within 3 s of the tab's data arriving                                        |

A gesture's cost scales with what it changes and what is on screen, never with the whole board.

### Dragging a very large selection

A selection of any size drags as smoothly as a few elements. Measured on the large-selection board
(1,770 elements: 900 labelled shapes in a 30 × 30 grid and 870 arrows, each joining a shape to its
right-hand neighbour), with every element selected:

| Moment                        | Budget                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------- |
| One pointer move of the drag  | At most 16 ms of script (the move's handler and the render it causes), median   |
| One frame of the drag         | At most 16 ms from the move to the frame painted (script, style, paint), median |
| A drag frame's arrow work     | At most 16 ms of CPU, held by a CPU-time test at that size                      |
| A typical (five-element) drag | No slower than before this budget                                               |
| A collaborator watching       | Sees the whole-board drag move live, not only on release                        |

The script and frame budgets are read unthrottled on a developer's laptop, the "mid-range laptop" it
stands for; the bench also reports them at the reference speed (4× slower), where they are not
budgets. The frame is what the page spends restyling and repainting what the drag shifts, which is
why a very large move shifts one layer, not each element ([Drag preview](drag-preview.md) "A very
large move rides as one layer").

## The rules

- **A still canvas does nothing.** Chrome that positions itself re-measures on a real change (a
  resize, a move, a layout event), and an observer never re-arms in a way that notifies itself
  again.
- **A pan or zoom moves the canvas, not its elements.** The viewport is one transform on the
  element layer. No element view takes the pan offset as a prop or reads it from a context; zoom
  reaches only what is counter-scaled to stay a constant screen size (grips, handles, badges).
- **A pan or zoom repaints no filter.** A look every element of a kind wears by default (a soft
  shadow) is drawn as a picture made once, never as a live CSS or SVG filter: Safari runs every
  filter on screen again on every frame of a pan, a zoom or a page glide, and fifty sticky notes'
  blurred peel cost about 180 ms a frame in WebKit at a phone's size. The sticky note's peel is a
  border-image computed from its recipe ([Canvas and palette](canvas-and-palette.md) "Sticky notes
  read as paper"); it takes no pointer, so a click or a drop beside a note reaches the board. A filter a person chooses for one element (an element shadow, the Sketch finish)
  stays a filter.
- **A pan or zoom renders the canvas, not the editor.** The view (pan offset and zoom) is held in
  one viewport store per editor, not as the editor's render state. A wheel tick, a pinch frame, a
  pan or a glide renders what shows the view (the canvas and its counter-scaled parts, the zoom
  controls, the Map's view box) and nothing else: the editor root, the panels and the chrome do not
  render for it. Handlers read the view from the store when they run. A touch pinch, whose events can
  outrun the display, changes the view at most once a frame, and measures the canvas once, as it
  starts. A pan does not render the canvas either: the canvas renders for a zoom, and a change of the
  offset alone is written straight to the canvas's transform and its floor pattern's position, outside
  React. What reads the offset as a fact (whether everything is off screen) subscribes by value; what
  acts on it (a press, a walk's camera, a Walk In) reads it when it runs; what is drawn in screen space
  from it (the speech and call bubbles, a path's toolbar) subscribes where it is drawn.
- **Someone else panning renders nothing.** Each peer's viewport (sent about ten a second while they
  pan, for [Follow me](../012-collaboration/follow-me-viewport.md)) is held in a store, not as the
  editor's render state. A viewport from a peer you are not following renders nothing; one from the
  peer you follow renders the follow, which moves your view. Before, each one rendered the whole
  editor, so a room of thirty people scrolling rendered it hundreds of times a second.
- **A collaborator moving renders what shows them, not the editor.** Peers' cursors and characters
  (Avatar mode) are held in one peer-motion store per editor, not as the editor's render state. A
  frame of their movement (up to 60 a second in a small room) renders the cursor layer (for a cursor)
  or the canvas that draws the characters (for a character) and nothing else: the editor root, the
  panels and the chrome do not render for it. What reads presence coarsely (who is on which tab, the
  people lists) is kept by value and changes only when someone joins, leaves or changes tab.
- **Walking renders the characters, not the canvas.** Your own character's pose from frame to frame
  (where its feet are, which way it faces, its step, hop, flag wave and reaction pose) is held in one
  pose store per canvas, not as the canvas's render state, and peers' characters are read from the
  peer-motion store by the characters layer alone. A frame of anyone walking renders that layer (the
  characters, the hearing ring, the talking bars, raised hands, call bubbles, pad arrivals and speech
  bubbles) and the sprites that changed; it renders neither the canvas nor the element layer. What
  follows a character as a fact (the element under your feet and its ring, the stage you speak from,
  who sits or stands on each piece, which pod is shut) subscribes by value and renders only when the
  fact changes; what acts on a position (a click on a peer, Walk There, a climb, a seat on arrival)
  reads it when it runs. What follows everyone's positions as a fact and draws nothing that walks
  with them (the call's scene, the Screens and Room Signs, the game seats, who is where, the pad
  arrivals) reads a coarse copy of the characters and of your feet: taken at most 10 times a second
  while people walk, and at once when someone appears or leaves, sits or stands, changes tab, or
  crosses into another room or onto a stage, so a room's call and its signs never lag a door. In a
  20 to 50 person office somebody is almost always walking, and before the coarse copy each of those
  ran on every frame of it (50 peers walking: the call fed 60 scenes a second, 6,000 costume parses
  and 6,240 room tests a second). A peer's costume is read once per costume, not per frame. A character is placed by a transform, not by `left` and `top`, so a step
  moves a layer without laying the page out, and a peer's glide is a transition of that transform. The
  centred camera pans with every step, and that pan renders nothing more than a pan does: no canvas
  view and no element view.
- **A gesture frame never reads layout after writing it.** Chrome that follows a selection (the
  floating toolbar, the selection popover) is **hidden while a selection is being moved or
  resized** and placed again when the gesture ends; elsewhere it positions from canvas geometry
  (bounds, offset, zoom) and a measurement taken outside the gesture.
- **Opening a board animates nothing across the board.** The board appears at once, with no fade
  on the canvas world ([Motion](../004-interface-design/motion.md) "Editor arrival") and no
  pop-in on the elements it opens with ([Canvas and palette](canvas-and-palette.md) "Motion and
  animations"): an animation over the whole board makes the browser lay out the page's
  compositing again as it starts and as it ends, and a per-element entry re-renders every element
  view once more. Chrome may still fade in; it is small.
- **A Tab Style change on a busy Space eases the canvas, not its parts.** On a tab of more than 20 elements the
  canvas's own colour (its backdrop) still eases into a new theme, look, finish, typeface, size or pattern, and every
  part inside it snaps ([Canvas and theme dialog](../011-theme/canvas-and-theme-dialog.md) "Eased changes"). Easing the
  parts sets a colour transition on every node of every element at once, and the browser restyles each of them on
  every frame of the 250 ms ease: on Company Campus (114 elements, about 2,500 nodes) a theme pick took about 270 ms to
  paint and held the page in long frames for 600 to 850 ms, the board changing in steps; snapping the parts paints it
  in about 40 ms with no long frame. The state change was already one commit, one undo step and one room op.
- <a id="theme-pick-big-board"></a>**A theme pick on a big Space keeps the page answering.** On the reference Space
  at 400 elements no frame of a pick in the Tab Style dialog takes more than about a tenth of a second on the
  reference machine (it took about a quarter of a second). The new colours are worked out between frames while the
  canvas keeps the old ones, then shown in one step; on a busy canvas only the canvas's own surface takes the ease,
  never the rest of the page, and the toolbars do not measure themselves again while the canvas redraws. Only the
  elements whose colours the pick changes draw again: one the pick leaves as it was (a hand-picked colour, a sticky)
  keeps its view as it is.
- **The Map redraws its content when a gesture ends**, not on every frame of it. During a drag,
  pan or stroke it keeps its last drawing and moves only its viewport rectangle; a remote edit
  redraws it at most once every 250 ms. Opening a board draws the board first; the Map's picture
  follows in a later render.
- **The Map is one image.** It draws the board as a picture, not as a second copy of the board's
  elements in the page, which every style pass, layout, hit test and collection would otherwise
  walk. The lit window and the dimmed surround sit on a layer of their own above the picture, so a
  pan moves the window without repainting the picture: Safari draws an SVG picture again in full
  each time anything over it repaints, and on a 100-room office that was about 45 ms of every frame
  of a walk (a walk's frame went from about 56 ms to about 14 ms in WebKit at iPad size). The Map's
  body is the one every editor shares (`MinimapMap`, `@liveworkspace/workbench`).
- **Questions about neighbours ask a spatial index.** Anything that asks, for each element, which
  other elements are near it (arrows passing behind boxes) queries one shared index of element
  bounds, updated for the elements that changed, so its per-frame cost follows the neighbourhood,
  not the board. A per-frame pass is never quadratic in the board. A question about a rect wider
  than the board's occupied cells (a long arrow's) asks those cells instead, so its cost never grows
  with how far apart two points are.
- **Whole-board passes stay linear and run once.** What deliberately looks across the whole board
  (alignment and distribution snapping, the endpoint spread, the arrow label pass) makes one
  linear pass per frame at most, shared by everything that reads it.
- **A move that only translates renders nothing.** When a gesture shifts elements without
  reshaping them (a move, of any number of elements), each of them is drawn where the document has
  it, shifted by one offset written to the page outside React, so a move frame renders no element
  view at all, however large the selection. Arrows with both ends on moved elements ride along the
  same way; only an arrow with one end in the selection and the other outside it re-routes, frame by
  frame ([Drag preview](drag-preview.md) "Moves ride an offset").
- **Per-frame arrow work is linear in what moved.** Which arrows a moved box crosses, and which
  moved boxes cut an arrow, are asked of spatial grids (the arrows' bounds, bucketed once per
  document change; the moved boxes, once per frame), never by scanning every moved element for
  every arrow.
- **A move re-renders what moved.** A move, resize or reshape draws from a preview and writes the
  document once, on release ([Drag preview](drag-preview.md)): the moved elements and the arrows
  that depend on them re-render each frame, and nothing derived from the rest of the board is
  recomputed. A preview frame renders neither the canvas nor the element layer: each element view
  reads its own part of the preview, so a frame's work follows what moved, not the board, and only
  what follows the moved selection (its chrome) reads the whole preview.
- **Selection chrome derives a frame once.** Every piece of chrome that follows the selection (the
  layer's resize box and pluses, the toolbars and popover) reads the same preview frame: the board
  with the preview laid over it, and the selection derived from it, are built once a frame and
  shared, never once per reader.
- **One listener per media query.** Every caller of one media query (each grip asking whether the
  pointer is coarse) shares one query list and one listener.
- **A sweep moves one layer.** The marquee's rectangle changes on every frame of a sweep; it is held
  outside the editor's render state and only the rectangle reads it, so a frame of the sweep renders
  that one node and never the canvas, the element layer or the chrome. The rectangle sits on a
  compositor layer of its own and is placed by transform, so a sweep frame moves it without
  repainting the board beneath it. The selection's resize outline is placed by transform too but is
  not promoted: it spans the whole selection, so a layer of its own made WebKit split every element
  over it into layers too (a 4,000-element drag's frame went from 57 ms to 200 ms). The rectangle stays
  in the page between sweeps, hidden, so a sweep's start and end add and remove no element: an element
  added beside the board, or taken away, makes Safari restyle the board (the next rule).
- **Nothing shown over the page restyles the editor.** A tooltip, a menu, a toast, a dialog or a
  dragged copy is added at the end of the page and taken away again. Safari restyles the whole of
  whatever was last in the page before it, and after it goes, and the editor was last: showing and
  hiding one tooltip over a design of 2,000 boxes and 1,999 arrows froze it for about 0.87 s (three frames
  of 0.2 to 0.4 s). An empty element stays at the end of the page while an editor is up, so what comes
  and goes there restyles only that (one frame of about 0.19 s, measured in WebKit).
- **A press on the canvas selects no text.** The canvas is not selectable text, yet Safari starts a
  text selection from a mouse press on it and, on the drag's first move, works out where that
  selection would run across the whole board: one frame of about 0.7 s at the start of every marquee
  or pan on 2,000 boxes and 1,999 arrows. The canvas cancels a text selection as it starts, except in
  what is being typed (a label, a note, a field) and in an element that is selectable text on purpose
  (measured in WebKit with the rectangle kept in the page: a marquee's press went from about 0.8 s
  to 0.13 to 0.16 s and its first move from about 0.7 s to 15 to 40 ms; a union resize's first
  frame from about 1.6 s to 1.1 s).
- **The canvas's cursor stays off the elements.** The cursor the canvas shows (the tool's, a pan's
  grab, a draw tool's intent) changes on a tool switch, at the start and end of a pan and when a
  stroke lands, and a cursor is inherited: set on what holds the elements, each change restyled
  every element on the board. The elements sit in a plane with a cursor of its own, so a change of
  the canvas's cursor restyles that plane and not what is in it. Each element shows its own cursor
  where it takes a press, as it already does; a whiteboard pen or a path in its edit mode, whose
  cursor shows over elements, passes it through the plane on purpose.
- **The canvas re-renders only for what it shows.** The editor around the canvas re-renders for
  many reasons (a panel opening, a toast, a collaborator's presence, the selection); none of them
  re-renders the canvas unless something the canvas shows changed. The canvas's event handlers keep
  their identity across the editor's renders, and calling one runs the editor's newest version.
- **A selection change re-renders what it touches.** Which elements are selected is held in one
  selection store per editor, not passed down as props. Selecting, deselecting, a marquee's result,
  select-all and a remote change of the local selection re-render, anywhere in the editor, only what
  shows the selection: the element views whose selected state changed, the selection chrome
  (toolbars, popover, resize box, handles and anchors), and the panels that describe the selection
  (Quick Style, the slide deck, an open context menu). The editor root, the canvas, the element
  layer and the Map do not re-render for it. Handlers read the selection from the store when they
  run; effects that follow it (presence, scrolling a selection into view, the screen-reader
  announcement, dropping hidden elements from it) subscribe to the store.
- **Derived layouts are computed once per change.** Arrow labels, ink projection and theme
  colours are laid out per element change and cached per element identity, as arrow labels are
  today.
- **A render that changes no element hands on the same board.** A pan, a zoom or a marquee frame
  re-renders the editor without touching an element; every display projection of the board (stock
  colours) then returns the same array it returned before, so nothing derived from
  the board (the Map, the arrow frames, the endpoint spread) recomputes.
- **An update that changes nothing renders nothing.** A tick of the tabs that changes none of them
  (a settle that finds everything where it was) hands the editor back the very history it had
  (`withPresent`, `@liveworkspace/workbench/lib/remote-op-log`), so React renders nothing for it. A
  new history object for an unchanged tab re-rendered the whole editor; in livedocuments that was
  every keystroke of a long article.

## Later

Taken up only when the rules above leave the budget unmet; each is a change to this spec first.

- **Not mounting off-screen elements** when zoomed in, with a margin of one screen. It does not
  help at fit zoom, where everything is on screen; it must keep a focused or selected element,
  remote selections, find-and-jump and the canvas live region working, and exports untouched
  (they use the headless renderer, not the DOM).
  Measured and set aside: unmounting what leaves the screen makes a zoom or pan mount and unmount
  element views as the view moves, and mounting is what makes long tasks. Culling to snapped canvas
  cells raised a 100% zoom's longest task from about 60-90 ms to 170-195 ms (research notes). Taken
  up again only with a way to show an element that costs no React mount (a raster stand-in).
- **Level of detail at low zoom**: text and icons below a few screen pixels drawn as simpler
  marks.
- **Containment** (`contain` on element wrappers) so a change inside one element does not
  invalidate the layout of others. Measured and set aside: `contain: layout` on every element left
  a diagram stroke's release unchanged (layout was about 8 ms of it; the rest was a restyle of the
  whole board, which the cursor rule above removes). A whiteboard pen's cursor passes through that
  rule on purpose, so its restyle remains.

## Measuring

- **Counts, not timings, pin the structural rules** deterministically. In the unit suite: an
  editor render that changes nothing renders no element view, a zoom renders only counter-scaled
  parts, a one-element move renders only it and the arrows whose geometry it changed, and the Map
  holds its drawing through a gesture, and two seconds of walking render the walk's host (the canvas)
  no more often than the facts under the feet change. In a real browser, in the end-to-end suite: a still board
  with a selection showing asks for no animation frames.
- **A large-selection bench** (`e2e/perf/large-selection-drag.perf.ts`) opens the large-selection
  board, drags its whole selection and a five-element one, and times each pointer move in the page:
  script (from the frame callback before the move's to the one after it, React's update included)
  and frame (to the first task after the frame's style, layout and paint), medians over three drags
  of 40 moves, unthrottled and at 4×. It reports and never fails on a number; a CPU-time unit test
  holds the arrow work, and render counts hold "renders nothing".
- **A performance probe** (`pnpm perf:canvas`) builds the reference board, runs each gesture at the
  reference speed and prints the budget table with pass or fail per row. It also runs by hand,
  against any build.
- **Each gesture runs five times and a row reads the median**, since one run of the same gesture
  can read two to five times another. Opening the board is no exception: it is opened five times,
  each in a fresh browser context, and the row reads the median.
- **Opening counts every long frame.** "Interactive" ends at the first 500 ms in which the page
  reports neither a long task nor a long animation frame. Long tasks alone miss a frame that only
  renders (style, layout, compositing, paint, with no script in it), which is how a 500 ms
  compositing pass once went uncounted. Counting both reads the same or longer than counting long
  tasks alone, so open rows from before the change are a lower bound on today's.
- **Nothing the probe does lands in the opening window.** It opens the board by URL (so no tour
  is offered), waits for the board and then for 500 quiet ms, reads the number, and only then
  dismisses anything or presses a key; its own queries of the page are work the page would
  otherwise count. The timings come from the page itself (its long-task entries
  and an animation-frame recorder), so they count the board's own work and nothing else, never
  from inside a profiler start: starting the CPU profiler costs a one-off task of about a second on
  a large page. A still board's work, which must stay under a task's length, is read from a trace.
  One more run of each gesture is traced for attribution and not counted.
- **It runs nightly on its own**, in a scheduled workflow, against the head of `main`; a night with
  no new commit on `main` since the last run is skipped, so it spends no CI minutes on an unchanged
  build. Each run writes the budget table to the job summary and keeps the raw traces as an
  artefact for 14 days.
- **It reports, it never blocks**: timings on shared runners are too noisy to fail a build on. A
  run with a failing row opens one issue, **Canvas performance budget: livehuddle**, or comments on it if open,
  with the table and the commits since the previous run (the latest 30, then how many more, so a long
  gap never outgrows GitHub's 65,536-character body); the first all-pass run closes it. No
  one has to remember to run or read it.
- **A branch can be measured on demand**: the same workflow, started by hand on any branch, runs
  the same probe and writes the same job summary, and leaves the issue alone; only a run on `main`
  reports to it.

## Observability

- In development builds a long-task observer logs `[canvas-perf] long task` (debug) with its
  duration and the gesture in progress (pan, zoom, drag, marquee, stroke, idle), so a regression
  is visible while working.
- Production sends nothing about performance: the anonymous-events schema stays about features
  used.

## Non-goals

- A canvas or WebGL renderer: the DOM and SVG stay the rendering surface, for text, accessibility
  and the element views as they are.
- Limits on board size: a board is never refused or truncated for being large.
