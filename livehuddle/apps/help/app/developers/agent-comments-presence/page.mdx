An agent holding an [API token](/help/account-and-data/api-tokens/) can show the people on a tab what it is doing while it works, under the name and colour of the person who owns the token, never as a new person. livehuddle has no comments: in a Space you say it to the person, in the call or in a speech bubble. A space made before that may still hold comment threads, and an agent can read them, but nothing writes to them any more.

Paths are relative to `https://livehuddle.app/api`, and the `curl` examples assume your token is in `$TOKEN`.

## Who Can Do What

What an agent may do follows its token, through the same gates as a share link:

- A **full-access token** on a space you can take part in shows presence and lists threads.
- A **read-only token** lists threads but shows no presence.
- Presence is for API tokens only. A signed-in browser session already shows itself in the editor, so the presence endpoints answer it `403 presence_requires_token`.

## List the Threads

Read the whole conversation without reading a tab:

```bash
curl "https://livehuddle.app/api/documents/$DOC/comments?status=open" \
  -H "Authorization: Bearer $TOKEN"
```

`status` is `open` (the default), `resolved` or `all`; anything else is `400 invalid_status`. The answer lists every thread across the space's tabs, in tab order and then outline order, with the element's **ref** and label so you can act on it straight away:

```json
{
  "threads": [
    {
      "tabId": "tab-1",
      "tabName": "Overview",
      "elementId": "n2",
      "ref": "n2",
      "label": "Orders API",
      "resolved": false,
      "comments": [
        {
          "id": "c1f0…",
          "text": "Should this be idempotent?",
          "createdAt": 1760180000000,
          "authorName": "Priya",
          "authorColor": "#7c3aed"
        }
      ]
    }
  ]
}
```

To read one tab's threads as text, ask for its comments view: `GET /documents/$DOC/tabs/$TAB?view=comments` (add `all=1` for resolved ones).

## Comment Writes Answer 410

Adding a comment, replying, resolving, reopening and deleting one (`POST …/tabs/$TAB/comments`, `…/comments/$COMMENT/reply`, `…/resolve`, `…/reopen` and `DELETE …/comments/$COMMENT`) all answer `410 comments_gone`, and the threads stay exactly as they were. Listing them keeps working.

## Show What Your Agent Is Doing

An agent at work can appear on a tab with a short **status line** ("Adding the payment flow") and a **focus**: the elements it is looking at.

```bash
curl -X PUT https://livehuddle.app/api/documents/$DOC/tabs/$TAB/presence \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "status": "Adding the payment flow", "focus": ["api", "db"], "ttl": 60000 }'
```

```json
{
  "presence": {
    "tabId": "tab-1",
    "status": "Adding the payment flow",
    "focus": ["api", "db"],
    "expiresAt": 1760180060000
  }
}
```

| Field    | Takes                                                                                      |
| -------- | ------------------------------------------------------------------------------------------ |
| `status` | Up to 80 characters, no control characters. Leave it out for presence with no status line. |
| `focus`  | Up to 20 elements, by ref, id prefix or id. The answer gives their full ids.               |
| `ttl`    | How long it stays, in **milliseconds**: 1,000 to 120,000, 30,000 when left out.            |

Setting presence again replaces both the status and the focus. `DELETE` on the same path takes it off at once and answers `204` whether or not it was there.

**You rarely need to keep it alive yourself.** Every changeset your token applies or reverts on a tab, and every read of a tab, keeps its presence there for three minutes, so an agent that is busy reading or editing stays visible and one that stops leaves on its own a few minutes later. A dry run or a refused changeset refreshes nothing. Reads refresh it at most once every 30 seconds per tab.

**An agent shows on one tab at a time:** the last one it read, changed or set presence on. Reading another tab moves it there.

Refusals name what was wrong: `400` with `status_too_long`, `invalid_status`, `too_many_focus`, `invalid_focus`, `ttl_out_of_range`, `focus_not_found` (listing the refs) or `focus_ambiguous` (listing the candidates); `409 agent_presence_full` when a space already shows 32 agents; and `503 room_unavailable` when the live room could not be reached, which is worth one retry.

## What People See

Presence shows in the editor as an avatar of its own, named after its owner ("Webber's Agent"), in the owner's colour and marked with a small star instead of initials. Everyone on the space sees it, the owner included, beside the owner's own avatar when they are on the same tab:

- **The status line** appears in the agent's hover card, on its row in Collaborators, and in what a screen reader announces. It never shows as text in the tab bar. Without one, the hover card says "Working on this tab".
- **The focus** is outlined with a thin ring in the owner's colour. It never locks anything: people keep working on those elements.
- An agent is listed in Collaborators under its tab, but it is not counted as a person, cannot be followed, and never holds the facilitator role or counts in a meeting's head count.
- Two of your tokens on one tab show as one avatar, with the status set last. A private space's presence stack, otherwise hidden, shows while your agent is on it.

[Live Presence](/help/collaboration/live-presence/#agents-at-work) has what this looks like for the people working beside your agent.
