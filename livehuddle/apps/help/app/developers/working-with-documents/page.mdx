These examples use `curl` against the hosted service. Each request carries your [API token](/help/developers/authentication/); the examples assume you have put it in a shell variable:

```bash
export TOKEN=lwt_your_token_here
```

Paths are relative to `https://livehuddle.app/api`. For the exact request and response shapes of every field, see the [OpenAPI reference](/help/developers/api-overview/) at `/api/openapi.json`.

## List your spaces

A space **list** returns the spaces in your personal library (spaces in a team library are not included), as metadata only, not the tab contents:

```bash
curl https://livehuddle.app/api/documents \
  -H "Authorization: Bearer $TOKEN"
```

```json
{
  "documents": [{ "id": "abc123", "name": "Service map", "folderId": null, "shareable": false }]
}
```

## Read a space and a tab

Fetching one space returns its metadata and a list of **tab summaries**, but still not the elements on each tab:

```bash
curl https://livehuddle.app/api/documents/abc123 \
  -H "Authorization: Bearer $TOKEN"
```

To get the actual contents of a tab, request it by id. This keeps listing a big space cheap:

```bash
curl https://livehuddle.app/api/documents/abc123/tabs/tab-1 \
  -H "Authorization: Bearer $TOKEN"
```

```json
{
  "tab": {
    "id": "tab-1",
    "name": "Overview",
    "rev": 7,
    "elements": [/* ... */]
  }
}
```

## Read a tab as text

The element JSON carries every coordinate and colour. When you want what a tab **means**, which is usually what a script or an AI model needs, ask for a **view** instead. The outline gives one line per element, in reading order:

```bash
curl "https://livehuddle.app/api/documents/abc123/tabs/tab-1?view=outline" \
  -H "Authorization: Bearer $TOKEN"
```

```text
tab tab-1 "Overview" · 2 elements: 2 boxes · rev 7
sticky n1 "Agenda"
sticky n2 "Actions"
```

Each element is named by a short **ref**: its id when that is short and readable, otherwise the first few characters of it. Anywhere the API takes an element, a ref, any unique start of the id or the full id all work. The first line ends with the tab's revision.

Other views answer other questions:

- `view=layout` gives positions and sizes; add `coarse=1` for rows instead.
- `view=comments` shows the open comment threads in full; add `all=1` for resolved ones too.
- `view=show&ref=n1` prints one element with every field.
- `view=find&q=api` lists the elements whose text contains `api`.

Every changeset's last line carries the new revision and the revert command. A changeset that changes nothing answers `nothing changed`.

Add `budget=2000` to fit any view to about 2,000 tokens. The view then leaves out detail in a fixed order, and its last line says what it left out and how to see it. Add `json=1` for the same view as JSON. To see every tab of a space at a glance, ask the space itself: `GET /documents/abc123?view=overview`.

## Create a space

`POST /documents` creates a space. You supply the `id`, a `name`, and optionally the `tabs` to seed it with. Each element has a position and size; this creates one tab with two sticky notes. Ids are shared across all of livehuddle, not just your account, so use a fresh UUID for the space, each tab and each folder; an id someone else already holds is refused or swapped for a new one:

```bash
DOC=$(uuidgen) TAB=$(uuidgen) FOLDER=$(uuidgen)

curl -X POST https://livehuddle.app/api/documents \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "id": "'"$DOC"'",
    "name": "Team sync",
    "tabs": [
      {
        "id": "'"$TAB"'",
        "name": "Overview",
        "elements": [
          { "id": "n1", "type": "sticky", "x": 0, "y": 0, "width": 200, "height": 200, "label": "Agenda" },
          { "id": "n2", "type": "sticky", "x": 240, "y": 0, "width": 200, "height": 200, "label": "Actions" }
        ]
      }
    ]
  }'
```

Text, images, the Space pieces and the rest of the element types follow the same pattern with their own fields. The OpenAPI document's `Tab` and `Element` schemas describe every one.

## Update a tab

Scripts and agents change a tab with a **changeset**: a short list of edit operations, applied together or not at all. Anyone with the space open sees the change arrive straight away, it is credited to you, and it can be undone as one unit for 30 days. Changes people make in the editor at the same time are kept.

```bash
curl -X POST https://livehuddle.app/api/documents/$DOC/tabs/$TAB/changesets \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "summary": "rename the actions note, add a decisions note",
    "operations": [
      { "op": "set", "target": "n2", "fields": { "label": "Next Steps" } },
      { "op": "add", "element": { "id": "n3", "type": "sticky", "x": 480, "y": 0, "width": 200, "height": 200, "label": "Decisions" } },
      { "op": "rm", "target": "n1" }
    ]
  }'
```

`set` changes only the fields you name, `add` takes a whole element, and `rm` removes an element (here the `Agenda` note). The answer lists what changed, the changeset's id and the tab's new revision. Add `?dryRun=1` to see the answer without changing anything.

The same operations read well as text, one a line, which is easier for a script or an agent to write. Send them as a string:

```bash
curl -X POST https://livehuddle.app/api/documents/$DOC/tabs/$TAB/changesets \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "operations": "set n2 label=\"Next Steps\"\nadd sticky id=risks label=\"Risks\" below:n2"
  }'
```

Elements are named by the refs a [text view](#read-a-tab-as-text) prints, or picked by what they are: `"Next Steps"` by label or `type:sticky`. [Edit Operations Reference](/help/developers/working-with-documents/edit-operations/) lists every operation, selector, placement and flag. Besides `add`, `set` and `rm` there are `move`, `order`, `layout` (tidy rows), and `test`, which refuses the changeset unless an element still holds the values you read. New boxes are sized for their label and placed beside what you name, and the answer has one line per element changed:

```text
~ n2  label "Actions"→"Next Steps"
+ risks  sticky "Risks" @240,240 200×200
```

To rebuild a whole tab, send `"replace"` instead of `"operations"`, with `elements` (or a `template`). A replace on a tab id the space doesn't have yet creates that tab.

<Note>
  Every tab read returns the tab's `rev`. Send it back as `"base": { "rev": 7 }` and the changeset is
  refused with `409 changeset_conflict` if an element it touches changed since you read it, so
  nothing you didn't see gets overwritten. An element somebody has selected in the editor is left
  alone too: the changeset is refused with `409 elements_held`, naming who holds it.
</Note>

To rename a tab, `PUT` its name: `PUT /documents/$DOC/tabs/$TAB/name` with `{ "name": "Overview" }`. The whole-tab `PUT` the editor saves with is not open to tokens; it answers `405 use_changesets`.

`GET /documents/$DOC/changesets` lists the recent changesets, and `POST /documents/$DOC/changesets/<id>/revert` undoes one, leaving any element somebody changed since.

Images, tab pictures and copies have endpoints of their own: see [Images, Copies and Libraries](/help/developers/working-with-documents/images-and-copies/).

## Organise into folders

Create a folder (add `"parentId"` to make it inside another, or `"teamId"` for a team's), then create a space straight into it by naming its id as `folderId`. Renaming and moving folders, and moving a space you already have, happens in the Explorer.

```bash
curl -X POST https://livehuddle.app/api/folders \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "id": "'"$FOLDER"'", "name": "Infrastructure" }'

curl -X POST https://livehuddle.app/api/documents \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "id": "'"$(uuidgen)"'", "name": "Network", "folderId": "'"$FOLDER"'" }'
```

`GET /api/folders` lists your folders with their ids.

## Delete and restore

`DELETE /documents/$DOC` moves the space to the [Trash](/help/account-and-data/trash/), where it waits for 30 days, and answers `204`. While it is there, reading or changing it answers `410 document_trashed`. Add `?permanent=true` to delete it for good straight away.

```bash
curl -X DELETE https://livehuddle.app/api/documents/$DOC \
  -H "Authorization: Bearer $TOKEN"

# What you can restore: your own Trash and every team's you belong to
curl https://livehuddle.app/api/trash \
  -H "Authorization: Bearer $TOKEN"

curl -X POST https://livehuddle.app/api/trash/$DOC/restore \
  -H "Authorization: Bearer $TOKEN"
```

`DELETE /trash/$DOC` deletes one trashed space for good, and `DELETE /trash` empties your personal Trash (`?team=<id>` empties a team's). A read-only token can list the Trash but not restore or purge.

## Share a space

Create a share link with a role of `view`, `participate` or `edit`:

```bash
curl -X POST https://livehuddle.app/api/documents/$DOC/share \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "role": "view" }'
```

The response includes the share code to build a link from. See [Sharing and Embeds](/help/collaboration/sharing/) for what the different roles allow.

<Note>
  **Send the `role` explicitly.** Omitting it does not mean "view": a body with no role mints an
  **edit** link, which is the app's own default. An unrecognised role is rejected outright rather
  than quietly falling back, so a typo fails loudly, but an absent one does not.
</Note>

<Tip>
  When a call fails, the status code and a small `{ "error": "..." }` body tell you why. See
  [Errors and Rate Limits](/help/developers/errors-and-rate-limits/).
</Tip>
