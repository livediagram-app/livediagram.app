# 22, Telemetry + public transparency dashboard

First-party, anonymous product analytics, surfaced on a **public** dashboard so anyone can see what we measure. The goal: understand which features get used so we know what works, while staying honest about the product's "no creepy tracking" stance.

## Principles

- **Anonymous, aggregate, first-party.** Events carry no user id, no IP, no user-generated content (never a diagram name, tab name, participant name, element text, share code, or diagram id). Only a fixed, app-defined vocabulary of enum values is ever stored.
- **No external vendors.** Ingestion is our api worker; storage is our existing D1 database; the dashboard is our own app. Nothing is sent to a third party, and data is never sold or shared beyond the public dashboard.
- **Off by default.** A single env var gates the whole system, so OSS self-hosters and forks emit/serve nothing unless they opt in. This keeps the "no required SaaS calls" rule ([03](03-open-source-and-business-model.md)) intact.
- **Transparent.** The dashboard is public (`/telemetry`), and the privacy policy + landing page say plainly what we capture and why, and link to it.

## Event schema

Every event is three small fields (`packages/api-schema`, shared by emitter + ingest so they can't drift):

```ts
type TelemetryEvent = {
  category: TelemetryCategory; // the "parent": Diagram | Element | Tab | Theme | Canvas | Template | Comment | Note | Action | Search | UI | Folder | Layer | Session | AI | Team | Participant | Help | Token | Mcp | Email | Error
  action: TelemetryAction; // the "verb": Created | Deleted | Shared | Joined | Added | ...
  type?: string | null; // one app-defined reference value: 'Square', 'Edit', 'PNG', a template id, a theme name
};
```

Examples: `{category:'Diagram', action:'Created'}`, `{category:'Diagram', action:'Shared', type:'Edit'}`, `{category:'Diagram', action:'Joined', type:'Edit'}`, `{category:'Element', action:'Added', type:'Square'}`.

`category` and `action` validate against closed enums: the ingest endpoint drops any event whose category or action is not in `TELEMETRY_CATEGORIES` / `TELEMETRY_ACTIONS`.

`type` is **not** an enum, and the guarantee on it is a different, weaker one worth stating plainly. Every caller passes an app-defined preset (a shape kind, a share role `Edit`/`View`, an export format, a template id, a theme name) — that is the rule, and it is what keeps UGC out. The endpoint cannot check membership of a set, because there isn't one: a new shape, template or theme would otherwise mean editing `packages/api-schema` every time. What it enforces instead is a **shape bound**, `TELEMETRY_TYPE_PATTERN` (`/^[A-Za-z0-9 ._-]{1,40}$/`): a short token of safe characters, which rejects anything that reads as free text and caps what a misusing caller could get onto the public dashboard.

So the safety property is: callers only ever send presets, and the pattern is defence-in-depth behind that, not a substitute for it. A short alphanumeric string that happens to be user content would pass the pattern, which is precisely why the calling rule is the thing that matters.

In practice a `type` is either a literal or derived from a closed vocabulary — an element kind through `titleCaseType`, an export format through a lookup table, a boolean through a ternary of two fixed strings. The case that proves the rule is the theme name: a **custom** theme is named by the user, so `themeTelemetryLabel` maps every custom id to the literal `'Custom'` and only ever emits the built-in themes by name. That is the shape any new `type` source should take — map user-owned values onto a fixed token before they reach `track`, rather than relying on the pattern to catch them.

## Storage (existing D1)

A new `events` table on the **existing** `DB` database (migration `apps/api/migrations/0015_*`), deliberately not a separate database so self-hosters who already provisioned `DB` get telemetry with zero extra setup:

```sql
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  category TEXT NOT NULL,
  action   TEXT NOT NULL,
  type     TEXT,
  ts       INTEGER NOT NULL  -- ms epoch
);
CREATE INDEX idx_events_ts ON events (ts);
```

No owner/IP column — rows are anonymous by construction. If write volume ever outgrows D1, the migration path is Workers Analytics Engine (write-optimised, same Cloudflare account, no new vendor); the ingest + summary contract stays the same.

## Retention

The dashboard surfaces three fixed windows that top out at **30 days** (Last 30 days). Rows older than that are dead storage: never read, never aggregated, never user-visible. The api worker's `scheduled` handler runs a daily **60-day sweep** at 03:00 UTC that deletes events older than the retention floor (twice the dashboard's longest window, so a future "Last 60 days" expansion would have data to populate). Symmetric with the existing 90-day `change_log` retention (spec/12); both fire on the same cron, dispatched on `event.cron`. Self-hosters with `TELEMETRY_ENABLED` off never accumulate events in the first place, so the sweep is a no-op for them.

## API

- **`POST /api/events`** — ingest. Body `{ events: TelemetryEvent[] }` (batched). Validates each against the schema; inserts the valid ones with a server-stamped `ts`. Returns 204. **Deliberately exempt from the diagram write-rate-limiter** so a busy editor session's telemetry can never eat into / block a user's real diagram saves; client-side batching keeps request volume low. Anonymous (no auth required); no body field is stored beyond the three enums + ts. When telemetry is disabled, no-ops with 204.
- **`GET /api/telemetry/summary`** — the dashboard's only data source. Returns grouped counts for three **fixed** windows so the queries stay simple and the response is cacheable: **Today** (since UTC midnight), **Last 7 days** (from UTC midnight six days back: today plus the six whole days before it), **Last 30 days** (from UTC midnight 29 days back). No custom ranges. The windows are whole UTC calendar days ending today, the **same days** the dashboard highlights on the 30-day trend line, so a card's count always equals the sum of its highlighted span. They used to be rolling (`now - 7d`, `now - 30d`), which counted a partial extra day the highlighted span didn't show. The spans live in one place, `TELEMETRY_WINDOW_DAYS` in `@livediagram/api-schema`, read by both the worker and the dashboard, and the worker computes all three windows **and** the daily series from a single per-day grouped query (`routes/telemetry.ts` `buildTelemetrySummary`, boundary-tested in `telemetry.test.ts`). Shape:
  ```ts
  {
    enabled: boolean;
    generatedAt: number;
    windows: {
      today: Window;
      last7: Window;
      last30: Window;
    };
    // Each window's counts over the same number of days just before it
    // (the day before today, the 7 days before the last 7, the 30 before
    // the last 30), for the dashboard's trend arrows. The query reads 60
    // days to fill it, inside the 60-day retention. Optional so a client
    // still parses an older api's response.
    previousWindows?: {
      today: Window;
      last7: Window;
      last30: Window;
    };
    // 30 zero-filled UTC-day buckets oldest -> newest, pre-aggregated
    // server-side so the dashboard's trend charts render without any
    // client work. Optional: absent in the disabled-state response so
    // older clients still parse, present whenever `enabled` is true.
    daily?: {
      days: number[];                       // UTC-midnight ms per bucket
      totals: number[];                     // total events that day
      byCategory: Record<string, number[]>; // per-category counts, same indexing
      byMetric: Record<string, number[]>;   // per-event counts, same indexing; key = `category|action|type`
    };
  }
  // Window = { total: number; rows: { category; action; type; count }[] }
  ```
  `byMetric` is the per-event (category·action·type) version of `byCategory` —
  one 30-day series per distinct event, keyed `category|action|type` (empty
  string for a null `type`). It drives the Search view's metric trend line so a
  single event can be charted over time, not just a whole category. Same
  zero-filled indexing as `days`/`totals`/`byCategory`.
  Cached at the edge (Cache API, a few minutes) so a public traffic spike never hammers D1. When disabled, returns `{ enabled: false }`. The cache is bypassed when the worker is serving from a localhost hostname (parallel to the same-origin escape hatch), so a developer iterating on the feature sees fresh counts immediately instead of waiting out a 5-minute TTL per emit.

## On/off env var

`TELEMETRY_ENABLED` (worker, `wrangler.toml [vars]`, default off) is **authoritative**: it gates both `POST /api/events` and `GET /api/telemetry/summary`. Every emitting frontend (editor, help centre, marketing, dashboard) also reads `NEXT_PUBLIC_TELEMETRY_ENABLED` (baked at build) to avoid emitting at all when off — a client optimisation; the server flag is the real gate. Both absent → fully off, which is the self-host default. On top of these, each user has a per-device opt-out flag stored alongside the other user preferences (spec/20, `telemetryEnabled`, default true). When that flag is false, `track()` is a no-op for that browser regardless of the server's stance; this is the user-facing lever the landing page and `/telemetry` reference when they say "first-party, no creepy tracking".

One further var, easy to miss because it changes no behaviour you can see: **`INTERNAL_EVENTS_KEY`** (a worker secret, the same value on the **api and mcp** workers) exempts our own service-binding callers from the anonymous per-IP rate limiter. Unset, MCP telemetry still flows — it just shares one 120/min bucket with every other internal caller and the overflow is dropped as a 204 nobody can observe, so `Mcp·Used` under-reports without any error to notice. See "Delivery losses" below, [spec/06](06-secrets-policy.md) for the secrets table, and `apps/api/wrangler.toml` for the operator notes.

## Abuse controls

`POST /api/events` is public + unauthenticated by design, so it's guarded in layers without identifying users (it's anonymous trend data, not billing — the goal is "not worth it" + protect cost, not "impossible"):

- **Closed vocabulary.** Events are validated against the `category`/`action`/`type` enums and the batch is capped (100), so an attacker can only ever inflate counts of _known_ events — never inject arbitrary strings into the public dashboard or store junk.
- **Per-IP rate limit.** A dedicated `EVENTS_RATE_LIMITER` binding (separate from the diagram `WRITE_RATE_LIMITER`, so it never touches real users) keyed on `CF-Connecting-IP` — which the client can't forge, unlike `X-Owner-Id`. 120 batches/60s/IP: generous for a real session, bounding for a flood. The IP is a transient key, never stored. Degrades to "allow" when the binding is absent (self-host).
- **Same-origin filter.** A request whose `Origin` header is present and isn't this site is dropped (silently, 204), which stops casual cross-origin / drive-by posting. Spoofable by curl, which the rate limit then catches. Localhost origins (any port) are mutually allowed so local dev (live editor on `:3002` posting to the api worker on `:8787`) actually reaches D1; production never sees a localhost origin, so this widening is dev-only in practice.
- **Cloudflare edge.** Automatic DDoS protection fronts the worker for free. **Recommended manual step:** add a WAF rate-limiting rule on `path eq /api/events` keyed by IP in the Cloudflare dashboard — it blocks abuse _before_ the worker runs (so it costs nothing per blocked request and never touches D1). This is the strongest, cheapest lever and is dashboard config, not code; hosted-only, so forks add their own.

Residual risk: a distributed botnet across many IPs could still nudge the numbers. Accepted — that's a lot of effort to juice an anonymous usage chart. If it ever matters, a global daily insert ceiling is the backstop.

## Emitting

A `track(category, action, type?)` helper buffers events and flushes them batched on an interval and on `visibilitychange`/unload via `navigator.sendBeacon`. Fire-and-forget; failures are swallowed (telemetry must never affect the host app). The buffering engine is the shared `@livediagram/telemetry-client`, wrapped with the policy (the `NEXT_PUBLIC_TELEMETRY_ENABLED` build gate + the spec/20 opt-out): the editor builds its own emitter, and the three public sites (help, marketing, the dashboard) share one, `siteTrack`, so their policy can't drift. **An opt-out made in the editor silences the help centre too**, since both sit on the livediagram.app origin and read the same localStorage preferences blob. How each reads it is app-owned (the editor caches behind its preference-change events, the help centre reads straight through), but _where_ it reads and _which way it defaults_ are not: `USER_PREFERENCES_STORAGE_KEY` and `telemetryOptInFromRaw` live in `@livediagram/telemetry-client` so a key rename in one app can't leave the other quietly emitting for a user who opted out. Six surfaces emit: the **editor** (`apps/live`), the **help centre** (`apps/help`, the `Help` category), the **marketing site** and the **dashboard** (`apps/marketing`, `apps/telemetry`: page views only, see below), the **MCP worker** (`apps/mcp`, the `Mcp` category), and the **api worker itself** (server-side self-reports written straight to the events table: `Error·Api·Internal.<Method>.<Route>` for an unhandled server exception, the whole `Email` category, which has no browser to emit from, and the counts only the server can make once each: `Session·SignedUp`, `Session·SignedIn`, `Diagram·Joined` and `Diagram·Used·Multiplayer` (the diagram room, once per multiplayer session), see below). Those server-owned pairs are listed in `SERVER_EMITTED_EVENT_PAIRS` (`@livediagram/api-schema`) and **dropped at `POST /api/events`**, so a stale cached editor bundle that still emits one (or anyone posting by hand) cannot double count what the worker records; the editor's coverage test also fails if an editor call site emits one. Server-side emits share one helper (`apps/api/src/server-telemetry.ts`), gated on `TELEMETRY_ENABLED`; they are anonymous counts like every other row, and the per-browser opt-out cannot reach them because no browser is involved. All four frontends also report `Page·View·<path>` on each path change ([spec/150](150-page-view-telemetry.md)), and for marketing and the dashboard that is their only event. (The landing funnel, [spec/153](153-landing-funnel.md), keeps it that way: a CTA's link carries which button it was, and the editor reports the `Cta` events.) This replaced an earlier rule that the marketing site never emits: a page count sent first-party to our own api, anonymous, cookie-free and honouring the same opt-out is within this spec's principles, and the marketing "0 third-party trackers" claim stays literally true. Call sites are one-liners, e.g. `track('Element', 'Added', 'Square')`.

The aim is to cover every meaningful interaction a person has with a diagram (discrete feature actions, never continuous gestures like drag/resize/pan/zoom or raw colour tweaks, which would just be noise). Current taxonomy:

- **Diagram**: Used `Multiplayer` (the diagram was open with at least one other person live in the room: **once per multiplayer session**, written **server-side** by the diagram room (`apps/api/src/diagram-room.ts`, rule in `room-multiplayer.ts`) the first time its hello'd roster reaches two. A session is a run of continuous occupancy: it ends only when the room empties, so a peer who refreshes or reconnects while a colleague is still in keeps the same session, and a room that empties and fills again later is a new one. The "already counted" mark rides on each socket's attachment, so it survives hibernation and disappears with the last socket. It used to be a client emit fired when each tab's presence list first held a peer, so every participant reported the same session: a five-person retro counted 5. Being server-side, it cannot honour a participant's per-browser telemetry opt-out, the same trade `Email·Sent` makes; it carries nothing but the three-field token either way). This is the only event that counts collaboration **happening** rather than being **offered**: `Joined` fires only for a share-link visitor, so two teammates editing the same team diagram at once were two indistinguishable `Loaded`s and the multiplayer product had no multiplayer metric. Read the rest of the Collaboration tab against it: many links shared and few multiplayer sessions means the links aren't being walked through. ## Counting rules: one event per gesture, or one per object?

Audited in full for issue #30, because "is this number the thing I think it is?" was unanswerable from the taxonomy alone. The rule, now stated rather than assumed:

**An event counts the GESTURE, not the objects the gesture touched.** Deleting a twelve-element marquee selection is one `Element·Deleted`; restyling it is one `Element·Changed`; an eraser stroke that wipes a dozen shapes is one `Element·Deleted·Eraser`. This is deliberate — the question these answer is "how often do people delete / restyle / erase", and a per-object count would let one marquee drag swamp a hundred single deletes. No `track()` call in the codebase sits inside a loop, so this holds uniformly.

**The one exception is creation, because creation feeds a census.** `Element·Added·<kind>` is what the dashboard's Palette ranking is built from, so it has to be a true count of elements created, not of creation gestures. Every from-scratch path already emitted one per element (you can only draw one at a time). The **copy** paths did not: duplicate, paste, and shift-drag emitted a single untyped `Element·Duplicated` and no `Added` at all, so an element born by copying was invisible to the census — under-counting precisely the shapes people liked enough to reuse. All five copy paths now go through `trackDuplicated`, which emits one `Duplicated` for the gesture **and** one `Added·<kind>` per element created. `elementTelemetryType` is the single mapper from an element to its token, so a copied code block lands in the same bucket as a drawn one.

Two related fixes from the same audit:

- Copy paths emitted **before** their own guards, so a duplicate that never happened still logged one (a multi-selection holding nothing copyable). They now emit after the copies exist, and an empty result emits nothing.
- `Element·Rotated` was in the enum and documented here as firing at rotate-gesture start. There is no rotate gesture — rotation is a context-menu control that emits `Element·Changed·Rotation` — so the action was dead. Removed from the enum.

**An event counts what the SERVER accepted, not what the user clicked.** Every list action in the Explorer and the team library is optimistic (spec/15, spec/35): the row updates locally so the UI feels instant, the request goes out, and a failure rolls the row back and usually toasts. The emits sat beside the request rather than inside its resolution, so a rename the server refused was reverted on screen, reported to the user as a failure, and still counted as a rename. Two spellings caused it — `void apiThing(…).catch(() => {}); track(…)`, and `await apiThing(…).catch(() => {}); track(…)`, the second reading as "ignore the failure" while actually meaning "treat every failure as success", since the next statement runs either way. Fifteen sites across `useDiagramListActions`, `useExplorerMoves`, `useTeamLibrary`, `useFolders`, `useDiagramActions` and `CustomThemeProvider` now emit from the success path, with `lib/accepted.ts` turning a swallowed rejection into a boolean the caller has to look at.

Two things deliberately still emit on the optimistic path, because for them the local action IS the fact: `Element·Copied` (the in-app buffer is the authoritative clipboard — the OS write is a best-effort extra that can fail on permissions without changing what a paste will do), and `Diagram·Duplicated` in a team library (the copy exists by then; only the follow-up filing into the team folder can fail).

Also `.then()` before `.catch()`, not after. Chained the other way round — `p.catch(() => {}).then(f)` — the success handler runs after a swallowed rejection too, which is harmless for a follow-up refresh and wrong for anything that counts.

**Deliberate double-emits** (so nobody reads them as double-counting): starting a private vote emits both `Tab·Started·Vote` and `Tab·Started·PrivateVote`, the first being the true vote count and the second a flag on that subset. Completing the `/new` wizard emits `Diagram·Created` + `Theme·Changed` + `Template·Used`, which are three genuinely different facts. Filing a tab into a folder name the diagram has not used before emits `Folder·Created·Tab` + `Tab·Moved·Folder`, also two different facts — the folder now exists, and this tab is in it — because reporting only the creation made "tabs filed into folders" undercount by exactly the number of folders anyone created.

## How completeness is tested

Telemetry drifts silently and there is no runtime signal when it does: emitting is fire-and-forget, and the public dashboard only ever renders what **arrived**, so a renamed or deleted event is indistinguishable from a feature nobody used. Two checked-in guards replace that missing signal.

- **`apps/live/lib/telemetry-manifest.ts` pins every `category·action` pair the editor emits**, enforced by `telemetry-coverage.test.ts`, which scans the source for `track()` call sites (ternary actions included) and diffs against the manifest. Adding, renaming, or removing an emitted pair fails CI until the manifest is updated — and the manifest's comment sends you here, so the taxonomy above gets updated in the same change. The same test asserts every pair is inside the closed enums, since an event outside them is silently dropped by the ingest validator.
- **`PALETTE_TELEMETRY_TYPES` in `@livediagram/api-schema` is the one definition of the palette `type` tokens**, consumed by the dashboard's Palette view instead of the hand-mirrored copy it used to keep. `palette-telemetry-coverage.test.ts` asserts every shape kind in `@livediagram/diagram` has a bucket there, **and every non-shape element kind too** — that second half was missing, and so was `Video`: all six embed tiles create a `video` element, so from the day embeds shipped their adds were counted nowhere. The copy had already drifted: the dashboard expected `Code-block` long after the editor settled on `CodeBlock`, so every code block anyone drew was emitted, validated, stored, and missing from the ranking.
  That test must derive its tokens by CALLING `elementTelemetryType`, never by restating its rule. It did restate it once, and the copy drifted the same way the dashboard's had: it spelled out seven camel-case tokens where the editor spelled three, so the session button, reaction pad, comment pin and done check each reported `Session-button` and friends on Added while the test proved the catalogue held `SessionButton`. Four features counted zero, and every assertion passed. A copy of the rule can only prove the copy agrees.

Pairs are pinned but `type` values generally are not — types are open-ended by design (a shape kind, a template id, an article slug) and pinning them all would fail on every new shape. The palette tokens are the exception because that is where drift is both invisible and costly.

## Delivery losses, and the two that were worth fixing

Emitting is fire-and-forget, so a dropped batch is invisible by construction. Audited alongside the coverage work; the losses split into ones we accept and ones we didn't.

**Fixed — a failed flush is now retried once.** The buffer used to be cleared before the request went out, with the result swallowed, so any network failure discarded that batch permanently. The problem wasn't the volume so much as the _distribution_: the losses concentrated in flaky-network and close-the-tab-quickly sessions, which biases the data rather than just thinning it. A rejected `fetch` now re-queues its events at the front of the next batch and gets exactly one more attempt.

The bounds matter more than the retry:

- **Only on a rejection**, never on a non-2xx. A rejection means the request got no response, so the events almost certainly didn't land. A server that _answered_ may well have stored them, and re-sending would double-count — while retrying a 429 would worsen the thing it's complaining about.
- **Exactly one attempt.** A retry trades a small over-count risk (request arrived, response lost) against a systematic under-count; that trade is worth making once. An endlessly retried batch on a dead network would grow the buffer, duplicate on every recovery, and still die at unload.
- **Bounded by the same 25-event cap**, oldest dropped first — the retried events have already had their chance.
- **Never on the beacon path.** We're unloading; there is no later.
- A failure **arms a fresh timer**, so the retry happens on its own rather than waiting for the next tracked event.

**Fixed — `sendBeacon`'s return value is no longer ignored.** It returns `false` when the UA's queue is full, and that batch was simply gone, at exactly the moment it mattered (page-hide, the tail of a session). It now falls through to the `keepalive` fetch, which is the same "outlive the page" guarantee by another route.

**Fixed — internal callers no longer share one rate-limit bucket.** Our own workers reach `/api/events` over a service binding, which carries no `CF-Connecting-IP`, so `clientIp` fell back to the literal `'anonymous'` and every internal caller worldwide contended for a single 120/min key, with the overflow dropped as a 204 nobody could observe. Since the MCP worker posts one request per tool call, that ceiling was roughly two tool calls per second globally — enough to make a growing integration look flat. A matching `INTERNAL_EVENTS_KEY` (a worker secret on both sides, compared in constant time) now exempts them from the per-IP limiter, which exists to stop _anonymous_ abuse of a public endpoint and was never aimed at us. Unset on either side means nobody is exempt, exactly as before, so self-hosting needs no configuration.

**Still accepted:** client errors, and the editor's api errors, cap at 10 per kind per page load (an error loop must not flood the pipeline, and the dashboard reads presence and order of magnitude, not exact storm size); events buffered when a tab is hard-killed are gone (nothing is persisted, deliberately: telemetry must not own storage); and a second consecutive failure discards the batch, per the one-retry bound above. All of these under-count rather than over-count, which is the safer direction for a usage chart.

Extend by adding to the `TELEMETRY_CATEGORIES` / `TELEMETRY_ACTIONS` enums (if needed) + a one-line `track()` call at the interaction's handler. Page hits are deliberately not wired; new-visitor counting goes through `Participant`/Created above.

**Every card must count an event something actually sends.** Two failure modes, both seen in production. **A card that counts the bare event must have no typed emitter.** A metric card with `type: null` counts only events sent with no type, so the moment an emitter starts typing that `category·action` the card silently drops every one of them. `Diagram·Created` read 0 on the Dashboard and Content from July to September 2026 while ~150 diagrams a month were created, because the New Diagram wizard had started sending `Cloud` / `Offline` (spec/76); `Layer·Opened·Panel`, `Diagram·Duplicated·Copy` and team-library `Folder·Created/Moved·Team` were missed the same way. The same test checks every typed card, and every type a ranking hard-codes (Selection Modes, the Canvas Styles and Themes exclusions and alias targets, the custom-theme tiles, the Exceptions recovery types). It reads emitters with the TypeScript parser (`emitter-scan.ts`), not a regex, so it sees every form the repo uses: literal `track` / `report(env, ...)` / `reportServerEvent(env, ...)` / `postTelemetry(env, ...)` calls, ternaries in any argument (`track('Tab', x ? 'Moved' : 'Removed', 'Folder')`), `const` values and lookup tables in the same file, forwarding helpers (resolved per call site, so a helper's category, action and type stay correlated), a callback's parameters through the calls the function it is handed to makes (the help centre's vote tally), a returned closure's parameters through the calls made on the variable holding it, in any file (the debounced canvas telemetry), the api worker's own `insertTelemetryEvents` rows, and the Settings catalogue rows (`event: { category, on, off }` / `changed`) that `SettingsCategoryPane` emits generically. What the scan cannot resolve is a **computed** type (a theme label, an email template kind, a presenter setting's field), and every computed emit site must declare the values it can send in `apps/telemetry/app/computed-emitters.ts`, keyed by `<path> <Category>·<Action>`: read from the source that defines them where the set is closed and written down (the api's `EmailKind` union, the MCP server's registered tools, `PresentationConfig`'s fields, the photo detector's token tables, the tour's step ids), or representative samples with the reason where it is open (an article slug, a page path, a status code). Every check here then reads those values as if they were literals. The test fails on a computed site with no entry, an entry for a site that no longer exists, or a declared value that no chart counts; it used to accept any chart on the site's category·action, which is how `UI·Changed·Presentation-<field>` sat on no chart and the photo import's `AI·Used·Photo*` swelled a card about the AI panel. An emit site whose category or action is itself a variable must be named in `DYNAMIC_EMITTERS` with the reason.

- **Exceptions**: error health. Four headline cards with 30-day trends via the shared `MetricGroups` renderer, then rankings. **Failed Requests** is every `Error·Api` failure a caller saw (the editor's `Http<status>.<Action>` and `Network.<Method>.<Route>`, the MCP worker's `Http<status>.<Tool>` / `Internal.<Tool>`, failed email sends). **Server Crashes** is the api worker's own `Internal.<Method>.<Route>` report, on its own card because one crash is reported twice (the worker's `Internal` plus the `Http500` its caller saw), so summing `Error·Api` double counted it; the two cards are read side by side, never added. **Client Exceptions** is `Error·Client` minus recovery events, and **Realtime Resyncs** (`Error·Client·RealtimeResync`, the editor refetching after the room says it missed updates) is shown separately because it is a recovery, not a crash. The predicates read the kind as the first dot-part, so the bare pre-#112 types (`Http500`, `Internal`, `Uncaught`) land in the same cards as the located ones; a bare `Internal` counts as a server crash, the api worker having been its main source, and an MCP `Internal.<Tool>` (second part a tool, not an HTTP method) as a failed request. Counts are generic by construction (the closed vocabulary above); an empty view is the goal state.
- **Search** — find one specific metric two ways: **type** a query for flat token matches, or **browse** the hierarchy (category → action → type) one level at a time, for when you can't name what you want. Selecting a metric **visualises it underneath** as its own 30-day trend line (from `daily.byMetric`, with the selected window highlighted) plus its Today / Last 7 days / Last 30 days totals.

**Every count carries a trend arrow.** Beside the number on every metric card, stack head and ranking row sits a badge saying which way it moved against the same number of days just before the window (today against yesterday, the last 7 days against the 7 before, the last 30 against the 30 before): ▲ / ▼ with the change as a percentage (a plain difference when there was nothing before to be a percentage of; under half a percent reads <1%), or → flat. **Green is good news, red is bad, yellow is neutral**: each chart declares whether rising is `good` (the default: most counts are usage), `bad` (errors, Failed Requests / Server Crashes / Client Exceptions / Realtime Resyncs and the Exceptions stack, Accounts Deleted and its email, Marked Not Helpful, Fell Back to Classical), or `neutral` (could read either way: Sign-Outs, Tokens Revoked, the Deleted charts, Invites Declined, Timers Paused / Reset, Dots Retracted, Votes Discarded, the win-back / activation / token-expiry emails, and stacks that mix both kinds, Account Activity, API Token Activity, Emails Sent); a flat count is yellow too. The earlier counts come from the summary's `previousWindows` (see API); against an older api without them, cards and stacks fall back to what the 30-day series can reach (no arrow behind the last 30 days) and rankings show none. Hovering the badge gives the earlier count.

**Every event has a chart.** The Dashboard and its Detail tabs chart every event the repo can send: `metric-emitters.test.ts` reads every emitter (the same TypeScript scan as the card checks below) and fails if one has no chart on any tab, so a new event lands in a stack, usually as a member of an existing one. Its short allowlist names the few the scan misreads, with the reason (a decline the tour routes to `UI·Closed·TourOffer`). Charts live in `apps/telemetry/app/catalogue/<area>.ts` (visitors, content, features, collaboration, settings, connections, health, email), one module per Dashboard area, re-exported from `metric-catalogue.ts`; a stack references charts by name, so one chart can sit in several stacks. Events stored under an old spelling no emitter sends any more (`Element·Grouped` since groups became web components, `SignInBanner` before the banner recorded its surface) have no chart and age out with retention; Search still reaches them.

**No event is counted by two unrelated charts.** One event matched by two different charts is how the dashboard double counts: Tabs Cleared once caught every discarded vote (`Tab·Cleared·Vote`), Share Links Copied caught team invite copies, Panels Docked caught slide reorders. `metric-emitters.test.ts` checks every event an emitter can send against every chart and allows exactly two kinds of overlap: a Settings Changed category chart rolling up the setting charts in it, and, inside one stack, a chart and its subset where the headline counts only one of them (AI Requests over Ask / Clean, Actions Assigned over Actions Emailed, Returning Visitors over its guest / signed-in split, Diagrams Created over Created Offline). The computed sites' declared values are checked too. A stack's combined head line sums the same members as its number, so the two always agree.

**Ranking cards keep their own height.** A ranking's length follows the data (Tools can run thirty rows, Devices three), and in a grid every row grows to its tallest card, stretching short ones into mostly-empty boxes. So every tab's rankings (Pages, Palette, Look & Feel, Help, Exceptions) sit in `CardColumns`: two independent columns, filled biggest card first into whichever column is shorter so far (a card's size estimated from its row count, an empty one as its placeholder panel), one column below `lg`. CSS `columns` was tried first and dropped, because it fills in source order and piled a long card onto an already-long column. Metric cards stay in an even grid on purpose: they are near-equal height, and stretching pins every trend line to the same baseline.

Charts render in inline SVG (a line with a shaded selected-window span and a dashed average reference line); no charting library, no extra request. Event names display in Title Case (preserving acronyms like PNG/JSON). Explains in-page that the data is anonymous, first-party, no vendors. Degrades to an "analytics not enabled" state when the summary returns `enabled: false`.

## Routing & deploy

- **Router** ([08](08-router-app.md)): a `TELEMETRY` service binding and a `/telemetry` route that strips the prefix and forwards (mirrors the live-asset strip).
- **Deploy** ([10](10-deployment.md)): build + upload `apps/telemetry/out`, a `deploy-telemetry` job in parallel with marketing/live/api, and `deploy-router` gains it as a dependency. The `events` migration applies in the existing `wrangler d1 migrations apply DB` step.

## Provisioning (one-time, owner only)

1. Apply the migration: `wrangler d1 migrations apply DB --remote` (the deploy workflow already does this).
2. Set `TELEMETRY_ENABLED = "true"` in `apps/api/wrangler.toml [vars]` (and `NEXT_PUBLIC_TELEMETRY_ENABLED=true` for the live, help, marketing and telemetry builds) to turn it on. Leaving them unset keeps telemetry off — the self-host default.
3. **Only if you also deploy the mcp worker:** generate a key (`openssl rand -hex 32`) and set the _same_ value on both workers — `wrangler secret put INTERNAL_EVENTS_KEY` from `apps/api`, then again from `apps/mcp`. Without it the MCP's telemetry throttles itself, silently. Skipping this is safe for a self-host that doesn't run the MCP; nothing else depends on it. Verify with `wrangler secret list` on both, because a mismatch produces no error — just quietly lower numbers.

## Privacy posture

The privacy policy + landing page state: we record anonymous, first-party product events (the three-field schema, examples), to learn which features help; no external analytics vendors; data is never sold or shared beyond the public `/telemetry` dashboard. This is consistent with the existing "no tracking pixels / no third-party analytics" claims — those remain true (first-party, anonymous, no third parties, no ad tracking).
