# 22, Telemetry + public transparency dashboard

First-party, anonymous product analytics, surfaced on a **public** dashboard so anyone can see what we measure. The goal: understand which features get used so we know what works, while staying honest about the product's "no creepy tracking" stance.

## Principles

- **Anonymous, aggregate, first-party.** Events carry no user id, no IP, no user-generated content (never a diagram name, tab name, participant name, element text, share code, or diagram id). Only a fixed, app-defined vocabulary of enum values is ever stored.
- **No external vendors.** Ingestion is our api worker; storage is our existing D1 database; the dashboard is our own app. Nothing is sent to a third party, and data is never sold or shared beyond the public dashboard.
- **Off by default.** A single env var gates the whole system, so OSS self-hosters and forks emit/serve nothing unless they opt in. This keeps the "no required SaaS calls" rule ([03](03-open-source-and-business-model.md)) intact.
- **Transparent.** The dashboard is public (`/telemetry`), and the privacy policy + landing page say plainly what we capture and why, and link to it.

## Event schema

Every event is three small fields (`packages/api-schema`, shared by emitter + ingest so they can't drift):

```ts
type TelemetryEvent = {
  category: TelemetryCategory; // the "parent": Diagram | Element | Tab | Theme | Canvas | Template | Comment | Note | Action | Search | UI | Folder | Layer | Session | AI | Team | Participant | Help | Token | Mcp | Email | Error
  action: TelemetryAction; // the "verb": Created | Deleted | Shared | Joined | Added | ...
  type?: string | null; // one app-defined reference value: 'Square', 'Edit', 'PNG', a template id, a theme name
};
```

Examples: `{category:'Diagram', action:'Created'}`, `{category:'Diagram', action:'Shared', type:'Edit'}`, `{category:'Diagram', action:'Joined', type:'Edit'}`, `{category:'Element', action:'Added', type:'Square'}`.

`category` and `action` validate against closed enums: the ingest endpoint drops any event whose category or action is not in `TELEMETRY_CATEGORIES` / `TELEMETRY_ACTIONS`.

`type` is **not** an enum, and the guarantee on it is a different, weaker one worth stating plainly. Every caller passes an app-defined preset (a shape kind, a share role `Edit`/`View`, an export format, a template id, a theme name) — that is the rule, and it is what keeps UGC out. The endpoint cannot check membership of a set, because there isn't one: a new shape, template or theme would otherwise mean editing `packages/api-schema` every time. What it enforces instead is a **shape bound**, `TELEMETRY_TYPE_PATTERN` (`/^[A-Za-z0-9 ._-]{1,40}$/`): a short token of safe characters, which rejects anything that reads as free text and caps what a misusing caller could get onto the public dashboard.

So the safety property is: callers only ever send presets, and the pattern is defence-in-depth behind that, not a substitute for it. A short alphanumeric string that happens to be user content would pass the pattern, which is precisely why the calling rule is the thing that matters.

In practice a `type` is either a literal or derived from a closed vocabulary — an element kind through `titleCaseType`, an export format through a lookup table, a boolean through a ternary of two fixed strings. The case that proves the rule is the theme name: a **custom** theme is named by the user, so `themeTelemetryLabel` maps every custom id to the literal `'Custom'` and only ever emits the built-in themes by name. That is the shape any new `type` source should take — map user-owned values onto a fixed token before they reach `track`, rather than relying on the pattern to catch them.

## Storage (existing D1)

A new `events` table on the **existing** `DB` database (migration `apps/api/migrations/0015_*`), deliberately not a separate database so self-hosters who already provisioned `DB` get telemetry with zero extra setup:

```sql
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  category TEXT NOT NULL,
  action   TEXT NOT NULL,
  type     TEXT,
  ts       INTEGER NOT NULL  -- ms epoch
);
CREATE INDEX idx_events_ts ON events (ts);
```

No owner/IP column — rows are anonymous by construction. If write volume ever outgrows D1, the migration path is Workers Analytics Engine (write-optimised, same Cloudflare account, no new vendor); the ingest + summary contract stays the same.

## Retention

The dashboard surfaces three fixed windows that top out at **30 days** (Last month). Rows older than that are dead storage: never read, never aggregated, never user-visible. The api worker's `scheduled` handler runs a daily **60-day sweep** at 03:00 UTC that deletes events older than the retention floor (twice the dashboard's longest window, so a future "Last 60 days" expansion would have data to populate). Symmetric with the existing 90-day `change_log` retention (spec/12); both fire on the same cron, dispatched on `event.cron`. Self-hosters with `TELEMETRY_ENABLED` off never accumulate events in the first place, so the sweep is a no-op for them.

## API

- **`POST /api/events`** — ingest. Body `{ events: TelemetryEvent[] }` (batched). Validates each against the schema; inserts the valid ones with a server-stamped `ts`. Returns 204. **Deliberately exempt from the diagram write-rate-limiter** so a busy editor session's telemetry can never eat into / block a user's real diagram saves; client-side batching keeps request volume low. Anonymous (no auth required); no body field is stored beyond the three enums + ts. When telemetry is disabled, no-ops with 204.
- **`GET /api/telemetry/summary`** — the dashboard's only data source. Returns grouped counts for three **fixed** windows so the queries stay simple and the response is cacheable: **Today** (since UTC midnight), **Last 7 days**, **Last 30 days** ("Last month"). No custom ranges. Shape:
  ```ts
  {
    enabled: boolean;
    generatedAt: number;
    windows: {
      today: Window;
      last7: Window;
      last30: Window;
    };
    // 30 zero-filled UTC-day buckets oldest -> newest, pre-aggregated
    // server-side so the dashboard's trend charts render without any
    // client work. Optional: absent in the disabled-state response so
    // older clients still parse, present whenever `enabled` is true.
    daily?: {
      days: number[];                       // UTC-midnight ms per bucket
      totals: number[];                     // total events that day
      byCategory: Record<string, number[]>; // per-category counts, same indexing
      byMetric: Record<string, number[]>;   // per-event counts, same indexing; key = `category|action|type`
    };
  }
  // Window = { total: number; rows: { category; action; type; count }[] }
  ```
  `byMetric` is the per-event (category·action·type) version of `byCategory` —
  one 30-day series per distinct event, keyed `category|action|type` (empty
  string for a null `type`). It drives the Search view's metric trend line so a
  single event can be charted over time, not just a whole category. Same
  zero-filled indexing as `days`/`totals`/`byCategory`.
  Cached at the edge (Cache API, a few minutes) so a public traffic spike never hammers D1. When disabled, returns `{ enabled: false }`. The cache is bypassed when the worker is serving from a localhost hostname (parallel to the same-origin escape hatch), so a developer iterating on the feature sees fresh counts immediately instead of waiting out a 5-minute TTL per emit.

## On/off env var

`TELEMETRY_ENABLED` (worker, `wrangler.toml [vars]`, default off) is **authoritative**: it gates both `POST /api/events` and `GET /api/telemetry/summary`. The live editor also reads `NEXT_PUBLIC_TELEMETRY_ENABLED` (baked at build) to avoid emitting at all when off — a client optimisation; the server flag is the real gate. Both absent → fully off, which is the self-host default. On top of these, each user has a per-device opt-out flag stored alongside the other user preferences (spec/20, `telemetryEnabled`, default true). When that flag is false, `track()` is a no-op for that browser regardless of the server's stance; this is the user-facing lever the landing page and `/telemetry` reference when they say "first-party, no creepy tracking".

One further var, easy to miss because it changes no behaviour you can see: **`INTERNAL_EVENTS_KEY`** (a worker secret, the same value on the **api and mcp** workers) exempts our own service-binding callers from the anonymous per-IP rate limiter. Unset, MCP telemetry still flows — it just shares one 120/min bucket with every other internal caller and the overflow is dropped as a 204 nobody can observe, so `Mcp·Used` under-reports without any error to notice. See "Delivery losses" below, [spec/06](06-secrets-policy.md) for the secrets table, and `apps/api/wrangler.toml` for the operator notes.

## Abuse controls

`POST /api/events` is public + unauthenticated by design, so it's guarded in layers without identifying users (it's anonymous trend data, not billing — the goal is "not worth it" + protect cost, not "impossible"):

- **Closed vocabulary.** Events are validated against the `category`/`action`/`type` enums and the batch is capped (100), so an attacker can only ever inflate counts of _known_ events — never inject arbitrary strings into the public dashboard or store junk.
- **Per-IP rate limit.** A dedicated `EVENTS_RATE_LIMITER` binding (separate from the diagram `WRITE_RATE_LIMITER`, so it never touches real users) keyed on `CF-Connecting-IP` — which the client can't forge, unlike `X-Owner-Id`. 120 batches/60s/IP: generous for a real session, bounding for a flood. The IP is a transient key, never stored. Degrades to "allow" when the binding is absent (self-host).
- **Same-origin filter.** A request whose `Origin` header is present and isn't this site is dropped (silently, 204), which stops casual cross-origin / drive-by posting. Spoofable by curl, which the rate limit then catches. Localhost origins (any port) are mutually allowed so local dev (live editor on `:3002` posting to the api worker on `:8787`) actually reaches D1; production never sees a localhost origin, so this widening is dev-only in practice.
- **Cloudflare edge.** Automatic DDoS protection fronts the worker for free. **Recommended manual step:** add a WAF rate-limiting rule on `path eq /api/events` keyed by IP in the Cloudflare dashboard — it blocks abuse _before_ the worker runs (so it costs nothing per blocked request and never touches D1). This is the strongest, cheapest lever and is dashboard config, not code; hosted-only, so forks add their own.

Residual risk: a distributed botnet across many IPs could still nudge the numbers. Accepted — that's a lot of effort to juice an anonymous usage chart. If it ever matters, a global daily insert ceiling is the backstop.

## Emitting

A `track(category, action, type?)` helper buffers events and flushes them batched on an interval and on `visibilitychange`/unload via `navigator.sendBeacon`. Fire-and-forget; failures are swallowed (telemetry must never affect the host app). The buffering engine is the shared `@livediagram/telemetry-client`; each emitting app wraps it with its own policy (the `NEXT_PUBLIC_TELEMETRY_ENABLED` build gate + the spec/20 opt-out). **An opt-out made in the editor silences the help centre too**, since both sit on the livediagram.app origin and read the same localStorage preferences blob. How each reads it is app-owned (the editor caches behind its preference-change events, the help centre reads straight through), but _where_ it reads and _which way it defaults_ are not: `USER_PREFERENCES_STORAGE_KEY` and `telemetryOptInFromRaw` live in `@livediagram/telemetry-client` so a key rename in one app can't leave the other quietly emitting for a user who opted out. Four surfaces emit: the **editor** (`apps/live`), the **help centre** (`apps/help`, the `Help` category), the **MCP worker** (`apps/mcp`, the `Mcp` category), and the **api worker itself** (server-side self-reports written straight to the events table: `Error·Api·Internal` for an unhandled server exception, and the whole `Email` category, which has no browser to emit from). Never the static marketing site, so the marketing "0 trackers" claim stays literally true. Call sites are one-liners, e.g. `track('Element', 'Added', 'Square')`.

The aim is to cover every meaningful interaction a person has with a diagram (discrete feature actions, never continuous gestures like drag/resize/pan/zoom or raw colour tweaks, which would just be noise). Current taxonomy:

- **Diagram**: Used `Multiplayer` (the diagram was open with at least one other person live in the room, emitted the first time the presence list holds anyone besides us and then once per diagram per page load — `app/diagram/[id]/multiplayer-telemetry.ts`, guarded there rather than at the call site because presence arrives as a frame per change). This is the only event that counts collaboration **happening** rather than being **offered**: `Joined` fires only for a share-link visitor (gated on `!isOwnerVisit`), so two teammates editing the same team diagram at once were two indistinguishable `Loaded`s and the multiplayer product had no multiplayer metric. Read the rest of the Collaboration tab against it: many links shared and few multiplayer sessions means the links aren't being walked through. Loaded (an existing diagram was opened — fired on every open, including a page refresh, from the editor bootstrap's owner and share branches; an opens/engagement signal distinct from the once-per-diagram Created); Created; Shared `Edit`/`View`/`PasswordSet`/`PasswordCleared`; Joined `Edit`/`View`; Duplicated (also `Copy` when a visitor clones a shared diagram into their own account); Removed `ShareLink` (a share link revoked — counterpart to Shared); Deleted; Exported `Markdown`/`PDF`/`PNG`/`SVG`/`JSON`; Renamed; Undone; Redone; Moved (to a folder, or back to Unsorted when folder=null); Reverted (single entry rolled back from the activity log).
- **Element**: Added `<shape kind | Text | Sticky | Arrow | Image | Freehand | TableColumn | TableRow>` (the `TableColumn`/`TableRow` types are a column/row inserted into a table element); Deleted (no type for a plain element delete — covering both single and marquee-multi delete — or `TableColumn`/`TableRow` when a table column/row is removed, `Eraser` when the eraser tool wipes it); Duplicated (**once per gesture**, plus one `Added·<kind>` per element the copy created — see "Counting rules" below; `ShiftDrag` when the copy came from a shift-drag); Copied (a selection copied to the in-app clipboard); Grouped (both the marquee-group and the drag-one-onto-another group-tool path); Ungrouped; Locked; Unlocked; Linked; Unlinked; Reordered `Front`/`Back`/`TableColumn`/`TableRow`; Toggled `Bold`/`Italic`/`Underline`/`Strikethrough`/`AspectLock`/`TableHeaderRow`/`TableHeaderColumn`/`TableZebra`; Changed `FormatPainter` (style copied from a source onto a target), `Font`, `TextSize`, `TextAlign`, `Padding`, `ShapeMorph`, `BorderStroke`, `BorderStyle`, `BorderRadius`, `ArrowEnds`, `ArrowThickness`, `ArrowheadSize`, `ArrowheadShape`, `ArrowStyle`, `ArrowLineStyle`, `TableCell`; Voted (a dot-vote cast on an element, spec/39); Removed `Vote` (a dot retracted — the counterpart to Voted, so "dots cast" reads net of second thoughts). The `Freehand` type corresponds to the pencil tool (spec/09). Per-element **colours** (fill / stroke / text) and **opacity** are deliberately NOT tracked — those are the "raw colour tweaks" the rule above carves out.
- **Tab**: Loaded (a tab's content was fetched for viewing — the first tab when a diagram opens (from the editor bootstrap) plus each tab switched to (`usePerTabLoad`); the search prefetch `loadAllTabs` deliberately does not emit); Created; Deleted; Duplicated; Renamed; Locked; Unlocked; Linked; Reordered (a drag that changed nothing but the position); Moved `Folder` / Removed `Folder` (a tab filed into, or taken out of, a tab folder — spec/30; the type is what keeps these off the untyped tab-lifecycle cards, and both the ellipsis menu and a folder-crossing drag emit them identically); Imported `JSON`/`Markdown`; Aligned; Cleared; Changed `Font`/`DefaultTextSize`; Started `CountdownTimer`/`StopwatchTimer`/`Vote`/`PrivateVote`/`Poll` (a live session tool launched on the tab, spec/39 + spec/88; `PrivateVote` is a SECOND event alongside `Vote` when a privacy switch is on, a flag on that subset rather than a separate vote); Ended `Vote`/`Poll`/`VoteReview`/`CountdownTimer`/`StopwatchTimer` (the timer types mirror Started, so started-vs-finished shows how many get abandoned); Revealed `Vote`; Cleared `Vote` (the round discarded entirely — distinct from Ended, which closes casting and keeps the tallies); Voted `Poll` (a participant answered); Toggled `TimerPaused`/`TimerResumed`; Changed `TimerReset`. The timer lifecycle beyond Started is instrumented because for a facilitation feature the drop-off is the interesting number, not the count: a timebox that is always paused or never finished is not working, and only the pairs show that.
- **Theme**: Changed `<theme label>`/`ResetElements` (the "Reset elements to theme" action force-recolours every element on the tab to the active theme); Created `Custom`; Changed `CustomEdited`; Deleted `Custom` (the custom-theme builder lifecycle).
- **Canvas**: Changed `<background pattern>`/`BackgroundColor`/`BackgroundOpacity`/`PatternColor`; Zoomed `In`/`Out`/`Fit`/`Reset`/`Preset`; Used `Laser`/`Spotlight`/`Eraser`/`FormatPainter`/`Isometric`/`AvatarMode`/`FollowMe` (a held canvas mode was entered — emitted on ENTERING the mode, never per sample, because the mode's own gesture is continuous). `FollowMe` is the follow-a-peer viewport (spec/131): it reports here so the pointing tools rank together, and it is the strongest signal that a session is being presented rather than co-edited. The `BackgroundColor` / `BackgroundOpacity` / `PatternColor` emits are debounced ~800ms per slider so a single drag collapses to one event rather than dozens (carved-out exception to the "raw colour tweaks are noise" rule, justified because a debounced single-emit captures the discrete "user changed canvas appearance" signal without flooding).
- **Template**: Used `<template kind>`.
- **Comment**: Added; Deleted; Resolved; Unresolved; Opened (user opened the comment popover on an element). View-role visitors can Add and Delete **their own** comments, but not Resolve / Unresolve or delete others'. Their Add goes through the dedicated `POST /api/diagrams/<id>/tabs/<tabId>/comments` endpoint and their Delete through `DELETE /api/diagrams/<id>/tabs/<tabId>/comments/<commentId>` (server-checked `authorId === caller`); both accept read-role auth (the only write paths open to view-role; spec/11).
- **Note**: Added (transition empty -> non-empty); Changed (existing note's text edited); Deleted (transition non-empty -> empty); Opened (user opened the note popover on an element). One Add/Change/Delete emit per save (popover commit), not per keystroke; a save that doesn't change the text emits nothing.
- **Action**: assigned actions (spec/68). Created `EmailOn`/`EmailOff` (an action assigned, the type carrying the email-checkbox state at send time); Changed `Reassigned`/`Edited` (an edit that changed the assignee vs one that only touched name/description); Resolved (completed); Unresolved (reopened); Deleted; Opened (the action popover opened, from the tile, badge, or panel row). The profile page's notification flip emits `UI`/`Toggled`/`NotifyActionAssigned{On,Off}` like the other spec/65 toggles. Never the action name, description, or any identity.
- **Search**: Opened (panel mount); Searched (query first becomes non-empty in a session, debounced to one emit per panel open so per-keystroke noise stays out); Selected `Diagram`/`Shared`/`Folder`/`Team`/`Tab`/`Element` (user picked a result, type = the result kind).
- **UI**: Toggled `Dark`/`Light` (editor chrome mode toggle, distinct from per-tab diagram theme), the Settings-dialog flips `AutoRebindOn`/`AutoRebindOff` / `TelemetryOn`/`TelemetryOff` / `MinimalPanelsOn`/`MinimalPanelsOff` (see spec/20), and the per-tool flip `RecogniseShapesOn`/`RecogniseShapesOff` (the pencil ModeBanner toggle, also spec/20, surfaced beside the tool rather than in Settings), `AlignmentGuidesOn`/`AlignmentGuidesOff` (spec/20), `ReduceMotionOn`/`ReduceMotionOff` (spec/20), `NotificationsOn`/`NotificationsOff` (the Settings flip for confirmation toasts, spec/20), and `ZenModeOn`/`ZenModeOff` (the distraction-free focus mode, spec/26). The type carries the new value so the dashboard reads as "users moved this way" rather than "users touched a setting". Also: Opened `Settings`/`Shortcuts`/`Share`/`Activity` (the editor's modal dialogs and the activity panel); Opened `ActionSignInNudge` (a signed-out user opened the Assign Action dialog and saw the Myself-only picker with its sign-in nudge, spec/68); Closed `Welcome` (user dismissed the first-run welcome modal); the keyboard-shortcuts master flip `ShortcutsOn`/`ShortcutsOff` (the per-device toggle in the Shortcuts dialog that disables every editor shortcut, spec/07); Copied `ShareLink` (clicked the copy button on a share link); Copied `EmbedCode` (copied a share link's iframe snippet from the Share dialog, spec/33); Copied `TeamInviteLink` (copied a team invite link from the Invite-by-link dialog, spec/32). The `TelemetryOff` flip fires BEFORE the preference is persisted so the opt-out itself still reaches the wire; the other preference flips do too so the wire event matches the value the user just clicked, not the prior state.
- **AI**: Used `<mode>` (where `<mode>` is `Ask` or `Clean` — the two remaining modes after `generate`/`review` were removed, spec/25). Fires on each successful request after the response is received / streaming completes; off-topic refusals don't inflate the count. Toggled `AiOn`/`AiOff` (the Settings opt-in for the AI panel). See spec/25.
- **Folder**: Created; Renamed; Deleted; Moved (re-parented under another folder, or promoted to the root when parent=null). Tracked from `useFolders` so both the editor side panel and the standalone explorer page emit identically; rename emits only when the trimmed name actually changes. The `type` says which kind of folder: absent for an explorer folder of diagrams, `Team` for one in a team's shared library (spec/35), `Tab` for a **tab folder** inside a single diagram (spec/30) — a different feature that happens to share the word, so it needs the type to stay legible rather than to stay separate.
- **Layer**: per-tab layers (spec/74), the panel and the rows. Added; Deleted; Cleared (a layer emptied but kept); Renamed `Manual`/`Adopted` (renamed by hand vs auto-named from an element's label); Reordered (dragged to restack); Changed `Opacity`; Selected (the active layer switched); Moved (a selection sent to another layer); Removed `MergedUp`/`MergedDown`; Toggled `Hidden`/`Shown`/`Locked`/`Unlocked`/`OthersHidden`; Opened (the panel expanded). Never a layer name.
- **Help**: View `<article slug>` (an article was read); Helpful / Unhelpful `<article slug>` (the per-article feedback widget); Searched `Results`/`NoResults` (a help-centre search settled, `apps/help/lib/search-telemetry.ts`). The search event carries the OUTCOME and never the query, which is user-generated content: a dry search is the most actionable number the help app produces (it is the backlog of articles worth writing), and the words that came up dry are deliberately not recoverable from it. One emit per settled query per page, debounced ~900ms so `flowc` on the way to `flowchart` doesn't report its own miss, and deduped so retyping one query counts once.
- **Email**: Sent `<template kind>` — `Welcome`/`Week1`/`Week2`/`Activation`/`WinBack`/`Milestone`/`FirstShare`/`TeamInvite`/`InviteResponse`/`DiagramJoined`/`CommentNotification`/`ActionAssigned`/`TokenExpiring`/`AccountDeleted` (spec/64). Written **server-side**, straight to the events table by the api worker, because nothing about an email reaches a browser: the send happens in a cron or a `waitUntil` after the response has gone, so this is the only place that can count it. Without it the whole onboarding series was unmeasurable and a dead `RESEND_API_KEY` was invisible, its failures going to `console.error` and nowhere else. The kind rides on the template builder's own return (`RenderedEmail.kind`), so it reaches `sendEmail` through the spread every caller already writes rather than being re-stated at fourteen call sites. Never an address, a name, or a recipient count. A failed send reports as `Error`/`Api`/`Http<status>.SendEmail` (or `Network.SendEmail` when the request never completed), with the other API faults.
- **Team**: Created; Joined (accepted an email invite or opened an invite link); Declined `Invite` (the recipient turned an invitation down); Shared `Link` (an admin turned on a shareable invite link, spec/32); Removed `Link` (that invite link turned off), `Invite` (an admin withdrew an invitation the recipient had not accepted), `Member`/`Self` (a member who had joined was removed, or the user left the team); Changed (team settings edited), `Role` (a member's Admin/Member role changed); Added `Member` (invited a member by email — the invitation, NOT the acceptance), `Diagram` (a diagram added to / moved within a team library); Moved `Diagram`; Deleted (the team disbanded). Membership only — see spec/32.

  The **invite funnel** is `Added·Member` (sent) → `Joined` (accepted) → `Declined·Invite` (turned down), and the three ways a row leaves the member list are kept apart on purpose. Both halves of that used to be pooled: an admin withdrawing an unaccepted invitation emitted `Removed·Member`, so "people who left a team" was inflated by invitations nobody ever took up, while `Removed·Invite` was being emitted by the RECIPIENT declining — so the accept rate on an invitation, the only number that says whether invites are landing for a feature that needs a second person to show up, could not be read from any pair of rows. `Declined` earns its place in the action enum for that reason rather than riding along as another `Removed` type: withdrawing is a change of mind about an invite, declining is an answer to it. The three-way split lives in `components/panels/team-removal.ts`, which owns the confirm-dialog wording too, so what the user is told and what gets counted come from one decision.

- **Session**: SignedIn (user just completed sign-in via Clerk); SignedUp (just completed sign-up); SignedOut (just signed out); Deleted `Account` (a signed-in user deleted their account and all its data, fired from the Delete-account dialog after the server-side wipe but before sign-out so the event still reaches the wire) — these only fire when Clerk is configured; pure-guest deploys emit nothing here. Opened `Embed` (a read-only embed view rendered, spec/33; one emit per iframe document).
- **Participant**: Created (a brand-new browser identity was minted — the daily new-visitors signal). Fires exactly once per browser, at whichever identity mint runs first: the local guest-id mint (`ensureGuestSelfId`, used by `/new` + `/explorer`) or the server-signed mint (`ensureSignedGuestIdentity`, the editor bootstrap); a returning browser hits the stored-id early-returns and never re-emits. First-time visitors who sign up without ever minting a guest id surface via `Session`/SignedUp instead. No type, no identifier — the event is a bare count. Returned `Anonymous`/`Authenticated` (a returning browser opened the app on a later UTC day — the daily-active-returns signal) is the counterpart: emitted at most once per browser per UTC day from the app-open bootstraps (editor `useIdentityBootstrap`, `/new`, `/explorer`), gated by a `livediagram:v2:last-active-day` key, with the type splitting guests (`Anonymous`) from signed-in users (`Authenticated`) so `Participant·Returned` sums both. A browser's first observed day only seeds the key and emits nothing (that day is a `Created`, not a return), so a pre-existing user's first day after this ships is a one-day ramp undercount. No identifier is sent — the per-day dedup happens entirely in the browser (`apps/live/lib/daily-return.ts`).
- **Token**: Created `Manual` (an API token minted by hand from the Explorer New-token popover, via `useTokens.create`) or `Created` `MCP` (an AI tool connected through the OAuth consent screen, spec/62, which mints a token under the hood); Removed (a token revoked, `useTokens.revoke`). The `type` is the fixed source only — never the token, its name, or the client name.
- **Mcp**: Used `<tool>` (an MCP server tool call, where `<tool>` is the PascalCase tool name: `FindDiagrams`, `ReadDiagram`, `ListTemplates`, `CreateDiagram`, `AddTab`, `UpdateDiagram`, `ShareDiagram`, `RenameDiagram`, `DeleteDiagram` — every registered tool emits). Emitted by the MCP worker (apps/mcp, spec/62) fire-and-forget to the public `/api/events` endpoint over the api service binding (no token; a worker-to-worker call sends no Origin header so the same-origin guard passes). The third app that reports telemetry (after the editor and help centre), kept as its own category so MCP usage reads distinctly from the in-editor AI panel (`AI`).
- **Error**: failures, counted generically — never a message, stack, URL, or anything user-generated; fixed kinds and HTTP status tokens only. The action carries the error's **source** (a deliberate noun in the verb slot): `Api` `Http<status>.<Action>` (the editor's api-client observed a non-2xx response; the suffix is the caller's own intent string PascalCased — `Http403.SaveTab`, `Http500.CreateDiagram` — because a bare status is unattributable: a spike of 297 `Http403` in one day says something is being refused and nothing about what. The strings are authored in `lib/api`, never derived from user input, and non-alphanumerics are stripped, so a path, id, or share code can't ride along; the dot is deliberate, since `TELEMETRY_TYPE_PATTERN` would reject a colon and the ingest would drop the event silently — emitted from the shared response choke point in `lib/api/core.ts` (`expectOk*` -> `ApiError`), wired via `setApiErrorReporter` from the editor boot so the api module never imports the telemetry wrapper (it sits under the user-preferences -> api-client import cycle); the expected-404 read paths that return null don't emit); `Api` `Internal` (the api worker's own top-level catch-all recorded an unhandled server exception — the worker writes the row straight into the events table, so a server crash counts even when no client survives to report it; gated on `TELEMETRY_ENABLED` like the ingest); `Client` `Uncaught`/`UnhandledRejection` (window-level uncaught exceptions and unhandled promise rejections in the editor AND the help centre, installed by `installClientErrorTracking` from `@livediagram/telemetry-client`, capped at 10 emits per kind per page load so an error loop can't flood the pipeline). Known v1 limit: network-level fetch failures that call sites catch and surface in-UI are not counted (there is no shared fetch wrapper; the uncaught ones still surface via the Client kinds).

## Counting rules: one event per gesture, or one per object?

Audited in full for issue #30, because "is this number the thing I think it is?" was unanswerable from the taxonomy alone. The rule, now stated rather than assumed:

**An event counts the GESTURE, not the objects the gesture touched.** Deleting a twelve-element marquee selection is one `Element·Deleted`; restyling it is one `Element·Changed`; an eraser stroke that wipes a dozen shapes is one `Element·Deleted·Eraser`. This is deliberate — the question these answer is "how often do people delete / restyle / erase", and a per-object count would let one marquee drag swamp a hundred single deletes. No `track()` call in the codebase sits inside a loop, so this holds uniformly.

**The one exception is creation, because creation feeds a census.** `Element·Added·<kind>` is what the dashboard's Palette ranking is built from, so it has to be a true count of elements created, not of creation gestures. Every from-scratch path already emitted one per element (you can only draw one at a time). The **copy** paths did not: duplicate, paste, and shift-drag emitted a single untyped `Element·Duplicated` and no `Added` at all, so an element born by copying was invisible to the census — under-counting precisely the shapes people liked enough to reuse. All five copy paths now go through `trackDuplicated`, which emits one `Duplicated` for the gesture **and** one `Added·<kind>` per element created. `elementTelemetryType` is the single mapper from an element to its token, so a copied code block lands in the same bucket as a drawn one.

Two related fixes from the same audit:

- Copy paths emitted **before** their own guards, so a duplicate that never happened still logged one (a multi-selection holding nothing copyable). They now emit after the copies exist, and an empty result emits nothing.
- `Element·Rotated` was in the enum and documented here as firing at rotate-gesture start. There is no rotate gesture — rotation is a context-menu control that emits `Element·Changed·Rotation` — so the action was dead. Removed from the enum.

**Deliberate double-emits** (so nobody reads them as double-counting): starting a private vote emits both `Tab·Started·Vote` and `Tab·Started·PrivateVote`, the first being the true vote count and the second a flag on that subset. Completing the `/new` wizard emits `Diagram·Created` + `Theme·Changed` + `Template·Used`, which are three genuinely different facts. Filing a tab into a folder name the diagram has not used before emits `Folder·Created·Tab` + `Tab·Moved·Folder`, also two different facts — the folder now exists, and this tab is in it — because reporting only the creation made "tabs filed into folders" undercount by exactly the number of folders anyone created.

## How completeness is tested

Telemetry drifts silently and there is no runtime signal when it does: emitting is fire-and-forget, and the public dashboard only ever renders what **arrived**, so a renamed or deleted event is indistinguishable from a feature nobody used. Two checked-in guards replace that missing signal.

- **`apps/live/lib/telemetry-manifest.ts` pins every `category·action` pair the editor emits**, enforced by `telemetry-coverage.test.ts`, which scans the source for `track()` call sites (ternary actions included) and diffs against the manifest. Adding, renaming, or removing an emitted pair fails CI until the manifest is updated — and the manifest's comment sends you here, so the taxonomy above gets updated in the same change. The same test asserts every pair is inside the closed enums, since an event outside them is silently dropped by the ingest validator.
- **`PALETTE_TELEMETRY_TYPES` in `@livediagram/api-schema` is the one definition of the palette `type` tokens**, consumed by the dashboard's Palette view instead of the hand-mirrored copy it used to keep. `palette-telemetry-coverage.test.ts` asserts every shape kind in `@livediagram/diagram` has a bucket there, **and every non-shape element kind too** — that second half was missing, and so was `Video`: all six embed tiles create a `video` element, so from the day embeds shipped their adds were counted nowhere. The copy had already drifted: the dashboard expected `Code-block` long after the editor settled on `CodeBlock`, so every code block anyone drew was emitted, validated, stored, and missing from the ranking.
  That test must derive its tokens by CALLING `elementTelemetryType`, never by restating its rule. It did restate it once, and the copy drifted the same way the dashboard's had: it spelled out seven camel-case tokens where the editor spelled three, so the session button, reaction pad, comment pin and done check each reported `Session-button` and friends on Added while the test proved the catalogue held `SessionButton`. Four features counted zero, and every assertion passed. A copy of the rule can only prove the copy agrees.

Pairs are pinned but `type` values generally are not — types are open-ended by design (a shape kind, a template id, an article slug) and pinning them all would fail on every new shape. The palette tokens are the exception because that is where drift is both invisible and costly.

## Delivery losses, and the two that were worth fixing

Emitting is fire-and-forget, so a dropped batch is invisible by construction. Audited alongside the coverage work; the losses split into ones we accept and ones we didn't.

**Fixed — a failed flush is now retried once.** The buffer used to be cleared before the request went out, with the result swallowed, so any network failure discarded that batch permanently. The problem wasn't the volume so much as the _distribution_: the losses concentrated in flaky-network and close-the-tab-quickly sessions, which biases the data rather than just thinning it. A rejected `fetch` now re-queues its events at the front of the next batch and gets exactly one more attempt.

The bounds matter more than the retry:

- **Only on a rejection**, never on a non-2xx. A rejection means the request got no response, so the events almost certainly didn't land. A server that _answered_ may well have stored them, and re-sending would double-count — while retrying a 429 would worsen the thing it's complaining about.
- **Exactly one attempt.** A retry trades a small over-count risk (request arrived, response lost) against a systematic under-count; that trade is worth making once. An endlessly retried batch on a dead network would grow the buffer, duplicate on every recovery, and still die at unload.
- **Bounded by the same 25-event cap**, oldest dropped first — the retried events have already had their chance.
- **Never on the beacon path.** We're unloading; there is no later.
- A failure **arms a fresh timer**, so the retry happens on its own rather than waiting for the next tracked event.

**Fixed — `sendBeacon`'s return value is no longer ignored.** It returns `false` when the UA's queue is full, and that batch was simply gone, at exactly the moment it mattered (page-hide, the tail of a session). It now falls through to the `keepalive` fetch, which is the same "outlive the page" guarantee by another route.

**Fixed — internal callers no longer share one rate-limit bucket.** Our own workers reach `/api/events` over a service binding, which carries no `CF-Connecting-IP`, so `clientIp` fell back to the literal `'anonymous'` and every internal caller worldwide contended for a single 120/min key, with the overflow dropped as a 204 nobody could observe. Since the MCP worker posts one request per tool call, that ceiling was roughly two tool calls per second globally — enough to make a growing integration look flat. A matching `INTERNAL_EVENTS_KEY` (a worker secret on both sides, compared in constant time) now exempts them from the per-IP limiter, which exists to stop _anonymous_ abuse of a public endpoint and was never aimed at us. Unset on either side means nobody is exempt, exactly as before, so self-hosting needs no configuration.

**Still accepted:** client errors cap at 10 per kind per page load (an error loop must not flood the pipeline, and the dashboard reads presence and order of magnitude, not exact storm size); events buffered when a tab is hard-killed are gone (nothing is persisted, deliberately — telemetry must not own storage); and a second consecutive failure discards the batch, per the one-retry bound above. All of these under-count rather than over-count, which is the safer direction for a usage chart.

Extend by adding to the `TELEMETRY_CATEGORIES` / `TELEMETRY_ACTIONS` enums (if needed) + a one-line `track()` call at the interaction's handler. Page hits are deliberately not wired; new-visitor counting goes through `Participant`/Created above.

## Dashboard app (`apps/telemetry`)

A new Next.js static-export app (same stack as the others), mounted by the router at **`/telemetry`** (`basePath: '/telemetry'`, prefix stripped by the router, like the live app's assets). Public, read-only.

A **global timeframe panel** sits above the view tabs and is shared by every tab (the window is not tab-specific): three selectable cards (Today / Last 7 days / Last month) each show that window's total and act as the filter, with the selected window highlighted on a 30-day daily **trend line** directly below — so the reader controls the filter and sees the volume line in one always-visible place. The selected window drives the counts in all the tabs. Once the full panel scrolls under the site header, a **condensed sticky selector** (the same three windows as small pills) fades in fixed below the header, so the timeframe stays changeable while reading a long list. To its right, an **ellipsis menu** switches the active view (the tab row also scrolls away), so both controls stay reachable; the timeframe pills stay inline, only the view picker collapses into the menu.

Below it, twelve top-level **view tabs** switch between ways of reading the single `GET /api/telemetry/summary` payload, ordered as a product funnel (who arrives, what they open + make, what they build, how they get unstuck, how machines connect, then the power-user lenses). On mobile the tab row **wraps** rather than overflowing a single line; Search and Raw sit last:

- **Highlights** (default) — the key product metrics we most want to watch, **grouped into the questions they answer** (Visitors, Creation, Collaboration, Output & Preferences), each a card with the selected-window count, a plain-language description, and a 30-day mini trend line. A fixed curated list, not "top by volume", so a low-volume but important signal (a first-time visitor, `Participant·Created`; a returning one, `Participant·Returned` summed across guest + signed-in) is always on screen. A highlight is either a single typed event or an **aggregate** over every type of a `category·action` (e.g. all `Element·Added` shapes, all `Diagram·Exported` formats) where the type split is arbitrary for that lens — but stays type-specific where the type is meaningful (Edit vs View share links; the Dark UI toggle, which shares `UI·Toggled` with unrelated setting flips). Metrics absent from the payload render as zero rather than vanishing.
- **Acquisition**: the top of the funnel: New Visitors (`Participant·Created`), Returning Visitors (`Participant·Returned` — a combined sum plus its guest/signed-in split from the `Anonymous`/`Authenticated` types), Sign-Ups / Sign-Ins, the account lifecycle (Sign-Outs, Accounts Deleted via `Session·Deleted·Account`), and **email sent** (`Email·Sent`, the total plus Welcome / Team invite / Action notification — the onboarding series exists to bring people back, so it reads against Returning Visitors above; a deploy with `RESEND_API_KEY` set that shows zeroes here is a broken key, which used to be visible only in `wrangler tail`). Metric cards with 30-day trends, sharing the same `MetricGroups` renderer as Highlights. Account events only fire where sign-in is configured.
- **Content**: the diagram + tab lifecycle side by side — two groups (Diagram, Tab), each with Loaded / Created / Renamed / Deleted / Duplicated as metric cards with 30-day trends, sharing the same `MetricGroups` renderer as Highlights. Loaded is the opens/engagement signal (every open of an existing diagram, every tab whose content is fetched), read against the once-per-object Created beside it.
- **Palette**: what people reach for in the creation palette, most to least, one ranked list per palette tab: **Shapes**, **Tools**, **Components**, **Devices**, **Icons** (all `Element·Added`, bucketed by the palette catalogue) plus **Selection modes** (`Canvas·Used`: laser, spotlight, eraser, format painter, isometric, which are canvas modes, not palette elements). Reuses the shared `RankCard`. (Pointer-tool picks like select/hand aren't in the event vocabulary yet, so they don't appear.)
- **Look & Feel** — which visual presets get used, most to least: ranked lists of templates (`Template·Used`), built-in themes (`Theme·Changed`), and canvas patterns (`Canvas·Changed`), the most-used tagged, plus the custom-theme builder's lifecycle (created / applied / edited / deleted).
- **Editing**: the in-editor tools that organise the work rather than draw it — AI assistance (requests, split Ask vs Clean, plus the Settings opt-in that gates them), layers (created, visibility / lock toggles, selections moved, panel opens), notes and assigned actions (assigned vs completed, and how many were emailed), and organisation (folders, diagrams filed). Metric cards with 30-day trends via the shared `MetricGroups` renderer. This tab exists because every metric on it was **already arriving and being read by nobody**: `AI·Used` had no card on any tab, and the `Layer`, `Note`, `Folder` and `Action` categories appeared only in the `event-vocab` labeller the Raw table uses. Data stored but unread is the same blind spot as data never sent, one step further along.
- **Help**: how the help centre (apps/help) is doing: headline cards for article views and helpful / not-really votes (`Help·View` / `Help·Helpful` / `Help·Unhelpful`), then rankings of most-read, found-helpful, and the not-really-helpful articles (the ones worth rewriting). `type` is the article slug. Search outcomes (`Help·Searched·Results` vs `NoResults`) read alongside them: a rising dry-search count is the backlog of articles that don't exist yet.
- **External Connections**: programmatic access. The API-token lifecycle (`Token·Created·Manual`, `Token·Created·MCP`, `Token·Removed`) as cards, plus MCP tool usage (`Mcp·Used`) as a headline count and a per-tool ranking.
- **Collaboration**: how much work happens together rather than solo — the multiplayer story the other tabs don't tell. **Live together** first (`Diagram·Used·Multiplayer`, `Canvas·Used·FollowMe`), because it is the only group that counts two people on one canvas at the same moment rather than an invitation to be there, and every other group reads against it. Then sharing & joining (`Diagram·Shared·Edit/View`, `Diagram·Joined·Edit/View`), discussion (`Comment·Added/Opened/Resolved`), and teams (`Team·Created`, `Team·Added·Member`, `Team·Added·Diagram`). Metric cards with 30-day trends via the shared `MetricGroups` renderer; high-signal for retention / network effects.
- **Exceptions**: error health — API failures vs client-side exceptions. Headline cards (all `Error·Api·*` vs all `Error·Client·*`) with 30-day trends via the shared `MetricGroups` renderer, then rankings of the API failure statuses (`Http500`, `Http403`, …, plus the worker-reported `Internal`) and the client exception kinds. Counts are generic by construction (the closed vocabulary above); an empty view is the goal state.
- **Search** — find one specific metric two ways: **type** a query for flat token matches, or **browse** the hierarchy (category → action → type) one level at a time, for when you can't name what you want. Selecting a metric **visualises it underneath** as its own 30-day trend line (from `daily.byMetric`, with the selected window highlighted) plus its Today / Last 7 / Last month totals.
- **Raw** — the full aggregate view: a category-share **donut** (legend below) and a top-N **leaderboard** side by side, then every event in the window as a **sortable, category-filterable table** (category badge, event, count + share with bar, 30-day trend sparkline). Click a header to sort; the Category funnel narrows to a chosen subset.

Charts render in inline SVG (a line with a shaded selected-window span and a dashed average reference line); no charting library, no extra request. Event names display in Title Case (preserving acronyms like PNG/JSON). Explains in-page that the data is anonymous, first-party, no vendors. Degrades to an "analytics not enabled" state when the summary returns `enabled: false`.

## Routing & deploy

- **Router** ([08](08-router-app.md)): a `TELEMETRY` service binding and a `/telemetry` route that strips the prefix and forwards (mirrors the live-asset strip).
- **Deploy** ([10](10-deployment.md)): build + upload `apps/telemetry/out`, a `deploy-telemetry` job in parallel with marketing/live/api, and `deploy-router` gains it as a dependency. The `events` migration applies in the existing `wrangler d1 migrations apply DB` step.

## Provisioning (one-time, owner only)

1. Apply the migration: `wrangler d1 migrations apply DB --remote` (the deploy workflow already does this).
2. Set `TELEMETRY_ENABLED = "true"` in `apps/api/wrangler.toml [vars]` (and `NEXT_PUBLIC_TELEMETRY_ENABLED=true` for the live + telemetry builds) to turn it on. Leaving them unset keeps telemetry off — the self-host default.
3. **Only if you also deploy the mcp worker:** generate a key (`openssl rand -hex 32`) and set the _same_ value on both workers — `wrangler secret put INTERNAL_EVENTS_KEY` from `apps/api`, then again from `apps/mcp`. Without it the MCP's telemetry throttles itself, silently. Skipping this is safe for a self-host that doesn't run the MCP; nothing else depends on it. Verify with `wrangler secret list` on both, because a mismatch produces no error — just quietly lower numbers.

## Privacy posture

The privacy policy + landing page state: we record anonymous, first-party product events (the three-field schema, examples), to learn which features help; no external analytics vendors; data is never sold or shared beyond the public `/telemetry` dashboard. This is consistent with the existing "no tracking pixels / no third-party analytics" claims — those remain true (first-party, anonymous, no third parties, no ad tracking).
