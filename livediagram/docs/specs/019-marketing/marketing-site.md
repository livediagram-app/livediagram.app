# Marketing site

The marketing app (`apps/marketing`) is the public landing site served at `/` (everything the router doesn't hand to the live editor's routes, `/api/*`, or `/telemetry`, see [08-router-app](../016-platform/router-app.md)). Static Next.js export, no SSR. It is the top of the acquisition funnel: its only job is to explain what livediagram is and send visitors to `/new`.

## Golden rule: claims map to shipped features

**Every feature claim on the marketing site must correspond to something a visitor can actually do today.** No aspirational copy, no roadmap dressed as present tense.

- If a feature is not built (teams/permissions, true concurrent/CRDT editing, see [02-prototype-scope](../005-project-roadmap/prototype-scope.md)), it does **not** appear on the landing page, even softened.
- When the editor gains or loses a feature, update the landing page in the same change. Drift between the page and the product is a bug.
- Counts (templates, themes, shapes) must match the source of truth ([09-canvas-and-palette](../008-canvas/canvas-and-palette.md), `packages/templates/src/templates.ts`, `apps/editor/lib/themes.ts`). As of this spec: **82 templates** in nine categories (three blanks, one per editor mode, leading the landing gallery's Blank Slate, and Draw templates of their own ([Templates by mode](../007-editor/templates-by-mode.md)), grouped into Brainstorm / Flowcharts / Hierarchies / Agile / Projects / Strategy / Design / Technical categories in the picker, including three mind-map styles (radial / tree / bubble), four flowchart styles (basic / swimlane / decision tree / approval workflow) plus a data-flow diagram, a Flywheel momentum loop, Timeline + horizontal/vertical Milestone timelines + Gantt + Roadmap + RACI project-planning starters, agile User story map + Affinity map boards, Lean Coffee + Town Hall Q&A live-session boards built on the Q&A board, a Pub Quiz, Icebreaker Questions, Two Truths and a Lie, Would You Rather and Find Someone Who Bingo under Quizzes & Games ([Quiz and game templates](../012-collaboration/quiz-and-game-templates.md)), a Virtual Office, a Coworking Space, a Team Pod and an All-Hands Hall to walk round in Avatar mode ([Virtual office template](../012-collaboration/virtual-office-template.md)), strategy canvases (Business Model Canvas, Empathy map, Funnel, Sankey diagram), OKR tree + Sitemap hierarchies, and the technical System / Cloud architecture, Database schema, Sequence, Class and State machine diagrams and an Event storming board plus an Impact-vs-Effort Prioritization matrix, four more retro formats (Start / Stop / Continue, Mad / Sad / Glad, 4Ls, Sailboat), an Incident postmortem, an Opportunity solution tree, Crazy 8s, a Stakeholder map, a Risk matrix, a User persona, a Meeting agenda and a personal Objectives planner, a Wardley map, a STRIDE Threat model, a Service blueprint, a north-star Metric tree, the Value Proposition Canvas, a Family tree and a Value stream map), **24 themes** (12 default + 12 extra, the extras including the dark schemes and three multi-colour "rainbow" schemes; see [Multi-colour (rainbow) themes](../011-theme/multicolour-themes.md)). Both counts are pinned by `apps/editor/lib/templates.test.ts` + `themes.test.ts` so spec drift surfaces as a test failure.
- Be honest about trade-offs where it builds trust: realtime is **last-write-wins**, not CRDT, say so rather than implying conflict-free merging.

## Structure

Single landing page (`app/page.tsx`), in this order: a sticky header, the hero, the template gallery, the Community section ([Community](../025-community/community.md#featured-on-the-home-page): six shared documents, loaded after the page, the one landing section that reads the api), the promises, **three story beats**, the privacy callout, a closing CTA, and a footer. The beats tell the product as its core features (collaborate, diagrams, whiteboard) rather than as generic categories.

**The landing page tells a story; the detail lives on a page per category.** The page once ran one block per category, thirteen identical bands (about 12,500px) that read as a checklist; then five beats grouped those thirteen generic categories (The basics, Customisation, Reliability and so on) under ideas. Neither said what the app is for. So the body is now **one story beat per core feature**, and the feature categories are those same three: `LANDING_SECTIONS` in `lib/landing-content.tsx` is both the beats and the `/features/<id>` pages, rendered on the landing page by `components/StoryBeat.tsx`. A beat has the feature's **glyph and plain name** (`label`, in brand caps beside a brand disc holding the category's glyph from `components/category-icons.tsx` (it held the beat's number until October 2026), one per id and none shared, pinned by `category-icons.test.tsx`), a **headline** above a pitch, **four highlights** (`highlights`: feature titles, each a link to its card on the category page via `lib/feature-anchor.ts`), a primary link into its category page, and **the hero scene that shows the feature** (`scene`, see "Feature scenes" below) playing beside it. The beats run wider than the page's other bands (`max-w-7xl`) and the text column has a **fixed width** (22rem, 26rem from `xl`), the scene taking the rest (about 760px at a 1440px screen, the size the hero draws its scenes), so its small text stays crisp, and it starts on a whole pixel, where a fractional split (5fr to 7fr) landed it between pixels and blurred it. The scene column has **no scroll-in slide**: the scene plays its own build as it arrives, and a transform held mid-entry kept the window on its own layer, painted off the pixel grid; the text column keeps its entrance. Beats alternate the scene's side and the tinted background. While a beat is **one column** (below `lg`, the scene hidden) its text is **centred** (eyebrow, headline, pitch and link), the highlights a centred block with their ticks still lined up on the left; from `lg` it sits left-aligned beside the scene. A category page's hero centres the same way. `landing-content.test.ts` pins the three ids in order, a different scene per beat, four highlights that each resolve to one of the beat's own cards, art on every card and no em dash in a beat's copy. The full `FeatureGrid` of cards renders on each **`/features/<id>`** page. See "Feature category pages" below.

### Start Blank

**Start Blank** (`StartBlankLink` and `START_BLANK_HREF` in `packages/ui`) is a **plain link to the wizard**, `/new?start=blank`, never a menu of blanks: the wizard already asks what the visitor is making, so a menu asking the same question first was only friction. The mode chosen there opens its blank **with no start screen** over the canvas, as Skip's does ([Start Blank after a mode](../007-editor/new-document-route.md#start-blank-after-a-mode)), since whoever asked for a blank has already said they want no templates. It sits in the header outside the marketing pages (slot `HeaderBlank`; a marketing page's bar has none) and in the hero's search bar (slot `HeroBlank`).

Until October 2026 Start Blank was a menu of five blanks (Blank Diagram, Whiteboard, Session, Illustration and Plan, each straight into the editor), in the header, in the hero's search bar and as the closing band's **Or start blank** launcher; its funnel slots stay in the table as retired ([Landing funnel](landing-funnel.md)).

**Every CTA is measured** ([Landing funnel](landing-funnel.md)). A link into the editor from a public page builds its `href` with `ctaHref(href, source)` from `@livediagram/api-schema`, which adds `via=<Surface>.<Slot>` (`Home.Hero`, `Home.Gallery`, `Feature.Closing`, ...). The header takes its surface as a prop (`<Header surface="Faq" />`, passed through to the shared `SiteHeader`'s `ctaSurface`), and `StartDrawingCta` takes `surface` too. A new CTA adds its slot to `CTA_SOURCES` first; a bare `href="/new"` on a public page is a CTA the funnel can't see.

Reusable building blocks: `Section` + `FeatureGrid` (`components/Section.tsx`), `StoryBeat` (`components/StoryBeat.tsx`), `FeatureScene` (`components/FeatureScene.tsx`), `Header`, `Footer`, `Brand` (from `@livediagram/ui`). The feature categories are data, not markup: they live in `lib/landing-content.tsx` as the `LANDING_SECTIONS` array (each entry an `id`, a plain-name `label`, a headline `title`, a `description`, a hand-written `cta` link label, its `scene`, its four `highlights` and its `items`). That single array drives both the landing page's beats and the `/features/<id>` pages, so adding a feature card is a one-place edit and the two surfaces can never drift. **`LANDING_SECTIONS` is the authoritative list** (the numbered walkthrough above is illustrative and may lag); do not fork the grid or hard-code a category list anywhere else. The AI cards (the MCP connection, the optional assistant, Mermaid, Markdown import, export and the API) sit in `diagrams` under AI & your tools, while the footer's "AI & MCP" link and the FAQ's MCP answer open the [Build with AI](build-with-ai.md) setup page (`/ai`).

## Feature category pages

**Arriving on a page is animated, never a cut** (`app/page-motion.css`). Moving between two marketing pages (home to a category page and back) is a cross-document **view transition**: the pages crossfade and the sticky header (`view-transition-name: site-header` on the shared `SiteHeader`) holds still. The opt-in, `@view-transition { navigation: auto }`, is **inlined in the root layout's `<head>`** rather than left in the bundled stylesheet: the browser only runs the transition if the new page has opted in by its first paint, and from the stylesheet it sometimes arrived later, so the transition was skipped and the old page logged "Transition was skipped" (about half of navigations in testing; none since). A link out of the marketing site (into the editor at `/new`, the help centre, the dashboard) **skips the transition** as the page swaps: only the marketing pages opt in, so the browser would otherwise start one, find the editor declined, and report "Transition was aborted because of invalid state" as an uncaught error on every hero click. The marketing page decides by the destination's app, the router's own split (`pageViewApp`), in a small inline `pageswap` listener beside the opt-in. On arrival the category hero eases up piece by piece (`.enter`, staggered by `--enter-delay`), and the feature cards and the landing beats rise in as they scroll into view (`.enter-on-scroll`, a scroll-driven animation where supported, a load-time one elsewhere; on the cards it sits on a wrapper, because the card's hover lift is a transform the animation would pin). All of it is CSS over content already in the static HTML, so crawlers and no-JS visitors get the same page, a browser without these features shows the page as before, and reduced motion turns it all off.

## Social sharing

Word of mouth is part of the acquisition funnel, so the page lets a happy visitor pass it on in one click. `packages/ui/src/ShareRail.tsx` renders a **vertical rail pinned to the right edge of the page**: a rotated "Share" label above the share targets (X, LinkedIn, Facebook, WhatsApp, email) and a **Copy link** action.

It began as a "Share" popover in the header and moved out to the edge to give the header room to breathe. Two consequences of where it ended up:

- **It lives in `@livediagram/ui`, not in the marketing app**, because `SiteHeader` renders it. Surfaces that use the shared header carry the rail by default (the telemetry dashboard is just as worth passing on as the landing page); the help centre turns it off (`shareRail={false}`) because its pages run `max-w-7xl`, so the rail would cover the article sidebar ([Help app](../018-help/help-app.md)).
- **It renders as a _sibling_ of the header, not a descendant.** The header's `backdrop-filter` establishes a containing block that would trap the rail's `fixed` positioning against the header instead of the viewport.

Beyond that:

- **Wide desktop only (`xl`, 1280px).** Page content is `max-w-6xl` (1152px), so only past `xl` is there a real gutter for a fixed rail to sit in without overlapping the content. Below that it is hidden, and a page URL is inherently shareable anyway.
- **Share targets are plain anchor links** to each network's public share-intent URL (`twitter.com/intent/tweet`, `linkedin.com/sharing/share-offsite`, `facebook.com/sharer`, `wa.me`, `mailto:`). No SDKs, no tracking pixels (keeps the "no tracking pixels" claim honest under [03](../002-project-scope/open-source-and-business-model.md)). They open in a new tab (`target="_blank"` + `rel="noopener noreferrer"`).
- **The Appearance rail sits under it.** A second, separate rail of the same card, a gap below, holds the [Appearance](../004-interface-design/appearance.md) toggle, its only place on the public sites: never in the header, and left out below `xl`.
- **Copy link** uses the Clipboard API to copy the canonical URL and flips to a tick for a beat, via the shared `useCopiedFlash`, so a rapid second copy restarts its own countdown rather than inheriting the first one's remainder.
- The shared URL is the canonical production site, `SITE_URL` from the package's own `site.ts` (the one origin constant every app uses), and the share text mirrors the product's one-line description, a constant in the component; update it if the positioning copy changes.
- The icons are stored as raw `<path>` `d` strings rather than JSX, so the module evaluates no top-level JSX at import time and the shared barrel stays importable from non-React test transforms.
- On the landing page itself the `'use client'` boundaries are the `TemplateGallery` (search state over the template cards) and the `HeroIllustration` (the click-to-centre seven-window stage); everything else stays a server component for static export. The rail is a client component too, but it now arrives via the shared header rather than the page.

**Feature-card illustrations.** Every feature card carries a small animated mock of the real editor surface it describes (`components/FeatureArt.tsx`), passed via the card's `art` slot. Like the hero, the motion is **pure CSS**, shared keyframe classes (`fa-*`) live in `app/globals.css`, so it works under static export with no JS and settles to a finished frame under `prefers-reduced-motion`. The mocks must stay faithful to how the feature actually looks (presence avatars, the explorer / share panels), and every diagram in them is drawn as the editor draws it on the **Default theme**: its canvas, grid and the ink of unpainted shapes, arrows and labels, in the light half or the dark half with the appearance ([Appearance](../004-interface-design/appearance.md)). Only identity colours (stickies, cursors, highlights, selection), elements the example deliberately painted (the editor keeps a user's paint on any theme) and art whose subject is colour keep other colours; when a feature's UI changes, update its art. This is part of the golden rule above, an illustration is a claim too.

## SEO and metadata

The marketing site is the indexable surface for the product, so its `<head>` carries the search and social signals. The editor's routes and the API at `/api/*` are not optimised for organic search (the editor lives behind client-side bootstraps and has nothing useful to index).

- **One rule for every subpage, shared with the help centre**: subpage metadata comes from `pageMetadata()` in `@livediagram/ui` (the help centre wraps the same function, [Help app](../018-help/help-app.md) "SEO"). The title passes through verbatim (no suffix added), `og:type` is `article`, and the card is the large brand card (`summary_large_image`, `/opengraph-image` + `/twitter-image` by absolute URL) unless the page ships its own route-level image (`ownOgImage`, the `/features/<id>` cards). An app's front page that is a hub or dashboard rather than an article (the Community gallery, the Telemetry dashboard) passes `type: 'website'`; both now carry the brand card like every other public page. A `/features/<id>` card carries the category's label as its kicker, its headline, and a subtitle from `cardSubtitle` (`packages/ui/src/social-card.tsx`, beside the shared `renderSocialCard`): the first sentence of the description when it fits two lines (100 characters), otherwise cut at the last whole word, so the card never ends mid-word or runs into its footer. The origin, site name, repo URL, favicon set (`BRAND_ICONS`) and public viewport (`PUBLIC_VIEWPORT`) are shared constants in the same package, used by every app.
- `metadataBase`: `https://livediagram.app`. Lets relative paths in metadata resolve into absolute URLs (the canonical, OG image, sitemap entries).
- `alternates.canonical`: every static page declares its own canonical (`/`, `/faq`, ...). Stops query-string variants and the `www` mirror from competing with the canonical form. The retired `/terms` and `/privacy` routes are the exception: they are noindex redirect stubs whose canonical points at the help-centre Policies articles they now forward to (see "Content pages" below).
- `<html lang="en-GB">` on the root layout. Matches the OG locale + JSON-LD `inLanguage` so every locale signal across the page agrees. The earlier broader `lang="en"` worked but reads inconsistent next to OG's specific `en_GB` declaration.
- `openGraph`: title, description, url, siteName, locale (`en_GB`), type (`website` for the landing page, `article` for the FAQ and the comparisons, whose `article:modified_time` is their last review). Mirrors the page-level title/description so social cards match the actual head. (The Terms and Privacy Policy moved into the help centre and carry their own "Last updated" lines there.) Card image is generated by `apps/marketing/app/opengraph-image.tsx` via `next/og`'s `ImageResponse`; Next.js's file convention pre-renders it to a static 1200x630 PNG at build time and ships it in `out/`, so the asset has no runtime dependency.
- `twitter`: card `summary_large_image`, title, description, and the card image. `apps/marketing/app/twitter-image.tsx` re-exports the OG handler so the Twitter card and the OG card stay byte-identical. Copy is identical to the OG / page-level title and description.
- **Meta descriptions** are 50 to 160 characters, so a search result shows each one whole. A feature category page uses its section's `metaDescription` (written for the result, not the on-page lede, which runs longer); comparison pages use their `description`. `lib/meta-descriptions.test.ts` holds every page to it, and the shared `comparisonProblems` every comparison (`lib/alternatives.test.ts`).
- `robots`: explicit `{ index: true, follow: true }` on every page. The hosted product wants indexing; ambiguity about defaults is the kind of thing a future migration silently breaks.
- `app/sitemap.ts`: lists the indexable marketing URLs, `/` + `/faq` + `/alternatives` + one entry per `/alternatives/<slug>` competitor page (`comparisonSitemap` over the same list the routes read, dated by the comparisons' last review, see [the comparison-pages spec](../../../../packages/comparisons/README.md)). `/community/` ([Community](../025-community/community.md), the public gallery of shared documents, priority 0.6, daily) is listed beside them. The two public operational surfaces, `/telemetry` (the anonymous-events dashboard) and `/status` (the service-status page), are also listed: both are public, indexable (each sets `robots` `index: true` and a self-canonical), and reachable from the footer, so sitemapping them lets crawlers discover them directly rather than depending on footer links. They sit at a lower priority (0.4) than the marketing content because they're transparency pages, not primary landing destinations. `/terms`, `/privacy` and `/security` are deliberately not listed: all three policies live in the help centre (the help app's own sitemap lists the canonical Policies articles), and each marketing route is now a noindex redirect there. `lastModified` is per-page truth, not blanket build-time: `/` and `/faq` use `new Date()` because they change with product releases; `/telemetry` and `/status` also use `new Date()` (the dashboard reflects live event data, the status page reflects the latest deployed state, so both are "fresh as of this build"). Without that split, every build claims content changed today, which is misleading to crawlers and dilutes the change-frequency signal for pages that actually move. Next.js generates `/sitemap.xml` at the root from this file.
- `app/robots.ts`: allows the marketing routes, points at the sitemap, and `Disallow`s the editor app routes and `/api/`. The router worker stitches all three apps onto the same hostname, so an unconditional allow would let crawlers waste budget on the editor's auth-walled HTML and the API's JSON responses. The editor app also declares `noindex, nofollow` at its root layout (see [07-editor-app.md](../007-editor/editor-app.md)) as the in-page complement; together the two signals tell crawlers to skip the editor app entirely.
- **`viewport` export** (Next.js metadata API): the root layout exports a `Viewport` object carrying `themeColor: '#0EA5E9'` (brand-500, see [01-color-scheme](../004-interface-design/color-scheme.md)) and `colorScheme: 'light dark'`. The first tints mobile browser chrome (Android Chrome's URL bar, iOS PWA status bar) to the brand, the second says the pages paint both appearances; which one follows the reader's origin-wide [Appearance](../004-interface-design/appearance.md) (System by default, the rail's toggle to override), applied before first paint. Every page, illustrations included, has a dark appearance, and its editor mock-ups show the editor as it looks in dark. Both are head meta, not page content, so they don't conflict with the "claims map to shipped features" rule.
- **`app/manifest.ts`**: emits `/manifest.webmanifest` at build time with `name`, `short_name`, `start_url: '/'`, `display: 'standalone'`, the brand theme + background colours, and the existing `/icon.svg` as the icon (which `purpose: 'any'` covers since the cube's corners reach outside a maskable safe zone). Surfaces the Android Chrome "Add to Home Screen" prompt + the iOS Safari "Add to Home Screen" landing icon, with no behaviour change for normal page loads. Same `export const dynamic = 'force-static'` opt-in as robots.ts / sitemap.ts so it round-trips through `output: 'export'`. Because `livediagram.app` is one origin (the router stitches the apps by path), this is the **origin's** manifest: the editor (editor app) references it (and `/apple-icon`) by absolute path from its own layout metadata, so installing the PWA from the editor gets the same icon + name rather than nothing (see [07-live-app](../007-editor/editor-app.md)).
- **JSON-LD structured data**: the root layout renders a single `<script type="application/ld+json">` carrying a `@graph` of two schema.org types: `WebSite` (so the brand-name search produces a rich result) and `SoftwareApplication` (so the product is categorised correctly in browse / category-style results). Both schemas restate facts already in the page (name, url, description) and the SoftwareApplication offer is `price: "0"` (truthful: the hosted product is free with no paid tier, see [03](../002-project-scope/open-source-and-business-model.md)). No claims that aren't already true on the surface. Each schema also carries an `image` field pointing at the same OG card (`/opengraph-image`) so Google can pair the brand card with a visual, an `inLanguage` field matching the OG locale (`en-GB`), and a `sameAs` array on the SoftwareApplication that links the canonical GitHub repo (already linked from the footer + the FAQ self-host answer) so the brand's open-source presence is connected to the same entity.
- **FAQ JSON-LD**: `/faq` emits an additional `<script type="application/ld+json">` with schema.org `FAQPage` + a `Question` / `Answer` pair per entry. Unlocks Google's "expandable FAQ" rich result for the page. The JSON-LD `acceptedAnswer.text` is the plain-text form of each answer; entries that render JSX (a link to the help-centre privacy policy in the data-storage question, for instance) carry a parallel `aText` field with the same sentence, sans markup. The page builds it from the same `FAQ_CATEGORIES` it renders, and `lib/faq-content.test.tsx` renders every JSX answer and fails if its visible text differs from `aText`, so the structured data can't drift from the visible content.
- **Breadcrumb JSON-LD**: every indexable subpage (`/faq`, each `/features/<id>`, `/alternatives` and each `/alternatives/<slug>`) emits a `BreadcrumbList` script. (The retired `/terms` + `/privacy` redirect stubs don't, since they render no breadcrumb trail.) Two items for two-level pages (`Home → <Page>`), three for a comparison (`Home → Comparison → <competitor> alternative`). The comparison hub adds an `ItemList` and each comparison a `FAQPage` ([the comparison-pages spec](../../../../packages/comparisons/README.md) "Metadata"). Unlocks Google's SERP breadcrumb display so the search result shows `livediagram.app > FAQ` instead of the bare URL. Rendered via `components/BreadcrumbJsonLd.tsx` so the pages share one source of truth; the `BreadcrumbList` shape itself is the shared `breadcrumbJsonLd` builder in `@livediagram/ui`, which the help centre's breadcrumbs use too. The landing page (`/`) doesn't get a breadcrumb (it IS home, the trail would be a single entry).

When a new public page lands, add it to both `app/sitemap.ts` and its own metadata block (with `alternates.canonical`). Updating one without the other is a regression.

## Content pages (FAQ)

`/faq` (`app/faq`) is the marketing site's one long-form content route. Its questions live in `lib/faq-content.tsx` as `FAQ_CATEGORIES`, ten categories (Getting started, Free and open source, Creating, Working together, Sharing and embedding, AI, API and MCP, Import and export, Privacy and your data, Self-hosting, Help and support), each with a Lucide icon, a one-line blurb and its questions; the template and template-category counts are written out (the catalogue is too heavy for the FAQ's client bundle) and `faq-content.test.tsx` pins each to its catalogue, so they never drift. The page (`components/faq/FaqBrowser.tsx`) opens on a tinted hero with a search box that narrows every category as you type (`lib/faq-filter.ts`: every word must appear in the question, its plain-text answer or its category title; matches open, empty categories drop out, no match points at the Help Centre). Wide screens add a sticky category index with per-category counts beside the questions. Each question is a native `<details>` card, so every answer is in the static HTML and opens without script. The page closes on three "Still have a question?" cards: the Help Centre, the contact page and a Start drawing card (`Faq.Card`). The **Terms of Service** and **Privacy Policy** no longer live here: they are liveworkspace's and cover every liveworkspace app (`https://liveworkspace.app/terms`, `https://liveworkspace.app/privacy`). The help centre's old `/help/policies/terms/` and `/help/policies/privacy-policy/` redirect there too. The old `/terms` and `/privacy` marketing routes survive only as thin `noindex` client redirects (`app/terms`, `app/privacy`, sharing `components/LegalRedirect.tsx`) so historical links keep resolving; `/security` is the same stub pointing at the help centre's vulnerability disclosure policy (`/help/policies/report-a-vulnerability/`), and `apps/marketing/app/.well-known/security.txt/route.ts` emits the RFC 9116 file at build time (see [Vulnerability disclosure](../002-project-scope/vulnerability-disclosure.md)); the help articles carry their own "Last updated" lines, so the old `LegalPage` shell and `legal-revisions.ts` constant are gone. The footer sets the brand and tagline on top, with its links grouped below into four titled columns (two per row on a phone). Only the key links carry a 16px icon (New Document, AI & MCP, Help Centre and GitHub); the rest are plain text: **Product** (New Document, `/new`; AI & MCP, `/ai`, the [Build with AI](build-with-ai.md) page; Comparison, `/alternatives`, this app's comparison hub, see [the comparison-pages spec](../../../../packages/comparisons/README.md); Community, `/community/`, the shared `CommunityFooterLink`, gone while the [Community](../025-community/community.md#turning-the-community-off) is switched off; FAQ), **Resources** (Help Centre, `/help/`; About, `/help/about/what-is-livediagram/`; Status, `/status`, the operational dashboard; Telemetry, `/telemetry`), **Legal** (Terms, `https://liveworkspace.app/terms`; Privacy Policy, `https://liveworkspace.app/privacy`; Data & Security, `/help/privacy-and-security/`, the help centre's privacy and security hub, named apart from the policy so the two never read as duplicates; Report a Vulnerability, `/help/policies/report-a-vulnerability/`, the [vulnerability disclosure](../002-project-scope/vulnerability-disclosure.md) policy, named for what it asks so it never reads as a twin of Data & Security; Licences, `/licences`, the generated third-party licences page, see [Third-party licences](../002-project-scope/third-party-licences.md)) and **Connect** (Contact, `/help/contact/`, the help centre's contact page; GitHub). The bottom copyright row carries the MIT licence note alongside a "Built by" credit naming the human contributors (`CONTRIBUTORS` in `packages/ui/src/contributors.ts`: Tom McClean and Webber), each with their GitHub avatar and a link to their GitHub profile. The avatars are inlined as 64px JPEG data URIs (about 2 KB each), never hotlinked from GitHub, so the footer makes no third-party request; the Connect column carries a GitHub link (mark + label) for visitors who want the source code, with the repo additionally linked from FAQ, the status page, and the `sameAs` JSON-LD in `layout.tsx`. The policies are plain-English first drafts grounded in what the hosted service actually does (Cloudflare for hosting/DB, liveworkspace accounts for sign-in, a localStorage guest id, no trackers/telemetry); they have **not** had legal review, and any governing-law / legal-entity details are placeholders to confirm. Keep the privacy policy honest against the data the product really touches (it backs the "no tracking pixels" claim). No email address is published anywhere: every "get in touch" surface (the help centre's contact page, the FAQ's "How do I get in touch?", the status page, the Terms and the Privacy Policy) points at the public contact form, `CONTACT_FORM_URL` in `packages/ui/src/site.ts` (a livediagram Form). The outgoing transactional email sender (`RESEND_FROM`) is unaffected.
