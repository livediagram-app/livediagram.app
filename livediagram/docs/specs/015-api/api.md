# API app

The HTTP + WebSocket layer the live editor calls for document persistence and realtime collab.

- **Workspace:** `apps/api` (`@livediagram/api`).
- **Worker name:** `livediagram-api`.
- **Mount:** routed from the [router worker](../016-platform/router-app.md) at `/api/*`. The router forwards the request as-is — the api worker sees the full `/api/...` path.

## Why this exists

The first prototype phase ([spec 02](../005-project-roadmap/prototype-scope.md)) ran entirely client-side with `localStorage` persistence. Once realtime collaboration entered scope, server state became necessary: a Durable Object per document holds the in-room participant list, orders and relays ops between connected clients and keeps the collaboration state that must outlive a socket, and holds the document's content in its own SQLite. The editor app no longer reads or writes `localStorage` for documents — `apps/editor/lib/api-client.ts` is the single boundary.

## Tech

- **Runtime:** Cloudflare Workers.
- **No database of its own:** the api has no D1 binding and no SQL migrations. Content is each document's Durable Object; what a person keeps here is in their own Durable Objects; API tokens are checked with liveworkspace and never stored (see **Storage**).
- **Index:** where every document is, who may open it, its sharing, folders, favourites, Trash, Timeline, Home and Inbox are liveworkspace's index ([one-explorer.md](../../../../liveworkspace/docs/one-explorer.md), [one-explorer-contracts.md](../../../../liveworkspace/docs/one-explorer-contracts.md)). The api reaches it at `INDEX_ORIGIN` (`apps/api/src/index-service.ts`).
- **Images:** the bytes are in liveworkspace's media service (`MEDIA_URL`, `MEDIA_KEY`, `apps/api/src/media.ts`); R2 (binding `IMAGES`) caches document snapshots.
- **Documents:** one SQLite-backed Durable Object per document (`DocumentRoom`, binding `DOCUMENT_ROOM`, `new_sqlite_classes`), named by the document's id via `idFromName`. It holds the document's content and is its realtime room (see **Storage** and **Realtime model**).

## Wire-format types

The DTO shapes the api worker emits + the live editor consumes live in `packages/api-schema` (`@livediagram/api-schema`) — `LiveDoc` (published as `Document`), `TabSummary`, `TabRecord`, `Folder`, `ShareLink`, `ServerMessage` / `ClientMessage`, and the room op vocabulary (`RoomOp` / `RoomOutgoing` / `RoomIncoming`). Both apps import them; the api worker also re-exports under historical `XxxDTO` aliases (`apps/api/src/types.ts`) for backward compatibility with its existing call sites.

Defining the wire shapes once means server and client cannot drift — adding a field on one side without updating the other is a typechecker error. **Do not redefine these types inline in `apps/api/` or `apps/editor/`**; extend the schema package instead. Per AGENTS.md the reuse-over-duplication rule is non-negotiable.

## Auth

The api resolves the request owner through four identities, all carried as `Authorization: Bearer`, in this order of preference (see [Auth + guest access](../014-identity/auth-and-guest-access.md) and [Public API and API tokens](public-api-and-tokens.md)):

1. **Account access token or guest token**: `Authorization: Bearer <jwt>`, minted by the liveworkspace accounts Worker, for a signed-in person ([Auth + guest access → Signing in](../014-identity/auth-and-guest-access.md#signing-in)) or a guest ([Auth + guest access → Guest identity](../014-identity/auth-and-guest-access.md#guest-identity)). Verified locally in `apps/api/src/auth/accounts.ts` (`getPersonIdentity`, via `@liveworkspace/auth-client`'s `createPersonVerifier`, which answers the kind, `account` or `guest`) against `${ACCOUNTS_URL}/api/auth/jwks`, with issuer `${ACCOUNTS_URL}/api/auth` and audience `API_RESOURCE`, so a token minted for another liveworkspace app is refused here. No call to the accounts Worker per request; the key set is cached per isolate. An account token's `sub` claim is the owner id (`user_…`), and its `email` is trusted only when `email_verified` is true; a guest token's id (`guest_<uuid>`) is the owner id, the same guest in every liveworkspace app. Returns null on any failure (invalid signature, expired, wrong audience, malformed, `ACCOUNTS_URL` / `API_RESOURCE` unset), logged as `[auth] access_token_rejected`, never 401, because the worker must still serve the other paths and a link visitor. A bearer shaped as an API token (`isApiTokenFormat`, `lwt_…`) or a workbench session (`isWorkbenchSessionFormat`, `lvw_…`) is never handed to the verifier: it is no access token, so `getPersonIdentity` returns null for it at once and logs nothing, and the token paths below resolve it.
2. **API token** — `Authorization: Bearer lwt_…`, consulted only when no account access token or guest token verified. `resolveApiToken` checks it with liveworkspace, which made it ([Public API and API tokens](public-api-and-tokens.md)), remembering the answer for a minute per isolate; the owner id is the token's account, so a token request flows through the same ownership and gate checks as a signed-in one. A token minted **read-only** is refused on every `POST` / `PUT` / `DELETE` with `403 read_only_token`, at one choke point in `index.ts`.
3. **Workbench session** — `Authorization: Bearer lvw_…`, consulted only when neither an account access token nor a token resolved ([Workbench embeds](../013-workspace/workbench-embeds.md)). The secret names its person's workbench store (a Durable Object, `src/workbench-store.ts`); `resolveWorkbenchSession` reads the session there by its hash, with its token's state, in one call; an unknown, expired or revoked one is refused `401 invalid_session`, never read as a guest. The owner is the session's owner, `accountUserId` and the token stay null (a person's editor, never an administrator or an agent), and `workbenchRefusal` confines it before any route runs, by its scope: a document session answers another document `404`, any route outside `WORKBENCH_ROUTES` `403 workbench_confined`, and an `X-Share-Code` or `X-Share-Password` beside it `403 workbench_confined`; a workspace session reaches the Explorer's routes (`WORKSPACE_ROUTES`), never the account's. A view session's write, or its read of the share-link list, is `403 workbench_read_only`.
4. **No identity.** No Bearer resolved: a link visitor, admitted only by what a share code grants (`X-Share-Code`, below). An owner id is never a credential: there is no header that names one, so knowing someone's id grants nothing.

The request handler computes the resolution once at the top of `fetch`:

```ts
const person = await getPersonIdentity(env, request); // account | guest | null
const accountUserId = person?.kind === 'account' ? person.userId : null;
// tokenAuth: { ownerId, tokenId, readOnly } | null, only when no person verified
// workbench: the session's owner and scope | null, only when neither resolved
const guestId = person?.kind === 'guest' ? person.guestId : null;
const resolveOwner = (): string | null =>
  accountUserId ?? tokenAuth?.ownerId ?? workbench?.ownerId ?? guestId;
const verifiedUserId = accountUserId ?? tokenAuth?.ownerId ?? workbench?.ownerId ?? null;
```

Every endpoint uses `resolveOwner()`, so adding new endpoints inherits the hybrid behaviour automatically. `verifiedUserId` (a server-verified account id, never a guest's) is the person an API token or workbench session asks the index for; the interactive-only doors (`DELETE /api/account`, `POST /api/teams`, publishing to the Community, the team notify doors) read `accountUserId` alone, so a token can't reach them. API tokens and teams are managed on liveworkspace.app; `/api/tokens` keeps only `current` (the token a request presented).

`ACCOUNTS_URL`, `API_RESOURCE`, `ACCOUNTS_CLIENT_ID` and `ACCOUNTS_CLIENT_SECRET` are **worker secrets** (`wrangler secret put`, synced from GitHub repo secrets on deploy), not `[vars]` entries — only the client secret is sensitive, but keeping every out-of-band value in one mechanism is simpler than reasoning about which ones are safe in the open ([Secrets policy](../002-project-scope/secrets-policy.md)). Leaving `ACCOUNTS_URL` or `API_RESOURCE` unset puts the api in pure-guest mode — useful for local dev or for environments without an accounts client yet. The sign-in round trip itself (`/api/auth/sign-in`, `/callback`, `/token`, `/sign-out`) lives in `apps/api/src/routes/auth.ts`.

**Access to a canvas is the index's grant** ([one-explorer-contracts.md "Grants"](../../../../liveworkspace/docs/one-explorer-contracts.md)). Before a request about one canvas reaches its Durable Object, the worker settles the caller's grant on it (`resolveDocumentGrant`, `routes/document-grant.ts`, over `@liveworkspace/index-app`'s `resolveItemGrant`): an `X-Index-Grant` the request carries (the editor sends the one it holds), verified offline against the index's key and this canvas's id; else one fetched for the caller (`requestGrant`). The caller is who the index sees (`grantCallerOf`): an API token or workbench session as a delegate the app vouches for, with its person and teams; anyone else by their own Bearer, a link visitor's being none. A link visitor's `X-Share-Code`, and `X-Share-Password` when the link has a [share password](../013-workspace/share-password.md), go to the index with the request; the index answers `password_required` (401) or `password_invalid` (403), which pass through, and every other refusal (no access, a canvas in the Trash, an expired or revoked link) reads as no grant, so the door answers 404. Every share-code read and write is gated the same way, not just the share resolve.

The grant names a level (`view`, `participate`, `edit`; [Share roles](../013-workspace/share-roles.md)), the one tab a tab-scoped link confines it to, the share code that granted it, and the canvas's owner and team. The doors read it through `routes/context.ts`: `gateRead`, `gateParticipate` and `gateEdit` hold the ladder (each level holds everything below it), and a tab-scoped grant reaches only its own tab (a canvas-level request with one fails closed); `gateGrant` hands a door the grant itself, for the doors that narrow their answer to a scoped visitor's tab rather than refuse. A workbench session holds no more than its own level (`capWorkbenchRole`). A Community post's link opens to view only, and only the doors marked `COMMUNITY_CONTENT` (the canvas, its tabs, images, copy) serve it; a post hidden after reports, off the Community or no longer its author's own opens nothing. `ownsDocument` (the caller is the owner the canvas knows, with a grant) only decides what the owner sees more of (comment authors, publishing to the Community); who may change, move or share a canvas is the index's.

### Document dates

A document's dates are its `createdAt` (shown as created) and `savedAt` (last
modified, the lists' order), both milliseconds since the epoch, as everywhere
on the wire. A create stamps both with the server's now, unless the body
carries its own: an Offline Mode sync carries the local record's `createdAt`
([Offline Mode](../006-document/offline-mode.md)), and an imported board
carries the board's own created and last-modified dates
([Microsoft Whiteboard import](../020-import-export/whiteboard-import.md)), so
it sits in the Explorer where its age puts it.

- Each given date must be a whole number of milliseconds no earlier than
  `DOCUMENT_DATE_MIN` (1 January 2000, before any document a person could
  bring) and no later than the server's now plus `DOCUMENT_DATE_SKEW_MS`
  (one day, for a device clock that runs ahead), and `createdAt` must not be
  later than `savedAt`.
- A given `createdAt` alone keeps `savedAt` at now (or at `createdAt`, if a
  clock running ahead put that later); a given `savedAt` alone is refused (a
  document is never modified before it is created).
- Seeding the create's tabs leaves `savedAt` as given.
- Anything else is refused whole, 400 `bad_request` "invalid document dates";
  nothing is created.
- Only a genuine create takes them: re-committing an id the caller already
  owns keeps the stored `createdAt`.

### Marking a document used

A use of a canvas (a use day and the person's latest use, the measures
[Explorer Home](../013-workspace/explorer-home.md#opens)'s Jump Back In reads) is the index's: an open
recorded there, or an edit the canvas reports to it. Making a canvas is a use for whoever makes it when the editor
records it so.

- The editor records an open at the index as it makes a canvas, unless it sends `markUsed: false`: it does so for
  every document of an import that makes more than one in one go, which then join Jump Back In at their first open
  or edit.
- This api validates `markUsed` on a create (anything but a boolean is refused whole, 400 "invalid markUsed";
  nothing is created) and records no open itself, so an API client's create joins Jump Back In at its first open or
  edit.

### Documents in the Trash

A document's Trash state is the index's. A trashed document is reached only by its owner and team, so the index
grants nobody else anything for it, and every door answers as for a document that is not there. The index keeps a
document 30 days in the Trash, then deletes it for good and has the document's object drop its content
([Trash](../013-workspace/trash.md)). There is no Trash cron here.

### Tab save

The whole-tab autosave (`PUT /api/documents/<id>/tabs/<tabId>`, about every 600 ms while someone edits) reads
only what it needs of the document, in one query (`getDocumentForSave`: owner, team, name, the owner's participant
name and colour, and the tab count), where it ran the full document read (the row with its share-code and
Community subqueries, then the owner's participant and the tab summaries) as two sequential round trips. The stored
tab, the changesets the editor had not seen and the realtime room's ledger are then read together; the ledger is
merged after the changesets, as before. A denied save still answers 403.

### Tab size

A tab is stored as one text value in one row of its document's SQLite (`tabs.data`, the tab's
JSON without its id and name), and a Durable Object's SQLite, like D1, caps a string, a BLOB and a
row at **2,000,000 bytes** ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)).
Local `wrangler dev` does not enforce it, so the api enforces it itself:

- `D1_MAX_ROW_BYTES` = 2,000,000. `MAX_TAB_BYTES` = `D1_MAX_ROW_BYTES` less
  `D1_ROW_HEADROOM_BYTES` (8 KiB) = 1,991,808 bytes of UTF-8 JSON. The
  headroom covers the row's other columns (the tab id, a UUID; the name, at
  most 60 characters, so at most 240 bytes; `updated_at`; SQLite's record
  header) many times over, so a tab under the cap always fits its row.
- Both numbers live in `@livediagram/api-schema`, so the editor checks the same
  cap the worker does and the two cannot drift.
- **Every write of a tab's data** is checked against it, at the storage layer
  (`upsertTab`, `seedTabs`, `swapTabData`), so no route can store what the store
  would refuse: document create, the tab save, a comment added or deleted
  through the api, and a Q&A board write. A tab over the cap is refused with
  the named 413 (`payload_too_large`) and nothing is written; the worker logs
  `[tab-size] refused` with the write (`create`, `upsertTab`, `seedTabs`,
  `swapTabData`), the tab id, the bytes and the cap. The comment routes list
  413 among their answers in the OpenAPI manifest. The routes
  also check the request up front, so a create never leaves a document
  without its tabs.
- The cap is not raised and the storage format is unchanged; a tab that needs
  more is a separate decision.

## Caching

Every JSON answer is the caller's live state, so it goes out `Cache-Control: no-cache` unless its
route chooses a policy of its own (the OpenAPI document, the public telemetry summary): a browser
may store it but asks the server again before reusing it. Without it a browser may reuse an answer
the server has since changed: Chromium holds a `410` with no explicit expiry indefinitely, so a
share-link visitor who once saw a document deleted would keep seeing it after the owner restored
it. Not `no-store`: the browser's cache drains a stored answer's body, and without it an answer
whose caller never reads the body holds its request open. Images and SVG snapshots set their own
policies.

The write ceiling sits well above realistic editing traffic (autosave fires once per debounce window, comments are typed by humans) but low enough to stop a bot from spamming document / image creation into storage quota exhaustion. The room-ticket mint is exempt because it shares the per-owner budget with the autosave, and a 429 there would cost a team member the whole session's realtime; `/api/events` is exempt so telemetry never competes with a user's real writes.

Before any limiter, a write whose `Content-Length` exceeds the body cap (`MAX_BODY_BYTES`, or `MAX_IMAGE_BYTES` for `/api/images`, `limits.ts`) is refused with `413`.

Self-host: every limiter is optional. When a binding is absent its check short-circuits to "allow", so deployments without the feature still serve. The bindings are a Cloudflare paid-tier capability; the open-source path stays unaffected (per [Open source + distribution](../002-project-scope/open-source-and-business-model.md)).

## Storage

Each document's content lives in its own SQLite-backed Durable Object, `DocumentRoom` (`apps/api/src/document-room/`),
one per document id. What livediagram keeps for one person lives in their own Durable Objects, `PersonStore` and
`WorkbenchStore`. The api has no D1 database; where a document is and who may reach it is the index's.

**What the document's object holds** (`document-schema.ts`, created on first use, `CREATE ... IF NOT EXISTS`):

- `document`: the document's own row: the slide deck ([Presentation mode](../012-collaboration/presentation-mode.md)),
  `saved_at`, `created_at`, its owner and team as the index last said.
- `tabs` (the body, one JSON row per tab: elements, articles, pages and the page flow) and `document_tabs` (order and
  folder), with `tab_stats` (the Details view's numbers).
- `image_refs`: which gallery images each tab places ([Images, Reference index](../009-elements/images.md#reference-index)),
  written in the same transaction as the body; `image_owners` and `image_grants` (below).
- `community_post`: the document's Community post, at most one ([Community](../025-community/community.md)).
- `notify_claims`: which notification emails the document has sent, for their throttles.
- `agent_changesets` and `agent_changeset_parts` (the changeset log).
- `tab_shares` and `share_outbox`: the other documents each shared tab is in, and what they are still to hear
  ([Tab ↔ document many-to-many](../006-document/tab-document-many-to-many.md)).
- `guest_voters`: the guests who have voted, counted per network ([Vote integrity](../012-collaboration/vote-integrity.md)).
- `outbox`: what the index and the media service still have to hear (below).
- In the object's key-value storage: the order state (`epoch`, `seq`), the collaboration ledger, selections and
  agent presence.

A tab is one row. A tab over 2 MB does not fit a SQLite row in a Durable Object, so the cap in **Tab size** stands;
storing a large tab in chunks is the follow-up.

**What each person's object holds.** What livediagram keeps for one person rather than for one canvas lives in
their own SQLite-backed Durable Object, `PersonStore` (`apps/api/src/person-store/`, binding `PERSON_STORE`, one per
person id, reached through `person-client.ts`): their shape libraries
([Shape libraries](../013-workspace/shape-libraries.md)) and their Google Drive mirror
([Google Drive mirror](../022-drive-mirror/drive-mirror.md#data)). Deleting an account purges it; a guest signing in has
theirs adopted by the account's.

**What each person's workbench holds.** A person's workbench (pairing requests, pairings, tickets, sessions and the
rooms a workspace session joined) is their own Durable Object, `WORKBENCH` (`src/workbench-store.ts`, the store in
`@liveworkspace/index-app`), reached by their id or by the store id a ticket or session secret ends in
([Workbench embeds](../013-workspace/blueprints/workbench-embeds.md)). Closing an account closes it. API tokens are
liveworkspace's (liveworkspace/docs/accounts.md "API tokens"); this api keeps no copy. Nothing about folders,
favourites, sharing, teams, the Trash, the Timeline, Home or the Inbox is kept here.

**Routing.** The worker authenticates the caller, applies its cross-cutting gates (rate limits, read-only tokens,
workbench confinement, body caps), resolves the caller's grant from the index and hands every request under
`/api/documents/:id/...` to the document's object, `documentRoom(env, id).route(request, identity)` (typed RPC,
`document-client.ts`). The object rebuilds the route context from that identity and the grant and runs the handlers
against its own SQLite as `env.DOCUMENT_DB` (`@liveworkspace/index-app` `item-db.ts`, the D1-shaped surface over
`ctx.storage.sql`, which tells the room only of calls that changed a row, so a read never counts as an edit). The
editor's wire protocol is unchanged. Other RPCs: `outline` (a document read's tab list and deck), `image`
(thumbnails and live images, drawn where the content is), `hasTab`, `servesImage` (the image byte endpoint's share
check), `exportCopy` / `importCopy` (a document copy), `community`, `joined`, `anonymise`, `purge` and `revokeCodes`.

**A save is one call and one transaction.** The tab `PUT` reaches the object in one RPC and writes the body, its
`document_tabs` row, its stats, `document.saved_at` and its image references in one `transactionSync`, with no
network round trip on its path. A read is one RPC. Measured on a laptop (CPU time, node:sqlite standing in for the
object's SQLite; `document-room-store.test.ts` keeps budgets on them): a 1 MB tab saves in about 40 ms and reads in
about 20 ms; a tab placing 500 images saves in about 6 ms, and saves again in about 10 ms; a 200-tab document's read
takes about 4 ms.

**Images.** The bytes live in liveworkspace's media service; the document keeps the rest in its own SQLite:
`image_refs` (which images each tab places, written in the same transaction as the tab), `image_owners` (each
placed image's owner, as the media service answered, so a read never asks it) and `image_grants` (the images it may
serve beyond its owner's own: one a collaborator placed, or one a copy brought from its source). The byte endpoint
(`GET /api/images/:id`) asks the document (`servesImage`) whether it places the image, on the visitor's tab for a
tab-scoped link, and may serve it: its owner owns the image, or a grant covers it. Snapshots and live images are
drawn in the object with the same filter.

**The outbox.** Triggers on the document's tables key every change in the same transaction as the write, so no
write path can forget one and a save makes no network call. The object's alarm drains it on idle and at most once a
minute (`document-outbox.ts`): the document's summary to the index (`PUT /app/items/:id/summary`, the Explorer's
thumbnails and counts), each changed tab's comment threads and actions for the Inbox (`PUT
/app/items/:id/collab/:tabId`) and who edited it for the Timeline (`PUT /app/items/:id/events`, an `edited` event),
all with this app's key ([one-explorer-contracts.md](../../../../liveworkspace/docs/one-explorer-contracts.md)
"What an item pushes"); the document's whole set of placed images to the media service (`MEDIA_KEY`), with the
placement grants that set earns; and the owner's newest save to the accounts Worker for its onboarding emails.
A drain that fails keeps every key it did not push and retries a minute later, so the Explorer, the Inbox and the
media service lag a write by up to about a minute. A tab that has gone also drops its tab-scoped share links.

**Upkeep.** Each object runs its own daily upkeep from its alarm: changesets past their retention go, and a
document with a Community post asks the index where it stands (`COMMUNITY_CHECK_MS`, every 10 minutes). The worker
has no cron (no `[triggers]` in `wrangler.toml`): every sweep is a Durable Object's alarm.

**Duration.** The object is billed while it runs a request or an alarm. Content requests and thumbnail renders
run there rather than in the worker, so a document under heavy API traffic keeps its object awake for that
traffic; an idle document costs nothing, and sockets still hibernate.

## Realtime model

The `DocumentRoom` Durable Object (`apps/api/src/document-room/document-room.ts`) is the realtime hub for one document id. Clients connect via the `/ws` endpoint and immediately send a `hello`; the room broadcasts a `presence` snapshot whenever the set changes.

**Hibernation.** The room uses the Workers WebSocket Hibernation API (`state.acceptWebSocket` + class-level `webSocketMessage` / `webSocketClose` / `webSocketError` handlers) rather than in-memory `ws.accept()`, so the runtime can evict an idle room from memory between messages while every client's socket stays open — an open-but-quiet session no longer bills DO duration. All per-session state that matters (the server-assigned ephemeral presence id, the `X-Verified-Role` trust-boundary role, and the `hello` presence including the remembered `tab-focus` tab) survives eviction in each socket's serialized attachment; only the per-session rate-cap window is in-memory and deliberately resets on a wake.

**Access is gated at the upgrade, by the index's grant.** Browsers can't set headers on a WebSocket upgrade, so what admits a socket rides its URL: the room ticket, `?t=`, and nothing else. A ticket is the caller's index grant on _this_ canvas (the editor sends the grant it holds; `POST /room-ticket` above answers one for a caller that holds none), or, for a workbench session, that grant sealed with this app's key to the session's pairing and level cap. The worker opens it offline (`openRoomTicket`, `@liveworkspace/index-app`'s `room-ticket.ts`): the grant's signature, its item and its lapse, and a sealed ticket's MAC, by a constant-time compare. Anything forged, lapsed or for another canvas is refused outright (403); so is a grant through a Community post's link (`community_link`), whose visitors never join the author's room. A share password is the index's to check when it grants, so the URL carries none, and no owner id ever rides it. A person who opened a link may add `?s=<code>`: it only marks the session as that code's, so revoking the code closes exactly its sockets; it admits nothing. The resolved level (a workbench session's capped to its own) is forwarded to the DO as `X-Verified-Role`; the DO re-stamps it onto presence in the `hello` handler, ignoring any role the client typed into its own payload, so that header is the trust boundary. The other trust headers are stamped on every upgrade, so a client can never supply them: `X-Verified-Owner` (`1` when the grant's person is the canvas's owner, else `0`; a bit, never an id, which the facilitator baton needs so the owner can always take it back), `X-Verified-Tab-Scope` (a tab-scoped link's tab, empty otherwise), `X-Verified-Share-Code` (the code the session came in by), `X-Verified-Person` (the person tag), `X-Verified-Workbench-Pairing`, `X-Verified-Adder` (a Participant's adder key), `X-Verified-Document`, `X-Verified-Network` (the network tag polls cap answers by), `X-Verified-Grant-Exp` (when the grant lapses) and `X-Verified-Item-Owner` / `X-Verified-Item-Team` (the canvas's owner and team as the index has them now; the room keeps its copy from these). The DO pins them on the session and confines a scoped session to its tab, live and in catch-up ([Tab-scoped share links](../013-workspace/tab-scoped-share-links.md)).

**A grant lapses; the session renews it.** A grant lasts ten minutes. Shortly before a session's grant lapses the room sends it `grant-renew`, and the session answers with a `grant` frame holding a fresh one (the editor renews early anyway and sends each new grant unasked). A fresh grant for the same canvas, level and tab moves the session's lapse on; one that says something else (a level changed, a tab rescoped) closes the session `4005` (`ACCESS_CHANGED_CLOSE`) and the editor rejoins with what it holds now. A session still holding a lapsed grant is closed `4007` (`GRANT_LAPSED_CLOSE`); its editor asks the index for a fresh grant and rejoins, or, when the index grants nothing any more (the canvas went to the Trash, the link was revoked), stays out.

Edits and presence propagate as `op` messages. The room is **not** a stateless relay: it classifies every op, orders the ones that change the document, rewrites a few fields on the way through, keeps a small amount of collaboration state in its own storage, and performs one kind of document write itself. The document's own SQLite, in the same object, is the system of record for its content ([Realtime conflict resolution](../012-collaboration/realtime-conflict-resolution.md), [Collaboration race hardening](../012-collaboration/collab-race-hardening.md)).

### Op classes

Every op kind belongs to exactly one of three lists in `@livediagram/api-schema` (`packages/api-schema/src/room-messages.ts`), and the class decides its ordering, its role gate, and whether a client may send it at all. The room reads `op.kind` to classify; the payload stays `op: unknown` on the wire.

- **Presence** (`PRESENCE_OP_KINDS`): ephemeral, mutate nothing. Relayed unordered (no `seq`), never logged, never replayed, from **any** connected session, so a view-only visitor still shows peers their cursor, selection, laser, walking character and tab, and can answer a poll.
- **Mutation** (`MUTATION_OP_KINDS`): change the document. Relayed **only from a session whose verified role is `edit`**; each gets a monotonic `seq` within the room's `epoch` and a slot in the catch-up log.
- **System** (`SYSTEM_OP_KINDS`): originated only by the api worker through the DO's internal endpoints, stamped `from: 'system'`. Dropped outright when a client sends one, so no peer can forge a revoke or rewrite a Q&A board.

**Access changes end the sessions they affect.** Two api actions narrow who may be in a room without revoking a link: setting a share password, and a member leaving or being removed from a team. Matched sockets close with **4005** (`ACCESS_CHANGED_CLOSE`, reason `access-changed`); nothing is broadcast, so no other session learns who left. The connector stops on 4005 and the editor reloads, which runs the ordinary access path again: a password prompt, a refusal page, or (when access remains another way) the editor. The `follow` op is presence the room keeps and never relays.

### What the room does to a frame

In order, for every inbound frame: a frame over 256 KiB is dropped; a per-session sliding-window rate cap (240 frames per second) drops a flood; an op from a session that hasn't said `hello` is dropped; a system-kind op from a client is dropped; a tab-scoped session may only touch its own tab and never the document's structure (`scopedSenderMayRelay`); a non-presence op from a session whose verified role isn't `edit` is dropped; `poll-start` / `poll-end` must come from the baton holder when one is held. Then:

- **Presence ops** relay to every other socket (or, for `avatar-push`, to the one addressed socket).
- **Mutation ops** are rewritten before they go anywhere: `opForTheWire` strips every comment `authorId` (an owner id, which no reader is shown), and `stampCommentAuthor` sets a posted comment's author name and colour to the sending session's presence, whatever the frame claimed. The rewritten op gets the next `seq`, lands in the catch-up log, relays to every other socket, is recorded in the ledger when it is an `el-delta` or `vote`, and the sender receives a `cursor` frame naming the `seq` its own op took, echoing the op frame's `ref` when it carried one (a positive integer), so the sender knows that op is sequenced.
- Every outbound op frame to a tab-scoped session is filtered or redacted for its scope (`opForScope`), live and in catch-up.

On `hello` the room builds the session's presence itself (`helloPresence`): the id is a server-minted per-socket random (never the connector's owner id), the role is the verified one, and every claimed string is length-clamped. It then sends the joiner a `cursor` frame, replays the running poll and its answers, broadcasts presence (each socket gets the roster minus its own entry), and tells the joiner who holds the facilitator baton.

### Ordering and catch-up

Mutations are totally ordered by the single-threaded DO: a monotonic `seq` within an `epoch`. `epoch` and `seq` are persisted in DO storage (`order-state`) and restored on every wake, so hibernation does not strand reconnecting clients ([Resync without reloading the page](../012-collaboration/resync-without-reload.md)). The catch-up log (the last 256 mutations, `OP_LOG_LIMIT`) lives in memory only. On reconnect a client sends `{ kind: 'sync', epoch, lastSeq }`; `resolveCatchup` answers with the ops it missed, or `resync: true` when the gap is behind the log's floor or the epoch is foreign, and the client re-fetches its loaded tabs from the api in place.

### What the room stores

Besides the document's content (**Storage**), its key-value storage holds:

- **`order-state`**: `{ epoch, seq }`, written on every mutation.
- **The collaboration ledger** (`RoomLedgerStore`, `room-ledger-store.ts`; entries defined by the pure `collab-ledger.ts` in `@livediagram/document`): for every `el-delta` and `vote` it sequences, the latest state of each answer, idea, checklist tick, comment and the round's dots, one key per element (plus the tab's vote), tagged with the `seq` that set it. An entry that would pass the storage value limit stops growing. The api reads it back to merge a tab save (see the tab `PUT` above).
- **The live poll** (`RoomLivePoll`, `room-live-poll.ts`, key `live-poll`): the running poll and every answer, replayed on `hello`, dropped on `poll-end`.
- **The facilitator baton** (`RoomFacilitator`, `room-facilitator.ts`, key `facilitator`; rules in `facilitator.ts`): who holds it, the token only the holder was sent, and a grace deadline enforced by a DO alarm when the holder's socket goes away ([Facilitator](../012-collaboration/facilitator.md)).

Per-session state (presence id, verified role, owner bit, tab scope, admitting share code, presence) lives in each socket's serialized attachment, so it survives hibernation; only the rate-cap windows and the catch-up log reset on a wake.

The room's other parts each have a module of their own in `apps/api/src/`, beside the room (`document-room/document-room.ts`): the session attachment and the verified upgrade headers (`room-session.ts`), the role gate on client ops (`room-op-gate.ts`, the [Share roles](../013-workspace/share-roles.md) level ladder), the worker-only internal endpoints (`room-internal.ts`) and the presence roster each socket is sent (`room-roster.ts`).

### What the room writes itself

- **Q&A board writes.** `POST /api/documents/:id/tabs/:tabId/qa` hands each board action to the room's internal `POST /qa`; `handleQaWrite` runs them one at a time through an in-memory queue and calls `writeQaAction` (`qa-board-write.ts`), which reads the tab row, applies `applyQaAction`, bumps `qaRev` and compare-and-swaps the row. The result goes out as a sequenced `qa` system op. This is the one document write that happens inside the room, in its own SQLite.
- **One telemetry row**: the room counts a multiplayer session once (`Document·Used·Multiplayer`, `reportServerEvent`) to the liveworkspace telemetry service, when `TELEMETRY_ENABLED` is on ([Telemetry + public transparency dashboard](../017-telemetry/telemetry.md)).

Every other document write is a REST call from a client (see the persistence boundary below).

### Internal endpoints

The api worker reaches the DO through its stub (`env.DOCUMENT_ROOM.get(...).fetch(...)`; content goes through the typed RPCs under **Storage**), which never traverses the public edge, so these paths are implicitly internal:

- **`POST /broadcast`** `{ op, ordered? }`: push a system op to every socket (`from: 'system'`), sequenced when `ordered` is true. Used by share-link revoke (`DELETE /api/documents/:id/share/:code`), a tab delete that takes scoped links with it (both `share-revoked`) and a rescope (`share-rescoped`), via `broadcastShareOp` in `room-client.ts`; after relaying either the room closes the sockets that code admitted. Best-effort: a failure is logged (`[room-broadcast]`), never fails the request.
- **`POST /mutation`** `{ op }`: sequence a document change the worker made, as if a peer had sent it. `el-delta`, `changeset` and `tab-meta` are accepted (400 otherwise); the comment endpoints use `el-delta` so a view-role visitor's comment reaches connected editors (`relayElementDelta`), the changeset route uses `changeset` ([Agent changesets](../024-agents/agent-changesets.md#what-the-room-does)), and the tab rename route uses `tab-meta` (`relayTabRename`).
- **`GET /selections?tab=<tabId>&person=<tag>`**: the elements each connected person has selected on a tab (every `select` is recorded in DO storage per session, pruned when the socket goes), each marked `mine` when the session's person tag is the one asked about. The changeset route reads it to find held elements.
- **`PUT /presence`**, **`DELETE /presence`**: an agent's presence entry with its expiry ([Agent presence](../024-agents/agent-presence.md#presence)).
- **`POST /qa`**: one Q&A board write, above.
- **`GET /ledger?tab=<tabId>&epoch=<epoch>`**: the tab's collaboration ledger, or an empty one when `epoch` isn't the room's current epoch (the saver's cursor can't be interpreted then).
- **Purging a room** (the `purge` RPC; `POST /purge` reaches the same code): the document was removed for good, so the room closes every socket (`DOCUMENT_TRASHED_CLOSE`, reason `document-purged`), waits for the ledger's queued writes, drops its alarm and deletes all of its storage (`deleteAll`): the document's content with it, and the ledger with its comment text, the order state, selections and agent entries. The index calls it through the internal `DELETE /api/internal/items/:id` (and its batch `POST /api/internal/items/purge`) after every removal for good: the Trash purge, Take Offline and account deletion.

### Conflict model

- **Different elements on one tab merge.** `el` ops apply by id, so concurrent edits to different elements survive on every peer.
- **The same element is last-writer-wins, over the whole element.** Two `el` updates to one element apply in room order and the later one replaces the earlier, whoever held the selection. The concurrent-selection lock ([Editor app](../007-editor/editor-app.md)) is advisory and client-only (`remoteSelectionsByElement`, built from `select` ops): it makes these collisions rare, and the room does not enforce it. `tab-meta` patches are last-writer-wins per field, and `document-meta` per whole tab list.
- **Multi-writer fields merge.** Answers, ideas, checklist ticks, comments and dots travel as `el-delta` / `vote` deltas that commute, and whole-element or whole-tab ops don't overwrite a receiver's copy of them.
- **Q&A boards are server-owned** and ordered by `qaRev`.

### The persistence boundary

The document's object holds both the content and the ordering and collaboration state. Tab content reaches its store through `PUT /api/documents/:id/tabs/:tabId`, fired by each editor's debounced autosave with the editor's whole copy of the tab. The store keeps the last save of a tab, with the room ledger merged in as described on that row. Each editor's copy already folds in the ops it has received, so the last save normally carries everyone's work; an element edit that reached the saver only after its snapshot can be missing from the store until a later save carries it, while live peers still hold it.

A tab `PUT` is not relayed to the room; it is the editor's autosave and nothing else's. Every other writer of tab content (the MCP server, the CLI, an API-token script) writes a [changeset](../024-agents/agent-changesets.md), which the api records in the document's store and relays to the room, and which every later editor save re-applies unless that editor has seen it. The comment endpoints also tell the room about their writes.

Every tab the api receives (document create, tab save) runs the stored-tab migration (`migrateStoredTab`) before `isValidTab`, as every tab read does, so an element in a former stored shape (for example freehand points before [Stroke points](../006-document/stroke-points.md)) from a browser loaded before a deploy, an API-token script or a Google Drive copy is stored in the current shape rather than refused.

## Data model

The api has no D1 database and no SQL migrations. Its data is in three kinds of SQLite-backed Durable Object, each
creating its schema on first use:

- **Document content** (`document`, `community_post`, `tabs`, `document_tabs`, `tab_stats`, `image_refs`, `image_owners`, `image_grants`, `notify_claims`, `agent_changesets`, `agent_changeset_parts`, `tab_shares`, `share_outbox`, `guest_voters`, `outbox`) is in each document's Durable Object, `apps/api/src/document-room/document-schema.ts`. The document's own row holds its name, owner and deck. See [Per-tab storage](../006-document/per-tab-storage.md) for why a tab is its own row.
- **A person's own store** (`PERSON_STORE`, `apps/api/src/person-store/`): their shape libraries and their Google Drive mirror.
- **A person's workbench** (pairing requests, pairings, tickets, sessions and the rooms a workspace session joined) is their own Durable Object (`WORKBENCH`, the store in `@liveworkspace/index-app`, [Workbench embeds](../013-workspace/workbench-embeds.md)). It keeps only hashes of tickets and session secrets.

Document-store hybrid: the document's meta lives in real columns; element content lives in tab `data` JSON. Element-level SQL filtering isn't a use case, so normalising element rows would buy nothing — and the editor already round-trips JSON for every save.

API tokens are liveworkspace's alone ([Public API and API tokens](public-api-and-tokens.md)). Where a document is filed (folders, favourites), who it is shared with (share links, their passwords, Shared With You), whether it is in the Trash, the Timeline and Home are the index's ([one-explorer-contracts.md](../../../../liveworkspace/docs/one-explorer-contracts.md)).

### Owner-keyed data

What this app keeps for a person, and what the two owner-wide operations do with it. Both live in `apps/api/src/db/account.ts`. **Account deletion** (`deleteAccount`) runs on `DELETE /api/account` and whenever the index says an account closed (`POST /api/internal/people/:id/purge`, the `personClosed` door), wherever it was closed. **The guest merge** (`mergeGuest`) runs when the index says a guest became an account (`POST /api/internal/people/:guest/merge`, `personMerged`); the guest's documents move to the account in the index itself ([Auth + guest access](../014-identity/auth-and-guest-access.md#guest--account-merge)).

| Data                                                 | Account deletion                                                                                                                   | Guest merge                                                                                                                       |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Images at the media service                          | Deleted first (`forgetOwner`, every image the account uploaded, in any app), so a failure leaves the account whole to delete again | Moved to the account (`mergeOwner`); an image the service keeps on the guest serves in the moved documents by its placement grant |
| `document.owner_id` (each document's own store)      | The account's own documents are deleted for good through the index, which purges each store                                        | The index moves the document; the room keeps the owner the index's grant names (`X-Verified-Item-Owner`)                          |
| `agent_changesets.author_id` (each document's store) | Those on someone else's document stay until the 30-day changeset retention ages them out                                           | Stay under the id they were written with                                                                                          |
| `image_owners.owner_id` (each document's store)      | The media service's answer cached: the service deletes the account's images, and a document then serves nothing of theirs          | Unchanged                                                                                                                         |
| The Google Drive mirror (`PERSON_STORE`)             | The grant is revoked at Google (the Drive files are the person's and stay), then the store is emptied                              | Account-only                                                                                                                      |
| Shape libraries (`PERSON_STORE`)                     | Deleted with the store                                                                                                             | Moved to the account's store                                                                                                      |
| The workbench store (`WORKBENCH`)                    | Closed: every pairing ends (closing the rooms its sessions had open) and the store is deleted                                      | A guest has none (it needs an API token)                                                                                          |
| Community copier records                             | The copies they took stop counting (`forgetCommunityCopier`)                                                                       | Become the account's (`mergeCommunityCopier`)                                                                                     |
| Their name on other people's documents               | Taken off each listed document (the index's `anonymise` door)                                                                      | —                                                                                                                                 |

**Account-only** means a guest id never holds it: the Google Drive mirror needs a verified account identity, and the merge source is always a guest id.

**Kept by liveworkspace, not here.** API tokens are the account's and close with it. A person's preferences, display name and presence colour (the participant), teams, the record of which accounts this app has seen, which milestone emails it has sent, and their email address are the liveworkspace accounts Worker's (liveworkspace/docs/accounts.md "Settings", "Profiles", "Sign-ups and milestones per app"; `apps/api/src/liveworkspace/`). Closing an account deletes them there. A livediagram guest is `guest_<guest id>` there.

A new kind of owner-keyed data adds a row here and a step to `deleteAccount` and `mergeGuest`, in the same change.

## One-time setup

Before the first deploy:

1. `pnpm --filter @livediagram/api exec wrangler r2 bucket create livediagram-images`, the bucket for snapshots.

There is no database to create and no migration to apply: the Durable Objects (`DocumentRoom`, `PersonStore`, `WorkbenchStore`) are declared in `wrangler.toml` (`new_sqlite_classes`) and make their own schema on first use.

After that, GitHub Actions handles deploys via `deploy.yml` (`deploy-api` step). The router's service binding to `livediagram-api` means the API must deploy before the router.
