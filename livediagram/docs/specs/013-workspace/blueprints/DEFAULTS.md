# Workspace blueprint defaults

One row per default applied where a spec is silent or qualitative.

| #    | Blueprint        | Spec silence                                                          | Default applied                                                                                                                                                                                   |
| ---- | ---------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D7   | shape-libraries  | Where the libraries are stored                                        | The person's own `PersonStore` Durable Object (`shape_libraries` in its SQLite), reached by their id                                                                                              |
| D8   | shape-libraries  | Whether name clashes compare case                                     | Trimmed and case-insensitive: "UML" and "uml" read as the same name                                                                                                                               |
| D9   | shape-libraries  | How long an item id may be                                            | 64 characters; the client mints UUIDs (36)                                                                                                                                                        |
| D10  | shape-libraries  | How large one item may be                                             | Each side in (0, 100 000] px                                                                                                                                                                      |
| D11  | shape-libraries  | Whether sign-up may carry an account past the library cap             | Yes: the cap applies to creates; a migration never drops a guest's library                                                                                                                        |
| D12  | shape-libraries  | Order of an import holding diagrams and libraries                     | Diagrams first, then libraries, one progress count over both                                                                                                                                      |
| D13  | shape-libraries  | Whether deleting one shape asks first                                 | No: one shape is small; the library's delete asks                                                                                                                                                 |
| D14  | shape-libraries  | Whether an empty library shows in My shapes                           | No: it shows only in the Explorer, where it can be deleted                                                                                                                                        |
| SR1  | share-roles      | What the level field is called in storage and on the wire             | `role` everywhere stored or sent (`share_links.role`, `ShareLink.role`); `level` in code (`AccessLevel`)                                                                                          |
| SR2  | share-roles      | Which queue a Participant's content write uses                        | The Q&A board's, renamed `tabWriteQueue`: both read-modify-write the same tab rows, so one queue keeps them from racing                                                                           |
| SR3  | share-roles      | Who hears a Participant op the rule changed                           | Everyone including the sender, so the sender's screen converges on what was stored; an unchanged op skips the sender as an Editor's does                                                          |
| SR4  | share-roles      | How the server derives an adder key                                   | The first 32 hex characters of SHA-256 over `livediagram:adder:v1:<documentId>:<ownerId>`: stable per person and document, opaque, unlinkable across documents                                    |
| SR5  | share-roles      | What a Participant session without an adder key may do                | Update text, move and recolour; never add or remove, since nothing could later prove the element was theirs                                                                                       |
| SR6  | share-roles      | Where an embed's cap to Viewer is applied                             | In the editor (`sessionRole`), as embeds have no identity screen; the room cannot tell an embed from a link holder                                                                                |
| SR7  | share-roles      | Where the pass's role mark sits                                       | A full-width header band across the top of the card, so `PARTICIPANT` fits and the link has the card's width                                                                                      |
| SR8  | share-roles      | How the three role cards sit                                          | One per row at every width: three across left each blurb four lines deep and the title under the check                                                                                            |
| SR9  | share-roles      | How soon a Participant's answers reach storage                        | 1500 ms after the first unflushed answer on a tab (`ANSWERS_FLUSH_MS`), one write for a burst of dots                                                                                             |
| SR10 | share-roles      | Whether writing on someone else's text box may resize it              | Yes, only for a text box that sizes to its words (`sizing` set): its width and height follow the words. A Participant never moves or resizes someone else's text box by hand (decided 2026-10-10) |
| SR11 | share-roles      | How the stored level admits `participate`                             | A nullable `level` column beside the two-valued `role` (written `view` for a Participant): no table rebuild under `community_posts`' cascade, and an older reader of `role` fails closed          |
| SR12 | share-roles      | How many of one socket's writes may wait                              | 64 (`PARTICIPANT_PENDING_MAX`): far above a person's pace, one op per changed element every 600 ms; past it the sender re-hydrates                                                                |
| SR13 | share-roles      | How a held-back gesture is reported                                   | One info toast per 4 s burst (`HELD_BACK_NOTICE_MS`): "As a participant you can add and write, move stickies, and remove what you added."                                                         |
| WB2  | workbench-embeds | How long a workbench name may be                                      | 1 to 40 characters, trimmed (`normaliseWorkbenchName`); the CLI refuses any other with exit 1                                                                                                     |
| WB3  | workbench-embeds | What a share link in `workbench open` gets                            | Exit 2, "a workbench opens your own documents": a frame opens the owner's own access, never a share code                                                                                          |
| WB7  | workbench-embeds | What the editor shows when the session's person has no name or colour | A random name and colour locally; the participant record is never written                                                                                                                         |
| WB8  | workbench-embeds | What another credential header beside `lvw_` gets                     | `403 workbench_confined`: a session never borrows a share code's or a guest's access                                                                                                              |
| WB9  | workbench-embeds | How a view session's writes are refused, and which pass               | `403 workbench_read_only` at the choke point; the room-ticket mint and the session's own end pass                                                                                                 |
| WB10 | workbench-embeds | Which write budget a session spends                                   | `WRITE_RATE_LIMITER` keyed `workbench:<sessionId>`, apart from its token's agent writes                                                                                                           |
| WB11 | workbench-embeds | What a room matches when access ends; what the page's own end closes  | The pairing id, carried by the room ticket, so a socket outlives renewal; the page's own end closes nothing                                                                                       |
| WB12 | workbench-embeds | Whether an ended page can be revived by a later ticket                | No: `ended` is terminal; the workbench frames a fresh URL to reconnect                                                                                                                            |
| WB13 | workbench-embeds | What a `hello-ack` with a missing or overlong name gets               | Invalid, ignored and logged; the wait runs on to the deadline                                                                                                                                     |
| WB14 | workbench-embeds | Whether a ticket outside the renew window is redeemed                 | Yes, as a renewal: a workbench may renew early                                                                                                                                                    |
| WB15 | workbench-embeds | Which scheme shows before the first `livediagram:theme`               | The system's; the frame's stored Appearance setting is ignored in a workbench                                                                                                                     |
| WB16 | workbench-embeds | How the editor treats a request the allow-list refuses                | Refused locally (`WorkbenchConfinedError`), nothing sent, logged once per route, not a network error                                                                                              |
| WB17 | workbench-embeds | Whether an unchanged selection is sent again                          | No: a settled selection is sent only when its text differs from the last sent                                                                                                                     |
| WB18 | workbench-embeds | How `reveal` brings elements into view and outlines them              | The changeset toast's Show and outline, in the person's colour, for `CHANGESET_REVEAL_MS`, on the active tab                                                                                      |
| WB19 | workbench-embeds | How the header names the document                                     | By its full id: the frame cannot see the library a shorter ref is unique in, and `<doc>` always resolves it                                                                                       |
| WB20 | workbench-embeds | In which order selected elements are listed                           | The tab's element order, so the text does not depend on the order of clicks                                                                                                                       |
| WB21 | workbench-embeds | Whether a reference with no selection carries a `read:` line          | No: the header and `whole tab`, as the spec lists                                                                                                                                                 |
| WB22 | workbench-embeds | Where the `… and n more` tail goes                                    | On the `selected:` line, after the last item                                                                                                                                                      |
| WB23 | workbench-embeds | Which exit `workbench open` gives a 428                               | 4, mapped by the verb (`exitCodeForStatus` alone reads 428 as 1)                                                                                                                                  |
| WB24 | workbench-embeds | How a workbench reads the pairing URL before the wait ends            | stdout's first line, flushed before waiting: the URL, or `{ status, pairingUrl, expiresAt }` with `--json`                                                                                        |
| WB25 | workbench-embeds | When `workbench pair` opens a browser                                 | Only when stdout is a terminal; piped, as a workbench runs it, it prints and waits                                                                                                                |
| WB26 | workbench-embeds | Where the error tokens live                                           | `WORKBENCH_ERROR_CODES` in `packages/api-schema/src/workbench.ts`, as `CHANGESET_ERROR_CODES`                                                                                                     |

| WB35 | workbench-embeds | What a token card with no pairings shows                              | Nothing extra: no empty heading                                                                                                                                                                   |

| WB44 | workbench-embeds | What `tabId` is when `workbench open` names none                      | `null`; the editor opens the document's first tab                                                                                                                                                 |
