# Architecture

A pnpm + Turborepo monorepo: seven Cloudflare-deployed apps, one distributed command-line app and twenty-two shared packages. Everything runs on Cloudflare Workers (Static Assets for the Next.js apps); there's no Node-hosted backend.

```
apps/
  marketing/    static landing site (Next.js export, /)
  editor/       the editor (Next.js export; clean routes)
  help/         help centre (Next.js export + MDX, /help)
  community/    public gallery of shared documents (Next.js export, /community)
  api/          REST + WebSocket worker (Durable Objects, /api)
  mcp/          MCP server for AI tools (OAuth + tools, mcp.livediagram.app)
  router/       service-binding router stitching the apps under one hostname
  cli/          the livediagram command line for agents and scripts (Node, one esbuild bundle)
packages/
  ui/             shared UI primitives + chrome icons (Brand, Tooltip, CloseIcon, etc.)
  document/       document data model (Tab, Element types + helpers) over @liveworkspace/model-core
  templates/      template catalogue + pure element builders (editor template starts + MCP)
  template-previews/ per-template preview SVGs (editor template starts + marketing template gallery)
  help-registry/  this product's help-centre articles + categories, bound to @liveworkspace/help-registry's lookups (help app + editor search)
  api-schema/     wire-format DTOs the api worker emits + the live editor consumes
  agent-verbs/    the verbs the CLI routes to: schemas, handlers, compact text, addressing, guides, the skill
  edit-operations/ the engine agent changesets run on: edit operations and replace into element ops
  document-views/ read-only text views of a tab (outline, graph, layout, ...) for agents and scripts
  diagram-lint/ checks how a tab is drawn: overlaps, crossings, arrows behind boxes, with a fix each
  sticky-vision/  finds sticky notes in a photo of a wall (classical CV, no DOM)
  sticky-model/   the learned boundary model's pure parts (cues, decode) + its training scripts
  telemetry-client/ this product's telemetry facts (app, preferences key, tokens) bound to @liveworkspace/telemetry-client
  licences/       this product's licence tables (apps, overrides, embedded works) for @liveworkspace/licences' generator
  (shared with every product, in the monorepo's packages/ as @liveworkspace/*: api-client, api-kit, mcp-kit, cli-kit,
  telemetry-client, render-png, source-ast, style-guards, model-core, help-registry, tailwind-config, icons, licences, and the oxlint, prettier, vitest, next configs)
docs/specs/          product source of truth, read these before adding features
scripts/        repo-wide dev tooling (next-dev.mjs: shared Next.js dev launcher)
marketing/      off-site copy + media for listings and promotion (see docs/specs/019-marketing/marketing-assets.md)
  copy/         taglines, descriptions, tags, the canonical fact sheet
  media/
    desktop/    desktop product screenshots, captioned
    mobile/     mobile product screenshots, captioned
```

## The editor's shape

The editor route (`apps/editor/app/document/[id]/`) is split three ways so no file becomes a god component:

- `useEditorState.ts` is the orchestration hook: it calls each domain sub-hook, threads their dependencies, and assembles the return view-model.
- `EditorContext.tsx` carries that view-model as `EditorContextValue = ReturnType<typeof useEditorState>`.
- `EditorView.tsx` renders the JSX, leaving `editor-page.tsx` a thin page shell.

`useEditorState.ts` is large by design: what remains in it is wiring, not logic, so it is exempt from the ~400-line soft target ([AGENTS.md](../../AGENTS.md#core-principle-no-god-files-plan-placement-first)). New behaviour goes into its own sub-hook, not into it.

## The shared packages

Each app pulls these in via `workspace:*`:

- **`@livediagram/document`** owns the document data model: `Tab`, every `Element` type (Shape / Text / Sticky / Image / Freehand / Table / Annotation / Link card / Arrow), defaults, geometry helpers, snap math, layer ordering, the web components' layouts, the load-time migration of documents saved with groups, and the Shape Pen's shape-recognition heuristics. It also holds the authoring input every non-editor writer shares: raw elements made safe (`normaliseElement`), graph input capped and laid out (`layoutGraph`), finished tabs built (`buildTab`, `buildGraphTab`), workshop notes landed on lanes (`landWorkshopArrivals`), every stored field per element type (`ELEMENT_FIELD_NAMES`) and validation that names the field and rule it fails (`elementValidationIssue`). The single source of what a document IS. What every product's model shares and needs nothing of its element union is **`@liveworkspace/model-core`** (the monorepo's `packages/model-core`): the plain vocabulary (ids, text size, padding, alignment, arrow flows, background patterns), geometry primitives, the stroke points codec, rich-text runs, fonts, border, label and icon sizing, names, small helpers (plurals, string hashing, seeded random) and embeds' URL rules. `@livediagram/document` re-exports it, so callers import from `@livediagram/document` as before; it binds the one embed setting that is its own, the host Figma is told.
- **`@livediagram/sticky-vision`** finds the sticky notes in a photograph of an event-storming wall ([Event storming](../specs/021-event-storming/event-storming.md) Phase 8): colour classification against the notation catalogue, connected components, box fitting and row clustering, over a plain RGBA buffer. It is deliberately classical rather than a vision model — the notation IS colour, a hue histogram knows colour exactly, and the whole photo then never has to leave the browser (only crops of individual notes go to the model, to read the handwriting). See `packages/sticky-vision/README.md` and `docs/research/vision/sticky-detection.md`. A small learned boundary model (**`@livediagram/sticky-model`**, trained on synthetic walls only) may correct its boxes: the editor runs it in a Web Worker on TensorFlow.js (WebGPU, else WASM), loaded on demand from the editor app's own static assets, and hands its cues to the detector; without it, the classical detector runs alone (`apps/editor/lib/photo-model/`, `docs/research/vision/experiments/m-editor-model.md`).
- **`@livediagram/sticky-model`** is the learned boundary model the photo import runs beside the classical detector ([Event storming](../specs/021-event-storming/event-storming.md) Phase 9): a tiny U-Net (note core / seam / background) trained ONLY on procedurally generated walls, so nothing in it derives from anyone's photograph. Its browser-safe entry (cues, decode) runs in a Web Worker the editor loads lazily when a photo import starts (TensorFlow.js, WebGPU falling back to WASM, falling back to the classical detector on any failure); its uint8 weights (~83 KB) ship as a static asset of `apps/editor`. The synthetic wall generator and the Node training scripts live beside it. See [the boundary model](../research/vision/experiments/e-model.md) and [the hybrid](../research/vision/experiments/j-hybrid.md).
- **`@livediagram/api-schema`** owns the wire format between the api worker and the live editor: every request / response shape, plus the response envelopes (`DocumentResponse`, `TabResponse`, ...) the editor and the MCP server both read, the small shared pure helpers it backs (`sha256Hex` for image-upload dedupe, worker-safe `bytesToBase64` / `bytesToBase64Url`, `embedTabImages` which inlines a tab's uploads for the api snapshot and the MCP preview, `titleCase` for display-casing preset values across the editor and liveworkspace's telemetry dashboard, and the page-view path normaliser + the editor app's route-segment list, shared by every frontend and the router, [Page view telemetry](../specs/017-telemetry/page-view-telemetry.md)). Adding a field on the server without updating the client used to be routine drift; the typechecker catches it now.
- **`@liveworkspace/explorer`** (`packages/explorer/src/lens/` at the repo root) owns the Explorer's one filter state: the lens string's grammar (`parseLens` / `serialiseLens`), matching, autocomplete and the chips' view models.
- **`@livediagram/diagram-lint`** checks how a tab is drawn ([Diagram lint](../specs/024-agents/diagram-lint.md)): `lintTab` answers the measures (crossings, arrows behind boxes, overlaps, extent) and thirteen kinds of finding, each with the refs the views print and a fix as edit operations; `lintGraph` lays a graph source out first and `compareGraphLayouts` measures its variants. Errors judge the diagram's graph, so decoration may overlap. Pure and deterministic, consumed by the api worker (`?view=lint`, every changeset's footer) and the MCP (the summary line). The parts that read no element (the summary and report text, label quoting, the finding order over a product's own codes, the logger and the shared `LINT_*` numbers) are one copy in `@liveworkspace/diagram-lint` (`../packages/diagram-lint`), each a subpath; the checks, typed on this product's elements, stay here.
- **`@livediagram/document-views`** renders a tab as a [document view](../specs/024-agents/document-views.md): `renderView` builds one view model (refs, derived containment, reading order, edges) and answers the outline, `graph`, `layout`, `comments`, `show` or `find` as text and JSON, fitted to a token budget with one closing line naming what it left out; `overviewView` summarises a document from per-tab header facts, and `diffView` compares two reads of a tab for the CLI. Refs, slug ids, kind words and containment themselves live in `@livediagram/document` (`element-refs.ts`, `containment.ts`), so edit operations and the lint name elements the same way. Pure and deterministic, consumed by the api worker (`?view=`). The parts that read no product's element union (text escaping, field reads, attributes, budgets and elision, reading order and freehand runs over any element, the shared view constants) are one copy in `@liveworkspace/document-views` (`../packages/document-views`), each a subpath; the views themselves stay here.
- **`@livediagram/edit-operations`** is the engine an agent changeset runs on ([Edit operations](../specs/024-agents/edit-operations.md)): `parseEditOperations` reads the line form (JSON objects allowed on a line) and `validateEditOperations` the JSON form; `applyEditOperations` applies the twelve operations to a tab, resolving refs and selectors, placing new boxes beside what they name and making room on insert; and `applyReplace` builds a whole tab from a graph, Mermaid, a template or raw elements. Each answers the next tab, its element ops and their inverse, the result lines and the targets it resolved, or named refusals with nothing applied; `formatResultLines`, `formatResultFooter` and `formatRejections` print them. Containment and carrying (`containerContents`) and refs live in `@livediagram/document`, shared with the views. Pure and deterministic, consumed by the api worker.
- **`@livediagram/ui`** owns the cross-app UI primitives. The chrome (`Brand`, `SiteHeader`, `SiteFooter`, `SiteSwitcher`), the form + feedback controls (`Button`, `TextInput`, `Select`, `EmptyState`), the hover and focus hints (`Tooltip` for a name, `HoverCard` for a title and description; see [Tooltips, hover cards and popovers](../specs/004-interface-design/tooltips-hover-cards-popovers.md)), the shared behaviour hooks (`useMediaQuery`, `useCopiedFlash`, and the dismiss / focus trio `useClickOutside`, `useEscape`, `useFocusTrap` the editor's dialogs and the public sites' popovers share) plus the popover-clamping helpers. It also holds the public sites' shared plumbing: the site constants (`SITE_URL`, `SITE_NAME`, `REPO_URL`, the `BRAND_ICONS` favicon set, the `PUBLIC_VIEWPORT`), the SEO builders (`pageMetadata` for per-page metadata; `breadcrumbJsonLd` and the `BreadcrumbTrail` it describes are `@liveworkspace/ui`'s, rendered by `JsonLd`), and `PageViewBoot`, the page-view tracker wired to the shared `siteTrack` emitter. Reach for these before re-typing a class list: a control that exists here and is rebuilt in an app is the drift this package was made to stop. The **chrome icons** are `@liveworkspace/ui`'s (`../packages/ui/src/icons/`, re-exported here; this package keeps only its `EDITOR_MODE_ICONS`): named React icons drawn on its `Glyph` base (square viewBox, `currentColor` stroke, round caps, `aria-hidden`) (`CloseIcon`, `TrashIcon`, `ChevronDownIcon`, `SearchIcon`, `LinkIcon`, `SharedDotIcon`, ...) that take `size` / `strokeWidth` / `className` overrides, so a glyph the editor and marketing hero both draw is one path, not a copy per file. These are app-chrome components; the canvas's own icon catalogue (SVG markup strings for canvas elements) is `@liveworkspace/icons`.
- **`@liveworkspace/icons`** (the monorepo's `packages/icons`, shared with every product) owns the three catalogues (the line-art glyphs, the Technology brand marks, and the stickers of [Stickers](../specs/010-palette/stickers.md)) plus pure SVG-markup builders for them, and `xmlEscape`, the one XML escaper every SVG builder in the monorepo shares (`@livediagram/document` re-exports it). The editor dynamic-imports the data modules through its icon registry so they stay out of its first-load JS; the api + mcp workers static-import `@liveworkspace/icons/resolve` so headless renders (the live image, Explorer thumbnails, MCP inline images) draw the real glyphs.
- **`@livediagram/templates`** owns the template library: the catalogue (kinds, titles, categories, per-template canvas overrides) and the pure per-template element builders. Two callers: the editor's template starts (which layer its theme recolour on top in `apps/editor/lib/template-builders.ts`) and the mcp worker's `list_templates` / `template` tools ([MCP server](../specs/015-api/mcp-server.md)), so the scaffolds can't drift between them. `buildTemplateTab` makes a finished template tab for the MCP and a changeset's `replace` alike.
- **`@livediagram/template-previews`** owns the per-template preview illustrations: one static SVG per `TemplateKind`, rendered by the editor's template picker and by the marketing site's template gallery, so a template's card looks the same wherever it is offered and a new kind gets its artwork in one place. Its tests assert every listed template has a preview and that each drawing stays inside its viewBox.
- **`@livediagram/help-registry`** owns the help-centre article + category registry: slugs, titles, descriptions, and per-article search keywords. The pure href, grouping and search helpers over it are the monorepo's `@liveworkspace/help-registry`, which every product binds to its own catalogue. Two callers: the help app's browse + search (`apps/help/lib/articles.ts` re-exports it) and the live editor's search-panel Help group (`apps/editor/lib/help-search.ts`), so adding an article once makes it findable in both.
- **`@liveworkspace/help-site`** is the help centre's code, shared by every product: its pages, components, MDX styles, SEO helpers, styles and catalogue checks. `apps/help` binds it to this product in `lib/help-site.tsx` (server) and `lib/help-client.tsx` (the client provider), and keeps its articles, illustrations, card art, header, footer, home layout and page copy.
- **`@livediagram/licences`** binds this product's tables (its apps, overrides and embedded works) to **`@liveworkspace/licences`** (the monorepo's `packages/licences`, one engine and one pool of texts for every product), which generates the third-party licences page ([Third-party licences](../specs/002-project-scope/third-party-licences.md)). The marketing build runs it after every other app has built: it reads what each Next app ships to the browser from `next experimental-analyze` and what each worker bundles from a `wrangler --dry-run` metafile, collects each package's licence and notice files (with reviewed overrides for packages that ship none, and a reviewed table for what sits inside WASM and fonts), and writes a manifest plus deduplicated plain-text files that `apps/marketing/app/licences` renders. A package with no licence text, an unrecognised licence, a disallowed one or an unreviewed binary fails the build with a named error.
- **`@liveworkspace/fake-google`** (the monorepo's `packages/fake-google`) is an in-memory Google for tests only, used by the [Google Drive mirror](../specs/022-drive-mirror/drive-mirror.md)'s engine tests and the opt-in Drive e2e. Never imported by an app bundle.
- **`@liveworkspace/source-ast`** parses the repo's own TypeScript for the static guards that read code ([Source scanners](../specs/003-system-architecture/source-scanners.md)): `parseSourceFiles(paths)` opens the files as one in-memory project in TypeScript 7's native compiler (`typescript/unstable/sync`) and returns their syntax trees.
- **`@liveworkspace/oxlint-config`** / **`prettier-config`** / **`vitest-config`** / **`next-config`** / **`tailwind-config`** (the monorepo's `packages/`, shared with every product) own the lint / format / test / Next.js / theme configs so every workspace stays consistent. The shared theme also owns the motion tokens (`duration-micro` / `-short` / `-long`); their numbers and the static motion-budget guard every app runs in its tests are `@liveworkspace/style-guards` ([Motion](../specs/004-interface-design/motion.md)). livediagram paints with the shared theme as it is: its sky is the platform default.

## Tech stack

What's running:

- **Frontend**: Next.js 16 (Turbopack) with `output: 'export'`, React 19, TypeScript 7 (the Go compiler, see [contributing](contributing.md#typescript)), Tailwind CSS 4.
- **API**: Cloudflare Workers (vanilla `fetch` handlers, not Hono).
- **Database**: none of its own. Each document's content is in its own SQLite-backed Durable Object, and each person's shape libraries, Drive mirror and workbench in theirs ([API app](../specs/015-api/api.md) "Storage"). Where documents are filed, favourites, sharing, teams, the Trash, the Timeline, Home and the Inbox are liveworkspace's index; API tokens, a person's settings, name and email are the liveworkspace account's; uploaded images are liveworkspace's media service.
- **Local persistence** (optional per document, [Offline Mode](../specs/006-document/offline-mode.md)): Offline Mode stores a document only in the browser's IndexedDB, never the api. It is opt-in at create time (or by taking a cloud document offline) and dispatched behind the single `apps/editor/lib/api-client.ts` persistence boundary on `isOfflineId(id)`, so the rest of the editor takes the same code path either way. Convertible both directions: Sync Canvas uploads it to the account, Take Offline downloads it and deletes the server copy. See [Offline Mode](../specs/006-document/offline-mode.md).
- **Realtime**: Cloudflare Durable Objects, one room per document. Edits sync as granular, id-addressed element ops, so concurrent edits to _different_ elements merge instead of clobbering, and the room stamps each mutation with a per-`epoch` sequence so peers converge and a reconnecting client catches up from a bounded op log (see [Realtime conflict resolution](../specs/012-collaboration/realtime-conflict-resolution.md)). Two people editing the _same_ element at once is last-writer-wins; the advisory, client-only selection lock ([Editor app](../specs/007-editor/editor-app.md)) makes it rare, not impossible. The fields a whole room writes at once (dot votes, answers, ideas, checklist ticks, comments) instead travel as per-change deltas that commute, and the room keeps a small ledger of them which the api merges into each tab save, so a save snapshotted before somebody's answer can't erase it from the store (see [Collaboration race hardening](../specs/012-collaboration/collab-race-hardening.md)). Every server-stored document has a room, personal ones included: agents and API-token scripts change tabs with [changesets](../specs/024-agents/agent-changesets.md), which the api applies, records in the document's Durable Object (`agent_changesets`, with the tab's compare-and-swap revision `tabs.rev`) and relays to the room, and which every editor save re-applies unless that editor has seen it. The whole-tab `PUT` is the editor's autosave alone.
- **Image storage**: liveworkspace's media service (`MEDIA_URL`, `MEDIA_KEY`), gated on owner + share-code reads (see [Image element + per-owner gallery](../specs/009-elements/images.md)).
- **Note reader** (optional): the api worker's one model call. `POST /api/ai/read-notes` reads the handwriting on sticky-note CROPS that the browser cut out of a wall photograph ([Event storming](../specs/021-event-storming/event-storming.md) Phase 8) through an OpenAI-compatible chat-completions endpoint, the provider inferred from the model key that is set (`GOOGLE_AI_STUDIO_API_KEY`, or a generic `AI_API_KEY` + `AI_BASE_URL` + `AI_VISION_MODEL`). The crops are forwarded to the provider and discarded, never stored, and the whole photo never leaves the browser: the stickies are found there by `packages/sticky-vision`. `GET /api/capabilities` reports whether a model key resolves to a provider, and when it does not the route answers 503 and the editor reads the crops in the browser instead, so OSS forks need no key (see [Note reader](../specs/021-event-storming/note-reader.md)). There is no in-editor AI assistant; AI tools connect through the MCP server and API tokens.
- **Auth** (optional): sign-in through the liveworkspace accounts Worker (`liveworkspace.app`, OAuth 2.1 authorization code + PKCE), with livediagram as an OAuth client. The api worker runs the round trip (`/api/auth/*`, refresh token in an HttpOnly cookie), verifies access tokens locally against `${ACCOUNTS_URL}/api/auth/jwks`, and silently degrades to pure-guest mode when `ACCOUNTS_URL` / `API_RESOURCE` are unset.
- **Email** (optional): the api worker sends notification email through Cloudflare Email Service (`apps/api/src/email/`, via `@liveworkspace/email`; [Email](../../../liveworkspace/docs/email.md)): opt-out notifications (someone joins your shared document, comments, mentions, assigned actions), first-share and document-count milestone notes, and the account-deleted confirmation. Addresses and the record of which milestone notes went are the liveworkspace accounts Worker's (`apps/api/src/liveworkspace/emails.ts`); the welcome and onboarding series and the team emails are its own. Gated on the `send_email` binding `EMAIL`, with the sender in `EMAIL_FROM` and no API key (see [Transactional & lifecycle email](../specs/014-identity/transactional-email.md) and [Account settings & email notifications](../specs/014-identity/profile-and-email-notifications.md)).
- **People** (with sign-in): preferences, display names and presence colours are kept by the liveworkspace accounts Worker, one profile and one set of shared settings per person across every app (`apps/api/src/liveworkspace/`); the api keeps no table of its own for them. Without sign-in, preferences stay in the browser.
- **Timeline** ([Timeline](../specs/013-workspace/timeline.md)): liveworkspace's, kept by its index and shown by the shared Explorer, with What Happened on Home. The index records a document's lifecycle (created, renamed, moved, trashed, restored, shared, favourited, synced, taken offline) itself and comments, resolved threads and assigned actions from the collab push; livediagram sends it who edited a document (`PUT /app/items/:id/events`, one key per person, from the room's outbox) and image uploads. Team and token events are the accounts Worker's.
- **Inbox** ([Inbox](../specs/013-workspace/inbox.md)): liveworkspace's, one view in the shared Explorer across every app. A document's Durable Object pushes each changed tab's comment threads and actions to the index from its outbox, on idle and at most once a minute (`apps/api/src/document-room/document-outbox.ts`). A row links into the editor with `#t=<tab>&el=<element>&open=action|comments`, which selects the element and opens its popover.
- **Explorer Home** ([Explorer Home](../specs/013-workspace/explorer-home.md)): the shared Explorer's Home view (Jump Back In, Shared With You Recently, What Happened), read from the index. The editor declares its first tab read an open (`X-Document-Open: 1`, `DOCUMENT_OPEN_HEADER` in `@livediagram/api-schema`, the one piece of Home's wire livediagram still holds; never an embed, a resync or a duplicate), and the api worker records it with the index (`POST /items/:id/open`). Documents stored only in this browser keep their open days on their own IndexedDB record (`apps/editor/lib/offline/offline-opens.ts`).
- **Trash** ([Trash](../specs/013-workspace/trash.md)): the index's. A deleted document stays 30 days in the Trash, restorable, then the index deletes it for good and asks the document's Durable Object to drop its content. Offline Mode documents get the same rule in IndexedDB. The MCP server can bin and restore but never purge.
- **API tokens** (optional, [Public API and API tokens](../specs/015-api/public-api-and-tokens.md)): signed-in users make revocable liveworkspace account tokens (`lwt_…`) on liveworkspace.app to call the REST API from their own scripts; the api worker checks an `Authorization: Bearer lwt_…` with liveworkspace and caches the answer for a minute. Signed-in only (like teams), six-month expiry. Absent in pure-guest mode.
- **API description** ([API documentation (OpenAPI)](../specs/015-api/api-documentation.md)): `GET /api/openapi.json` serves a public OpenAPI 3.1 document of the whole `/api/*` surface, assembled (`apps/api/src/openapi/`) from a declarative route manifest plus component schemas generated from `@livediagram/api-schema` (`pnpm --filter @livediagram/api gen:openapi`). A drift test pins the manifest to the real dispatch and the committed schemas to the types. The human-facing companion is the help centre's **Developers** category (`apps/help`).
- **Routing edge**: a Cloudflare Worker stitching the apps under one hostname via service bindings.

## Hard constraints

The repo's shape isn't accidental. Three rules keep the stack honest:

- **Static-only frontends.** Next.js apps use `output: 'export'`. No SSR, no Node runtime, no Next.js API routes. Server logic goes in the api worker. Breaking this breaks Cloudflare Pages deploys.
- **Reuse over duplication.** Shared types, UI primitives, configs, and the document data model live in `packages/`, never copy-pasted across apps. If two apps need the same thing, it lives in `packages/` on first occurrence.
- **No secrets in source.** The repo is public; secrets travel via env vars (`.env.local`), `wrangler secret put`, and GitHub Actions repo secrets. See [Secrets policy](../specs/002-project-scope/secrets-policy.md).

## Auth model in one sentence

Every owner is a liveworkspace identity sent as `Authorization: Bearer`: a guest token (from the accounts site's guest handoff, kept in `localStorage`; its `guest_<uuid>` is the owner id) for guests, or an account access token (whose `sub` claim becomes the owner id) for signed-in users. Guests need the accounts site configured too. The canvas always works without signing in. See [Auth + guest access](../specs/014-identity/auth-and-guest-access.md) for the full hybrid model and [API app](../specs/015-api/api.md) for how the api worker resolves the owner.

## Deployment

GitHub Actions → Cloudflare Workers. Build artefacts get uploaded once, then marketing / help / api ship in parallel; live, community and mcp deploy after `api` (all three have service bindings to it), and the router deploys last because its service bindings need the others to exist.

Two environments run that same sequence, from one reusable workflow (`deploy-reusable.yml`) so they cannot drift:

|         | Production                   | Staging                                                      |
| ------- | ---------------------------- | ------------------------------------------------------------ |
| Host    | `livediagram.app`            | `staging.livediagram.app`                                    |
| Trigger | Manual, after a green CI run | Automatic, on every green CI run on `main`                   |
| Workers | `livediagram-<app>`          | `livediagram-<app>-staging` (wrangler `[env.staging]`)       |
| Data    | Durable Objects              | Its own Durable Objects and index — no production data, ever |

Staging exists so every change runs against real remote Workers, Durable Objects and liveworkspace's staging index one deploy before it reaches people's documents. It is public but `noindex` (the router stamps `X-Robots-Tag` when its `DEPLOY_ENV` is `staging`). See [Staging environment](../specs/016-platform/staging-environment.md).

Both environments also get the **hosted profile** (`apps/api/hosted-vars.json`: telemetry on, per-owner image caps), which the workflow adds with `wrangler deploy --var` only in livediagram.app's own repository and then reads back off the live api worker. A fork deploys the committed config alone, so it is telemetry-off and uncapped. See [Deployment](../specs/016-platform/deployment.md) "Hosted profile".

See [Deployment](../specs/016-platform/deployment.md) for the deeper deployment contract.
