A **repository link** binds a directory in your code repository to canvases in livediagram. Coding agents look for context by searching the files in front of them, and a diagram that only lives behind a link is invisible to them. Once a repository is linked, they find your diagrams by name, read them as text through the [CLI](/help/developers/cli/), and can change them while you watch.

livediagram stays the home of every canvas. What the repository holds is a **snapshot** at a known revision, never a second copy you edit in parallel.

## Link a Repository

Run this in the repository (or in one package of a monorepo), signed in to the [CLI](/help/developers/cli/):

```bash
livediagram link init --folder "Minigames" --level files
```

It writes `livediagram.toml` beside you. In a terminal, giving neither `--folder` nor `--doc` shows a list of your folders to pick from; in a script it lists them as commands instead. `--doc` links single canvases, and you can repeat it or combine it with a folder. A link file looks like this (the ids are placeholders for your real ones, and `dir` is optional, defaulting to `diagrams`):

```toml
host = "https://www.livediagram.app"

[covers]
folder = "fld_8k2m4q"          # this folder and its subfolders
documents = ["doc_3h9x2a"]     # and these documents, wherever they live

[mirror]
level = "files"                # none | index | files
dir = "docs/diagrams"
```

Commit `livediagram.toml`. It holds ids and settings, never a credential: someone without access to your canvases gains nothing from it.

## Choose How Much Lands in the Repository

| Level   | A sync writes                                              | Good for                                      |
| ------- | ---------------------------------------------------------- | --------------------------------------------- |
| `none`  | Nothing                                                    | Projects that only use the CLI                |
| `index` | `INDEX.md`: every canvas, its tabs and its link            | Agents finding diagrams by name (the default) |
| `files` | `INDEX.md`, plus a snapshot and a text outline per diagram | Reading diagrams offline, in reviews and git  |

At `files`, each canvas gets a `.livediagram.json` snapshot (one element per line, so a change is a one-line diff) and a `.md` outline that an agent reads at a fraction of the size. The outline opens with a line saying it is generated and linking the canvas.

## Sync

```bash
livediagram sync              # write what changed
livediagram sync --watch      # keep the files in step until Ctrl-C
livediagram sync --dry-run    # print what a sync would do, and write nothing
livediagram link status       # each document and whether it is in step
livediagram link ls           # the documents the link covers
```

A sync writes newer snapshots, adds canvases that joined the folder and removes the files of canvases that left it or went to the Trash. Git history keeps what was removed. With `--watch`, the files follow within a moment of each change in the editor. `--dry-run` cannot be combined with `--watch`, since it writes nothing to keep in step.

A snapshot's file name comes from the canvas's name when it is first synced, and then stays put, so renaming or moving a canvas never churns your repository. Instead, a sync names the files whose path would now be different. Run `livediagram sync --relocate` to move them (with `git mv` inside a git repository). A move never overwrites a file livediagram did not write: if one is already at the new path, the canvas stays where it is and the sync names that file.

Snapshots are for reading. If a snapshot was changed by hand, the sync leaves it alone and names it, so nothing you wrote is lost; send it back with `livediagram push <file>`. If a tab you changed also changed in livediagram since, push refuses that tab as stale and sends the rest. Keep a copy of your change, restore the file (`git checkout -- <file>`, or delete it), sync, then make the change again. A file that git left with conflict markers is held back the same way until you keep one side.

A teammate syncing with their own sign-in only reaches what they can open. A canvas they cannot open stays exactly as committed.

## Several Repositories

A command acts on the nearest `livediagram.toml` at or above the directory you run it in. In a monorepo with a link per package, add `--all` to `sync`, `link status` or `link ls` to act on every link below the current directory.

A link can cover a team folder, so several repositories can link the same diagrams, or a single repository can hold your diagrams for everything else. Each repository keeps its own snapshot; livediagram keeps the one canvas.

## Drawing Your Infrastructure

Your repository already describes what you deploy. `link from-code` reads Cloudflare `wrangler.toml` and Docker Compose files and draws them as one laid-out architecture tab, each Worker, binding and service a box with its technology's icon:

```bash
livediagram link from-code                                     # wrangler.toml and compose files here, as a new canvas
livediagram link from-code apps/*/wrangler.toml --doc "Arch"   # several Workers as one system, a tab on "Arch"
livediagram link from-code --env staging                       # a wrangler.toml environment instead of the top level
livediagram link from-code --dry-run | livediagram graph render - --png arch.png
```

Service bindings join Workers across files, so a monorepo's Workers draw as one system. Keys it doesn't draw, such as `vars`, are listed on stderr, never an error. `--dry-run` prints the graph without signing in. Each run draws a fresh tab: to bring a changed file into a diagram you've already arranged, run it again into a new tab. The editor's [Import](/help/tabs/import-tabs/#import-formats) draws one file the same way.

## Diagram Changes in Pull Requests

A snapshot's text diff tells a reviewer that a diagram changed, not what it now looks like. `link review` draws it: each changed tab before and after, with the changed elements outlined (green solid for added, amber dashed for changed, red dotted for removed). It reads only git and your snapshots, so it needs no sign-in:

```bash
livediagram link review origin/main      # pictures and comment.md in livediagram-review/
```

To see the pictures on every pull request, add this workflow. It posts one comment and updates it on each push, and needs nothing but the workflow's own token, so it works on private repositories too:

```yaml
# .github/workflows/diagram-changes.yml
name: Diagram changes
on:
  pull_request:
    types: [opened, synchronize, reopened, closed] # closed removes the pull request's pictures
permissions:
  contents: write # the pictures go on a livediagram-previews branch
  pull-requests: write # the comment
jobs:
  diagrams:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: livediagram-app/livediagram.app/livediagram/apps/cli/github-action@main
```

The pictures are kept on a `livediagram-previews` branch of your repository, so only people who can read the repository can see them. When a pull request closes, the Action removes its folder from that branch, so the branch doesn't keep growing; leave `closed` out of `types` to keep the pictures. The comment draws up to ten tabs and lists the rest, and it has an **Open in livediagram** link for each canvas. Images on a canvas are drawn as placeholder boxes. A pull request from a fork can't comment, so its pictures are attached to the workflow run instead.

## Public Repositories

Snapshots are as public as the repository they are committed to. `link init` reminds you when the repository has a remote. Choose `index` or `none` if the diagrams themselves should stay private.
