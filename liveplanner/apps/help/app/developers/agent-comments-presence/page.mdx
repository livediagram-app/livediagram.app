Comments are how people and agents talk in a plan when nobody is chatting. An agent holding an [API token](/help/account-and-data/api-tokens/) reads, adds to, resolves and reopens comment threads through the same endpoints the editor uses, and can show the people on a tab what it is doing while it works. Everything it writes appears under the name and colour of the person who owns the token, never as a new person.

The examples use the [CLI](/help/developers/cli/) and `curl`. Paths are relative to `https://www.liveplanner.app/api`, and the `curl` examples assume your token is in `$TOKEN`.

## Who Can Do What

What an agent may do follows its token, through the same gates as a share link:

- A **full-access token** on a plan you can comment on adds, replies, resolves, reopens and shows presence. Commenting needs the access a **Participant** or **Editor** has; someone who can only view reads the threads.
- A **read-only token** lists threads but writes nothing: no comments and no presence.
- Presence is for API tokens only. A signed-in browser session already shows itself in the editor, so the presence endpoints answer it `403 presence_requires_token`.

A comment an agent writes records the token's id for the audit trail, and the people reading it see only your name.

## List the Threads

Read the whole conversation without reading a tab:

```bash
liveplanner comment ls "Budget 2027"                  # open threads (the default)
liveplanner comment ls "Budget 2027" --status all     # resolved ones too
```

```bash
curl "https://www.liveplanner.app/api/projects/$DOC/comments?status=open" \
  -H "Authorization: Bearer $TOKEN"
```

`status` is `open` (the default), `resolved` or `all`; anything else is `400 invalid_status`. The answer lists every thread across the plan's tabs, in tab order and then outline order, with the element's **ref** and label so you can act on it straight away. A thread is on an element (a board, a sheet) or, on a Sheet, on one of its cells:

```json
{
  "threads": [
    {
      "tabId": "449e1b37-…",
      "tabName": "Costs",
      "elementId": "1e17c0d2-…",
      "ref": "1e17",
      "label": "Costs",
      "resolved": false,
      "comments": [
        {
          "id": "c1f0…",
          "text": "Is hosting monthly or yearly?",
          "createdAt": 1760180000000,
          "authorName": "Priya",
          "authorColor": "#7c3aed"
        }
      ]
    }
  ]
}
```

To read one tab's threads as text, ask for its comments view: `GET /projects/$DOC/tabs/$TAB?view=comments` (add `all=1` for resolved ones).

## Reply, Resolve and Reopen

In the CLI, a thread is named by its element's ref, from any [view](/help/developers/working-with-projects/#read-a-tab-as-text):

```bash
liveplanner comment add "Budget 2027" 1e17 --cell B4 "Is hosting monthly or yearly?"   # a cell's thread
liveplanner comment add "Budget 2027" 1e17 "Totals look right to me"                  # the sheet's own thread
liveplanner comment reply "Budget 2027" 1e17 "Yearly, so divide by twelve"
liveplanner comment resolve "Budget 2027" 1e17
liveplanner comment reopen "Budget 2027" 1e17
```

Add `--tab Costs` when the element is not on the first tab. `reply`, `resolve` and `reopen` on an element with no thread are refused, with the `comment add` command to start one.

Over the API, a thread is named by **any comment in it**, so take a comment id from the listing:

```bash
# Start a thread on an element (or add to its thread)
curl -X POST https://www.liveplanner.app/api/projects/$DOC/tabs/$TAB/comments \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "elementId": "1e17c0d2-…", "text": "Is hosting monthly or yearly?" }'

# Reply on the thread that holds comment c1f0…
curl -X POST https://www.liveplanner.app/api/projects/$DOC/tabs/$TAB/comments/$COMMENT/reply \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "text": "Yearly, so divide by twelve" }'

# Resolve it, or reopen it
curl -X POST https://www.liveplanner.app/api/projects/$DOC/tabs/$TAB/comments/$COMMENT/resolve \
  -H "Authorization: Bearer $TOKEN"
curl -X POST https://www.liveplanner.app/api/projects/$DOC/tabs/$TAB/comments/$COMMENT/reopen \
  -H "Authorization: Bearer $TOKEN"
```

- Adding and replying answer `201` with the new `comment`. A comment is at most 2,000 characters, and a reply to a resolved thread reopens it, as it does in the editor.
- Resolving and reopening answer `204`. Resolving a resolved thread, or reopening an open one, changes nothing.
- `DELETE …/comments/$COMMENT` deletes a comment you wrote. Removing someone else's is left to the editor.
- A Sheet cell's thread takes `"cell"` beside `elementId`, the cell's key as `<rowId>:<colId>` (the row and column ids a [sheet read](/help/developers/working-with-projects/plan-sheets-images/#sheets) returns). The CLI's `--cell B4` works this out for you.

Everyone with the plan open sees each change arrive at once, exactly as if you had typed it. See [Comments](/help/collaboration/comments/) for how threads look in the editor.

## Comment Threads on Plan Cards

A Plan card (an **item**) holds any number of comment threads, each with an id (`th-…`), a title, its comments and open or resolved. One thread can be on several cards, in this plan and others.

```bash
liveplanner thread ls "Sprint 14"                          # open threads (the default)
liveplanner thread ls "Sprint 14" --item "#12" --status all
liveplanner thread start "Sprint 14" "#12" "The cart resets on route change."
liveplanner thread reply "Sprint 14" th-3k9 "Fixed in #131."
liveplanner thread resolve "Sprint 14" th-3k9              # and thread reopen
liveplanner thread edit "Sprint 14" th-3k9 cm-81 "Fixed in #132."
liveplanner thread delete "Sprint 14" th-3k9 cm-81
```

Name a thread by its id, an id prefix of four or more, or its title; a comment by its id or a prefix. Through the [MCP server](/help/account-and-data/connect-ai-mcp/) the same work is `list_threads` and `change_threads`.

**Every comment an agent writes is marked Generated by AI**, and people see that label above it. An agent edits and deletes only the comments an agent wrote for you: a comment a person typed is refused, and agents don't rename, share or delete threads.

Over the API:

```bash
# Every thread on this plan's cards (?item=$ITEM for one card's)
curl "https://www.liveplanner.app/api/projects/$DOC/threads" -H "Authorization: Bearer $TOKEN"

# Start a thread on a card, then reply, resolve and reopen it
curl -X POST https://www.liveplanner.app/api/projects/$DOC/items/$ITEM/threads \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "text": "Blocked on the payments review" }'
curl -X POST https://www.liveplanner.app/api/projects/$DOC/threads/$THREAD/comments \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "text": "Review booked for Thursday" }'
curl -X POST https://www.liveplanner.app/api/projects/$DOC/threads/$THREAD/resolve -H "Authorization: Bearer $TOKEN"
curl -X POST https://www.liveplanner.app/api/projects/$DOC/threads/$THREAD/reopen -H "Authorization: Bearer $TOKEN"
```

Each write answers `{ "thread": …, "commentId": … }` with the thread as stored (`thread` is `null` once deleting its last comment deleted it). Starting answers `201`. Resolving a resolved thread, or reopening an open one, answers `204`. `PUT …/threads/$THREAD/comments/$COMMENT` edits and `DELETE` on the same path deletes one of your agent's comments. Refusals: `404 thread_not_found`, `comment_not_found` or `item_not_found`; `403 forbidden` for a comment you may not change; `413 comments_full` (200 a thread), `threads_full` (50 a card). See [Cards](/help/plan/cards/#comment-threads) for how threads look in the editor.

## Show What Your Agent Is Doing

An agent at work can appear on a tab with a short **status line** ("Triaging new requests") and a **focus**: the elements it is looking at, such as a board or a sheet.

```bash
liveplanner presence set "Sprint 14" --status "Triaging new requests" --focus 0933
liveplanner presence set "Sprint 14" --tab Flow --status "Reviewing the dashboard" --ttl 120
liveplanner presence clear "Sprint 14"
```

```bash
curl -X PUT https://www.liveplanner.app/api/projects/$DOC/tabs/$TAB/presence \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{ "status": "Triaging new requests", "focus": ["0933"], "ttl": 60000 }'
```

```json
{
  "presence": {
    "tabId": "8bf83102-…",
    "status": "Triaging new requests",
    "focus": ["0933dace-0d37-4520-84bd-104bb636764c"],
    "expiresAt": 1760180060000
  }
}
```

| Field    | Takes                                                                                                                                    |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `status` | Up to 80 characters, no control characters. Leave it out for presence with no status line.                                               |
| `focus`  | Up to 20 elements, by ref, id prefix or id. The answer gives their full ids.                                                             |
| `ttl`    | How long it stays, in **milliseconds** over the API: 1,000 to 120,000, 30,000 when left out. The CLI's `--ttl` is in seconds (1 to 120). |

Setting presence again replaces both the status and the focus. `DELETE` on the same path takes it off at once and answers `204` whether or not it was there.

**You rarely need to keep it alive yourself.** Every changeset your token applies or reverts on a tab keeps its presence there for 30 seconds, so an agent that is busy editing stays visible and one that stops leaves on its own within two minutes at most. A dry run or a refused changeset refreshes nothing.

Refusals name what was wrong: `400` with `status_too_long`, `invalid_status`, `too_many_focus`, `invalid_focus`, `ttl_out_of_range`, `focus_not_found` (listing the refs) or `focus_ambiguous` (listing the candidates); `409 agent_presence_full` when a plan already shows 32 agents; and `503 room_unavailable` when the live room could not be reached, which is worth one retry.

## What People See

Presence shows in the editor as its owner, never as a new person:

- **The status line** appears in the hover card on the owner's avatar, on their row in Collaborators, and in what a screen reader announces. It never shows as text in the tab bar. When the owner is not on that tab, the agent gets an avatar in their name and colour there.
- **The focus** is outlined with a thin ring in the owner's colour. It never locks anything: people keep working on those elements.
- An agent is listed in Collaborators under its tab, but it is not counted as a person or in a session's head count.
- Two of your tokens on one tab show as one avatar, with the status set last. A private plan's presence stack, otherwise hidden, shows while your agent is on it.

[Live Presence](/help/collaboration/live-presence/#agents-at-work) has what this looks like for the people working beside your agent.

## Waiting for People

To answer comments as they arrive, let the CLI wait for the next one rather than polling:

```bash
liveplanner wait "Sprint 14" --for comment --timeout 600
```

It prints the comment and exits, so an agent can read it, reply and wait again. Agents cannot be @mentioned; they read new comments as they arrive or on their next read.
