# Architecture

A pnpm + Turborepo monorepo: seven apps built for Cloudflare, one distributed command-line app and the shared packages. Everything runs on Cloudflare Workers (Static Assets for the Next.js apps); there's no Node-hosted backend.

```
apps/
  marketing/    static landing site (Next.js export, /)
  editor/       the planner: the project editor, hosting the shared Explorer (Next.js export; clean routes)
  help/         help centre (Next.js export + MDX, /help)
  api/          REST + WebSocket worker (Durable Objects, /api)
  mcp/          MCP server for AI tools (OAuth + tools, mcp.liveplanner.app)
  router/       service-binding router stitching the apps under one hostname
  cli/          the liveplanner command line for agents and scripts (Node, one esbuild bundle)
packages/
  ui/             shared UI primitives + chrome icons (Brand, CloseIcon, etc.)
  project/       project data model (Tab, Element types + helpers) over @liveworkspace/model-core
  templates/      template catalogue + pure element builders (editor template starts + MCP)
  template-previews/ per-template preview SVGs (editor template starts + marketing template gallery)
  help-registry/  this product's help-centre articles + categories, bound to @liveworkspace/help-registry's lookups (help app + editor search)
  api-schema/     wire-format DTOs the api worker emits + the live editor consumes
  agent-verbs/    the verbs the CLI routes to: schemas, handlers, compact text, addressing, guides, the skill
  forms/          Form tabs: the form model, answer checks, mapping answers to card fields, starters (pure)
  plan-art/       Plan tab images: Board, Sheet and Dashboard tabs as laid out, plan view and card pictures (pure)
  items/          items and the Plan board: item types, field validation, ranks, writes, board projection
  sheets/         the Sheet engine: A1 addressing, formulas and functions, recalculation, writes, CSV, clipboard (pure)
  edit-operations/ the engine agent changesets run on: edit operations and replace into element ops
  project-views/ read-only text views of a tab (outline, graph, layout, ...) for agents and scripts
  telemetry-client/ this product's telemetry facts (app, preferences key, tokens) bound to @liveworkspace/telemetry-client
  licences/       this product's licence tables (apps, overrides, embedded works) for @liveworkspace/licences' generator
  tailwind-config/ this product's brand ramps (violet) over @liveworkspace/tailwind-config's theme
  (shared with every product, in the monorepo's packages/ as @liveworkspace/*: api-client, api-kit, mcp-kit, cli-kit,
  telemetry-client, render-png, source-ast, style-guards, model-core, page-background, help-registry, tailwind-config, icons, licences, and the oxlint, prettier, vitest, next configs)
docs/specs/          product source of truth, read these before adding features
scripts/        repo-wide dev tooling (next-dev.mjs: shared Next.js dev launcher)
marketing/      off-site copy + media for listings and promotion (see docs/specs/019-marketing/marketing-assets.md)
  copy/         taglines, descriptions, tags, the canonical fact sheet
  media/
    desktop/    desktop product screenshots, captioned
    mobile/     mobile product screenshots, captioned
```

## The editor's shape

The editor route (`apps/editor/app/project/[id]/`) is split three ways so no file becomes a god component:

- `useEditorState.ts` is the orchestration hook: it calls each domain sub-hook, threads their dependencies, and assembles the return view-model.
- `EditorContext.tsx` carries that view-model as `EditorContextValue = ReturnType<typeof useEditorState>`.
- `EditorView.tsx` renders the JSX, leaving `editor-page.tsx` a thin page shell.

`useEditorState.ts` is large by design: what remains in it is wiring, not logic, so it is exempt from the ~400-line soft target ([AGENTS.md](../../AGENTS.md#core-principle-no-god-files-plan-placement-first)). New behaviour goes into its own sub-hook, not into it.

## The shared packages

Each app pulls these in via `workspace:*`:

- **`@liveplanner/project`** owns the project data model: `Tab`, every `Element` type (Shape / Text / Sticky / Image / Freehand / Table / Annotation / Link card / Arrow), defaults, geometry helpers, snap math, layer ordering, the web components' layouts, and the load-time migrations of stored projects (groups, retired element kinds and modes). It also holds the authoring input every non-editor writer shares: raw elements made safe (`normaliseElement`), finished tabs built (`buildTab`), every stored field per element type (`ELEMENT_FIELD_NAMES`) and validation that names the field and rule it fails (`elementValidationIssue`). The single source of what a project IS. What every product's model shares and needs nothing of its element union is **`@liveworkspace/model-core`** (the monorepo's `packages/model-core`): the plain vocabulary (ids, text size, padding, alignment, arrow flows, background patterns), geometry primitives, the stroke points codec, rich-text runs, fonts, border, label and icon sizing, names, small helpers (plurals, string hashing, seeded random) and embeds' URL rules. `@liveplanner/project` re-exports it, so callers import from `@liveplanner/project` as before; it binds the one embed setting that is its own, the host Figma is told.
- **`@liveplanner/api-schema`** owns the wire format between the api worker and the live editor: every request / response shape, plus the response envelopes (`ProjectResponse`, `TabResponse`, ...) the editor and the MCP server both read, the small shared pure helpers it backs (worker-safe `bytesToBase64` / `bytesToBase64Url`, `titleCase` for display-casing preset values across the editor and liveworkspace's telemetry dashboard, and the page-view path normaliser + the editor app's route-segment list, shared by every frontend and the router, [Page view telemetry](../specs/017-telemetry/page-view-telemetry.md)). Adding a field on the server without updating the client used to be routine drift; the typechecker catches it now.
- **`@liveplanner/forms`** owns the form a Form tab holds ([Forms](../specs/030-forms/forms.md)): the model and its sanitiser (`readForm`), answer checks shared by the respondent page and the api (`checkAnswer`, `checkResponse`, `answerErrorMessage`), where an answer goes on a card (`effectiveTarget`, `fieldChoices`), the card a response makes (`responseCard`), the starters and what a form link shows (`publicForm`). Pure, depending on `@liveplanner/items` alone.
- **`@liveplanner/plan-art`** draws a Plan tab as an image ([Plan tabs](../specs/026-plan/plan-tabs.md) "Export"): a Board, Sheet or Dashboard tab laid out as the editor shows it (`planImageOf`), and the still pictures of plan views, metrics and Dashboard cards (`planViewArt`, `cardArt`), with the board widget stats they read. Pure, so the editor's exports and the MCP's previews draw the same image.
- **`@liveplanner/items`** owns items ([Items](../specs/026-plan/items.md)): the `Item` shape, the item-type catalogue, field validation and bounds, fractional ranks, the writes as pure functions (`makeItem`, `applyPatch`, `applyMove`, `applyVote`) and the Plan board's set-up and projection (`projectBoard`). Pure and dependency-free, so the api's item store, the editor's offline store and its optimistic writes, the SVG renderer and the agent verbs apply one set of rules.
- **`@liveplanner/sheets`** owns the Sheet ([Sheet](../specs/029-sheets/sheet.md)): A1 addressing over stable row and column ids, the formula tokenizer, parser and evaluator with its function catalogue, the lazy recalculating `Workbook`, the writes (`applySheetWrite`, `inverseSheetWrite`, `mergeSheetChange`) and the commands that build them, CSV, the clipboard forms and `renderWindow` for drawing. Pure and dependency-free, so the api's sheet store, the editor, the SVG renderer and the agent verbs read and write sheets by one set of rules.
- **`@liveplanner/project-views`** renders a tab as a [project view](../specs/024-agents/project-views.md): `renderView` builds one view model (refs, derived containment, reading order, edges) and answers the outline, `graph`, `layout`, `comments`, `show` or `find` as text and JSON, fitted to a token budget with one closing line naming what it left out; `overviewView` summarises a project from per-tab header facts, and `diffView` compares two reads of a tab for the CLI. Refs, slug ids, kind words and containment themselves live in `@liveplanner/project` (`element-refs.ts`, `containment.ts`), so edit operations and the lint name elements the same way. Pure and deterministic, consumed by the api worker (`?view=`).
- **`@liveplanner/edit-operations`** is the engine an agent changeset runs on ([Edit operations](../specs/024-agents/edit-operations.md)): `parseEditOperations` reads the line form (JSON objects allowed on a line) and `validateEditOperations` the JSON form; `applyEditOperations` applies the twelve operations to a tab, resolving refs and selectors, placing new boxes beside what they name and making room on insert; and `applyReplace` builds a whole tab from a graph, Mermaid, a template or raw elements. Each answers the next tab, its element ops and their inverse, the result lines and the targets it resolved, or named refusals with nothing applied; `formatResultLines`, `formatResultFooter` and `formatRejections` print them. Containment and carrying (`containerContents`) and refs live in `@liveplanner/project`, shared with the views. Pure and deterministic, consumed by the api worker.
- **`@liveplanner/ui`** owns the cross-app UI primitives. The chrome (`Brand`, `SiteHeader`, `SiteFooter`, `SiteSwitcher`), the form + feedback controls (`Button`, `TextInput`, `Select`, `EmptyState`), the hover and focus hints (`Tooltip` for a name, `HoverCard` for a title and description; see [Tooltips, hover cards and popovers](../specs/004-interface-design/tooltips-hover-cards-popovers.md)), the shared behaviour hooks (`useMediaQuery`, `useCopiedFlash`, and the dismiss / focus trio `useClickOutside`, `useEscape`, `useFocusTrap` the editor's dialogs and the public sites' popovers share) plus the popover-clamping helpers. It also holds the public sites' shared plumbing: the site constants (`SITE_URL`, `SITE_NAME`, the `BRAND_ICONS` favicon set, the `PUBLIC_VIEWPORT`), the SEO builders (`pageMetadata` for per-page metadata; `breadcrumbJsonLd` and the `BreadcrumbTrail` it describes are `@liveworkspace/ui`'s, rendered by `JsonLd`), and `PageViewBoot`, the page-view tracker wired to the shared `siteTrack` emitter. Reach for these before re-typing a class list: a control that exists here and is rebuilt in an app is the drift this package was made to stop. The **chrome icons** are `@liveworkspace/ui`'s (`../packages/ui/src/icons/`, re-exported here; this package keeps only its `EDITOR_MODE_ICONS`): named React icons drawn on its `Glyph` base (square viewBox, `currentColor` stroke, round caps, `aria-hidden`) (`CloseIcon`, `TrashIcon`, `ChevronDownIcon`, `SearchIcon`, `LinkIcon`, `SharedDotIcon`, ...) that take `size` / `strokeWidth` / `className` overrides, so a glyph the editor and marketing hero both draw is one path, not a copy per file. These are app-chrome components; the canvas's own icon catalogue (SVG markup strings for canvas elements) is `@liveworkspace/icons`.
- **`@liveworkspace/icons`** (the monorepo's `packages/icons`, shared with every product) owns the three catalogues (the line-art glyphs, the Technology brand marks, and the stickers of [Stickers](../specs/010-palette/stickers.md)) plus pure SVG-markup builders for them, and `xmlEscape`, the one XML escaper every SVG builder in the monorepo shares (`@liveplanner/project` re-exports it). The editor dynamic-imports the data modules through its icon registry so they stay out of its first-load JS; the api + mcp workers static-import `@liveworkspace/icons/resolve` so headless renders (the live image, Explorer thumbnails, MCP inline images) draw the real glyphs.
- **`@liveplanner/templates`** owns the template library: the catalogue (kinds, titles, categories, per-template canvas overrides) and the pure per-template element builders. Two callers: the editor's template starts (which layer its theme recolour on top in `apps/editor/lib/template-builders.ts`) and the mcp worker's `list_templates` / `template` tools ([MCP server](../specs/015-api/mcp-server.md)), so the scaffolds can't drift between them. `buildTemplateTab` makes a finished template tab for the MCP and a changeset's `replace` alike.
- **`@liveplanner/template-previews`** owns the per-template preview illustrations: one static SVG per `TemplateKind`, rendered by the editor's template picker and by the marketing site's template gallery, so a template's card looks the same wherever it is offered and a new kind gets its artwork in one place. What every product's previews share (the hover-story kit `motion`, `story-parts` and `preview-motion.css`, the dark re-lighting `preview-art-tile.css`, the category fan `PreviewFan` and the checks) is `@liveworkspace/template-previews` (`../packages/template-previews`); this package keeps the drawings and binds the fan to them. Its tests (`describeTemplatePreviews`) assert every listed template has a preview, that each drawing stays inside its viewBox, and that every hover story is hidden at rest and uses only the stylesheet's classes.
- **`@liveplanner/help-registry`** owns the help-centre article + category registry: slugs, titles, descriptions, and per-article search keywords. The pure href, grouping and search helpers over it are the monorepo's `@liveworkspace/help-registry`, which every product binds to its own catalogue. Two callers: the help app's browse + search (`apps/help/lib/articles.ts` re-exports it) and the live editor's search-panel Help group (`apps/editor/lib/help-search.ts`), so adding an article once makes it findable in both.
- **`@liveworkspace/help-site`** is the help centre's code, shared by every product: its pages, components, MDX styles, SEO helpers, styles and catalogue checks. `apps/help` binds it to this product in `lib/help-site.tsx` (server) and `lib/help-client.tsx` (the client provider), and keeps its articles, illustrations, card art, header, footer, home layout and page copy.
- **`@liveplanner/licences`** binds this product's tables (its apps, overrides and embedded works) to **`@liveworkspace/licences`** (the monorepo's `packages/licences`, one engine and one pool of texts for every product), which generates the third-party licences page ([Third-party licences](../specs/002-project-scope/third-party-licences.md)). The marketing build runs it after every other app has built: it reads what each Next app ships to the browser from `next experimental-analyze` and what each worker bundles from a `wrangler --dry-run` metafile, collects each package's licence and notice files (with reviewed overrides for packages that ship none, and a reviewed table for what sits inside WASM and fonts), and writes a manifest plus deduplicated plain-text files that `apps/marketing/app/licences` renders. A package with no licence text, an unrecognised licence, a disallowed one or an unreviewed binary fails the build with a named error.
- **`@liveworkspace/source-ast`** parses the repo's own TypeScript for the static guards that read code ([Source scanners](../specs/003-system-architecture/source-scanners.md)): `parseSourceFiles(paths)` opens the files as one in-memory project in TypeScript 7's native compiler (`typescript/unstable/sync`) and returns their syntax trees.
- **`@liveworkspace/oxlint-config`** / **`prettier-config`** / **`vitest-config`** / **`next-config`** / **`tailwind-config`** (the monorepo's `packages/`, shared with every product) own the lint / format / test / Next.js / theme configs so every workspace stays consistent. The shared theme also owns the motion tokens (`duration-micro` / `-short` / `-long`); their numbers and the static motion-budget guard every app runs in its tests are `@liveworkspace/style-guards` ([Motion](../specs/004-interface-design/motion.md)). This product's own **`tailwind-config`** is only its palette: the shared theme, then its brand ramps in violet.

## Tech stack

What's running:

- **Frontend**: Next.js 16 (Turbopack) with `output: 'export'`, React 19, TypeScript 7 (the Go compiler, see [engineering notes](engineering-notes.md#typescript)), Tailwind CSS 4.
- **API**: Cloudflare Workers (vanilla `fetch` handlers, not Hono).
- **Storage**: no D1. Each plan's content and form links are in its own SQLite-backed Durable Object, and each person's workbench in theirs ([API app](../specs/015-api/api.md) "Storage"), reached only via the api worker. A person's settings, name and colour and email address are the liveworkspace accounts Worker's ([liveworkspace/docs/accounts.md](../../../liveworkspace/docs/accounts.md)).
- **Index** ([One Explorer](../../../liveworkspace/docs/one-explorer.md), [its contracts](../../../liveworkspace/docs/one-explorer-contracts.md)): where every plan is filed, who may open it, its sharing, folders, favourites, Trash and Inbox are liveworkspace's index, shared by every liveworkspace app. The editor calls it on its own origin at `/api/index/*`, which the router forwards to liveworkspace.app; access is a short-lived grant the index signs, sent to the api as `X-Index-Grant` and to the room as its `?t=` ticket. `/explorer` renders the shared `@liveworkspace/explorer`, which lists every app's items.
- **Local persistence** (optional per project, [Offline Mode](../specs/006-project/offline-mode.md)): Offline Mode stores a project only in the browser's IndexedDB, never the api. It is opt-in at create time (or by taking a cloud project offline) and dispatched behind the single `apps/editor/lib/api-client.ts` persistence boundary on `isOfflineId(id)`, so the rest of the editor takes the same code path either way. Convertible both directions: Sync Project uploads it to the plan's Durable Object, Take Offline downloads it and deletes the server copy. See [Offline Mode](../specs/006-project/offline-mode.md).
- **Realtime**: Cloudflare Durable Objects, one room per project. Edits sync as granular, id-addressed element ops, so concurrent edits to _different_ elements merge instead of clobbering, and the room stamps each mutation with a per-`epoch` sequence so peers converge and a reconnecting client catches up from a bounded op log (see [Realtime conflict resolution](../specs/012-collaboration/realtime-conflict-resolution.md)). Two people editing the _same_ element at once is last-writer-wins; the advisory, client-only selection lock ([Editor app](../specs/007-editor/editor-app.md)) makes it rare, not impossible. The fields a whole room writes at once (dot votes, answers, ideas, checklist ticks, comments) instead travel as per-change deltas that commute, and the room keeps a small ledger of them which the api merges into each tab save, so a save snapshotted before somebody's answer can't erase it from the store (see [Collaboration race hardening](../specs/012-collaboration/collab-race-hardening.md)). Every server-stored project has a room, personal ones included: agents and API-token scripts change tabs with [changesets](../specs/024-agents/agent-changesets.md), which the api applies, records in the plan's store (`agent_changesets`, with the tab's compare-and-swap revision `tabs.rev`) and relays to the room, and which every editor save re-applies unless that editor has seen it. The whole-tab `PUT` is the editor's autosave alone.
- **Items** ([Items](../specs/026-plan/items.md)): the work Plan boards show lives apart from tabs, in the plan's own `items` table (one row per item: a `type`, an open JSON `fields` bag, a fractional `rank`, a per-project `item_key`, and a `rev`; `projects.items_rev` / `items_next_key` beside it), read and written through `/api/projects/:id/items` and pushed to every open editor as a system `items` room op. The write rules are pure functions in `@liveplanner/items`, applied by the api, by the editor's optimistic updates and by an offline project's store (its record's `items` array), so a write lands the same way everywhere. A Plan board element holds only its set-up and projects the items into columns (`projectBoard`); the SVG renderer draws boards from the same items for exports and thumbnails.
- **Sheets** ([Sheet store](../specs/029-sheets/sheet-store.md)): each Sheet element's cells live apart from tabs, in the plan's own `sheets` (one row per sheet: tab, title, layout JSON, `rev`) and `sheet_cells` (one row per filled cell, keyed by row id and column id) tables, read and written through `/api/projects/:id/sheets` and pushed to every open editor as a system `sheets` room op; selections travel as ephemeral `sheet-presence` ops. The editor keeps each sheet's confirmed state plus its pending writes and recalculates in the browser; the Sheet's grid code and the formula engine load as their own chunk the first time a Sheet is drawn, so a project without one pays nothing.
- **Previews**: a project's Explorer thumbnail, live image and share card are liveworkspace's ([previews.md](../../../liveworkspace/docs/previews.md)), drawn by the plan's object through its export door on request and stored by liveworkspace's media service; liveplanner keeps no bucket and takes no image uploads (see [Project previews](../specs/006-project/project-snapshots.md)).
- **Auth** (optional): sign-in through the liveworkspace accounts Worker (`liveworkspace.app`, OAuth 2.1 authorization code + PKCE), with liveplanner as an OAuth client. The api worker runs the round trip (`/api/auth/*`, refresh token in an HttpOnly cookie), verifies access tokens and liveworkspace guest tokens locally against `${ACCOUNTS_URL}/api/auth/jwks`, and treats every caller as a link visitor when `ACCOUNTS_URL` / `API_RESOURCE` are unset.
- **Email** (optional): the api worker sends transactional email through Cloudflare Email Service (`apps/api/src/email/`, [liveworkspace/docs/email.md](../../../liveworkspace/docs/email.md)) — account-deleted messages and the opt-out new-comment and form notifications. Gated on the `EMAIL` `send_email` binding, with the sender in `EMAIL_FROM` and no API key: no binding, no sends. Addresses come from the liveworkspace accounts Worker, which also sends the onboarding series and the team emails (see [Transactional email](../specs/014-identity/transactional-email.md) and [Account settings & email notifications](../specs/014-identity/profile-and-email-notifications.md)).
- **Inbox** ([Inbox](../specs/013-workspace/inbox.md)): liveworkspace's, one view in the shared Explorer across every app. A plan's Durable Object pushes each changed tab's comment threads and actions to the index from its outbox, on idle and at most once a minute (`apps/api/src/plan-room/plan-outbox.ts`). A row links into the editor with `#t=<tab>&el=<element>`.
- **Explorer Home** ([Explorer Home](../specs/013-workspace/explorer-home.md)): the shared Explorer's Home view (Jump back in, Shared with you recently), read from the index. The editor records an open with the index (`POST /items/:id/open`) when it loads a plan. The Timeline, What Happened and liveplanner's own `/api/home` are gone.
- **Trash** ([Trash](../specs/013-workspace/trash.md)): the index's. A deleted plan stays 30 days in the Trash, restorable, then the index deletes it for good and asks the plan's Durable Object to drop its content. Offline Mode projects keep their own Trash rule in IndexedDB. The MCP server can bin and restore but never purge.
- **API tokens** (optional, [Public API and API tokens](../specs/015-api/public-api-and-tokens.md)): signed-in users mint revocable `lwt_…` tokens (Settings → API Tokens) to call the REST API from their own scripts; `Authorization: Bearer lwt_…` resolves to the owning account via a hashed-token lookup. Signed-in only (like teams), six-month expiry, stored hashed. Absent in pure-guest mode.
- **API description** ([API documentation (OpenAPI)](../specs/015-api/api-documentation.md)): `GET /api/openapi.json` serves a public OpenAPI 3.1 project of the whole `/api/*` surface, assembled (`apps/api/src/openapi/`) from a declarative route manifest plus component schemas generated from `@liveplanner/api-schema` (`pnpm --filter @liveplanner/api gen:openapi`). A drift test pins the manifest to the real dispatch and the committed schemas to the types. The human-facing companion is the help centre's **Developers** category (`apps/help`).
- **Routing edge**: a Cloudflare Worker stitching the apps under one hostname via service bindings.

## Hard constraints

The repo's shape isn't accidental. Three rules keep the stack honest:

- **Static-only frontends.** Next.js apps use `output: 'export'`. No SSR, no Node runtime, no Next.js API routes. Server logic goes in the api worker. Breaking this breaks Cloudflare Pages deploys.
- **Reuse over duplication.** Shared types, UI primitives, configs, and the project data model live in `packages/`, never copy-pasted across apps. If two apps need the same thing, it lives in `packages/` on first occurrence.
- **No secrets in source**, ever; secrets travel via env vars (`.env.local`), `wrangler secret put`, and GitHub Actions repo secrets. See [Secrets policy](../specs/002-project-scope/secrets-policy.md).

## Auth model in one sentence

Every caller is a verified token: a liveworkspace account's access token, or a liveworkspace guest token (a year-long `guest_…` identity fetched once through the accounts site, the same in every app), sent as `Authorization: Bearer`, whose `sub` is the owner id; API tokens and workbench sessions have their own paths, and a share link alone admits a link visitor. The canvas always works without signing in. See [Auth + guest access](../specs/014-identity/auth-and-guest-access.md) for the full model and [API app](../specs/015-api/api.md) for how the api worker resolves the caller and checks the index's grant.

## Deployment

GitHub Actions → Cloudflare Workers. Build artefacts get uploaded once, then marketing / help / api ship in parallel; live and mcp deploy after `api` (both have service bindings to it), and the router deploys last because its service bindings need the others to exist.

Two environments run that same sequence, from one reusable workflow (`deploy-reusable.yml`) so they cannot drift:

|         | Production                   | Staging                                                |
| ------- | ---------------------------- | ------------------------------------------------------ |
| Host    | `liveplanner.app`            | `staging.liveplanner.app`                              |
| Trigger | Manual, after a green CI run | Automatic, on every green CI run on `main`             |
| Workers | `liveplanner-<app>`          | `liveplanner-<app>-staging` (wrangler `[env.staging]`) |
| Data    | Durable Objects              | Its own KV / objects — no production data, ever        |

Staging exists mainly so a schema change runs against real remote storage one deploy before it reaches people's projects. It is public but `noindex` (the router stamps `X-Robots-Tag` when its `DEPLOY_ENV` is `staging`). See [Staging environment](../specs/016-platform/staging-environment.md).

Both environments also get the **hosted profile** (`apps/api/hosted-vars.json`: telemetry on, per-owner image caps), which the workflow adds with `wrangler deploy --var` only in liveplanner.app's own repository and then reads back off the live api worker. Any other deployment (a preview, a deploy from another repository) gets the committed config alone, so it is telemetry-off and uncapped. See [Deployment](../specs/016-platform/deployment.md) "Hosted profile".

See [Deployment](../specs/016-platform/deployment.md) for the deployment contract and its step-by-step.
