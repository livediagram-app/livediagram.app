# Telemetry + public transparency dashboard

First-party, anonymous product analytics, surfaced on a **public** dashboard so anyone can see what we measure. The goal: understand which features get used so we know what works, while staying honest about the product's "no creepy tracking" stance.

**Centralised at liveworkspace (October 2026).** Ingest, storage, retention and the dashboard are no longer liveplanner's own: every liveworkspace app sends its events to one service, `liveworkspace/apps/telemetry`, whose API is `https://liveworkspace.app/api/telemetry` and dashboard `https://liveworkspace.app/telemetry`, which stores them, tagged with the app (`liveplanner.app`), in its own D1 database, and serves one dashboard with an **All apps** view and a filter per app ([liveworkspace telemetry](../../../../liveworkspace/docs/telemetry.md)). liveplanner keeps what is liveplanner's: the closed vocabulary (`packages/api-schema`), the emitters, and its dashboard catalogue (`liveworkspace/apps/site/app/telemetry/liveplanner/`). The old `POST /api/events` and `GET /api/telemetry/summary` routes, the api's `events` table writes and sweep, and `liveworkspace/apps/site/app/telemetry` are gone; the `events` table is left in place, unread (telemetry started fresh centrally, with no history carried over). `/telemetry` on liveplanner.app redirects to the central dashboard filtered to liveplanner. What follows describes the vocabulary and the counting rules, which are unchanged; where it describes the service, the liveworkspace spec is the source of truth.

## Principles

- **Anonymous, aggregate, first-party.** Events carry no user id, no IP, no user-generated content (never a project name, tab name, participant name, element text, share code, or project id). Only a fixed, app-defined vocabulary of enum values is ever stored.
- **No external vendors.** Ingestion, storage (a D1 database) and the dashboard are liveworkspace's own telemetry service, run by us. Nothing is sent to a third party, and data is never sold or shared beyond the public dashboard.
- **Off by default.** A single env var gates the whole system, so any deployment (local development, previews) emits/serves nothing unless it opts in. No committed config turns it on: liveplanner.app's own deploys do, through the hosted profile ([Deployment](../016-platform/deployment.md) "Hosted profile"), which no other deploy applies. This keeps the "no required SaaS calls" rule ([03](../002-project-scope/business-model-and-licence.md)) intact.
- **Transparent.** The dashboard is public (`https://liveworkspace.app/telemetry`, and `/telemetry` here redirects to it), and the privacy policy + landing page say plainly what we capture and why, and link to it.

## Event schema

Every event is three small fields (`packages/api-schema`, shared by emitter + ingest so they can't drift):

```ts
type TelemetryEvent = {
  category: TelemetryCategory; // the "parent": Project | Element | Tab | Theme | Canvas | Template | Comment | Note | Action | Search | UI | Folder | Layer | Session | AI | Team | Participant | Help | Token | Mcp | Cli | Email | Error | Timing
  action: TelemetryAction; // the "verb": Created | Deleted | Shared | Joined | Added | ...
  type?: string | null; // one app-defined reference value: 'Square', 'Edit', 'PNG', a template id, a theme name
};
```

Examples: `{category:'Project', action:'Created'}`, `{category:'Project', action:'Shared', type:'Edit'}` (plus `TabScoped` / `Rescoped` for [Tab-scoped share links](../013-workspace/tab-scoped-share-links.md)), `{category:'Project', action:'Joined', type:'Edit'}`, `{category:'Element', action:'Added', type:'Square'}`.

`category` and `action` validate against closed enums: the ingest endpoint drops any event whose category or action is not in `TELEMETRY_CATEGORIES` / `TELEMETRY_ACTIONS`.

`type` is **not** an enum, and the guarantee on it is a different, weaker one worth stating plainly. Every caller passes an app-defined preset (a shape kind, a share role `Edit`/`View`, an export format, a template id, a theme name) — that is the rule, and it is what keeps UGC out. The endpoint cannot check membership of a set, because there isn't one: a new shape, template or theme would otherwise mean editing `packages/api-schema` every time. What it enforces instead is a **shape bound**, `TELEMETRY_TYPE_PATTERN` (`/^[A-Za-z0-9 ._-]{1,40}$/`): a short token of safe characters, which rejects anything that reads as free text and caps what a misusing caller could get onto the public dashboard.

So the safety property is: callers only ever send presets, and the pattern is defence-in-depth behind that, not a substitute for it. A short alphanumeric string that happens to be user content would pass the pattern, which is precisely why the calling rule is the thing that matters.

In practice a `type` is either a literal or derived from a closed vocabulary — an element kind through `titleCaseType`, an export format through a lookup table, a boolean through a ternary of two fixed strings. The case that proves the rule is the theme name: a **custom** theme is named by the user, so `themeTelemetryLabel` maps every custom id to the literal `'Custom'` and only ever emits the built-in themes by name. That is the shape any new `type` source should take — map user-owned values onto a fixed token before they reach `track`, rather than relying on the pattern to catch them.

## Storage (existing D1)

Events are stored by liveworkspace's telemetry service in **its own** D1 database (`liveworkspace-telemetry`), one `events` table with an `app` column, so each row says which app sent it ([liveworkspace telemetry](../../../../liveworkspace/docs/telemetry.md) "Storage"). No owner or IP column: rows are anonymous by construction.

liveplanner's own `DB` has no telemetry table: events are stored only by liveworkspace.

## Retention

The central service keeps 60 days (twice the dashboard's longest window, Last 30 days, so each window can be compared with the one before it) and sweeps older rows daily. liveplanner's api no longer runs an events sweep.

## API

The ingest (`POST https://liveworkspace.app/api/telemetry/events`, body `{ app: 'liveplanner.app', events: TelemetryEvent[] }`) and the summary (`GET https://liveworkspace.app/api/telemetry/summary?app=liveplanner.app`, or every app) are the central service's, specified in [liveworkspace telemetry](../../../../liveworkspace/docs/telemetry.md). The ingest validates each batch against **this app's** closed vocabulary (`isValidTelemetryEvent` in `@liveplanner/api-schema`) and drops this app's server-emitted pairs from browser batches (`SERVER_EMITTED_EVENT_PAIRS`). The summary's windows are the same fixed UTC days as before (`TELEMETRY_WINDOW_DAYS`, now in `@liveworkspace/telemetry` and re-exported from `@liveplanner/api-schema`), and it adds each app's share of every window and day (`byApp`).

## On/off env var

Browser builds read `NEXT_PUBLIC_TELEMETRY_ENABLED` (baked at build; liveplanner.app's deploys set it through the hosted profile, `apps/api/hosted-vars.json`) and send nothing when it is off, and `NEXT_PUBLIC_TELEMETRY_URL` names the service (unset is production's; staging's comes from the hosted profile; locally `http://localhost:8790/api/telemetry`). The api and mcp workers send their own events only with `TELEMETRY_ENABLED = "true"` **and** liveplanner's Worker key, `TELEMETRY_KEY` (a secret, the same value on both workers and as the service's `TELEMETRY_KEY_LIVEPLANNER`), at `TELEMETRY_URL` (hosted profile per environment; unset is production's). The service's own `TELEMETRY_ENABLED` decides whether anything is stored at all. On top of these, each user has a per-device opt-out flag stored alongside the other user preferences ([User preferences](../007-editor/user-preferences.md), `telemetryEnabled`, default true). When that flag is false, `track()` is a no-op for that browser; this is the user-facing lever the landing page and the dashboard reference when they say "first-party, no creepy tracking".

## Abuse controls

The central ingest is public and unauthenticated by design, and its guards are the service's ([liveworkspace telemetry](../../../../liveworkspace/docs/telemetry.md) "Abuse controls"): this app's **closed vocabulary** and a 100-event batch cap, an **Origin check** (a browser batch naming `liveplanner.app` must come from one of liveplanner's own origins, so another site can't post in its name), a **per-network rate limit** on browser batches (the IP is a transient key, never stored), and **liveplanner's Worker key** for posts from our Workers, which send no Origin. The CLI's counts (`Cli·Used`) are sent from people's machines, with neither an Origin nor a key, so they go through the relay below.

### The relay

The CLI runs on somebody's machine, has no page origin and holds no key, and it posts to its profile's api. So the api keeps **`POST /api/events`** as a thin relay: body `{ events }`, validated against the vocabulary, server-emitted pairs dropped, capped at 100, then passed on to the service under the api's key. Always 204. It keeps the old guards (a same-origin filter, the per-IP `EVENTS_RATE_LIMITER`, 120 batches/60s, the IP a transient key never stored or passed on) and stays exempt from the project write limiter. Nothing in the browser uses it.

## Emitting

A `track(category, action, type?)` helper buffers events and flushes them batched on an interval and on `visibilitychange`/unload via `navigator.sendBeacon`. Fire-and-forget; failures are swallowed (telemetry must never affect the host app). The buffering engine is the shared `@liveplanner/telemetry-client`, which posts each batch to the central service as `text/plain` JSON (a cross-site request with no preflight and no cookies), wrapped with the policy (the `NEXT_PUBLIC_TELEMETRY_ENABLED` build gate + the [User preferences](../007-editor/user-preferences.md) opt-out): the editor builds its own emitter, and the public sites (help, marketing) share one, `siteTrack`, so their policy can't drift. **An opt-out made in the editor silences the help centre too**, since both sit on the liveplanner.app origin and read the same localStorage preferences blob. How each reads it is app-owned (the editor caches behind its preference-change events, the help centre reads straight through), but _where_ it reads and _which way it defaults_ are not: `USER_PREFERENCES_STORAGE_KEY` and `telemetryOptInFromRaw` live in `@liveplanner/telemetry-client` so a key rename in one app can't leave the other quietly emitting for a user who opted out. Six surfaces emit: the **editor** (`apps/editor`), the **help centre** (`apps/help`, the `Help` category), the **marketing site** (`apps/marketing`: page views only, see below), the **MCP worker** (`apps/mcp`, the `Mcp` category), and the **api worker itself** (server-side self-reports, posted with its Worker key: `Error·Api·Internal.<Method>.<Route>` for an unhandled server exception, the whole `Email` category, which has no browser to emit from, and the counts only the server can make once each: `Session·SignedUp`, `Session·SignedIn`, `Project·Joined` and `Project·Used·Multiplayer` (the project room, once per multiplayer session), see below). Those server-owned pairs are listed in `SERVER_EMITTED_EVENT_PAIRS` (`@liveplanner/api-schema`) and **dropped from browser batches by the central ingest**, so a stale cached editor bundle that still emits one (or anyone posting by hand) cannot double count what the worker records; the editor's coverage test also fails if an editor call site emits one. Server-side emits share one helper (`apps/api/src/server-telemetry.ts`, `reportServerEvent`), gated on `TELEMETRY_ENABLED` and `TELEMETRY_KEY`; they are anonymous counts like every other row, and the per-browser opt-out cannot reach them because no browser is involved. All five frontends also report `Page·View·<path>` on each path change ([Page view telemetry](page-view-telemetry.md)), and for marketing that is its only event. (The landing funnel, [Landing funnel](../019-marketing/landing-funnel.md), keeps it that way: a CTA's link carries which button it was, and the editor reports the `Cta` events.) This replaced an earlier rule that the marketing site never emits: a page count sent first-party to our own telemetry service, anonymous, cookie-free and honouring the same opt-out is within this spec's principles, and the marketing "0 third-party trackers" claim stays literally true. Call sites are one-liners, e.g. `track('Element', 'Added', 'Square')`.

The aim is to cover every meaningful interaction a person has with a project (discrete feature actions, never continuous gestures like drag/resize/pan/zoom or raw colour tweaks, which would just be noise). Current taxonomy:

A session is a run of continuous occupancy: it ends only when the room empties, so a peer who refreshes or reconnects while a colleague is still in keeps the same session, and a room that empties and fills again later is a new one. The "already counted" mark rides on each socket's attachment, so it survives hibernation and disappears with the last socket. It used to be a client emit fired when each tab's presence list first held a peer, so every participant reported the same session: a five-person retro counted 5. ## Counting rules: one event per gesture, or one per object?

Audited in full for issue #30, because "is this number the thing I think it is?" was unanswerable from the taxonomy alone. The rule, now stated rather than assumed:

**An event counts the GESTURE, not the objects the gesture touched.** Deleting a twelve-element marquee selection is one `Element·Deleted`; restyling it is one `Element·Changed`. This is deliberate — the question these answer is "how often do people delete / restyle", and a per-object count would let one marquee drag swamp a hundred single deletes. No `track()` call in the codebase sits inside a loop, so this holds uniformly.

**The one exception is creation, because creation feeds a census.** `Element·Added·<kind>` is what the dashboard's Palette ranking is built from, so it has to be a true count of elements created, not of creation gestures. Every from-scratch path already emitted one per element (you can only draw one at a time). The **copy** paths did not: duplicate, paste, and shift-drag emitted a single untyped `Element·Duplicated` and no `Added` at all, so an element born by copying was invisible to the census — under-counting precisely the shapes people liked enough to reuse. All five copy paths now go through `trackDuplicated`, which emits one `Duplicated` for the gesture **and** one `Added·<kind>` per element created. `elementTelemetryType` is the single mapper from an element to its token, so a copied code block lands in the same bucket as a drawn one.

Two related fixes from the same audit:

- Copy paths emitted **before** their own guards, so a duplicate that never happened still logged one (a multi-selection holding nothing copyable). They now emit after the copies exist, and an empty result emits nothing.
- `Element·Rotated` was in the enum and documented here as firing at rotate-gesture start. There is no rotate gesture — rotation is a context-menu control that emits `Element·Changed·Rotation` — so the action was dead. Removed from the enum.

**An event counts what the SERVER accepted, not what the user clicked.** Every list action in the Explorer and the team library is optimistic ([Folders](../013-workspace/folders.md), [Team shared projects](../013-workspace/team-shared-projects.md)): the row updates locally so the UI feels instant, the request goes out, and a failure rolls the row back and usually toasts. The emits sat beside the request rather than inside its resolution, so a rename the server refused was reverted on screen, reported to the user as a failure, and still counted as a rename. Two spellings caused it — `void apiThing(…).catch(() => {}); track(…)`, and `await apiThing(…).catch(() => {}); track(…)`, the second reading as "ignore the failure" while actually meaning "treat every failure as success", since the next statement runs either way. Fifteen sites across `useProjectListActions`, `useExplorerMoves`, `useTeamLibrary`, `useFolders` and `useProjectActions` now emit from the success path. (Those list actions are the shared Explorer's now; the editor's lib/accepted.ts helper went with them.)

Two things deliberately still emit on the optimistic path, because for them the local action IS the fact: `Element·Copied` (the in-app buffer is the authoritative clipboard — the OS write is a best-effort extra that can fail on permissions without changing what a paste will do), and `Project·Duplicated` in a team library (the copy exists by then; only the follow-up filing into the team folder can fail).

Also `.then()` before `.catch()`, not after. Chained the other way round — `p.catch(() => {}).then(f)` — the success handler runs after a swallowed rejection too, which is harmless for a follow-up refresh and wrong for anything that counts.

**Deliberate double-emits** (so nobody reads them as double-counting): starting a private vote emits both `Tab·Started·Vote` and `Tab·Started·PrivateVote`, the first being the true vote count and the second a flag on that subset. Completing the `/new` wizard emits `Project·Created` + `Theme·Changed` + `Template·Used`, which are three genuinely different facts. Filing a tab into a folder name the project has not used before emits `Folder·Created·Tab` + `Tab·Moved·Folder`, also two different facts — the folder now exists, and this tab is in it — because reporting only the creation made "tabs filed into folders" undercount by exactly the number of folders anyone created.

## How completeness is tested

Telemetry drifts silently and there is no runtime signal when it does: emitting is fire-and-forget, and the public dashboard only ever renders what **arrived**, so a renamed or deleted event is indistinguishable from a feature nobody used. Two checked-in guards replace that missing signal.

- **`apps/editor/lib/telemetry-manifest.ts` pins every `category·action` pair the editor emits**, enforced by `telemetry-coverage.test.ts`, which scans the source for `track()` call sites (ternary actions included) and diffs against the manifest. Adding, renaming, or removing an emitted pair fails CI until the manifest is updated — and the manifest's comment sends you here, so the taxonomy above gets updated in the same change. The same test asserts every pair is inside the closed enums, since an event outside them is silently dropped by the ingest validator.
- **`PALETTE_TELEMETRY_TYPES` in `@liveplanner/api-schema` is the one definition of the palette `type` tokens**, consumed by the dashboard's Palette view instead of the hand-mirrored copy it used to keep. `palette-telemetry-coverage.test.ts` asserts every shape kind in `@liveplanner/project` has a bucket there, **and every non-shape element kind too** — that second half was missing, and so was `Video`: all six embed tiles create a `video` element, so from the day embeds shipped their adds were counted nowhere. The copy had already drifted: the dashboard expected `Code-block` long after the editor settled on `CodeBlock`, so every code block anyone drew was emitted, validated, stored, and missing from the ranking.
  That test must derive its tokens by CALLING `elementTelemetryType`, never by restating its rule. It did restate it once, and the copy drifted the same way the dashboard's had: it spelled out seven camel-case tokens where the editor spelled three, so the session button and the comment pin, among others, reported `Session-button` and friends on Added while the test proved the catalogue held `SessionButton`. Those features counted zero, and every assertion passed. A copy of the rule can only prove the copy agrees.

Pairs are pinned but `type` values generally are not — types are open-ended by design (a shape kind, a template id, an article slug) and pinning them all would fail on every new shape. The palette tokens are the exception because that is where drift is both invisible and costly.

## Delivery losses, and the two that were worth fixing

Emitting is fire-and-forget, so a dropped batch is invisible by construction. Audited alongside the coverage work; the losses split into ones we accept and ones we didn't.

**Fixed — a failed flush is now retried once.** The buffer used to be cleared before the request went out, with the result swallowed, so any network failure discarded that batch permanently. The problem wasn't the volume so much as the _distribution_: the losses concentrated in flaky-network and close-the-tab-quickly sessions, which biases the data rather than just thinning it. A rejected `fetch` now re-queues its events at the front of the next batch and gets exactly one more attempt.

The bounds matter more than the retry:

- **Only on a rejection**, never on a non-2xx. A rejection means the request got no response, so the events almost certainly didn't land. A server that _answered_ may well have stored them, and re-sending would double-count — while retrying a 429 would worsen the thing it's complaining about.
- **Exactly one attempt.** A retry trades a small over-count risk (request arrived, response lost) against a systematic under-count; that trade is worth making once. An endlessly retried batch on a dead network would grow the buffer, duplicate on every recovery, and still die at unload.
- **Bounded by the same 25-event cap**, oldest dropped first — the retried events have already had their chance.
- **Never on the beacon path.** We're unloading; there is no later.
- A failure **arms a fresh timer**, so the retry happens on its own rather than waiting for the next tracked event.

**Fixed — `sendBeacon`'s return value is no longer ignored.** It returns `false` when the UA's queue is full, and that batch was simply gone, at exactly the moment it mattered (page-hide, the tail of a session). It now falls through to the `keepalive` fetch, which is the same "outlive the page" guarantee by another route.

**Fixed — internal callers no longer share one rate-limit bucket.** Our own workers used to reach `/api/events` over a service binding with no `CF-Connecting-IP`, so they shared one anonymous 120/min key and the overflow vanished. Centrally, a Worker post carries liveplanner's Worker key and skips the browser rate limit altogether.

**Still accepted:** client errors, and the editor's api errors, cap at 10 per kind per page load (an error loop must not flood the pipeline, and the dashboard reads presence and order of magnitude, not exact storm size); events buffered when a tab is hard-killed are gone (nothing is persisted, deliberately: telemetry must not own storage); and a second consecutive failure discards the batch, per the one-retry bound above. All of these under-count rather than over-count, which is the safer direction for a usage chart.

Extend by adding to the `TELEMETRY_CATEGORIES` / `TELEMETRY_ACTIONS` enums (if needed) + a one-line `track()` call at the interaction's handler. Page hits are deliberately not wired; new-visitor counting goes through `Participant`/Created above.

**Every metric says what someone did, in plain words.** Each card, and each metric charted in Search, carries one sentence explaining the event for a reader who has never seen the code: what the person did, in the product's own visible words (the button, panel or menu as the UI names it), where when that helps, and the counting rule when it is not simply once per action ("Counted once per burst of presses"). Never a spec number, a code name (`FillColor`), infrastructure or vendor jargon, or the old "One occurrence of Changed · Session Button" filler. The sentences live as data in `../liveworkspace/apps/site/app/telemetry/liveplanner/event-explanations.ts` (an exact one per category·action·type, plus one per category·action that fits any type), and `event-explanation.ts` looks them up, with patterns for types computed at runtime: a help article reads by its title (the API Tokens help article), an `Error·Api` code as what was being tried and why it failed (`Http403.SaveTab` is "Saving a tab's contents was refused because the visitor didn't have permission"), an element kind or import format with the right article. `event-explanation.test.ts` fails if any event the code can send falls through to the last resort, if a described action has no any-type sentence, or if a sentence carries jargon or a code name. A curated card's own `blurb` still overrides the event's sentence, and answers to the same test. Type names read as words everywhere they are shown (rankings, the Search breadcrumb and box): `SessionButton` is Session Button, `AiOn` is AI On, an article slug is its title; a page path or an error code stays exactly as recorded.

**Every card must count an event something actually sends.** Two failure modes, both seen in production. **A card that counts the bare event must have no typed emitter.** A metric card with `type: null` counts only events sent with no type, so the moment an emitter starts typing that `category·action` the card silently drops every one of them. `Project·Created` read 0 on the Dashboard and Content from July to September 2026 while ~150 projects a month were created, because the New Project wizard had started sending `Cloud` / `Offline` ([Offline Mode](../006-project/offline-mode.md)); `Layer·Opened·Panel`, `Project·Duplicated·Copy` and team-library `Folder·Created/Moved·Team` were missed the same way. A card that means "all of them" says `allTypes` (or `typeIn` to exclude a subset kept on its own card, as Folders Created does with tab folders), and `../liveworkspace/apps/site/app/telemetry/liveplanner/metric-emitters.test.ts` fails if any untyped card has an emitter anywhere in the repo that can send a type. **A card with a specific type must have an emitter that can send exactly that category·action·type**: "AI Turned On" read `UI·Toggled·AiOn` while the Settings row sends `AI·Toggled·AiOn`, so it counted nothing. The same test checks every typed card, and every type a ranking hard-codes (Selection Modes, the Canvas Styles and Themes exclusions and alias targets, the Exceptions recovery types). It reads emitters with the TypeScript parser (`emitter-scan.ts`), not a regex, so it sees every form the repo uses: literal `track` / `siteTrack` (the public sites' shared tracker) / `report(env, ...)` / `reportServerEvent(env, ...)` / `postTelemetry(env, ...)` calls, ternaries in any argument (`track('Tab', x ? 'Moved' : 'Removed', 'Folder')`), `const` values and lookup tables in the same file, forwarding helpers (resolved per call site, so a helper's category, action and type stay correlated), a callback's parameters through the calls the function it is handed to makes (the help centre's vote tally), a returned closure's parameters through the calls made on the variable holding it, in any file (the debounced canvas telemetry), the api worker's own `insertTelemetryEvents` rows, and the Settings catalogue rows (`event: { category, on, off }` / `changed`) that `SettingsCategoryPane` emits generically. What the scan cannot resolve is a **computed** type (a theme label, an email template kind), and every computed emit site must declare the values it can send in `../liveworkspace/apps/site/app/telemetry/liveplanner/computed-emitters.ts`, keyed by `<path> <Category>·<Action>`: read from the source that defines them where the set is closed and written down (the api's `EmailKind` union, the MCP server's registered tools, the tours' step ids), or representative samples with the reason where it is open (an article slug, a page path, a status code). Every check here then reads those values as if they were literals. The test fails on a computed site with no entry, an entry for a site that no longer exists, or a declared value that no chart counts; it used to accept any chart on the site's category·action, which is how . An emit site whose category or action is itself a variable must be named in `DYNAMIC_EMITTERS` with the reason.

- **Health › Exceptions** (first in Health): error health. Five headline cards with 30-day trends via the shared `MetricGroups` renderer, then rankings. **Failed Requests** is every `Error·Api` failure a caller saw (the editor's `Http<status>.<Action>` and `Network.<Method>.<Route>`, the MCP worker's `Http<status>.<Tool>` / `Internal.<Tool>`, failed email sends). **Server Crashes** is the api worker's own `Internal.<Method>.<Route>` report, on its own card because one crash is reported twice (the worker's `Internal` plus the `Http500` its caller saw), so summing `Error·Api` double counted it; the two cards are read side by side, never added. **Client Exceptions** is `Error·Client` minus recovery events, and **Realtime Resyncs** (`Error·Client·RealtimeResync`, the editor refetching after the room says it missed updates) is shown separately because it is a recovery, not a crash. **Stale Build Reloads** (`Error·Client·StaleChunkReload`, a tab from an earlier build loading the page in full when a removed code chunk failed to load, [Stale builds](../016-platform/stale-builds.md)) is a recovery too, shown separately; the failure itself stays a client exception. The predicates read the kind as the first dot-part, so the bare pre-#112 types (`Http500`, `Internal`, `Uncaught`) land in the same cards as the located ones; a bare `Internal` counts as a server crash, the api worker having been its main source, and an MCP `Internal.<Tool>` (second part a tool, not an HTTP method) as a failed request. Counts are generic by construction (the closed vocabulary above); an empty view is the goal state. The **Load Recovery** stack follows the rankings.
- **Health › Timings**: how fast the experience is ([Timing telemetry](timing-telemetry.md)): a card per editor timing (Project Load, Tab Switch, Save, Live Connect, Live Reconnect) with its estimated p75, p50 and p95 and the window's bucket bars, then a Core Web Vitals card per app rating LCP, INP and CLS against Google's thresholds.
- **Search** — find one specific metric two ways: **type** a query for flat token matches, or **browse** the hierarchy (category → action → type) one level at a time, for when you can't name what you want. Selecting a metric **visualises it underneath** as its own 30-day trend line (from `daily.byMetric`, with the selected window highlighted) plus its Today / Last 7 days / Last 30 days totals.

**Every count carries a trend arrow.** Beside the number on every metric card, stack head and ranking row sits a badge saying which way it moved against the same number of days just before the window (today against yesterday, the last 7 days against the 7 before, the last 30 against the 30 before): ▲ / ▼ with the change as a percentage (a plain difference when there was nothing before to be a percentage of; under half a percent reads <1%), or → flat. **Green is good news, red is bad, yellow is neutral**: each chart declares whether rising is `good` (the default: most counts are usage), `bad` (errors, Failed Requests / Server Crashes / Client Exceptions / Realtime Resyncs and the Exceptions stack, Accounts Deleted and its email, Marked Not Helpful, Fell Back to Classical), or `neutral` (could read either way: Sign-Outs, Tokens Revoked, the Deleted charts, Invites Declined, Timers Paused / Reset, Dots Retracted, Votes Discarded, the win-back / activation / token-expiry emails, and stacks that mix both kinds, Account Activity, API Token Activity, Emails Sent); a flat count is yellow too. The earlier counts come from the summary's `previousWindows` (see API); against an older api without them, cards and stacks fall back to what the 30-day series can reach (no arrow behind the last 30 days) and rankings show none. Hovering the badge gives the earlier count.

**Every event has a chart.** The Dashboard and its Detail tabs chart every event the repo can send: `metric-emitters.test.ts` reads every emitter (the same TypeScript scan as the card checks below) and fails if one has no chart on any tab, so a new event lands in a stack, usually as a member of an existing one. Its allowlist (empty today) names any the scan misreads, with the reason. Charts live in `../liveworkspace/apps/site/app/telemetry/liveplanner/catalogue/<area>.ts` (visitors, content, features, collaboration, settings, connections, health, email), one module per Dashboard area, re-exported from `metric-catalogue.ts`; a stack references charts by name, so one chart can sit in several stacks. Events stored under an old spelling no emitter sends any more (`Element·Grouped` since groups became web components, `SignInBanner` before the banner recorded its surface) have no chart and age out with retention; Search still reaches them.

**No event is counted by two unrelated charts.** One event matched by two different charts is how the dashboard double counts: Tabs Cleared once caught every discarded vote (`Tab·Cleared·Vote`), Share Links Copied caught team invite copies, Panels Docked caught slide reorders. `metric-emitters.test.ts` checks every event an emitter can send against every chart and allows exactly two kinds of overlap: a Settings Changed category chart rolling up the setting charts in it, and, inside one stack, a chart and its subset where the headline counts only one of them (Actions Assigned over Actions Emailed, Returning Visitors over its guest / signed-in split, Projects Created over Created in This Browser). The computed sites' declared values are checked too. A stack's combined head line sums the same members as its number, so the two always agree.

**Ranking cards keep their own height.** A ranking's length follows the data (Tools can run thirty rows, Devices three), and in a grid every row grows to its tallest card, stretching short ones into mostly-empty boxes. So every tab's rankings (Pages, Palette, Look & Feel, Help, Exceptions) sit in `CardColumns`: two independent columns, filled biggest card first into whichever column is shorter so far (a card's size estimated from its row count, an empty one as its placeholder panel), one column below `lg`. CSS `columns` was tried first and dropped, because it fills in source order and piled a long card onto an already-long column. Metric cards stay in an even grid on purpose: they are near-equal height, and stretching pins every trend line to the same baseline.

Charts render in inline SVG (a line with a shaded selected-window span and a dashed average reference line); no charting library, no extra request. Event names display in Title Case (preserving acronyms like PNG/JSON). Explains in-page that the data is anonymous, first-party, no vendors. Degrades to an "analytics not enabled" state when the summary returns `enabled: false`.

## Routing & deploy

- **Router** ([08](../016-platform/router-app.md)): `/telemetry` and everything under it answer `301` to the central dashboard with `?app=liveplanner.app` (`TELEMETRY_DASHBOARD_URL` names staging's and local dev's).
- **Deploy** ([10](../016-platform/deployment.md)): nothing of telemetry deploys from here. The api and mcp deploys sync `TELEMETRY_KEY` from one GitHub secret (`TELEMETRY_KEY`, staging `TELEMETRY_KEY_STAGING`); the central service deploys from liveworkspace.

## Provisioning (one-time, owner only)

1. In liveworkspace, provision the telemetry service and give it liveplanner's key as `TELEMETRY_KEY_LIVEPLANNER` ([liveworkspace telemetry](../../../../liveworkspace/docs/telemetry.md) "Provisioning").
2. Set the same value as the `TELEMETRY_KEY` GitHub secret (and `TELEMETRY_KEY_STAGING` for staging); the deploy puts it on the api and mcp workers.
3. Turn telemetry on: liveplanner.app's deploys do it through the hosted profile. Another deployment sets `TELEMETRY_ENABLED = "true"` in `apps/api/wrangler.toml [vars]` and `NEXT_PUBLIC_TELEMETRY_ENABLED=true` for the live, help and marketing builds. Leaving them unset keeps telemetry off — the committed default.

## Privacy posture

The privacy policy + landing page state: we record anonymous, first-party product events (the three-field schema, examples), to learn which features help; no external analytics vendors; data is never sold or shared beyond the public dashboard (liveworkspace's, `https://liveworkspace.app/telemetry`), and events go to liveworkspace's own telemetry service, not a vendor. This is consistent with the existing "no tracking pixels / no third-party analytics" claims — those remain true (first-party, anonymous, no third parties, no ad tracking).
