# API app

The HTTP + WebSocket layer the live editor calls for project persistence and realtime collab.

- **Workspace:** `apps/api` (`@liveplanner/api`).
- **Worker name:** `liveplanner-api`.
- **Mount:** routed from the [router worker](../016-platform/router-app.md) at `/api/*`. The router forwards the request as-is — the api worker sees the full `/api/...` path.

## Why this exists

The first prototype phase ([spec 02](../005-project-roadmap/prototype-scope.md)) ran entirely client-side with `localStorage` persistence. Once realtime collaboration entered scope, server state became necessary: a Durable Object per project holds the in-room participant list, orders and relays ops between connected clients and keeps the collaboration state that must outlive a socket, and holds the plan's content in its own SQLite. The editor app no longer reads or writes `localStorage` for projects — `apps/editor/lib/api-client.ts` is the single boundary.

## Tech

- **Runtime:** Cloudflare Workers.
- **DB:** Cloudflare D1 (binding `DB`) for what is liveplanner's own and not a plan's content: tokens, form links, workbench pairings and sessions. A person's settings, name and colour, sign-in sighting and email address are the liveworkspace accounts Worker's ([liveworkspace/docs/accounts.md](../../../../liveworkspace/docs/accounts.md)), read through its internal API as `liveplanner.app`. Schema lives in `apps/api/migrations/`.
- **Index:** where every plan is, who may open it, its sharing, folders, tags, favourites, Trash and Inbox are liveworkspace's index ([one-explorer.md](../../../../liveworkspace/docs/one-explorer.md), [one-explorer-contracts.md](../../../../liveworkspace/docs/one-explorer-contracts.md)). The api reaches it at `INDEX_ORIGIN` (`apps/api/src/index-service.ts`).
- **Plans:** one SQLite-backed Durable Object per plan (`PlanRoom`, binding `PLAN_ROOM`, `new_sqlite_classes`), named by the plan's id via `idFromName`. It holds the plan's content and is its realtime room (see **Storage** and **Realtime model**).

## Wire-format types

The DTO shapes the api worker emits + the live editor consumes live in `packages/api-schema` (`@liveplanner/api-schema`) — `Project`, `TabSummary`, `TabRecord`, `Folder`, `ShareLink`, `ServerMessage` / `ClientMessage`, and the room op vocabulary (`RoomOp` / `RoomOutgoing` / `RoomIncoming`). Both apps import them; the api worker also re-exports under historical `XxxDTO` aliases (`apps/api/src/types.ts`) for backward compatibility with its existing call sites.

Defining the wire shapes once means server and client cannot drift — adding a field on one side without updating the other is a typechecker error. **Do not redefine these types inline in `apps/api/` or `apps/editor/`**; extend the schema package instead. Per AGENTS.md the reuse-over-duplication rule is non-negotiable.

## Auth

The api resolves who is calling through three identities, in this order of preference (see [Auth + guest access](../014-identity/auth-and-guest-access.md) and [Public API and API tokens](public-api-and-tokens.md)):

1. **A person's token** — `Authorization: Bearer <jwt>`, minted by the liveworkspace accounts Worker: an account's access token ([Auth + guest access → Signing in](../014-identity/auth-and-guest-access.md#signing-in)) or a guest's token (`kind: "guest"`, `sub: guest_<uuid>`, [Auth + guest access → Guests](../014-identity/auth-and-guest-access.md#guests)). Verified locally in `apps/api/src/auth/accounts.ts` (`getPersonIdentity`, via `@liveworkspace/auth-client`'s `createVerifier`) against `${ACCOUNTS_URL}/api/auth/jwks`, with issuer `${ACCOUNTS_URL}/api/auth` and audience `API_RESOURCE`, so a token minted for another liveworkspace app is refused here. No call to the accounts Worker per request; the key set is cached per isolate. The `sub` claim is the owner id; an account's `email` is trusted only when `email_verified` is true, and its `teams` claim lists its teams. Returns null on any failure (invalid signature, expired, wrong audience, malformed, `ACCOUNTS_URL` / `API_RESOURCE` unset), logged as `[auth] access_token_rejected`, never 401: the request goes on as a link visitor's. A bearer shaped as an API token (`lwt_…`) or a workbench session (`lvw_…`) is never handed to the verifier; the paths below resolve it.
2. **API token** — `Authorization: Bearer lwt_…`, consulted only when no person's token verified. `resolveApiToken` hashes it and looks up a live (non-revoked, non-expired) `api_tokens` row ([Public API and API tokens](public-api-and-tokens.md)); the owner id is that row's account, so a token request flows through the same checks as a signed-in one. A token minted **read-only** is refused on every `POST` / `PUT` / `DELETE` with `403 read_only_token`, at one choke point in `index.ts`.
3. **Workbench session** — `Authorization: Bearer lvw_…`, consulted only when neither of the above resolved ([Workbench embeds](../013-workspace/workbench-embeds.md)). `resolveWorkbenchSession` hashes it and looks up a live `workbench_sessions` row of a live token; an unknown, expired or revoked one is refused `401 invalid_session`. `workbenchRefusal` confines it before any route runs, by its scope: a project session answers another project `404`, any route outside `WORKBENCH_ROUTES` `403 workbench_confined`, and an `X-Share-Code` or `X-Share-Password` beside it `403 workbench_confined`; a workspace session reaches the Explorer's routes (`WORKSPACE_ROUTES`), never the account's. A view session's write is `403 workbench_read_only`.

No Bearer at all is a **link visitor**: someone holding only a share code. There is no guest header: `X-Owner-Id`, `X-Owner-Sig`, `POST /api/guest-id` and `POST /api/migrate` are gone with the self-minted guest id.

`ACCOUNTS_URL`, `API_RESOURCE`, `ACCOUNTS_CLIENT_ID` and `ACCOUNTS_CLIENT_SECRET` are **worker secrets** (`wrangler secret put`, synced from GitHub repo secrets on deploy), not `[vars]` entries — only the client secret is sensitive, but keeping every out-of-band value in one mechanism is simpler than reasoning about which ones are safe in the open ([Secrets policy](../002-project-scope/secrets-policy.md)). Leaving `ACCOUNTS_URL` or `API_RESOURCE` unset leaves every caller a link visitor — useful for local dev or for environments without an accounts client yet. The sign-in round trip itself (`/api/auth/sign-in`, `/callback`, `/token`, `/sign-out`) and the guest handoff (`/api/auth/guest`) live in `apps/api/src/routes/auth.ts`.

### Access

Who may open a plan, and at what level (`view` < `participate` < `edit`, and a tab when a link opens only one), is the index's to say, in a **grant**: a ten-minute ES256 JWT naming the person (or `link:<code>`), the plan, the level and the tab ([one-explorer-contracts.md](../../../../liveworkspace/docs/one-explorer-contracts.md) "Grants"). The owner and every joined member of the plan's team get `edit`; anyone else needs a live share link.

- **The editor fetches its own** (`POST /api/index/items/:id/grant`, through the router, `apps/editor/lib/api/plan-grants.ts`) while the plan's code loads, keeps it until a minute before it lapses, and sends it on every request about that plan as `X-Index-Grant` (`INDEX_GRANT_HEADER`). The api checks it offline against the index's published keys (`verifyPlanGrant`, `apps/api/src/index-service.ts`): its `aud` is liveplanner, its `item` the plan in the path.
- **A caller without one** (an API token, a workbench session, a browser that sent none) gets one fetched here (`resolvePlanGrant`, `routes/plan-grant.ts`), cached until a minute before it lapses: as that account with this app's key, or with the browser's own Bearer and its share headers.
- **A share link** rides as `X-Share-Code` (and `X-Share-Password` when the plan has one), which the index's grant endpoint reads. A password refusal comes back as the index's: 401 `password_required` or 403 `password_invalid` ([Share password](../013-workspace/share-password.md)).
- **The room** takes the grant as its ticket on the upgrade (`?t=`), since a socket cannot send headers ([Realtime model](#realtime-model)).

Every route about one plan then gates on the grant's level: reads on `view`, a Participant's writes on `participate`, everything else on `edit`, and a grant with a `tab` reaches only that tab. No grant answers 404, never revealing that the plan exists.

## Endpoints

All JSON unless stated. CORS allows any origin (the editor app is same-origin via the router; this is mostly a dev convenience). Routes are dispatched in `apps/api/src/index.ts`, a thin switch over `segments[1]`; each owns a `handle<Resource>(ctx)` module under `apps/api/src/routes/` that implements every method and sub-path it handles. Read the dispatcher for the surface, then the matching route module for the authoritative behaviour. The machine-readable reference is `GET /api/openapi.json` ([API documentation (OpenAPI)](api-documentation.md)). `/api/auth/*` and `/api/internal/*` are answered before the caller is resolved. `/api/index/*` never reaches this worker: the router forwards it to liveworkspace's index ([Router app](../016-platform/router-app.md)).

### Project dates

A project's dates are its `createdAt` (shown as created) and `savedAt` (last
modified, the lists' order), both milliseconds since the epoch, as everywhere
on the wire. A create stamps both with the server's now, unless the body
carries its own: an Offline Mode sync carries the local record's `createdAt`
([Offline Mode](../006-project/offline-mode.md)), so it sits in the Explorer
where its age puts it.

- Each given date must be a whole number of milliseconds no earlier than
  `PROJECT_DATE_MIN` (1 January 2000, before any project a person could
  bring) and no later than the server's now plus `PROJECT_DATE_SKEW_MS`
  (one day, for a device clock that runs ahead), and `createdAt` must not be
  later than `savedAt`.
- A given `createdAt` alone keeps `savedAt` at now (or at `createdAt`, if a
  clock running ahead put that later); a given `savedAt` alone is refused (a
  project is never modified before it is created).
- Seeding the create's tabs leaves `savedAt` as given.
- Anything else is refused whole, 400 `bad_request` "invalid project dates";
  nothing is created.
- Only a genuine create takes them: re-committing an id the caller already
  owns keeps the stored `createdAt`.

### Marking a project used

The create body's `markUsed` (absent or `true`, or `false`) is still read and validated: anything but a boolean is refused whole, 400 `bad_request` "invalid markUsed", and nothing is created. It no longer changes a list: what Recent and Jump back in show is the index's record of opens, which the editor writes when it loads a plan (`POST /items/:id/open`, [Explorer Home](../013-workspace/explorer-home.md)).

### Projects in the Trash

A plan's Trash state is the index's. A trashed plan is reached only by its owner and team, so the index grants nobody else anything for it, and every door answers as for a plan that is not there. The index keeps a plan 30 days in the Trash, then deletes it for good and has the plan's object drop its content ([Trash](../013-workspace/trash.md)). There is no Trash cron and no empty-project sweep here.

### Tab save

The whole-tab autosave (`PUT /api/projects/<id>/tabs/<tabId>`, about every 600 ms while someone edits) reads
only what it needs of the project, in one query (`getProjectForSave`: owner, team, name and the tab count), where it ran the full project read (the row
with its share-code subqueries, then the owner's participant and the tab summaries) as two sequential round
trips. The owner's name and colour come from the profile cache (one batched accounts read a minute per person,
`apps/api/src/person/profiles.ts`), not from each save. The stored
tab, the changesets the editor had not seen and the realtime room's ledger are then read together; the ledger is
merged after the changesets, as before. A denied save still answers 403.

### Tab size

A tab is stored as one text value in one row of its plan's SQLite (`tabs.data`, the tab's
JSON without its id and name), and a Durable Object's SQLite, like D1, caps a string, a BLOB and a
row at **2,000,000 bytes** ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)).
Local `wrangler dev` does not enforce it, so the api enforces it itself:

- `D1_MAX_ROW_BYTES` = 2,000,000. `MAX_TAB_BYTES` = `D1_MAX_ROW_BYTES` less
  `D1_ROW_HEADROOM_BYTES` (8 KiB) = 1,991,808 bytes of UTF-8 JSON. The
  headroom covers the row's other columns (the tab id, a UUID; the name, at
  most 60 characters, so at most 240 bytes; `updated_at`; SQLite's record
  header) many times over, so a tab under the cap always fits its row.
- Both numbers live in `@liveplanner/api-schema`, so the editor checks the same
  cap the worker does and the two cannot drift.
- **Every write of a tab's data** is checked against it, at the storage layer
  (`upsertTab`, `seedTabs`, `swapTabData`), so no route can store what D1
  would refuse: project create, the tab save, a comment added or deleted
  through the api, and a participant content write. A tab over the cap is refused with
  the named 413 (`payload_too_large`) and nothing is written; the worker logs
  `[tab-size] refused` with the write (`create`, `upsertTab`, `seedTabs`,
  `swapTabData`), the tab id, the bytes and the cap. The comment routes list
  413 among their answers in the OpenAPI manifest. The routes
  also check the request up front, so a create never leaves a project
  without its tabs.
- The cap is not raised and the storage format is unchanged; a tab that needs
  more is a separate decision.

## Caching

Every JSON answer is the caller's live state, so it goes out `Cache-Control: no-cache` unless its
route chooses a policy of its own (the OpenAPI project, the public telemetry summary): a browser
may store it but asks the server again before reusing it. Without it a browser may reuse an answer
the server has since changed: Chromium holds a `410` with no explicit expiry indefinitely, so a
share-link visitor who once saw a project deleted would keep seeing it after the owner restored
it. Not `no-store`: the browser's cache drains a stored answer's body, and without it an answer
whose caller never reads the body holds its request open. SVG snapshots and share cards set their own
policies.

Over-limit requests get `429` with `{ "error": "rate_limited" }`, except the telemetry ingest, which answers with its usual no-op `204` so a throttled beacon never surfaces as an error.

The write ceiling sits well above realistic editing traffic (autosave fires once per debounce window, comments are typed by humans) but low enough to stop a bot from spamming project creation into D1 quota exhaustion. The room-ticket mint is exempt because it shares the per-owner budget with the autosave, and a 429 there would cost a team member the whole session's realtime; `/api/events` is exempt so telemetry never competes with a user's real writes.

## Storage

Each plan's content lives in its own SQLite-backed Durable Object, `PlanRoom` (`apps/api/src/plan-room/`), one per
plan id. D1 keeps only what is liveplanner's own and not content; where a plan is and who may reach it is the index's.

**What the plan's object holds** (`plan-schema.ts`, created on first use, `CREATE ... IF NOT EXISTS`):

- `plan`: the plan's own row: item type catalogue, the item counters, `saved_at`, `created_at`.
- `tabs` (the body, one JSON row per tab) and `plan_tabs` (order and folder), with `tab_stats` (the Details view's
  numbers).
- `items` (Plan cards; board columns live on the board elements in the tab bodies).
- `sheets`, `sheet_cells`, `sheet_refs`.
- `agent_changesets` and `agent_changeset_parts` (the changeset log).
- Forms data: a form is a Form tab's body, and its responses are cards or sheet rows, all above.
- `outbox`: what D1 still has to hear (below).
- In the object's key-value storage, as before: the order state (`epoch`, `seq`), the collaboration ledger,
  selections and agent presence.

A tab is one row. A tab over 2 MB does not fit a SQLite row in a Durable Object either, so the cap in **Tab size**
stands; storing a large tab in chunks is the follow-up.

**What D1 keeps**: `api_tokens`, `form_links`, `form_reads`, `form_reports` and the workbench tables. No plan row, tab body, card, cell or changeset is in D1, and nothing about folders, sharing, teams, the Trash or the Inbox.

**Routing.** The worker authenticates the caller, applies its cross-cutting gates (rate limits, read-only tokens,
workbench confinement, body caps) and hands every request under `/api/projects/:id/...` and `/api/forms/:code/...`
to the plan's object, `planRoom(env, id).route(request, identity)` (typed RPC, `plan-client.ts`). The object
rebuilds the route context from that identity and the grant and runs the handlers against its own SQLite as
`env.PLAN_DB` (`plan-db.ts`, the D1 surface over `ctx.storage.sql`). The editor's wire protocol is unchanged. Other RPCs: `outline` (a project read's tab
list), `image` (thumbnails, drawn where the content is), `hasTab`, `item`, `exportCopy` / `importCopy` (a project
copy), `purge` and `revokeCodes`.

**A save is one call and one transaction.** The tab `PUT` reaches the object in one RPC and writes the body, its
`plan_tabs` row, its stats, `plan.saved_at` and its sheet references in one `transactionSync`, with no D1 round
trip on its path. A read is one RPC. Measured on a laptop (CPU time, node:sqlite standing in for the object's
SQLite; `plan-room-store.test.ts` keeps budgets on them): a 1 MB tab saves in about 35 ms and reads in about 15 ms; a
200-tab plan's project read takes about 1 ms.

**The outbox.** Triggers on the plan's tables key every change in the same transaction as the write, so no write path can forget one and a save makes no network call. The object's alarm drains it on idle and at most once a minute (`plan-outbox.ts`): the plan's summary to the index (`PUT /app/items/:id/summary`, the Explorer's thumbnails and counts), each changed tab's comment threads and actions for the Inbox (`PUT /app/items/:id/collab/:tabId`), both with this app's key ([one-explorer-contracts.md](../../../../liveworkspace/docs/one-explorer-contracts.md) "What an item pushes"); a Form tab's name and heading on its form link and the owner's newest save for the lifecycle email go to D1. A drain that fails keeps every key it did not push and retries a minute later, so the Explorer and the Inbox lag a write by up to about a minute.

**Upkeep.** Each object runs its own daily upkeep from its alarm: sheets unreferenced for 30 days expire, and
changesets past their retention go. The D1 crons for both are gone.

**Duration.** The object is billed while it runs a request or an alarm. Content requests and thumbnail renders now
run there rather than in the worker, so a plan under heavy API traffic keeps its object awake for that traffic; an
idle plan costs nothing, and sockets still hibernate.

## Realtime model

The `PlanRoom` Durable Object (`apps/api/src/plan-room/plan-room.ts`) is the realtime hub for one plan id, and holds its content (see **Storage**). Clients connect via the `/ws` endpoint and immediately send a `hello`; the room broadcasts a `presence` snapshot whenever the set changes.

**Hibernation.** The room uses the Workers WebSocket Hibernation API (`state.acceptWebSocket` + class-level `webSocketMessage` / `webSocketClose` / `webSocketError` handlers) rather than in-memory `ws.accept()`, so the runtime can evict an idle room from memory between messages while every client's socket stays open — an open-but-quiet session no longer bills DO duration. All per-session state that matters (the server-assigned ephemeral presence id, the `X-Verified-Role` trust-boundary role, and the `hello` presence including the remembered `tab-focus` tab) survives eviction in each socket's serialized attachment; only the per-session rate-cap window is in-memory and deliberately resets on a wake.

**Access is gated at the upgrade.** Browsers can't set headers on a WebSocket upgrade, so what admits a socket rides its URL: the index's grant itself, as `?t=` (`apps/api/src/room-ticket.ts`; a workbench session's ticket also seals its pairing and level cap with this app's key). A grant is short-lived (ten minutes) and names its plan, so a logged one is soon useless. The worker checks it offline, **refuses the upgrade unless it admits this plan**, and forwards what it says on headers only it sets, stamped on every path so a client can never supply them: `X-Verified-Role` (the grant's level, capped for a workbench session), `X-Verified-Owner`, `X-Verified-Tab-Scope` (the grant's `tab`, empty otherwise) and `X-Verified-Share-Code` (the link a visitor came in by: the grant's `link:<code>`, or a person's `?s=`, which only ever closes sessions). The DO re-stamps the role onto presence in the `hello` handler, ignoring any role the client typed, so that header is the trust boundary, and confines a scoped session to its tab, live and in catch-up ([Tab-scoped share links](../013-workspace/tab-scoped-share-links.md)).

**Renewing the grant.** The room asks a session for a fresh grant (`{ kind: 'grant-renew', expiresAt }`) shortly before its grant lapses; the editor answers with a `grant` frame (and renews a minute early anyway). A fresh grant saying the same moves the lapse on; one with another level or tab closes the socket (4005) so it reconnects as what it now is; a session still holding a lapsed grant is closed (`GRANT_LAPSED_CLOSE`) and its editor rejoins with a fresh one, or not at all ([one-explorer-contracts.md](../../../../liveworkspace/docs/one-explorer-contracts.md) "Grants").

Edits and presence propagate as `op` messages. The room is **not** a stateless relay: it classifies every op, orders the ones that change the project, rewrites a few fields on the way through, keeps a small amount of collaboration state in its own storage, and stores the plan's content in its own SQLite, the system of record for it ([Realtime conflict resolution](../012-collaboration/realtime-conflict-resolution.md), [Collaboration race hardening](../012-collaboration/collab-race-hardening.md)).

### Op classes

Every op kind belongs to exactly one of three lists in `@liveplanner/api-schema` (`packages/api-schema/src/room-messages.ts`), and the class decides its ordering, its role gate, and whether a client may send it at all. The room reads `op.kind` to classify; the payload stays `op: unknown` on the wire.

- **Presence** (`PRESENCE_OP_KINDS`): ephemeral, mutate nothing. Relayed unordered (no `seq`), never logged, never replayed, from **any** connected session, so a view-only visitor still shows peers their cursor, selection and tab.
- **Mutation** (`MUTATION_OP_KINDS`): change the project. Relayed **only from a session whose verified role is `edit`**; each gets a monotonic `seq` within the room's `epoch` and a slot in the catch-up log.
- **System** (`SYSTEM_OP_KINDS`): originated only by the api worker through the DO's internal endpoints, stamped `from: 'system'`. Dropped outright when a client sends one, so no peer can forge a revoke.

The vocabulary (the client-side union is `RoomOp`):

| Kind             | Class    | Carries                                                            | Purpose                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------------- | -------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `cursor`         | presence | `{ tabId, x \| null, y \| null }`                                  | Cursor position in canvas coordinates, throttled to ~30 Hz; a position a window holds back is sent as the window ends, so peers see the cursor where it stopped. `null` hides the indicator (cursor left the surface).                                                                                                                                                                                                   |
| `select`         | presence | `{ elementId \| null, tabId? }`                                    | Sender's selected element changed; renders as a coloured ring on the peer's canvas and drives the advisory concurrent-selection lock ([Editor app](../007-editor/editor-app.md)).                                                                                                                                                                                                                                        |
| `tab-focus`      | presence | `{ tabId, besideTabId? }`                                          | Sender switched to a tab. Drives per-tab participant dots in the TabBar. The room also remembers it on the session, so a later joiner learns it from the presence list. `besideTabId` is the tab in the sender's other pane while working side by side ([Side by side tabs](../007-editor/split-view.md)): remembered and echoed the same way, cleared by a `tab-focus` without it, never held for a tab-scoped session. |
| `drag-preview`   | presence | `{ tabId, patches? \| end? }`                                      | A dragger's live preview ([Drag preview](../008-canvas/drag-preview.md)): one geometry patch per changed element, ~30 Hz; `end` says it is over. **Editor-only**: the room drops one from a non-edit session, and receivers draw only an editor's.                                                                                                                                                                       |
| `tab`            | mutation | `{ tabId, tab }`                                                   | One tab's full body. The fallback for a new tab or a bulk change; receivers take it but keep their own multi-writer fields and, within one vote round, their own dots.                                                                                                                                                                                                                                                   |
| `tab-meta`       | mutation | `{ tabId, patch, clear? }`                                         | A tab's non-element metadata (name, background, timer, vote lifecycle, ...). `clear` names fields the sender removed.                                                                                                                                                                                                                                                                                                    |
| `el`             | mutation | `{ tabId, op: ElementOp }`                                         | One element added / updated / removed / reordered, applied by id (`applyElementOp`). An `update` replaces the **whole element**; receivers keep their own copy of the multi-writer fields (`mergeIncomingElement`).                                                                                                                                                                                                      |
| `vote`           | mutation | `{ tabId, elementId, voter, delta: 1 \| -1, round? }`              | One dot placed or taken back ([Session tools](../012-collaboration/session-tools.md)). A delta, so concurrent dots commute.                                                                                                                                                                                                                                                                                              |
| `el-delta`       | mutation | `{ tabId, elementId, delta: ElementDelta }`                        | One change to a field many people write at once: an answer, a checklist tick, a comment add / remove / rekey / resolve ([Collaboration race hardening](../012-collaboration/collab-race-hardening.md)). Applied by the shared `applyElementDelta`; idempotent or order-free.                                                                                                                                             |
| `project-meta`   | mutation | `{ name, tabs: { id, name, orderIndex, folder?, outOfScope? }[] }` | Project rename / tab add / tab delete / tab reorder / tab folders.                                                                                                                                                                                                                                                                                                                                                       |
| `share-revoked`  | system   | `{ code }`                                                         | The named share link was turned off on the index. Visitors that hydrated with `X-Share-Code: <code>` leave the editor; the room then closes every socket that code admitted (close code 4003). Unsequenced.                                                                                                                                                                                                              |
| `share-rescoped` | system   | `{ code }`                                                         | The named share link changed scope ([Tab-scoped share links](../013-workspace/tab-scoped-share-links.md)). Its sessions reload into the new scope; the room closes their sockets (4003). Unsequenced.                                                                                                                                                                                                                    |

**Access changes end the sessions they affect.** A link turned off on the index ends its sessions at once: the index calls `POST /api/internal/items/:id/revoke` with the codes, and the room broadcasts `share-revoked` for each and closes the sockets that code admitted. Any other change (a password set, a team membership ended, a link's level or tab changed) takes effect when the session's grant is next renewed, within ten minutes. The room's internal `POST /close-sessions` (never reachable from outside, like `/broadcast`) closes matched sockets with **4005** (`ACCESS_CHANGED_CLOSE`, reason `access-changed`); nothing is broadcast, so no other session learns who left. The connector stops on 4005 and the editor reloads, which runs the ordinary access path again: a password prompt, a refusal page, or (when access remains another way) the editor.

Besides `op`, the room speaks a few non-op frames: `hello` and `sync` from clients; `presence`, `catchup` and `cursor` from the room.

### What the room does to a frame

In order, for every inbound frame: a frame over 256 KiB is dropped; a per-session sliding-window rate cap (240 frames per second) drops a flood; an op from a session that hasn't said `hello` is dropped; a system-kind op from a client is dropped; a tab-scoped session may only touch its own tab and never the project's structure (`scopedSenderMayRelay`); a non-presence op from a session whose verified role isn't `edit` is dropped. Then:

- **Presence ops** relay to every other socket.
- **Mutation ops** are rewritten before they go anywhere: `opForTheWire` strips every comment `authorId` (a guest's credential), and `stampCommentAuthor` sets a posted comment's author name and colour to the sending session's presence, whatever the frame claimed. The rewritten op gets the next `seq`, lands in the catch-up log, relays to every other socket, is recorded in the ledger when it is an `el-delta` or `vote`, and the sender receives a `cursor` frame naming the `seq` its own op took, echoing the op frame's `ref` when it carried one (a positive integer), so the sender knows that op is sequenced.
- Every outbound op frame to a tab-scoped session is filtered or redacted for its scope (`opForScope`), live and in catch-up.

On `hello` the room builds the session's presence itself (`helloPresence`): the id is a server-minted per-socket random (never the connector's owner id), the role is the verified one, and every claimed string is length-clamped. It then sends the joiner a `cursor` frame and broadcasts presence (each socket gets the roster minus its own entry).

### Ordering and catch-up

Mutations are totally ordered by the single-threaded DO: a monotonic `seq` within an `epoch`. `epoch` and `seq` are persisted in DO storage (`order-state`) and restored on every wake, so hibernation does not strand reconnecting clients ([Resync without reloading the page](../012-collaboration/resync-without-reload.md)). The catch-up log (the last 256 mutations, `OP_LOG_LIMIT`) lives in memory only. On reconnect a client sends `{ kind: 'sync', epoch, lastSeq }`; `resolveCatchup` answers with the ops it missed, or `resync: true` when the gap is behind the log's floor or the epoch is foreign, and the client re-fetches its loaded tabs in place.

### What the room stores

Besides the plan's content (**Storage**), its key-value storage holds:

- **`order-state`**: `{ epoch, seq }`, written on every mutation.
- **The collaboration ledger** (`RoomLedgerStore`, `room-ledger-store.ts`; entries defined by the pure `collab-ledger.ts` in `@liveplanner/project`): for every `el-delta` and `vote` it sequences, the latest state of each answer, checklist tick, comment and the round's dots, one key per element (plus the tab's vote), tagged with the `seq` that set it. An entry that would pass the storage value limit stops growing. The api reads it back to merge a tab save (see the tab `PUT` above).

Per-session state (presence id, verified role, owner bit, tab scope, admitting share code, presence) lives in each socket's serialized attachment, so it survives hibernation; only the rate-cap windows and the catch-up log reset on a wake.

The room's other parts each have a module beside `plan-room/plan-room.ts`: the session attachment and the verified upgrade headers (`room-session.ts`), the role gate on client ops (`room-op-gate.ts`, the [Share roles](../013-workspace/share-roles.md) level ladder), the worker-only internal endpoints (`room-internal.ts`) and the presence roster each socket is sent (`room-roster.ts`).

### What the room writes to D1

- **One telemetry row**: the room counts a multiplayer session once (`Project·Used·Multiplayer`, `reportServerEvent`) into liveworkspace's telemetry, when `TELEMETRY_ENABLED` is on ([Telemetry + public transparency dashboard](../017-telemetry/telemetry.md)).

Every other project write is a REST call from a client (see the persistence boundary below).

### Internal endpoints

The api worker reaches the DO through its stub (`env.PLAN_ROOM.get(...).fetch(...)`; content goes through the typed RPCs under **Storage**), which never traverses the public edge, so these paths are implicitly internal:

- **`POST /broadcast`** `{ op, ordered? }`: push a system op to every socket (`from: 'system'`), sequenced when `ordered` is true. A revoke from the index (`revokeCodes`) sends `share-revoked` the same way, then closes the sockets that code admitted. Best-effort: a failure is logged (`[room-broadcast]`).
- **`POST /mutation`** `{ op }`: sequence a project change the worker made, as if a peer had sent it. `el-delta`, `changeset` and `tab-meta` are accepted (400 otherwise); the comment endpoints use `el-delta` so a view-role visitor's comment reaches connected editors (`relayElementDelta`), the changeset route uses `changeset` ([Agent changesets](../024-agents/agent-changesets.md#what-the-room-does)), and the tab rename route uses `tab-meta` (`relayTabRename`).
- **`GET /selections?tab=<tabId>&person=<tag>`**: the elements each connected person has selected on a tab (every `select` is recorded in DO storage per session, pruned when the socket goes), each marked `mine` when the session's person tag is the one asked about. The changeset route reads it to find held elements.
- **`PUT /presence`**, **`DELETE /presence`**: an agent's presence entry with its expiry ([Agent presence](../024-agents/agent-presence.md#presence)).
- **`GET /ledger?tab=<tabId>&epoch=<epoch>`**: the tab's collaboration ledger, or an empty one when `epoch` isn't the room's current epoch (the saver's cursor can't be interpreted then).
- **Purging a room** (the `purge` RPC; `POST /purge` reaches the same code): the plan was deleted for good, so the room closes every socket (`PROJECT_TRASHED_CLOSE`, reason `project-purged`), waits for the ledger's queued writes, drops its alarm and deletes all of its storage (`deleteAll`): the plan's content with it, and the ledger with its comment and answer text, the order state, selections and agent entries. The index asks for it (`DELETE /api/internal/items/:id`) whenever a plan leaves its Trash for good, by hand, by its daily sweep or by account deletion, and retries a plan it could not reach.

### Conflict model

- **Different elements on one tab merge.** `el` ops apply by id, so concurrent edits to different elements survive on every peer.
- **The same element is last-writer-wins, over the whole element.** Two `el` updates to one element apply in room order and the later one replaces the earlier, whoever held the selection. The concurrent-selection lock ([Editor app](../007-editor/editor-app.md)) is advisory and client-only (`remoteSelectionsByElement`, built from `select` ops): it makes these collisions rare, and the room does not enforce it. `tab-meta` patches are last-writer-wins per field, and `project-meta` per whole tab list.
- **Multi-writer fields merge.** Answers, checklist ticks, comments and dots travel as `el-delta` / `vote` deltas that commute, and whole-element or whole-tab ops don't overwrite a receiver's copy of them.

### The persistence boundary

The plan's object holds both the content and the ordering and collaboration state. Tab content reaches its store through `PUT /api/projects/:id/tabs/:tabId`, fired by each editor's debounced autosave with the editor's whole copy of the tab. The store keeps the last save of a tab, with the room ledger and `qaRev` merged in as described on that row. Each editor's copy already folds in the ops it has received, so the last save normally carries everyone's work; an element edit that reached the saver only after its snapshot can be missing from the store until a later save carries it, while live peers still hold it.

A tab `PUT` is not relayed to the room; it is the editor's autosave and nothing else's. Every other writer of tab content (the MCP server, the CLI, an API-token script) writes a [changeset](../024-agents/agent-changesets.md), which the api records in the plan's store and relays to the room, and which every later editor save re-applies unless that editor has seen it. The comment and Q&A endpoints also tell the room about their writes.

Every tab the api receives (project create, tab save) runs the stored-tab migration (`migrateStoredTab`) before `isValidTab`, as every tab read does, so an element in a former stored shape (for example freehand points before [Stroke points](../006-project/stroke-points.md)) from a browser loaded before a deploy or an API-token script is stored in the current shape rather than refused.

## Data model

The schema is one baseline migration, `apps/api/migrations/0001_liveplanner_baseline.sql`, which creates every D1 table the worker reads and writes. liveplanner has no data, so the baseline is the schema as it stands, without the tables of removed or moved features (the projects table, share links and passwords, `shared_with`, folders, favourites, tags, placement defaults, the Trash state, teams and their members, the Timeline, the Inbox's collab index, opens, owner aliases, the room tickets). A later change adds a numbered migration after it. In broad strokes:

- **Plan content** (`plan`, `tabs`, `plan_tabs`, `tab_stats`, `items`, `sheets`, `sheet_cells`, `sheet_refs`, `agent_changesets`, `agent_changeset_parts`, `outbox`) is in each plan's Durable Object, `apps/api/src/plan-room/plan-schema.ts`, not in this migration. The plan's own row holds its name, owner and provenance.
- **`api_tokens`** — account-only rows.
- **`form_links`**, **`form_reads`**, **`form_reports`** — a Form tab's public link and what readers have seen ([Forms](../030-forms/forms.md)).
- **`workbench_pairing_requests`**, **`workbench_pairings`**, **`workbench_tickets`**, **`workbench_sessions`**, **`workbench_session_rooms`** — [Workbench embeds](../013-workspace/workbench-embeds.md).

Where a plan is filed, who it is shared with and whether it is in the Trash are the index's ([one-explorer-contracts.md](../../../../liveworkspace/docs/one-explorer-contracts.md)).

### Owner-keyed data

This is the one list of columns that hold an owner id (a guest id or an account userId), and what **account deletion** (`deleteAccount` in `apps/api/src/db/account.ts`, `DELETE /api/account`) does with each, in one D1 batch. There is no owner migration here: a guest's items move to the account in the index when they sign in ([Auth + guest access → Guest → account](../014-identity/auth-and-guest-access.md#guest--account)). A column holding an owner id is named `owner_id` (`author_id` on `agent_changesets`); `apps/api/src/db/account-owner-columns.test.ts` finds every such column in the schema, fails until it is listed there, and proves each against a real SQLite database.

| Column                                | Account deletion                                                                                                        |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `plan.owner_id`                       | In each plan's own store: the account's own plans are deleted for good through the index first, which purges each store |
| `agent_changesets.author_id`          | In each plan's own store: those on someone else's plan stay until the 30-day changeset retention ages them out          |
| `form_reads.owner_id`                 | Deleted ([Forms](../030-forms/forms.md#hearing-about-responses))                                                        |
| `api_tokens.owner_id`                 | Deleted ([Public API and API tokens](public-api-and-tokens.md))                                                         |
| `workbench_pairing_requests.owner_id` | Deleted, before the tokens ([Workbench embeds](../013-workspace/workbench-embeds.md))                                   |
| `workbench_pairings.owner_id`         | Deleted, before the tokens                                                                                              |
| `workbench_tickets.owner_id`          | Deleted, before the tokens                                                                                              |
| `workbench_sessions.owner_id`         | Deleted, before the tokens                                                                                              |

**Kept by the accounts Worker, not here.** A person's settings ([User preferences](../007-editor/user-preferences.md)), name and colour (`GET`/`PUT /api/participants`), sign-in sighting and email address live in the liveworkspace accounts database ([liveworkspace/docs/accounts.md](../../../../liveworkspace/docs/accounts.md)), under the account's user id or, for a guest, the `guest_<uuid>` id its guest token names. Closing an account deletes them there, and a guest's move to an account on sign-in is the accounts Worker's too.

A new owner-keyed table adds a row here, a statement to `deleteAccount`, and an entry in the test, in the same change.

## One-time setup

Before the first deploy:

1. `pnpm --filter @liveplanner/api exec wrangler d1 create liveplanner`
2. Copy the printed `database_id` into the `[[d1_databases]]` block in `apps/api/wrangler.toml`. The block is already there with its binding name (`DB`) — only the id changes. What is committed is liveplanner.app's own database id, so a new environment is replacing a real value rather than filling in a blank.
3. `pnpm --filter @liveplanner/api run db:migrate:remote` to apply migrations.

After that, GitHub Actions handles deploys via `deploy.yml` (`deploy-api` step). The router's service binding to `liveplanner-api` means the API must deploy before the router.
