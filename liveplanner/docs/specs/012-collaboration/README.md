- ./realtime-conflict-resolution.md - when working on Realtime conflict resolution: Robust simultaneous editing: element-level ops derived from each commit's before/after diff, applied by id, so same-tab/different-element edits stop clobbering; plus an ordered Durable Object (per-epoch seq + bounded op log) for convergence + clean reconnect catch-up. The plan's stored tabs stay the system of record. A full field-level CRDT for same-element concurrent edits was scoped and deliberately dropped; such edits stay last-writer-wins, made rare by the advisory selection lock ([Editor app](../007-editor/editor-app.md))
- ./vote-layer-scope.md - when working on Scoping a vote to one layer: A dot-vote can be scoped to one layer, picked before Start vote (active layer preselected, "All layers" available, hidden on single-layer tabs) and locked for the vote; off-layer elements dim to 0.35 while votable ones get a brand ring, both only while casting is open
- ./resync-without-reload.md - when working on Resync without reloading the page: A shared project never reloads itself: the realtime room persists its epoch/seq so a hibernation wake stops forcing spurious resyncs, and a genuine resync re-fetches tab content in place (preserving viewport, selection, and undo) instead of calling window.location.reload()
- ./session-button.md - when working on Session button: A canvas button that starts a session tool for the room when pressed: a countdown timer, a stopwatch or a dot vote. - ./picker.md - when working on Picker: A card that chooses at random when pressed: one of the people in the room, or one of the options written on it. Spins for a second over a result decided at press time, and writes it to the element so everyone lands on the same answer
- ./participant-responses.md - when working on Per-participant responses: A shared `responses` field recording ONE value per participant, persistently, the primitive under the temperature check. At most one response per person (a re-cast replaces), a string value so consumers can disagree about what an answer is, edit-role only, and deliberately not undoable so one person's Ctrl+Z can't retract another's answer
- ./temperature-check.md - when working on Temperature check: A fist-of-five gauge: everyone registers 1-5 and the element shows the distribution and the average live. Deliberately never hidden, because watching the bars move IS the reading
- ./decision-record.md - when working on Decision record: A decision on the diagram beside the thing it decided: statement as the label, a status chip (proposed / accepted / rejected / superseded), a date, and the drivers. The chip is tinted, never the element fill, so the theme still owns the box
- ./comment-pin.md - when working on The Comment Panel: A Collaborate card that shows a whole comment thread on the canvas, so a remark can be about a PLACE rather than whichever shape is nearest and, attached to an element by an ordinary arrow, can be read by everyone in the export and the session rather than in one reader's popover. No comment machinery of its own: it holds the ordinary commentThread
- ./comment-mentions.md - when working on Comment mentions: `@handle` a teammate from the project's team in a comment; stored as structured `mentions` on the comment, drawn as chips, put on the mentioned person's Inbox, and emailed by the api when the comment is saved, server-verified against the plan's team, behind the `notifyMentions` setting
- ./collaborator-enhancements.md - when working on Collaborator enhancements: Clicking any avatar in a tab's presence stack opens a Collaborators modal: everyone in the project grouped by the tab they are on, with Go to Tab per group. - ./action-panel.md - when working on The Action Panel: A Collaborate card holding a checklist of assigned actions (`actions: ElementAction[]`, read everywhere through `elementActions`), each added, ticked and edited from the card through the existing Assign Action dialog. - ./collab-race-hardening.md - when working on Collaboration race hardening: Presses on shared cards (temperature, checklist, comments, votes) must not be lost, duplicated or retracted when many people act at once. ## No activity log

liveplanner keeps no per-tab activity log: nothing records each undoable commit with its author, and nothing offers a per-entry Revert.

- There is no change-log table, no `/api/projects/:id/log` endpoint, and no `log` / `log-remove` room op.
- liveplanner has no `activityPanelEnabled` preference and no revert hover preview ([User preferences](../007-editor/user-preferences.md)).
- **Undo and Redo stay, unchanged in behaviour.** They are snapshot-based (`useProjectHistory`), personal to each editor and session, and sit in the bottom-right cluster and on Cmd/Ctrl+Z, Cmd/Ctrl+Shift+Z and Ctrl+Y. A continuous control (a background slider, an element colour or opacity picker) still takes one undo step per burst: the first tick checkpoints and ticks within 500 ms of the last stay in that step (`useBurstCheckpoint`).
- Project-level history (made, renamed, moved, trashed, who edited) is the [Timeline](../013-workspace/timeline.md), kept by liveworkspace's index; the [Inbox](../013-workspace/inbox.md) is unrelated, and is liveworkspace's index's too.
- Help has no Activity Panel category.
