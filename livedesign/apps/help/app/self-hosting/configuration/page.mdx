A self-hosted livedesign is configured through environment variables, secrets and each Worker's `wrangler.toml`, not application code. A few `wrangler.toml` values ship with livedesign.app's own settings (the database and KV ids, the allowed AI origins, the MCP issuer and consent URL, and the guest-signing date), so a fork replaces those with its own. The most important thing to understand is that the optional features are genuinely optional: leave them unset and the editor still works perfectly, just in a simpler mode. This page covers how configuration is supplied and the main toggles you will care about.

## How configuration is supplied

Secrets and settings never live in source code, since the repository is public. Instead, each Worker reads them at runtime.

- **Local development** uses a gitignored `.env.local` file per frontend app and a gitignored `.dev.vars` file per Worker.
- **Workers** receive secret values via `wrangler secret put`, and non-secret settings as `[vars]` in the Worker's `wrangler.toml`. Set plain settings in the file rather than the Cloudflare dashboard: every deploy replaces them with what the file declares.
- **Static frontends** only ever bundle values explicitly marked as publishable, prefixed `NEXT_PUBLIC_` so it is obvious they are safe to ship to the browser, and baked in at build time. Server-only secrets stay on the Worker side and never reach client code.

Each app that needs configuration ships an example file designing which variables it expects, so you can see at a glance what to set.

## Optional sign-in

Sign-in is optional. It goes through a liveworkspace accounts Worker, and the app supports three modes depending on what you configure.

1. **Hybrid**, the production setup: the live build has `NEXT_PUBLIC_SIGN_IN_ENABLED=true`, and the API has the accounts Worker's address and your client's details (`ACCOUNTS_URL`, `API_RESOURCE`, `ACCOUNTS_CLIENT_ID`, `ACCOUNTS_CLIENT_SECRET`), so guests and signed-in users coexist.
2. **Guest-only**, the typical self-host: leave the auth variables unset. The app runs without an account system, sign-in routes say sign-in isn't enabled and offer **Continue as guest**, and the editor is unchanged.
3. A partial misconfiguration (frontend configured, API not) exists only for debugging and is not meant for production: nobody can finish signing in, and the API treats everyone as a guest.

With sign-in on, also set `GUEST_ID_HMAC_SECRET` so guest ids are signed and nobody can claim another guest's designs when they sign up. Accounts unlock the features that need one: [teams](/help/collaboration/teams/), [API tokens](/help/account-and-data/api-tokens/), and, if you set them up, email and the MCP server.

Guest-only is what lets a self-hoster run with zero outbound runtime traffic beyond their own hosting if they want to.

## Guest-only fallback

The API identifies the owner of a request in one of two equivalent ways: a verified sign-in token, or a per-browser guest id sent as a header. When sign-in is not configured, every request simply uses the guest path, and the editor stays fully usable, with persistence, sharing, and real-time collaboration all working.

## Other optional features

Every other optional feature follows the same pattern: unset means off, and the editor hides what it cannot use.

| Feature                 | Turn it on with                                                                                                                                                                                                                                                                                                  |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Image uploads           | `MEDIA_KEY` on the api Worker, its secret on liveworkspace's media service, which keeps the images and their limits (100 images and 100 MB per person). Set `MEDIA_URL` too when the service is not liveworkspace.app's                                                                                          |
| Thumbnails              | Create the `livedesign-images` R2 bucket the api `wrangler.toml` already binds (or delete that binding to leave thumbnails off)                                                                                                                                                                                  |
| AI assistant            | One AI key on the api Worker: `OPENAI_API_KEY`, `GOOGLE_AI_STUDIO_API_KEY`, or `AI_API_KEY` with `AI_BASE_URL` and `AI_MODEL`. Also set `AI_ALLOWED_ORIGINS` to your own origin or remove it: it ships with livedesign.app's, and any other origin gets a 403                                                    |
| Email                   | `RESEND_API_KEY` on the api Worker, plus `RESEND_FROM` on a domain verified in Resend and `APP_BASE_URL` set to your origin, since both default to livedesign.app (needs sign-in)                                                                                                                                |
| MCP server for AI tools | Deploy the mcp Worker with its own KV namespace and hostname, then point `CONSENT_BASE_URL` (mcp Worker) at your editor's origin, and `NEXT_PUBLIC_MCP_ORIGIN` (live build) and `OAUTH_ISSUER` (api Worker) at your MCP host (needs sign-in). See [The MCP Server](/help/self-hosting/configuration/mcp-server/) |
| Telemetry               | `TELEMETRY_ENABLED` on the api Worker and `NEXT_PUBLIC_TELEMETRY_ENABLED` on every frontend build                                                                                                                                                                                                                |
| Workbenches             | Nothing extra beyond sign-in, but set `APP_BASE_URL` on the api Worker to the origin that serves the app, or pairing and frame links point at livedesign.app (needs sign-in)                                                                                                                                     |

The `NEXT_PUBLIC_*` values above are baked in at build time. When you deploy through the bundled GitHub Actions workflow, add them to the workflow's build step (or set `mcp_origin` in `deploy.yml`); apart from the sign-in flag, which the workflow turns on when the `ACCOUNTS_CLIENT_ID` repository secret is set, they are not read from repository secrets.
