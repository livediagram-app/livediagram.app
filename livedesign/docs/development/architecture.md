# Architecture

A pnpm + Turborepo monorepo: seven Cloudflare-deployed apps, one distributed command-line app and twenty-four shared packages. Everything runs on Cloudflare Workers (Static Assets for the Next.js apps); there's no Node-hosted backend.

```
apps/
  marketing/    static landing site (Next.js export, /)
  live/         the editor (Next.js export; clean routes)
  help/         help centre (Next.js export + MDX, /help)
  api/          REST + WebSocket worker (D1 + Durable Objects + R2, /api)
  mcp/          MCP server for AI tools (OAuth + tools, mcp.livedesign.app)
  router/       service-binding router stitching the apps under one hostname
  cli/          the livedesign command line for agents and scripts (Node, one esbuild bundle)
packages/
  ui/             shared UI primitives + chrome icons (Brand, Timeline, CloseIcon, etc.)
  design/       design data model (Tab, Element types + helpers)
  icons/          icon catalogues (line-art + stickers) + SVG markup builders
  templates/      template catalogue + pure element builders (editor template starts + MCP)
  template-previews/ per-template preview SVGs (editor template starts + marketing template gallery)
  help-registry/  help-centre article/category registry + search keywords (help app + editor search)
  api-schema/     wire-format DTOs the api worker emits + the live editor consumes
  api-client/     the api client the MCP and the CLI share (fetch, timeouts, ApiError)
  agent-verbs/    the verbs the CLI routes to: schemas, handlers, compact text, addressing, guides, the skill
  explorer-lens/  the Explorer's filter lens: token grammar, matching, autocomplete, chip view models
  page-background/ a page background's colours, patterns and motions, and their parser (pure)
  photo-engine/   photo pages: the photo's layer model and the pixel engine: composite, adjustments, filters, selections, paint, PSD (pure)
  edit-operations/ the engine agent changesets run on: edit operations and replace into element ops
  design-views/ read-only text views of a tab (outline, pages, layout, ...) for agents and scripts
  page-lint/      checks a tab's text fits where it is drawn, with a fix each
  render-png/     SVG to PNG with resvg (wasm) and Inter, for the MCP server's previews, the api's share cards and the CLI's renders
  telemetry-client/ shared browser telemetry emitter (buffer / flush / page-hide beacon)
  licences/       build-time generator of the /licences page from what each app bundles
  source-ast/     parses the repo's own TypeScript with TypeScript 7, for the static guards that read code
  oxlint-config/  shared oxlint config + the repo's own lint rules
  prettier-config/shared Prettier config
  tailwind-config/shared Tailwind theme (brand palette, motion tokens) + the motion-budget guard
  vitest-config/  shared Vitest defaults
  next-config/    shared Next.js settings (the build's type check, skipped only by E2E builds)
docs/specs/          product source of truth, read these before adding features
scripts/        repo-wide dev tooling (next-dev.mjs: shared Next.js dev launcher)
marketing/      off-site copy + media for listings and promotion (see docs/specs/019-marketing/marketing-assets.md)
  copy/         taglines, descriptions, tags, the canonical fact sheet
  media/
    desktop/    desktop product screenshots, captioned
    mobile/     mobile product screenshots, captioned
```

## The editor's shape

The editor route (`apps/live/app/design/[id]/`) is split three ways so no file becomes a god component:

- `useEditorState.ts` is the orchestration hook: it calls each domain sub-hook, threads their dependencies, and assembles the return view-model.
- `EditorContext.tsx` carries that view-model as `EditorContextValue = ReturnType<typeof useEditorState>`.
- `EditorView.tsx` renders the JSX, leaving `editor-page.tsx` a thin page shell.

`useEditorState.ts` is large by design: what remains in it is wiring, not logic, so it is exempt from the ~400-line soft target ([AGENTS.md](../../AGENTS.md#core-principle-no-god-files-plan-placement-first)). New behaviour goes into its own sub-hook, not into it.

## The shared packages

Each app pulls these in via `workspace:*`:

- **`@livedesign/design`** owns the design data model: `Tab`, every `Element` type (Shape / Text / Sticky / Image / Freehand / Table / Link card / Arrow), pages (logo, wireframe and photo), defaults, geometry helpers, snap math, layer ordering, the web components' layouts and the load-time migration of designs saved with groups. It also holds the authoring input every non-editor writer shares: raw elements made safe (`normaliseElement`), finished tabs built (`buildTab`), every stored field per element type (`ELEMENT_FIELD_NAMES`) and validation that names the field and rule it fails (`elementValidationIssue`). The single source of what a design IS.
- **`@livedesign/api-schema`** owns the wire format between the api worker and the live editor: every request / response shape, plus the response envelopes (`DesignResponse`, `TabResponse`, ...) the editor and the MCP server both read, the small shared pure helpers it backs (`sha256Hex` for image-upload dedupe, worker-safe `bytesToBase64` / `bytesToBase64Url`, `embedTabImages` which inlines a tab's uploads for the api snapshot and the MCP preview, `titleCase` for display-casing preset values across the editor + telemetry dashboard, and the page-view path normaliser + the live app's route-segment list, shared by every frontend, the router and the dashboard, [Page view telemetry](../specs/017-telemetry/page-view-telemetry.md)). Adding a field on the server without updating the client used to be routine drift; the typechecker catches it now.
- **`@livedesign/explorer-lens`** owns the Explorer's one filter state ([Explorer filters](../specs/013-workspace/explorer-filters.md)): the lens string's grammar (`parseLens` / `serialiseLens`), matching over listed rows (`applyLens`), the autocomplete engine (`suggestTokens`), the chip, pill and live-region view models, and the `?q=` helpers. Pure, no DOM or React, so the page and any later caller (saved views, the MCP server) read one grammar.
- **`@livedesign/page-lint`** checks a tab's text fits where it is drawn ([Page lint](../specs/024-agents/page-lint.md)): `lintTab` answers the measures (extent, boxes, texts) and two kinds of finding, labels that overflow their box and texts that overflow or print over each other, each with the refs the views print and a fix as edit operations. Pure and deterministic, consumed by the api worker (`?view=lint`, every changeset's footer) and the MCP (the summary line).
- **`@livedesign/design-views`** renders a tab as a [design view](../specs/024-agents/design-views.md): `renderView` builds one view model (refs, derived containment, reading order, edges) and answers the outline, `layout`, `comments`, `show` or `find` as text and JSON, fitted to a token budget with one closing line naming what it left out; `overviewView` summarises a design from per-tab header facts, and `diffView` compares two reads of a tab for the CLI. Refs, slug ids, kind words and containment themselves live in `@livedesign/design` (`element-refs.ts`, `containment.ts`), so edit operations and the lint name elements the same way. Pure and deterministic, consumed by the api worker (`?view=`).
- **`@livedesign/edit-operations`** is the engine an agent changeset runs on ([Edit operations](../specs/024-agents/edit-operations.md)): `parseEditOperations` reads the line form (JSON objects allowed on a line) and `validateEditOperations` the JSON form; `applyEditOperations` applies the twelve operations to a tab, resolving refs and selectors, placing new boxes beside what they name and making room on insert; and `applyReplace` builds a whole tab from a template or raw elements. Each answers the next tab, its element ops and their inverse, the result lines and the targets it resolved, or named refusals with nothing applied; `formatResultLines`, `formatResultFooter` and `formatRejections` print them. Its `pages` slice runs an agent's [Pages](../specs/024-agents/pages-for-agents.md) writes: `parsePagesRequest` reads the body, `applyPageChanges` adds, sets, lays out, moves and deletes pages, on the same pure page edits the editor's page panel uses (`packages/design/src/pages-edits.ts`). Containment and carrying (`containerContents`) and refs live in `@livedesign/design`, shared with the views. Pure and deterministic, consumed by the api worker.
- **`@livedesign/ui`** owns the cross-app UI primitives. The chrome (`Brand`, `SiteHeader`, `SiteFooter`, `SiteSwitcher`), the form + feedback controls (`Button`, `TextInput`, `Select`, `EmptyState`), the hover and focus hints (`Tooltip` for a name, `HoverCard` for a title and description; see [Tooltips, hover cards and popovers](../specs/004-interface-design/tooltips-hover-cards-popovers.md)), the shared behaviour hooks (`useMediaQuery`, `useCopiedFlash`, and the dismiss / focus trio `useClickOutside`, `useEscape`, `useFocusTrap` the editor's dialogs and the public sites' popovers share) plus the popover-clamping helpers. It also holds the public sites' shared plumbing: the site constants (`SITE_URL`, `SITE_NAME`, `REPO_URL`, the `BRAND_ICONS` favicon set, the `PUBLIC_VIEWPORT`), the SEO builders (`pageMetadata` for per-page metadata, `breadcrumbJsonLd`, rendered by `JsonLd`), and `PageViewBoot`, the page-view tracker wired to the shared `siteTrack` emitter. Reach for these before re-typing a class list: a control that exists here and is rebuilt in an app is the drift this package was made to stop. The package also owns the **chrome icons** (`src/icons/`): a `Glyph` base (square viewBox, `currentColor` stroke, round caps, `aria-hidden`) and named React icons (`CloseIcon`, `TrashIcon`, `ChevronDownIcon`, `SearchIcon`, `LinkIcon`, `SharedDotIcon`, ...) that take `size` / `strokeWidth` / `className` overrides, so a glyph the editor, marketing hero and telemetry dashboard all draw is one path, not a copy per file. These are app-chrome components; the canvas's own icon catalogue (SVG markup strings for canvas elements) is `@livedesign/icons`.
- **`@livedesign/icons`** owns the catalogues (the line-art glyphs and the stickers of [Stickers](../specs/010-palette/stickers.md)) plus pure SVG-markup builders for them, and `xmlEscape`, the one XML escaper every SVG builder in the monorepo shares (`@livedesign/design` re-exports it). The editor dynamic-imports the data modules through its icon registry so they stay out of its first-load JS; the api + mcp workers static-import `@livedesign/icons/resolve` so headless renders (the live image, Explorer thumbnails, MCP inline images) draw the real glyphs.
- **`@livedesign/templates`** owns the template library: the catalogue (kinds, titles, categories, per-template canvas overrides) and the pure per-template element builders. Two callers: the editor's template starts (which layer its theme recolour on top in `apps/live/lib/template-builders.ts`) and the mcp worker's `list_templates` / `template` tools ([MCP server](../specs/015-api/mcp-server.md)), so the scaffolds can't drift between them. `buildTemplateTab` makes a finished template tab for the MCP and a changeset's `replace` alike.
- **`@livedesign/template-previews`** owns the per-template preview illustrations: one static SVG per `TemplateKind`, rendered by the editor's template picker and by the marketing site's template gallery, so a template's card looks the same wherever it is offered and a new kind gets its artwork in one place. Its tests assert every listed template has a preview and that each drawing stays inside its viewBox.
- **`@livedesign/help-registry`** owns the help-centre article + category registry: slugs, titles, descriptions, and per-article search keywords, plus the pure href/search helpers. Two callers: the help app's browse + search (`apps/help/lib/articles.ts` re-exports it) and the live editor's search-panel Help group (`apps/live/lib/help-search.ts`), so adding an article once makes it findable in both.
- **`@livedesign/licences`** generates the third-party licences page ([Third-party licences](../specs/002-project-scope/third-party-licences.md)). The marketing build runs it after every other app has built: it reads what each Next app ships to the browser from `next experimental-analyze` and what each worker bundles from a `wrangler --dry-run` metafile, collects each package's licence and notice files (with reviewed overrides for packages that ship none, and a reviewed table for what sits inside WASM and fonts), and writes a manifest plus deduplicated plain-text files that `apps/marketing/app/licences` renders. A package with no licence text, an unrecognised licence, a disallowed one or an unreviewed binary fails the build with a named error.
- **`@livedesign/source-ast`** parses the repo's own TypeScript for the static guards that read code ([Source scanners](../specs/003-system-architecture/source-scanners.md)): `parseSourceFiles(paths)` opens the files as one in-memory project in TypeScript 7's native compiler (`typescript/unstable/sync`) and returns their syntax trees.
- **`@livedesign/oxlint-config`** / **`prettier-config`** / **`tailwind-config`** / **`vitest-config`** / **`next-config`** own the shared lint / format / theme / test / Next.js configs so every workspace stays consistent. `tailwind-config` also owns the motion tokens (`duration-micro` / `-short` / `-long`, mirrored as numbers in `@livedesign/tailwind-config/motion`) and the static motion-budget guard every app runs in its tests ([Motion](../specs/004-interface-design/motion.md)).

## Tech stack

What's running:

- **Frontend**: Next.js 16 (Turbopack) with `output: 'export'`, React 19, TypeScript 7 (the Go compiler, see [contributing](contributing.md#typescript)), Tailwind CSS 4.
- **API**: Cloudflare Workers (vanilla `fetch` handlers, not Hono).
- **Database**: none of livedesign's own. Each design's content is in its own SQLite-backed Durable Object, `DesignRoom` ([API app](../specs/015-api/api.md) "Storage"), and each person's workbench pairings in their own. Where a design is filed, who may reach it, the Trash, the Timeline and the Inbox are liveworkspace's index's ([one-explorer.md](../../../liveworkspace/docs/one-explorer.md)); a person's settings, name and email address are the liveworkspace accounts Worker's.
- **Local persistence** (optional per design, [Offline Mode](../specs/006-design/offline-mode.md)): Offline Mode stores a design only in the browser's IndexedDB, never the api. It is opt-in at create time (or by taking a cloud design offline) and dispatched behind the single `apps/live/lib/api-client.ts` persistence boundary on `isOfflineId(id)`, so the rest of the editor takes the same code path either way. Convertible both directions: Sync Design uploads it to D1, Take Offline downloads it and deletes the server copy. See [Offline Mode](../specs/006-design/offline-mode.md).
- **Realtime**: Cloudflare Durable Objects, one room per design. Edits sync as granular, id-addressed element ops, so concurrent edits to _different_ elements merge instead of clobbering, and the room stamps each mutation with a per-`epoch` sequence so peers converge and a reconnecting client catches up from a bounded op log (see [Realtime conflict resolution](../specs/012-collaboration/realtime-conflict-resolution.md)). Two people editing the _same_ element at once is last-writer-wins; the advisory, client-only selection lock ([Live app](../specs/007-editor/live-app.md)) makes it rare, not impossible. The fields a whole room writes at once (checklist ticks, comments) instead travel as per-change deltas that commute, and the room keeps a small ledger of them which the api merges into each tab save, so a save snapshotted before somebody's tick can't erase it from D1 (see [Collaboration race hardening](../specs/012-collaboration/collab-race-hardening.md)). Every server-stored design has a room, personal ones included: agents and API-token scripts change tabs with [changesets](../specs/024-agents/agent-changesets.md), which the api applies, records in D1 (`agent_changesets`, with the tab's compare-and-swap revision `tabs.rev`) and relays to the room, and which every editor save re-applies unless that editor has seen it. The whole-tab `PUT` is the editor's autosave alone.
- **Image storage**: Cloudflare R2, content-addressed by SHA-256, gated on owner + share-code reads (see [Image element + per-owner gallery](../specs/009-elements/images.md)).
- **Auth** (optional): sign-in through the liveworkspace accounts Worker (`liveworkspace.app`, OAuth 2.1 authorization code + PKCE), with livedesign as an OAuth client. The api worker runs the round trip (`/api/auth/*`, refresh token in an HttpOnly cookie), verifies access tokens locally against `${ACCOUNTS_URL}/api/auth/jwks`, and silently degrades to pure-guest mode when `ACCOUNTS_URL` / `API_RESOURCE` are unset.
- **Email** (optional): the api worker sends transactional email via Resend (`apps/api/src/email/`) — the account-deleted message and opt-out notifications (someone joins your shared design, comments, mentions, assigned actions, milestones) configurable on the Explorer profile page. Team invitations and API-token expiry warnings are the accounts Worker's to send. Addresses are the liveworkspace account's verified ones, asked of the accounts Worker; the onboarding series (welcome, tips, win-back) is the accounts Worker's to send. Gated on `RESEND_API_KEY`: no key, no sends (see [Transactional email (Resend)](../specs/014-identity/transactional-email.md) and [Account settings & email notifications](../specs/014-identity/profile-and-email-notifications.md)).
- **Timeline** ([Timeline](../specs/013-workspace/timeline.md)): liveworkspace's index keeps it for every app, and the shared Explorer shows it at `/explorer/timeline`. The index records what it changes itself (a design made, renamed, moved, trashed, restored, shared); a design's Durable Object reports who edited it from its outbox (`apps/api/src/design-room/design-outbox.ts`), which also counts toward that person's Most Used.
- **Inbox** ([Inbox](../specs/013-workspace/inbox.md)): liveworkspace's, one view in the shared Explorer across every app. A design's Durable Object pushes each changed tab's comment threads and actions to the index from its outbox, on idle and at most once a minute (`apps/api/src/design-room/design-outbox.ts`). A row links into the editor with `#t=<tab>&el=<element>&open=action|comments`, which selects the element and opens its popover.
- **Explorer Home** ([Explorer Home](../specs/013-workspace/explorer-home.md)): the shared Explorer's Home view (Jump Back In, What Happened), read from the index. The editor records an open with the index when it loads a design; designs stored only in this browser keep their open days on their own IndexedDB record and join Jump Back In by the same rule (`apps/live/lib/offline/offline-opens.ts`).
- **Trash** ([Trash](../specs/013-workspace/trash.md)): the index's. A deleted design stays 30 days in the Trash, restorable, then the index deletes it for good and asks the design's Durable Object to drop its content. Offline Mode designs get the same rule in IndexedDB. The MCP server can bin and restore but never purge.
- **API tokens** (optional, [Public API and API tokens](../specs/015-api/public-api-and-tokens.md)): signed-in users make revocable liveworkspace account tokens (`lwt_…`) on liveworkspace.app to call the REST API from their own scripts; the api worker checks an `Authorization: Bearer lwt_…` with liveworkspace and caches the answer for a minute. Signed-in only (like teams), six-month expiry. Absent in pure-guest mode.
- **API description** ([API documentation (OpenAPI)](../specs/015-api/api-documentation.md)): `GET /api/openapi.json` serves a public OpenAPI 3.1 design of the whole `/api/*` surface, assembled (`apps/api/src/openapi/`) from a declarative route manifest plus component schemas generated from `@livedesign/api-schema` (`pnpm --filter @livedesign/api gen:openapi`). A drift test pins the manifest to the real dispatch and the committed schemas to the types. The human-facing companion is the help centre's **Developers** category (`apps/help`).
- **Routing edge**: a Cloudflare Worker stitching the apps under one hostname via service bindings.

## Hard constraints

The repo's shape isn't accidental. Three rules keep the stack honest:

- **Static-only frontends.** Next.js apps use `output: 'export'`. No SSR, no Node runtime, no Next.js API routes. Server logic goes in the api worker. Breaking this breaks Cloudflare Pages deploys.
- **Reuse over duplication.** Shared types, UI primitives, configs, and the design data model live in `packages/`, never copy-pasted across apps. If two apps need the same thing, it lives in `packages/` on first occurrence.
- **No secrets in source.** The repo is public; secrets travel via env vars (`.env.local`), `wrangler secret put`, and GitHub Actions repo secrets. See [Secrets policy](../specs/002-project-scope/secrets-policy.md).

## Auth model in one sentence

Every person is a liveworkspace identity sent as `Authorization: Bearer`: a guest's year-long guest token (kept in `localStorage`) or a signed-in account's access token (whose `sub` claim becomes the owner id), and every request about one design also carries the index's grant on it as `X-Index-Grant`. The canvas always works without signing in. See [Auth + guest access](../specs/014-identity/auth-and-guest-access.md) for the full hybrid model and [API app](../specs/015-api/api.md) for how the api worker resolves the owner.

## Deployment

GitHub Actions → Cloudflare Workers. Build artefacts get uploaded once, then marketing / help / api ship in parallel; live and mcp deploy after `api` (both have service bindings to it), and the router deploys last because its service bindings need the others to exist.

Two environments run that same sequence, from one reusable workflow (`deploy-reusable.yml`) so they cannot drift:

|         | Production                               | Staging                                               |
| ------- | ---------------------------------------- | ----------------------------------------------------- |
| Host    | `livedesign.app`                         | `staging.livedesign.app`                              |
| Trigger | Manual, after a green CI run             | Automatic, on every green CI run on `main`            |
| Workers | `livedesign-<app>`                       | `livedesign-<app>-staging` (wrangler `[env.staging]`) |
| Data    | `livedesign` D1 + `livedesign-images` R2 | Its own D1 / R2 / KV — no production data, ever       |

Staging exists mainly so a D1 migration runs against a real remote database one deploy before it reaches the one holding people's designs. It is public but `noindex` (the router stamps `X-Robots-Tag` when its `DEPLOY_ENV` is `staging`). See [Staging environment](../specs/016-platform/staging-environment.md).

Both environments also get the **hosted profile** (`apps/api/hosted-vars.json`: telemetry on, per-owner image caps), which the workflow adds with `wrangler deploy --var` only in livedesign.app's own repository and then reads back off the live api worker. A fork deploys the committed config alone, so it is telemetry-off and uncapped. See [Deployment](../specs/016-platform/deployment.md) "Hosted profile".

See [Self-hosting](../operations/self-hosting.md) for the step-by-step, and [Deployment](../specs/016-platform/deployment.md) for the deeper deployment contract.
