# Telemetry + public transparency dashboard

First-party, anonymous product analytics, surfaced on a **public** dashboard so anyone can see what we measure. The goal: understand which features get used so we know what works, while staying honest about the product's "no creepy tracking" stance.

livedesign sends its events to liveworkspace's telemetry service, a platform service every liveworkspace app uses ([liveworkspace telemetry](../../../../liveworkspace/docs/specs/008-telemetry/telemetry.md)). The service (`liveworkspace/apps/telemetry`, API `https://liveworkspace.app/api/telemetry`) owns ingest, storage, retention and the public dashboard (`https://liveworkspace.app/telemetry`, one view per app); its spec is the source of truth for all of that. livedesign owns its closed vocabulary (`packages/api-schema`), its emitters, the CLI's relay (`POST /api/events`, below), and its dashboard data (`liveworkspace/apps/site/app/telemetry/livedesign/`). `/telemetry` on livedesign.app redirects to the dashboard filtered to livedesign. This spec defines the vocabulary and the counting rules.

## Principles

- **Anonymous, aggregate, first-party.** Events carry no user id, no IP, no user-generated content (never a design name, tab name, participant name, element text, share code, or design id). Only a fixed, app-defined vocabulary of enum values is ever stored.
- **No external vendors.** Ingestion, storage and the dashboard are liveworkspace's own telemetry service, run by us. Nothing is sent to a third party, and data is never sold or shared beyond the public dashboard.
- **Off by default.** A single env var gates the whole system, so a deployment emits/serves nothing unless it opts in. No committed config turns it on: livedesign.app's own deploys do, through the hosted profile ([Deployment](../016-platform/deployment.md) "Hosted profile"), which a fork's deploys never apply. This keeps the "no required SaaS calls" rule ([03](../002-project-scope/open-source-and-business-model.md)) intact.
- **Transparent.** The dashboard is public (`https://liveworkspace.app/telemetry`, and `/telemetry` here redirects to it), and the privacy policy + landing page say plainly what we capture and why, and link to it.

## Event schema

Every event is three small fields (`packages/api-schema`, shared by emitter + ingest so they can't drift):

```ts
type TelemetryEvent = {
  category: TelemetryCategory; // the "parent": Document | Element | Tab | Theme | Canvas | Template | Comment | Note | Action | Search | UI | Folder | Layer | Session | Facilitator | Team | Participant | Help | Token | Mcp | Cli | Email | Error | Timeline | Home | Activity | Page | Cta | Trash | Draw | Explorer | Agent | Timing
  action: TelemetryAction; // the "verb": Created | Deleted | Shared | Joined | Added | ...
  type?: string | null; // one app-defined reference value: 'Square', 'Edit', 'PNG', a template id, a theme name
};
```

The category for a whole design is `Document`, the vocabulary's name for it (`TELEMETRY_CATEGORIES` in `packages/api-schema/src/telemetry-schema.ts`); everywhere else livedesign calls it a design ([Domain language](../003-system-architecture/domain-language.md)).

Examples: `{category:'Document', action:'Created'}`, `{category:'Document', action:'Shared', type:'Edit'}` (plus `TabScoped` / `Rescoped` for [Tab-scoped share links](../013-workspace/tab-scoped-share-links.md)), `{category:'Document', action:'Joined', type:'Edit'}`, `{category:'Element', action:'Added', type:'Square'}`.

`category` and `action` validate against closed enums: the ingest endpoint drops any event whose category or action is not in `TELEMETRY_CATEGORIES` / `TELEMETRY_ACTIONS`.

`type` is **not** an enum, and the guarantee on it is a different, weaker one worth stating plainly. Every caller passes an app-defined preset (a shape kind, a share role `Edit`/`View`, an export format, a template id, a theme name) — that is the rule, and it is what keeps UGC out. The endpoint cannot check membership of a set, because there isn't one: a new shape, template or theme would otherwise mean editing `packages/api-schema` every time. What it enforces instead is a **shape bound**, `TELEMETRY_TYPE_PATTERN` (`/^[A-Za-z0-9 ._-]{1,40}$/`): a short token of safe characters, which rejects anything that reads as free text and caps what a misusing caller could get onto the public dashboard.

So the safety property is: callers only ever send presets, and the pattern is defence-in-depth behind that, not a substitute for it. A short alphanumeric string that happens to be user content would pass the pattern, which is precisely why the calling rule is the thing that matters.

In practice a `type` is either a literal or derived from a closed vocabulary — an element kind through `titleCaseType`, an export format through a lookup table, a boolean through a ternary of two fixed strings. The case that proves the rule is the theme name: a **custom** theme is named by the user, so `themeTelemetryLabel` maps every custom id to the literal `'Custom'` and only ever emits the built-in themes by name. That is the shape any new `type` source should take — map user-owned values onto a fixed token before they reach `track`, rather than relying on the pattern to catch them.

## Storage and retention

The telemetry service stores and ages out the events, one row per event tagged with the app (`livedesign.app`), with no owner or IP column, so rows are anonymous by construction ([liveworkspace telemetry](../../../../liveworkspace/docs/specs/008-telemetry/telemetry.md) "Retention"). livedesign stores no events itself.

## API

The ingest (`POST https://liveworkspace.app/api/telemetry/events`, body `{ app: 'livedesign.app', events: TelemetryEvent[] }`) and the summary (`GET https://liveworkspace.app/api/telemetry/summary?app=livedesign.app`, or every app) are the central service's, specified in [liveworkspace telemetry](../../../../liveworkspace/docs/specs/008-telemetry/telemetry.md). The ingest validates each batch against **this app's** closed vocabulary (`isValidTelemetryEvent` in `@livedesign/api-schema`) and drops this app's server-emitted pairs from browser batches (`SERVER_EMITTED_EVENT_PAIRS`). The summary's windows are fixed UTC days (`TELEMETRY_WINDOW_DAYS`, from `@liveworkspace/telemetry`, re-exported by `@livedesign/api-schema`), with each app's share of every window and day (`byApp`).

## On/off env var

Browser builds read `NEXT_PUBLIC_TELEMETRY_ENABLED` (baked at build; livedesign.app's deploys set it through the hosted profile, `apps/api/hosted-vars.json`) and send nothing when it is off, and `NEXT_PUBLIC_TELEMETRY_URL` names the service (unset is production's; staging's comes from the hosted profile; locally `http://localhost:8790/api/telemetry`). The api and mcp workers send their own events only with `TELEMETRY_ENABLED = "true"` **and** livedesign's Worker key, `TELEMETRY_KEY` (a secret, the same value on both workers and as the service's `TELEMETRY_KEY_LIVEDESIGN`), at `TELEMETRY_URL` (hosted profile per environment; unset is production's). The service's own `TELEMETRY_ENABLED` decides whether anything is stored at all. On top of these, each user has a per-device opt-out flag stored alongside the other user preferences ([User preferences](../007-editor/user-preferences.md), `telemetryEnabled`, default true). When that flag is false, `track()` is a no-op for that browser; this is the user-facing lever the landing page and the dashboard reference when they say "first-party, no creepy tracking".

## Abuse controls

The central ingest is public and unauthenticated by design, and its guards are the service's ([liveworkspace telemetry](../../../../liveworkspace/docs/specs/008-telemetry/telemetry.md) "Abuse controls"): this app's **closed vocabulary** and a 100-event batch cap, an **Origin check** (a browser batch naming `livedesign.app` must come from one of livedesign's own origins, so another site can't post in its name), a **per-network rate limit** on browser batches (the IP is a transient key, never stored), and **livedesign's Worker key** for posts from our Workers, which send no Origin. The CLI's counts (`Cli·Used`) are sent from people's machines, with neither an Origin nor a key, so they go through the relay below.

### The relay

The CLI runs on somebody's machine, has no page origin and holds no key, and it posts to its profile's api. So the api keeps **`POST /api/events`** as a thin relay: body `{ events }`, validated against the vocabulary, server-emitted pairs dropped, capped at 100, then passed on to the service under the api's key. Always 204. Its guards: a same-origin filter, the per-IP `EVENTS_RATE_LIMITER`, 120 batches/60s, the IP a transient key never stored or passed on; it is exempt from the design write limiter. Nothing in the browser uses it.

## Emitting

A `track(category, action, type?)` helper buffers events and flushes them batched on an interval and on `visibilitychange`/unload via `navigator.sendBeacon`. Fire-and-forget; failures are swallowed (telemetry must never affect the host app). The buffering engine is `@liveworkspace/telemetry`'s, bound to this app by `@livedesign/telemetry-client`, which posts each batch to the central service as `text/plain` JSON (a cross-site request with no preflight and no cookies), wrapped with the policy (the `NEXT_PUBLIC_TELEMETRY_ENABLED` build gate + the [User preferences](../007-editor/user-preferences.md) opt-out): the editor builds its own emitter, and the public sites (help, marketing) share one, `siteTrack`, so their policy can't drift. **An opt-out made in the editor silences the help centre too**, since both sit on the livedesign.app origin and read the same localStorage preferences blob. How each reads it is app-owned (the editor caches behind its preference-change events, the help centre reads straight through), but _where_ it reads and _which way it defaults_ are not: `USER_PREFERENCES_STORAGE_KEY` and `telemetryOptInFromRaw` live in `@livedesign/telemetry-client` so a key rename in one app can't leave the other quietly emitting for a user who opted out. Six surfaces emit: the **editor** (`apps/live`), the **help centre** (`apps/help`, the `Help` category), the **marketing site** (`apps/marketing`: page views only, see below), the **MCP worker** (`apps/mcp`, the `Mcp` category), and the **api worker itself** (server-side self-reports, posted with its Worker key: `Error·Api·Internal.<Method>.<Route>` for an unhandled server exception, the whole `Email` category, which has no browser to emit from, and the counts only the server can make once each: `Session·SignedUp`, `Session·SignedIn`, `Document·Joined` and `Document·Used·Multiplayer` (the design room, once per multiplayer session), see below). Those server-owned pairs are listed in `SERVER_EMITTED_EVENT_PAIRS` (`@livedesign/api-schema`) and **dropped from browser batches by the central ingest**, so a stale cached editor bundle that still emits one (or anyone posting by hand) cannot double count what the worker records; the editor's coverage test also fails if an editor call site emits one. Server-side emits share one helper (`apps/api/src/server-telemetry.ts`, `reportServerEvent`), gated on `TELEMETRY_ENABLED` and `TELEMETRY_KEY`; they are anonymous counts like every other row, and the per-browser opt-out cannot reach them because no browser is involved. All three frontends also report `Page·View·<path>` on each path change ([Page view telemetry](page-view-telemetry.md)), and for marketing that is its only event. (The landing funnel, [Landing funnel](../019-marketing/landing-funnel.md), keeps it that way: a CTA's link carries which button it was, and the editor reports the `Cta` events.) A page count sent first-party to our own telemetry service, anonymous, cookie-free and honouring the same opt-out, is within this spec's principles, and the marketing "0 third-party trackers" claim stays literally true. Call sites are one-liners, e.g. `track('Element', 'Added', 'Square')`.

The aim is to cover every meaningful interaction a person has with a design (discrete feature actions, never continuous gestures like drag/resize/pan/zoom or raw colour tweaks, which would just be noise). Current taxonomy:

A session is a run of continuous occupancy: it ends only when the room empties, so a peer who refreshes or reconnects while a colleague is still in keeps the same session, and a room that empties and fills again later is a new one. The "already counted" mark rides on each socket's attachment, so it survives hibernation and disappears with the last socket. SignedOut (just signed out); Deleted `Account` (a signed-in user deleted their livedesign data, fired from the Delete-account dialog after the server-side wipe but before the session ends so the event still reaches the wire; their liveworkspace account stays); these only fire when sign-in is configured; pure-guest deploys emit nothing here. Opened `Embed` (a read-only embed view rendered, [Read-only embeds (`/embed`)](../013-workspace/embeds.md); one emit per iframe document). Opened `Workbench` (the editor mounted inside a workbench's frame, signed in by a workbench session, [Workbench embeds](../013-workspace/workbench-embeds.md); one emit per mount).

A refreshed token for the same guest counts nothing. First-time visitors who sign up without ever being a guest surface via `Session`/SignedUp instead. No type, no identifier: the event is a bare count. Returned `Anonymous`/`Authenticated` (a returning browser opened the app on a later UTC day: the daily-active-returns signal) is the counterpart, at most once per browser per UTC day. It is sent from the editor's `useIdentityBootstrap`, from `/new`, and from the Explorer on this app's own address (`/explorer`, liveworkspace's page served here: liveworkspace/docs/specs/008-telemetry/telemetry.md "The Explorer on liveworkspace.app"), all gated by the one `livedesign:v2:last-active-day` key in this origin's storage, so the first open of the day wins wherever it happens and a visitor who only opens the Explorer still counts. The type splits guests (`Anonymous`) from signed-in users (`Authenticated`), so `Participant·Returned` sums both. A browser's first observed day only seeds the key and emits nothing (that day is a `Created` or a `SignedUp`, not a return). Like `Created` and `SignedUp`, it is per app: the key is this app's, so a browser that has used another app is still new here on its first visit and returns here only on a later day here. No identifier is sent: the per-day dedup is entirely in the browser (`createDailyReturn` in `@liveworkspace/telemetry-client`, bound in `apps/live/lib/daily-return.ts`).

Tokens are made by hand and revoked on liveworkspace.app, and not counted here. The `type` is the fixed source only — never the token, its name, or the client name.

A bare `void fetch` loses that race most often on the cheapest, fastest tools.

Sent by the CLI process (`apps/cli/src/telemetry.ts`) to the active profile's `/api/events` (the api's relay to liveworkspace's service, "The relay" above), one event, no credential, awaited at most 300 ms after the command's output; off with `LIVEDESIGN_TELEMETRY=0`, `DO_NOT_TRACK` or `telemetry = false` in its config, and the first send says on stderr what is counted. `telemetry off` sends `UI·Toggled·TelemetryOff` before it writes the setting, `telemetry on` sends `UI·Toggled·TelemetryOn` after. Charted as the CLI Commands stack beside MCP Tool Calls.

- **Error**: failures, counted generically: never a message, stack, URL, or anything user-generated. The action carries the error's **source** (a deliberate noun in the verb slot), and the type says **what and where**, as dot-separated PascalCase parts: `<Kind>.<Where>[.<Which>]`. A bare kind is unattributable (a spike of `Http403` says something is being refused and nothing about what), so every source names its location from a closed vocabulary. The parts are built by the shared helpers in `@livedesign/api-schema` (`error-telemetry.ts`: `errorTypeToken`, `apiRouteLabel`, `errorNameToken`, `errorPageToken`), which strip non-alphanumerics inside a part and cap the whole token at `TELEMETRY_TYPE_PATTERN`'s 40 characters (the first part, the kind, always survives; a rare long combination loses the tail). The dot is deliberate: the pattern rejects a colon and the ingest would drop the event silently.

The action is the caller's own intent string (`Http403.SaveTab`, `Http500.CreateDesign`), authored in `lib/api` and never derived from user input; the code is the worker's snake_case `error` token when the body carried one (`Http401.SaveTab.SignInRequired`), so a spike names the rule that fired. A prose `error` is left out, and the whole type is cut at the 40-character cap (`Http401.SaveTab.AccountIdNotAGuestCreden`). Emitted from the shared response choke point (`expectOk*` -> `ApiError`) through `lib/api/error-report.ts`, wired via `setApiErrorReporter` from the editor boot so the api module never imports the telemetry wrapper (it sits under the user-preferences -> api-client import cycle). The expected-404 read paths that return null don't emit.

An abort (the caller cancelling) and a browser reporting `navigator.onLine === false` are not counted: neither is our fault, and the second would report every autosave retry until the connection returned.
  - Both editor-side `Api` sources above share the client cap: at most 10 reports per distinct type per page load (`createPerTypeCap` / `ERROR_EMIT_CAP_PER_TYPE` from `@livedesign/telemetry-client`, the same budget `installClientErrorTracking` uses). A failing request in a loop floods exactly as hard as a throw in one; a failed tab load retries only on Retry or a real change of tab, design, or identity ([Per-tab storage](../006-design/per-tab-storage.md)), and the cap keeps any other loop to ten rows.
  - `Api` `Internal.<Method>.<Route>`: the api worker's own top-level catch-all recorded an unhandled server exception, e.g. `Internal.Put.Designs.Tabs`. Same route label, built from the request the worker was serving; a resource outside the dispatch switch reads `Unknown` rather than being echoed (a test keeps the label's resource list identical to the switch). The worker reports it itself (`reportServerEvent`), so a server crash counts even when no client survives to report it; gated on `TELEMETRY_ENABLED` and `TELEMETRY_KEY`.
  - `Api` `Http<status>.<Tool>` / `Internal.<Tool>` from the **MCP worker** ([MCP server](../015-api/mcp-server.md) §4.12): an api call inside a tool 5xx'd or never completed, labelled with the tool that was running (`Http503.UpdateDesign`, `Internal.FindDesigns`), the same token as its `Mcp·Used` event. `registerTool` runs every handler inside an `AsyncLocalStorage` scope (`tool-scope.ts`), so helpers several calls below the handler know the tool without threading it through, and concurrent calls in one isolate can't mislabel each other. 4xx stays unreported (model-correctable input, not a fault). The **CLI** reports the same way, labelled with its verb (`Http503.TabView`, `Internal.DesignLs`). A failed email send is `<code>.SendEmail` / `Network.SendEmail` (see Email).
  - `Client` `Uncaught.<Page>.<ErrorName>` / `UnhandledRejection.<Page>.<ErrorName>`: window-level uncaught exceptions and unhandled promise rejections in the editor AND the help centre, installed by `installClientErrorTracking` from `@livedesign/telemetry-client`, e.g. `Uncaught.Design.TypeError`. The page is the first segment of the [Page view telemetry](page-view-telemetry.md) page-view path (so ids are already gone: every design is `Design`, `/` is `Home`, the whole help centre is `Help`). The error name is the thrown value's constructor name **only if** it is in a closed list (the built-ins, the common DOMException names, and `ChunkLoadError`, which is a stale tab asking for a bundle chunk the last deploy removed); any other Error reads `Other`, and a thrown non-Error (`throw 'x'`, `reject(undefined)`) reads `NonError`. A stack's function names were rejected as the location: production bundles are minified, so they'd be noise that still leaks code shape. Capped at 10 emits per distinct type per page load, so an error loop can't flood the pipeline and one noisy page can't hide another. The one throw it skips is the edge's bot-detection snippet that Trusted Types refuses by design ([Trusted Types](../016-platform/trusted-types.md)): not our code, and it fired on every page load.
  - `Client` `Render.<Area>.<ErrorName>`: a React render crash caught by an **area error boundary** (`components/primitives/AreaErrorBoundary.tsx`), e.g. `Render.Canvas.TypeError`. This is the "which part of the UI broke" signal. The editor wraps each major area (`Canvas`, `Header`, `TabBar`, `TabDialogs`, `Collaborators`, `Search`, `Modals`, `Popovers`, `ContextMenu`, `ElementDialogs`, `Tour`), and the context menus `Menu` (`MenuErrorBoundary`). The area list is a closed type. Behaviour on a crash: a transient overlay (dialogs, popovers, menus, search, tour) just disappears; a layout area (canvas, header, tab bar, Explorer panes) shows a one-line "Something went wrong in the canvas." notice with **Try Again**, which remounts it.
  - `Warning` `ImageSearch.<Reason>`: the image picker's [Image search](../009-elements/image-search.md) failed in a way the user saw and could retry: `RateLimited` (Openverse's per-IP allowance spent), `SearchFailed`, `ThumbnailFallback` (the full picture was unusable and its thumbnail was tried), and `Pick.<Failure>` (`DownloadFailed`, `GalleryFull`, `ImagesUnavailable`, `TooLarge`, `OfflineBudget`, `Unsupported`, `MissingBytes`, `UploadFailed`). Never the query or a URL.
  - `Client` `DesignLoad.<ErrorName>` and `Warning` `DesignLoad.Slow` / `DesignLoad.TimedOut.<Step>` / `DesignLoad.AutoReload` / `DesignLoad.Late`, `OfflineStore.Unavailable`, `SessionToken.TimedOut`: the design load threw, passed its 10-second message, hit its watchdog at a step (`Identity`, `Participant`, `Design`, `Share`, `FirstTab`), ran its self-healing reload, finished after the watchdog, or carried on past an offline store or session token that gave up ([Load recovery](../007-editor/load-recovery.md)). The two `lib/api` warnings ride the api client's per-type cap through `setApiWarningReporter`.

## Counting rules: one event per gesture, or one per object?

**An event counts the GESTURE, not the objects the gesture touched.** Deleting a twelve-element marquee selection is one `Element·Deleted`; restyling it is one `Element·Changed`; an eraser stroke that wipes a dozen shapes is one `Element·Deleted·Eraser`. The question these answer is "how often do people delete / restyle / erase", and a per-object count would let one marquee drag swamp a hundred single deletes. No `track()` call sits inside a loop.

**The one exception is creation, because creation feeds a census.** `Element·Added·<kind>` is what the dashboard's Palette ranking is built from, so it is a true count of elements created, not of creation gestures. Every from-scratch path emits one per element. The **copy** paths (duplicate, paste, shift-drag) go through `trackDuplicated`, which emits one `Duplicated` for the gesture **and** one `Added·<kind>` per element created, after the copies exist; an empty result emits nothing. `elementTelemetryType` is the single mapper from an element to its token, so a copied code block lands in the same bucket as a drawn one. Rotation is a control, not a gesture, and emits `Element·Changed·Rotation`.

**An event counts what the SERVER accepted, not what the user clicked.** Every list action in the Explorer is optimistic ([Folders](../013-workspace/folders.md)): the row updates locally, the request goes out, and a failure rolls the row back. The emit sits in the request's success path, never beside it: `await apiThing(…).catch(() => {}); track(…)` treats every failure as success, so it is never written. `.then()` comes before `.catch()`, since `p.catch(() => {}).then(f)` runs the success handler after a swallowed rejection too.

Two things emit on the optimistic path, because for them the local action IS the fact: `Element·Copied` (the in-app buffer is the authoritative clipboard; the OS write is a best-effort extra), and `Document·Duplicated` (the copy exists by then; only its filing can fail).

**Deliberate double-emits** (so nobody reads them as double-counting): creating a design from `/new` with a template emits `Document·Created` + `Theme·Changed` + `Template·Used`, three different facts. Filing a tab into a folder name the design has not used before emits `Folder·Created·Tab` + `Tab·Moved·Folder`: the folder now exists, and this tab is in it.

## How completeness is tested

Emitting is fire-and-forget and the public dashboard only renders what **arrived**, so a renamed or deleted event is indistinguishable from a feature nobody used. Checked-in guards replace that missing signal:

- **`apps/live/lib/telemetry-manifest.ts` pins every `category·action` pair the editor emits**, enforced by `telemetry-coverage.test.ts`, which scans the source for `track()` call sites (ternary actions included) and diffs against the manifest. Adding, renaming, or removing an emitted pair fails CI until the manifest is updated, and the manifest's comment sends you here, so the taxonomy above changes in the same change. The same test asserts every pair is inside the closed enums, and that no editor call site emits a `SERVER_EMITTED_EVENT_PAIRS` pair.
- **`PALETTE_TELEMETRY_TYPES` in `@livedesign/api-schema` is the one definition of the palette `type` tokens**, read by the dashboard's Palette view. `palette-telemetry-coverage.test.ts` asserts every shape kind and every non-shape element kind in `@livedesign/design` has a bucket there. It derives its tokens by CALLING `elementTelemetryType`, never by restating its rule: a copy of the rule can only prove the copy agrees.
- **livedesign's dashboard data has its own tests** in `liveworkspace/apps/site/app/telemetry/livedesign/` (Dashboard, below).

Pairs are pinned but `type` values generally are not: types are open-ended by design (a shape kind, a template id, an article slug). The palette tokens are the exception because that is where drift is both invisible and costly.

## Delivery

The emitter's engine (`createTelemetryEngine` in `@liveworkspace/telemetry`, `packages/telemetry/src/emitter.ts`, bound by `@livedesign/telemetry-client`) bounds its losses:

- **A rejected flush is retried once.** A rejected `fetch` re-queues its events at the front of the next batch and arms a fresh timer. Only on a rejection, never on a non-2xx (a server that answered may have stored them, and retrying a 429 worsens it); exactly one attempt; bounded by the 25-event buffer cap (`TELEMETRY_MAX_BUFFER`), oldest dropped first; never on the beacon path.
- **`sendBeacon` returning `false`** (the UA's queue is full) falls through to a `keepalive` fetch.
- **Worker posts carry livedesign's Worker key**, so the api and mcp workers never share the browser rate limit.

Accepted losses: client errors and the editor's api errors cap at 10 per kind per page load; events buffered when a tab is hard-killed are gone (telemetry owns no storage); a second consecutive failure discards the batch. All of these under-count rather than over-count, the safer direction for a usage chart.

Extend by adding to the `TELEMETRY_CATEGORIES` / `TELEMETRY_ACTIONS` enums (if needed) + a one-line `track()` call at the interaction's handler. Page views go through `Page·View` ([Page view telemetry](page-view-telemetry.md)) and new visitors through `Participant`/Created above.

## Dashboard

The dashboard is liveworkspace's: one set of views for every app (`liveworkspace/apps/site/app/telemetry/_shared/`), at `https://liveworkspace.app/telemetry?app=livedesign.app`, and its timeframe panel, tabs, stacks, rankings, trend arrows and loading states are specified there ([liveworkspace telemetry](../../../../liveworkspace/docs/specs/008-telemetry/telemetry.md) "The dashboard"). livedesign's part is its data folder, `liveworkspace/apps/site/app/telemetry/livedesign/`:

- `config.ts`: the name, the noun (design), the accent and category colours, the call-to-action vocabulary and the charts on each tab and section.
- `catalogue/<area>.ts` (visitors, content, features, collaboration, settings, connections, health, email, timings, cli-commands), re-exported from `metric-catalogue.ts`: every chart and stack. A stack references charts by name, so one chart can sit in several stacks. The Dashboard opens with At a Glance (New Visitors, Returning Visitors, Sign-Ups, Designs Created, Multiplayer Sessions, Failed Requests), then the curated stacks by group: Visitors, Content, Features, Collaboration, Connections and Health & support. The Detail tabs are **Features** (Editing, Palette, Modes, Look & Feel, Settings, Collaboration, Connections), **Pages & Help** (Pages, Help, Tours & Prompts) and **Health** (Exceptions, Timings).
- `event-explanations.ts`: one plain sentence per category·action·type (and one per category·action for any type) saying what the person did in the product's own words; `event-explanation.test.ts` fails on an event that falls through, an action with no any-type sentence, or a sentence with jargon or a code name.
- `computed-emitters.ts`: the values every computed emit site can send (an email kind, a tool name, a theme label), keyed by `<path> <Category>·<Action>`, so the scan reads them as literals.
- `retired-events.ts`: the events of removed features, dropped from the summary before any chart (below).
- `palette-types.ts`, `logo-types.ts`, `element-tour-kinds.ts`, `cli-commands.ts`: the closed token tables the rankings read.

Its tests read livedesign's source with the TypeScript parser (`emitter-scan.ts`):

- **Every event has a chart** (`metric-emitters.test.ts`): every emitter (`track`, `siteTrack`, `reportServerEvent`, the Settings catalogue rows `SettingsCategoryPane` emits generically) is charted on some tab.
- **Every card counts an event something sends.** An untyped card (`type: null`) must have no typed emitter for its pair (a card that means "all of them" says `allTypes`, or `typeIn`); a typed card must have an emitter that can send exactly that category·action·type.
- **No event is counted by two unrelated charts.** The only overlaps allowed are a Settings Changed category chart over its setting charts, and a chart and its subset inside one stack whose headline counts one of them.

### Retired features

When a feature is removed, the dashboard drops its events from the summary the moment it arrives (`retired-events.ts`, through `_shared/retired-events.ts`), so no chart, stack, ranking, total, trend arrow or Search result renders them; their stored rows age out with retention and their explanation sentences stay for Search. Each removed feature lists its events there, with a test pinning them: the Activity panel, palette favourites, Settings › Experimental, the `/new` Location step and the Quick Start, custom themes, the in-editor AI assistant, slide decks and presenting ([Presentation mode](../012-collaboration/presentation-mode.md)), the isometric view and the Isometric background pattern ([Canvas and palette](../008-canvas/canvas-and-palette.md#not-in-livedesign)). `Element·Grouped` / `Ungrouped` stay in the vocabulary and no emitter sends them ([Web components are elements; groups are gone](../009-elements/web-components-and-no-groups.md)).

## Routing & deploy

- **Router** ([Router app](../016-platform/router-app.md)): `/telemetry` and everything under it answer `301` to the central dashboard with `?app=livedesign.app` (`TELEMETRY_DASHBOARD_URL` names staging's and local dev's).
- **Deploy** ([Deployment](../016-platform/deployment.md)): nothing of telemetry deploys from livedesign. `TELEMETRY_KEY` is a secret set on the api and mcp workers with `wrangler secret put`; the hosted profile turns telemetry on and names `TELEMETRY_URL`. The central service deploys from liveworkspace.

## Provisioning (one-time, owner only)

1. In liveworkspace, provision the telemetry service and give it livedesign's key as `TELEMETRY_KEY_LIVEDESIGN` ([liveworkspace telemetry](../../../../liveworkspace/docs/specs/008-telemetry/telemetry.md) "First deploy").
2. Set the same value as the `TELEMETRY_KEY` secret on `livedesign-api` and `livedesign-mcp` (and their `-staging` Workers) with `wrangler secret put`.
3. Turn telemetry on: livedesign.app's deploys do it through the hosted profile. Another deployment sets `TELEMETRY_ENABLED = "true"` in `apps/api/wrangler.toml [vars]` and `NEXT_PUBLIC_TELEMETRY_ENABLED=true` for the live, help and marketing builds. Leaving them unset keeps telemetry off, the default.

## Privacy posture

The privacy policy + landing page state: we record anonymous, first-party product events (the three-field schema, examples), to learn which features help; no external analytics vendors; data is never sold or shared beyond the public dashboard (liveworkspace's, `https://liveworkspace.app/telemetry`), and events go to liveworkspace's own telemetry service, not a vendor. This is consistent with the "no tracking pixels / no third-party analytics" claims: first-party, anonymous, no third parties, no ad tracking.
