# Marketing site

The marketing app (`apps/marketing`) is the public landing site served at `/` (everything the router doesn't hand to the live editor's routes, `/api/*`, or `/telemetry`, see [08-router-app](../016-platform/router-app.md)). Static Next.js export, no SSR. It is the top of the acquisition funnel: its only job is to explain what livedesign is and send visitors to `/new`.

## Golden rule: claims map to shipped features

**Every feature claim on the marketing site must correspond to something a visitor can actually do today.** No aspirational copy, no roadmap dressed as present tense.

- If a feature is not built (teams/permissions, true concurrent/CRDT editing, see [02-prototype-scope](../005-project-roadmap/prototype-scope.md)), it does **not** appear on the landing page, even softened.
- When the editor gains or loses a feature, update the landing page in the same change. Drift between the page and the product is a bug.
- Counts (templates, themes, shapes) must match the source of truth ([Canvas and palette](../008-canvas/canvas-and-palette.md), `packages/templates/src/templates.ts`, `apps/live/lib/themes.ts`). The copy never states a count the code does not produce; a count that changes changes the copy in the same change. The templates are the Pages templates: the blanks of each page kind (Blank Logo and the wireframe devices), ready-made logos and wireframe flows, and Photo Edit, one photo page to start.
- Be honest about trade-offs where it builds trust: realtime is **last-write-wins**, not CRDT, say so rather than implying conflict-free merging.

## Structure

Single landing page (`app/page.tsx`), in this order: a sticky header, the hero, the template gallery, the promises, **three story beats**, the privacy callout, a closing CTA, and a footer. The beats tell the product as what it does with pages (presenting them, logos and wireframes) and working on them together, rather than as generic categories.

**The landing page tells a story; the detail lives on a page per category.** The page once ran one block per category, thirteen identical bands (about 12,500px) that read as a checklist; then five beats grouped those thirteen generic categories (The basics, Customisation, Reliability and so on) under ideas. Neither said what the app is for. So the body is now **one story beat per core feature**, and the feature categories are those same beats: `LANDING_SECTIONS` in `lib/landing-content.tsx` is both the beats and the `/features/<id>` pages, rendered on the landing page by `components/StoryBeat.tsx`. A beat has the feature's **glyph and plain name** (`label`, in brand caps beside a brand disc holding the category's glyph from `components/category-icons.tsx` (it held the beat's number until October 2026), one per id and none shared, pinned by `category-icons.test.tsx`), a **headline** above a pitch, **four highlights** (`highlights`: feature titles, each a link to its card on the category page via `lib/feature-anchor.ts`), a primary link into its category page, and **the hero scene that shows the feature** (`scene`, see "Feature scenes" below) playing beside it. The beats run wider than the page's other bands (`max-w-7xl`) and the text column has a **fixed width** (22rem, 26rem from `xl`), the scene taking the rest (about 760px at a 1440px screen, the size the hero draws its scenes), so its small text stays crisp, and it starts on a whole pixel, where a fractional split (5fr to 7fr) landed it between pixels and blurred it. The scene column has **no scroll-in slide**: the scene plays its own build as it arrives, and a transform held mid-entry kept the window on its own layer, painted off the pixel grid; the text column keeps its entrance. Beats alternate the scene's side and the tinted background. While a beat is **one column** (below `lg`, the scene hidden) its text is **centred** (eyebrow, headline, pitch and link), the highlights a centred block with their ticks still lined up on the left; from `lg` it sits left-aligned beside the scene. A category page's hero centres the same way. `landing-content.test.ts` pins the ids in order, a different scene per beat, four highlights that each resolve to one of the beat's own cards, art on every card and no em dash in a beat's copy. The full `FeatureGrid` of cards renders on each **`/features/<id>`** page. See "Feature category pages" below.

All five show from `sm` up and on a phone the middle three, narrower, all on screen; the fan holds fewer cards than the pool (`HERO_FAN_SLOTS`), so a swap always has another template to deal in; a card out of sight is never swapped. It deals from **every listed template but the blanks** (`HERO_FAN_POOL`) in a **fresh random order each visit**: the static HTML is a fixed opening hand, hidden once script runs (`<html data-hero-deal>`, a one-line head script, `lib/hero-fan-boot.ts`; shown anyway after 1.5 s should the page's script never arrive) until the shuffled hand springs in. A small round **Shuffle templates** button sits to the right of the cards: a press flicks the whole hand down and out, card by card from the left (55 ms apart), then deals a new hand from the pool, none of the cards just shown, springing up the same way; the timed swap holds while it runs, and under reduced motion the hand changes with no motion. The button is not shown with a returning visitor's own recent work. Every few seconds one card flicks down and out and the next of the shuffled pool springs up in its place (`app/hero-fan.css`, paced as content); it holds while the pointer or focus is on it, while the hero is off screen or the tab hidden, and under reduced motion (which still deals a shuffled hand, without the motion). A **returning visitor with three or more recent designs** sees their own designs on the fan instead, the four most recent and a card to Explorer Home (the three most recent on a phone, without Explorer Home), and nothing is swapped ([Returning visitor](returning-visitor.md)). ### Start Blank

**Start Blank** (`StartBlankLink` and `START_BLANK_HREF` in `packages/ui`) is a **plain link to the wizard**, `/new?start=blank`, never a menu of blanks: the wizard already asks what the visitor is making, so a menu asking the same question first was only friction. The blank chosen there opens **with no start screen** over the canvas, as Skip's does ([Start Blank](../007-editor/new-design-route.md#start-blank)), since whoever asked for a blank has already said they want no templates. It sits in the header outside the marketing pages (slot `HeaderBlank`; a marketing page's bar has none) and in the hero's search bar (slot `HeroBlank`).

**Every CTA is measured** ([Landing funnel](landing-funnel.md)). A link into the editor from a public page builds its `href` with `ctaHref(href, source)` from `@livedesign/api-schema`, which adds `via=<Surface>.<Slot>` (`Home.Hero`, `Home.Gallery`, `Feature.Closing`, ...). The header takes its surface as a prop (`<Header surface="Faq" />`, passed through to the shared `SiteHeader`'s `ctaSurface`), and `StartDrawingCta` takes `surface` too. A new CTA adds its slot to `CTA_SOURCES` first; a bare `href="/new"` on a public page is a CTA the funnel can't see.

Reusable building blocks: `Section` + `FeatureGrid` (`components/Section.tsx`), `StoryBeat` (`components/StoryBeat.tsx`), `FeatureScene` (`components/FeatureScene.tsx`), `Header`, `Footer`, `Brand` (from `@livedesign/ui`). The feature categories are data, not markup: they live in `lib/landing-content.tsx` as the `LANDING_SECTIONS` array (each entry an `id`, a plain-name `label`, a headline `title`, a `description`, a hand-written `cta` link label, its `scene`, its four `highlights` and its `items`). That single array drives both the landing page's beats and the `/features/<id>` pages, so adding a feature card is a one-place edit and the two surfaces can never drift. **`LANDING_SECTIONS` is the authoritative list** (the numbered walkthrough above is illustrative and may lag); do not fork the grid or hard-code a category list anywhere else. The AI cards (the MCP connection, the optional assistant, export and the API) sit in `collaboration` under AI & your tools, while the footer's "AI & MCP" link and the FAQ's MCP answer open the [Build with AI](build-with-ai.md) setup page (`/ai`).

## Feature category pages

**Arriving on a page is animated, never a cut** (`app/page-motion.css`). Moving between two marketing pages (home to a category page and back) is a cross-design **view transition**: the pages crossfade and the sticky header (`view-transition-name: site-header` on the shared `SiteHeader`) holds still. The opt-in, `@view-transition { navigation: auto }`, is **inlined in the root layout's `<head>`** rather than left in the bundled stylesheet: the browser only runs the transition if the new page has opted in by its first paint, and from the stylesheet it sometimes arrived later, so the transition was skipped and the old page logged "Transition was skipped" (about half of navigations in testing; none since). A link out of the marketing site (into the editor at `/new`, the help centre, the dashboard) **skips the transition** as the page swaps: only the marketing pages opt in, so the browser would otherwise start one, find the editor declined, and report "Transition was aborted because of invalid state" as an uncaught error on every hero click. The marketing page decides by the destination's app, the router's own split (`pageViewApp`), in a small inline `pageswap` listener beside the opt-in. On arrival the category hero eases up piece by piece (`.enter`, staggered by `--enter-delay`), and the feature cards and the landing beats rise in as they scroll into view (`.enter-on-scroll`, a scroll-driven animation where supported, a load-time one elsewhere; on the cards it sits on a wrapper, because the card's hover lift is a transform the animation would pin). All of it is CSS over content already in the static HTML, so crawlers and no-JS visitors get the same page, a browser without these features shows the page as before, and reduced motion turns it all off.

Each `LANDING_SECTIONS` entry gets a static page at **`/features/<id>`** (`app/features/[slug]/page.tsx`, a single dynamic route with `generateStaticParams()` over the section ids and `dynamicParams = false`, so only known categories are generated and an unknown slug 404s at build). The page opens with a rich hero (`components/FeatureCategoryHero.tsx`: the category's `label` as the eyebrow, its headline as the h1, the positioning line, a "Start drawing" CTA, and the same scene its beat plays, laid out like a beat: a fixed text column and the scene taking the rest), then renders the section's full `FeatureGrid`, a breadcrumb (`components/Breadcrumb.tsx`, styled to match the help centre), and the shared closing CTA (`components/StartDrawingCta.tsx`) so a visitor who drills into a category can still convert without bouncing home.

**Every link into the help centre resolves.** A feature card's `href`, an FAQ answer's link and any other `/help/...` path in the marketing source must be a registered article or category in `@livedesign/help-registry`; `lib/help-links.test.ts` scans `app/`, `components/` and `lib/` and fails on any that is not, so a renamed or retired article cannot leave a quiet 404 on the marketing site.

**Feature scenes.** The landing beats and the detail-page hero play the **hero's own editor-window scenes**, one per feature (`components/FeatureScene.tsx` over the scene catalogue in `components/hero-scene-data.ts`, so a scene is declared once). A feature scene **loads only its own board's code** (fetched as the window mounts, well before it plays); the catalogue keeps the boards apart from the scenes' data, so a features page does not carry all of them. The catalogue holds four scenes: **Logo** (`hero-logo-board.tsx`: a mark and wordmark on a logo artboard, beside an App screens tab of wireframes), **Photo** (`hero-photo-board.tsx`: a photo page and its layers), **Present** (`hero-present-board.tsx`: the pages presented full screen) and **Together** (`hero-together-board.tsx`: two people on one brief, live cursors and a comment). A scene **plays its build when it comes into view** (an IntersectionObserver, 40% visible). **It never flashes on arrival:** the static HTML holds the window's frame and its canvas but not the scene, which is first drawn the moment it starts to play, building from an empty canvas; its first play starts with the veil clear (`hero-fade-end`, closing only over the cycle's last second, ready for a replay), where the stage's veil starts solid grey. (Drawing it settled ahead of time showed the finished picture, then the grey veil, then the build.) It **plays once per visit**: scrolled away, it rests on its settled frame with no veil, and does not play again on return, which would snap that frame back to an empty canvas. Under reduced motion it shows only the settled frame. The scenes' SVG stays out of the page's HTML (about 18 KB gzipped on the home page), and only the scene in view animates. Its canvas is sized by **aspect ratio** (16:10, room for the scene's 600 by 400 drawing under the toolbar strip, and no taller than the text beside it), not the hero's fixed heights, and the palette strip across its top answers to the **window's width** (a container query on the canvas: the extra tiles show from 600px of canvas), so a narrower window drops tiles rather than running the strip into the menu button. The scene is **hidden below the two-column breakpoint** (`hidden lg:block`) on both surfaces: stacked on mobile it ate the screen and restated the pitch beside it. Every scene is drawn after the real template it stands for, so what a visitor sees is what they get, on the editor's **Default theme** (the real canvas colour, grid and ink), in light the light half and in dark the dark half; elements whose colour is their identity (stickies, cursors, avatars, highlights, comment pins) keep it. All share the editor chrome, kept in step with today's editor (`components/hero-editor-window.tsx`, `hero-editor-chrome.tsx`, `hero-pages-bar.tsx`): the header as `EditorHeader` lays it out (the `Brand` mark, the design's name with the Shared/Private badge and the **Editing** role pill, and **Share**), the Pages bar where the editor has it, and the bottom tab bar whose active tab is outlined in its accent and carries presence inside the pill. The glyphs are the editor's own from `@livedesign/ui`, so the mock cannot drift from the editor.

- **Source of truth:** the page reads the matching `LANDING_SECTIONS` entry by `id`; there is no second copy of the feature copy. The golden rule (claims map to shipped features) therefore holds automatically, the detail pages show exactly the cards the landing page used to.
- **Card illustrations** (`components/FeatureArt.tsx`, a barrel over `components/feature-art/*`, one file per subject with shared parts in `*-parts.tsx`, `canvas-marks.tsx` and `page-kit.tsx`): every card's art is a small, product-accurate mock of the surface it describes, drawn on a **300 by 96 stage** that fills the card's frame (about 304 by 96 px; a 220-wide drawing sat small in the middle). It reads in **light and dark** alike: canvas marks take the `--art-*` palette and every panel, rule and label pairs its colour with a `dark:` variant. It shows its **finished picture at rest** and animates only accents (a caret, a cursor, a pulse, a piece landing), so no card blanks out mid-loop; the loops live in `app/feature-art/*.css`, one content stylesheet per art group in the motion budget, each with a reduced-motion rule that settles it to that finished frame.
- **Start from a template:** below the feature cards and above "Explore more of livedesign" (`components/OtherCategories.tsx`), each page has a **Start from a template** band (`components/SectionTemplates.tsx`): the category's `label` as the eyebrow over up to **nine** hand-picked templates, best first, in a grid of threes (two across from `sm`, one on a phone), so a visitor who has just read about a feature can start on one. The picks live in `lib/section-templates.ts`, one list per section id; a category with fewer good fits lists fewer rather than padding. Each card is the landing gallery's own (`components/TemplateCard.tsx`: the picker's preview, title and description) and creates the design straight away (`/new?template=<kind>`), counted as `Feature.Templates` ([Landing funnel](landing-funnel.md)). The band is the gallery's inset band (`BAND_SECTION`), so it reads apart from the white grid above it. `lib/section-templates.test.ts` holds every section id to a list, every list to nine or fewer distinct kinds, and every kind to a listed (not hidden) template.
- **Card edges in dark:** a feature card is the same slate-900 as its band in dark, so its border alone draws its edge; it is slate-700 (slate-800 on slate-900 all but vanished), and its Learn more footer sits on a faint slate-800 wash under a slate-700 rule. The same holds for the band's cards (`BAND_CARD`, the template cards here and on the landing gallery, and the privacy cards) and the Explore more pills.
- **Grouped sub-sections:** a category with many features is hard to scan as one long grid, so its features carry a `group` label and the detail page renders captioned sub-sections (`groupSectionFeatures` builds the ordered groups). `slides` groups into Build, Present and Point the room; `logos` into Logos, Wireframes, Pages and Make it yours; `collaboration` into Work together live, Share & access, and AI & your tools.
- **SEO:** every `/features/<id>` declares its own `alternates.canonical`, emits a `BreadcrumbList` (`Home → <Category>`), and is listed in `app/sitemap.ts` (derived from the section ids so a new section is sitemapped automatically).
- **No `/features` hub index.** The landing page is the feature overview; the category pages are reached from each section's "Explore …" link, not from a hub. (An earlier `/features` index page was removed.) The footer links to the comparison hub + content pages, not a features index.
- **Routing:** these live on the marketing origin under `/features/*`, which the router already forwards to the marketing worker as the default (non-live/api/telemetry/help) path, so no `apps/router` change is needed.

## Social sharing

Word of mouth is part of the acquisition funnel, so the page lets a happy visitor pass it on in one click. `packages/ui/src/ShareRail.tsx` renders a **vertical rail pinned to the right edge of the page**: a rotated "Share" label above the share targets (X, LinkedIn, Facebook, WhatsApp, email) and a **Copy link** action.

It began as a "Share" popover in the header and moved out to the edge to give the header room to breathe. Two consequences of where it ended up:

- **It lives in `@livedesign/ui`, not in the marketing app**, because `SiteHeader` renders it. Surfaces that use the shared header carry the rail by default (the telemetry dashboard is just as worth passing on as the landing page); the help centre turns it off (`shareRail={false}`) because its pages run `max-w-7xl`, so the rail would cover the article sidebar ([Help app](../018-help/help-app.md)).
- **It renders as a _sibling_ of the header, not a descendant.** The header's `backdrop-filter` establishes a containing block that would trap the rail's `fixed` positioning against the header instead of the viewport.

Beyond that:

- **Wide desktop only (`xl`, 1280px).** Page content is `max-w-6xl` (1152px), so only past `xl` is there a real gutter for a fixed rail to sit in without overlapping the content. Below that it is hidden, and a page URL is inherently shareable anyway.
- **Share targets are plain anchor links** to each network's public share-intent URL (`twitter.com/intent/tweet`, `linkedin.com/sharing/share-offsite`, `facebook.com/sharer`, `wa.me`, `mailto:`). No SDKs, no tracking pixels (keeps the "no tracking pixels" claim honest under [03](../002-project-scope/open-source-and-business-model.md)). They open in a new tab (`target="_blank"` + `rel="noopener noreferrer"`).
- **The Appearance rail sits under it.** A second, separate rail of the same card, a gap below, holds the [Appearance](../004-interface-design/appearance.md) toggle, its only place on the public sites: never in the header, and left out below `xl`.
- **Copy link** uses the Clipboard API to copy the canonical URL and flips to a tick for a beat, via the shared `useCopiedFlash`, so a rapid second copy restarts its own countdown rather than inheriting the first one's remainder.
- The shared URL is the canonical production site, `SITE_URL` from the package's own `site.ts` (the one origin constant every app uses), and the share text mirrors the product's one-line description, a constant in the component; update it if the positioning copy changes.
- The icons are stored as raw `<path>` `d` strings rather than JSX, so the module evaluates no top-level JSX at import time and the shared barrel stays importable from non-React test transforms.
- On the landing page itself the `'use client'` boundaries are the `TemplateGallery` (search state over the template cards) and the `HeroIllustration` (the click-to-centre seven-window stage); everything else stays a server component for static export. The rail is a client component too, but it now arrives via the shared header rather than the page.

**Feature-card illustrations.** Every feature card carries a small animated mock of the real editor surface it describes (`components/FeatureArt.tsx`), passed via the card's `art` slot. Like the hero, the motion is **pure CSS**, shared keyframe classes (`fa-*`) live in `app/globals.css`, so it works under static export with no JS and settles to a finished frame under `prefers-reduced-motion`. The mocks must stay faithful to how the feature actually looks (presence avatars, the explorer / share panels), and every page in them is drawn as the editor draws it on the **Default theme**: its canvas, grid and the ink of unpainted shapes, arrows and labels, in the light half or the dark half with the appearance ([Appearance](../004-interface-design/appearance.md)). Only identity colours (stickies, cursors, highlights, selection), elements the example deliberately painted (the editor keeps a user's paint on any theme) and art whose subject is colour keep other colours; when a feature's UI changes, update its art. This is part of the golden rule above, an illustration is a claim too.

## SEO and metadata

The marketing site is the indexable surface for the product, so its `<head>` carries the search and social signals. The editor's routes and the API at `/api/*` are not optimised for organic search (the editor lives behind client-side bootstraps and has nothing useful to index).

- **One rule for every subpage, shared with the help centre**: subpage metadata comes from `pageMetadata()` in `@livedesign/ui` (the help centre wraps the same function, [Help app](../018-help/help-app.md) "SEO"). The title passes through verbatim (no suffix added), `og:type` is `article`, and the card is the large brand card (`summary_large_image`, `/opengraph-image` + `/twitter-image` by absolute URL) unless the page ships its own route-level image (`ownOgImage`, the `/features/<id>` cards). An app's front page that is a hub or dashboard rather than an article (the Telemetry dashboard) passes `type: 'website'`; it carries the brand card like every other public page. A `/features/<id>` card carries the category's label as its kicker, its headline, and a subtitle from `cardSubtitle` (`packages/ui/src/social-card.tsx`, beside the shared `renderSocialCard`): the first sentence of the description when it fits two lines (100 characters), otherwise cut at the last whole word, so the card never ends mid-word or runs into its footer. The origin, site name, repo URL, favicon set (`BRAND_ICONS`) and public viewport (`PUBLIC_VIEWPORT`) are shared constants in the same package, used by every app.
- `metadataBase`: `https://livedesign.app`. Lets relative paths in metadata resolve into absolute URLs (the canonical, OG image, sitemap entries).
- `alternates.canonical`: every static page declares its own canonical (`/`, `/faq`, ...). Stops query-string variants and the `www` mirror from competing with the canonical form. The retired `/terms` and `/privacy` routes are the exception: they are noindex redirect stubs whose canonical points at the help-centre Policies articles they now forward to (see "Content pages" below).
- `<html lang="en-GB">` on the root layout. Matches the OG locale + JSON-LD `inLanguage` so every locale signal across the page agrees. The earlier broader `lang="en"` worked but reads inconsistent next to OG's specific `en_GB` declaration.
- `openGraph`: title, description, url, siteName, locale (`en_GB`), type (`website` for the landing page, `article` for the FAQ and the comparisons, whose `article:modified_time` is their last review). Mirrors the page-level title/description so social cards match the actual head. (The Terms and Privacy Policy moved into the help centre and carry their own "Last updated" lines there.) Card image is generated by `apps/marketing/app/opengraph-image.tsx` via `next/og`'s `ImageResponse`; Next.js's file convention pre-renders it to a static 1200x630 PNG at build time and ships it in `out/`, so the asset has no runtime dependency.
- `twitter`: card `summary_large_image`, title, description, and the card image. `apps/marketing/app/twitter-image.tsx` re-exports the OG handler so the Twitter card and the OG card stay byte-identical. Copy is identical to the OG / page-level title and description.
- **Meta descriptions** are 50 to 160 characters, so a search result shows each one whole. A feature category page uses its section's `metaDescription` (written for the result, not the on-page lede, which runs longer); comparison pages use their `description`. `lib/meta-descriptions.test.ts` holds every page to it, and the shared `comparisonProblems` every comparison (`lib/alternatives.test.ts`).
- `robots`: explicit `{ index: true, follow: true }` on every page. The hosted product wants indexing; ambiguity about defaults is the kind of thing a future migration silently breaks.
- `app/sitemap.ts`: lists the indexable marketing URLs, `/` + `/faq` + `/alternatives` + one entry per `/alternatives/<slug>` competitor page (`comparisonSitemap` over the same list the routes read, dated by the comparisons' last review, see [the comparison-pages spec](../../../../packages/comparisons/README.md)). The two public operational surfaces, `/telemetry` (the anonymous-events dashboard) and `/status` (the service-status page), are also listed: both are public, indexable (each sets `robots` `index: true` and a self-canonical), and reachable from the footer, so sitemapping them lets crawlers discover them directly rather than depending on footer links. They sit at a lower priority (0.4) than the marketing content because they're transparency pages, not primary landing destinations. `/terms`, `/privacy` and `/security` are deliberately not listed: all three policies live in the help centre (the help app's own sitemap lists the canonical Policies articles), and each marketing route is now a noindex redirect there. `lastModified` is per-page truth, not blanket build-time: `/` and `/faq` use `new Date()` because they change with product releases; `/telemetry` and `/status` also use `new Date()` (the dashboard reflects live event data, the status page reflects the latest deployed state, so both are "fresh as of this build"). Without that split, every build claims content changed today, which is misleading to crawlers and dilutes the change-frequency signal for pages that actually move. Next.js generates `/sitemap.xml` at the root from this file.
- `app/robots.ts`: allows the marketing routes, points at the sitemap, and `Disallow`s the live-app routes and `/api/`. The router worker stitches all three apps onto the same hostname, so an unconditional allow would let crawlers waste budget on the editor's auth-walled HTML and the API's JSON responses. The live app also declares `noindex, nofollow` at its root layout (see [07-live-app.md](../007-editor/live-app.md)) as the in-page complement; together the two signals tell crawlers to skip the live app entirely.
- **`viewport` export** (Next.js metadata API): the root layout exports a `Viewport` object carrying `themeColor: '#f43f5e'` (brand rose, see [01-color-scheme](../004-interface-design/color-scheme.md)) and `colorScheme: 'light dark'`. The first tints mobile browser chrome (Android Chrome's URL bar, iOS PWA status bar) to the brand, the second says the pages paint both appearances; which one follows the reader's origin-wide [Appearance](../004-interface-design/appearance.md) (System by default, the rail's toggle to override), applied before first paint. Every page, illustrations included, has a dark appearance, and its editor mock-ups show the editor as it looks in dark. Both are head meta, not page content, so they don't conflict with the "claims map to shipped features" rule.
- **`app/manifest.ts`**: emits `/manifest.webmanifest` at build time with `name`, `short_name`, `start_url: '/'`, `display: 'standalone'`, the brand theme + background colours, and the existing `/icon.svg` as the icon (which `purpose: 'any'` covers since the cube's corners reach outside a maskable safe zone). Surfaces the Android Chrome "Add to Home Screen" prompt + the iOS Safari "Add to Home Screen" landing icon, with no behaviour change for normal page loads. Same `export const dynamic = 'force-static'` opt-in as robots.ts / sitemap.ts so it round-trips through `output: 'export'`. Because `livedesign.app` is one origin (the router stitches the apps by path), this is the **origin's** manifest: the editor (live app) references it (and `/apple-icon`) by absolute path from its own layout metadata, so installing the PWA from the editor gets the same icon + name rather than nothing (see [07-live-app](../007-editor/live-app.md)).
- **JSON-LD structured data**: the root layout renders a single `<script type="application/ld+json">` carrying a `@graph` of two schema.org types: `WebSite` (so the brand-name search produces a rich result) and `SoftwareApplication` (so the product is categorised correctly in browse / category-style results). Both schemas restate facts already in the page (name, url, description) and the SoftwareApplication offer is `price: "0"` (truthful: the hosted product is free with no paid tier, see [03](../002-project-scope/open-source-and-business-model.md)). No claims that aren't already true on the surface. Each schema also carries an `image` field pointing at the same OG card (`/opengraph-image`) so Google can pair the brand card with a visual, an `inLanguage` field matching the OG locale (`en-GB`), and a `sameAs` array on the SoftwareApplication that links the canonical GitHub repo (already linked from the footer + the FAQ self-host answer) so the brand's open-source presence is connected to the same entity.
- **FAQ JSON-LD**: `/faq` emits an additional `<script type="application/ld+json">` with schema.org `FAQPage` + a `Question` / `Answer` pair per entry. Unlocks Google's "expandable FAQ" rich result for the page. The JSON-LD `acceptedAnswer.text` is the plain-text form of each answer; entries that render JSX (a link to the help-centre privacy policy in the data-storage question, for instance) carry a parallel `aText` field with the same sentence, sans markup. The page builds it from the same `FAQ_CATEGORIES` it renders, and `lib/faq-content.test.tsx` renders every JSX answer and fails if its visible text differs from `aText`, so the structured data can't drift from the visible content.
- **Breadcrumb JSON-LD**: every indexable subpage (`/faq`, each `/features/<id>`, `/alternatives` and each `/alternatives/<slug>`) emits a `BreadcrumbList` script. (The retired `/terms` + `/privacy` redirect stubs don't, since they render no breadcrumb trail.) Two items for two-level pages (`Home → <Page>`), three for a comparison (`Home → Comparison → <competitor> alternative`). The comparison hub adds an `ItemList` and each comparison a `FAQPage` ([the comparison-pages spec](../../../../packages/comparisons/README.md) "Metadata"). Unlocks Google's SERP breadcrumb display so the search result shows `livedesign.app > FAQ` instead of the bare URL. Rendered via `components/BreadcrumbJsonLd.tsx` so the pages share one source of truth; the `BreadcrumbList` shape itself is the shared `breadcrumbJsonLd` builder in `@livedesign/ui`, which the help centre's breadcrumbs use too. The landing page (`/`) doesn't get a breadcrumb (it IS home, the trail would be a single entry).

When a new public page lands, add it to both `app/sitemap.ts` and its own metadata block (with `alternates.canonical`). Updating one without the other is a regression.
