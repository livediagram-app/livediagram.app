# API app

The HTTP + WebSocket layer the live editor calls for design persistence and realtime collab.

- **Workspace:** `apps/api` (`@livedesign/api`).
- **Worker name:** `livedesign-api`.
- **Mount:** routed from the [router worker](../016-platform/router-app.md) at `/api/*`. The router forwards the request as-is; the api worker sees the full `/api/...` path.

## Why this exists

The first prototype phase ([spec 02](../005-project-roadmap/prototype-scope.md)) ran entirely client-side with `localStorage` persistence. Realtime collaboration needs server state: a Durable Object per design holds the in-room participant list, orders and relays ops between connected clients, keeps the collaboration state that must outlive a socket, and holds the design's content in its own SQLite. `apps/live/lib/api-client.ts` is the live app's single boundary to it.

## Tech

- **Runtime:** Cloudflare Workers.
- **No D1 database.** livedesign has no `DB` binding and no migrations. What a design holds is in its own Durable Object, and everything else is liveworkspace's, a person's workbench included: a person's settings, name and colour, sign-in sighting and email address are the liveworkspace accounts Worker's ([liveworkspace/docs/specs/003-accounts/accounts.md](../../../../liveworkspace/docs/specs/003-accounts/accounts.md)), read through its internal API as `livedesign.app`; API tokens are liveworkspace's alone, checked with it on use.
- **Index:** where every design is, who may open it, its sharing and share links, folders, favourites, placement defaults, the Trash, the Timeline, the Inbox, and teams and their members are liveworkspace's index and accounts ([one-explorer.md](../../../../liveworkspace/docs/specs/004-index/one-explorer.md), [one-explorer-contracts.md](../../../../liveworkspace/docs/specs/004-index/one-explorer-contracts.md)). The api reaches the index at `INDEX_ORIGIN` (`apps/api/src/index-service.ts`) with this app's key, `INDEX_KEY`.
- **Designs:** one SQLite-backed Durable Object per design (`DesignRoom`, binding `DESIGN_ROOM`, `new_sqlite_classes`), named by the design's id via `idFromName`. It holds the design's content and is its realtime room (see **Storage** and **Realtime model**).
- **Workbenches:** a person's workbench pairing requests, pairings, tickets and sessions are liveworkspace's ([liveworkspace/docs/specs/011-workbench/workbench.md](../../../../liveworkspace/docs/specs/011-workbench/workbench.md)); `/api/workbench/*` is forwarded to the accounts Worker unchanged ([Workbench embeds](../013-workspace/workbench-embeds.md)).
- **Images:** liveworkspace's media service ([liveworkspace/docs/specs/006-media/media.md](../../../../liveworkspace/docs/specs/006-media/media.md), `apps/api/src/media.ts`, `MEDIA_URL` and the secret `MEDIA_KEY`) keeps every uploaded image, its gallery, dedupe and caps. The api keeps who may read what (see **Images**).
- **R2:** `PHOTO_BLOBS` holds photo pages' pixels ([Photo store](../031-photo/photo-store.md)). Previews (the Explorer thumbnail, the live image and the share card) are liveworkspace's ([Previews](../../../../liveworkspace/docs/specs/006-media/previews.md)); the design only draws them, through its export door ([Design snapshots](../006-design/design-snapshots.md)).
- **One cron:** `0 3 * * *` daily, which tells the media service that livedesign's set of image references is complete (`announceMediaRefs`), so a quiet day never holds its unused-image sweep up. Each design keeps itself tidy on its own alarm.

## Wire-format types

The DTO shapes the api worker emits + the live editor consumes live in `packages/api-schema` (`@livedesign/api-schema`): `LiveDoc` (published as `Design`), `TabSummary`, `TabRecord`, `Folder`, `ShareLink`, `ServerMessage` / `ClientMessage`, and the room op vocabulary (`RoomOp` / `RoomOutgoing` / `RoomIncoming`). Both apps import them; the api worker also re-exports under historical `XxxDTO` aliases (`apps/api/src/types.ts`) for backward compatibility with its existing call sites.

Defining the wire shapes once means server and client cannot drift: adding a field on one side without updating the other is a typechecker error. **Do not redefine these types inline in `apps/api/` or `apps/live/`**; extend the schema package instead. Per AGENTS.md the reuse-over-duplication rule is non-negotiable.

## Auth

The api resolves who is calling through three identities, in this order of preference (see [Auth + guest access](../014-identity/auth-and-guest-access.md) and [Public API and API tokens](public-api-and-tokens.md)):

1. **A person's token**: `Authorization: Bearer <jwt>`, minted by the liveworkspace accounts Worker: an account's access token ([Auth + guest access → Signing in](../014-identity/auth-and-guest-access.md#signing-in)) or a guest's token (`kind: "guest"`, `sub: guest_<uuid>`, [Auth + guest access → Guests](../014-identity/auth-and-guest-access.md#guests)). Verified locally in `apps/api/src/auth/accounts.ts` (`getPersonIdentity`, via `@liveworkspace/auth-client`'s `createVerifier`) against `${ACCOUNTS_URL}/api/auth/jwks`, with issuer `${ACCOUNTS_URL}/api/auth` and audience `API_RESOURCE`, so a token minted for another liveworkspace app is refused here. No call to the accounts Worker per request; the key set is cached per isolate. The `sub` claim is the owner id; an account's `email` is trusted only when `email_verified` is true, and its `teams` claim lists its teams. Returns null on any failure (invalid signature, expired, wrong audience, malformed, `ACCOUNTS_URL` / `API_RESOURCE` unset), logged as `[auth] access_token_rejected`, never 401: the request goes on as a link visitor's. A bearer shaped as an API token (`lwt_…`) or a workbench session (`lvw_…`) is never handed to the verifier; the paths below resolve it.
2. **API token**: `Authorization: Bearer lwt_…`, consulted only when no person's token verified. `resolveApiToken` checks it with liveworkspace, which made it ([Public API and API tokens](public-api-and-tokens.md)), remembering the answer for a minute per isolate; there is no copy of a token here. The owner id is the token's account, so a token request flows through the same checks as a signed-in one. An unknown, revoked or expired token is refused `401 invalid_token`, never read as a guest; liveworkspace out of reach answers `503 accounts_unavailable`. A token minted **read-only** is refused on every `POST` / `PUT` / `DELETE` with `403 read_only_token`, at one choke point in `index.ts` (its own `DELETE /api/tokens/current` and the workbench ticket and pairing asks excepted).
3. **Workbench session**: `Authorization: Bearer lvw_…`, consulted only when neither of the above resolved ([Workbench embeds](../013-workspace/workbench-embeds.md)). Sessions are liveworkspace's ([liveworkspace/docs/specs/011-workbench/workbench.md](../../../../liveworkspace/docs/specs/011-workbench/workbench.md)): `resolveWorkbenchSession` (`src/auth/workbench-session.ts`) asks the accounts Worker about the secret with the api's client credentials, and keeps the answer per isolate (a live one up to a minute, a refused one ten seconds); an unknown, expired or revoked one is refused `401 invalid_session`, and accounts unreachable answers `503`. `workbenchRefusal` confines it before any route runs, by its scope: a design session answers another design `404`, any route outside `WORKBENCH_ROUTES` `403 workbench_confined`, and an `X-Share-Code` or `X-Share-Password` beside it `403 workbench_confined`; a workspace session reaches the Explorer's routes (`WORKSPACE_ROUTES`), never the account's. A view session's write is `403 workbench_read_only`.

No Bearer at all is a **link visitor**: someone holding only a share code. A guest is never a header: it is a guest token like any other Bearer, and a guest's designs move to their account in the index when they sign in.

`ACCOUNTS_URL`, `API_RESOURCE`, `ACCOUNTS_CLIENT_ID` and `ACCOUNTS_CLIENT_SECRET` are **worker secrets** (`wrangler secret put` on each worker and environment; a deploy never writes them, so they survive every deploy), not `[vars]` entries. Only the client secret is sensitive, but keeping every out-of-band value in one mechanism is simpler than reasoning about which ones are safe in the open ([Secrets policy](../002-project-scope/secrets-policy.md)). Leaving `ACCOUNTS_URL` or `API_RESOURCE` unset leaves every caller a link visitor, useful for local dev or for environments without an accounts client yet. The sign-in round trip itself (`/api/auth/sign-in`, `/callback`, `/token`, `/sign-out`) and the guest handoff (`/api/auth/guest`) live in `apps/api/src/routes/auth.ts`.

### Access

Who may open a design, and at what level (`view` < `participate` < `edit`, and a tab when a link opens only one), is the index's to say, in a **grant**: a ten-minute ES256 JWT naming the person (or `link:<code>`), the design, the level and the tab ([one-explorer-contracts.md](../../../../liveworkspace/docs/specs/004-index/one-explorer-contracts.md) "Grants"). The owner and every joined member of the design's team get `edit`; anyone else needs a live share link.

- **A caller holding one** sends it on every request about that design as `X-Index-Grant` (`INDEX_GRANT_HEADER`). The api checks it offline against the index's published keys (`apps/api/src/index-service.ts`, through `@liveworkspace/index-app`): its `aud` is livedesign, its `item` the design in the path.
- **A caller without one** (an API token, a workbench session, a browser that sent none) gets one fetched here (`resolveDesignGrant`, `routes/design-grant.ts`), cached until a minute before it lapses: as that account with this app's key, or with the browser's own Bearer and its share headers.
- **A share link** rides as `X-Share-Code` (and `X-Share-Password` when the design has one), which the index's grant endpoint reads. A password refusal comes back as the index's: 401 `password_required` or 403 `password_invalid` ([Share password](../013-workspace/share-password.md)).
- **The room** takes the grant as its ticket on the upgrade (`?t=`), since a socket cannot send headers ([Realtime model](#realtime-model)).

Every route about one design then gates on the grant's level: reads on `view`, a Participant's writes on `participate`, everything else on `edit`, and a grant with a `tab` reaches only that tab. No grant answers 404, never revealing that the design exists.

## Endpoints

All JSON unless stated. CORS allows any origin (the live app is same-origin via the router; this is mostly a dev convenience). Routes are dispatched in `apps/api/src/index.ts`, a thin switch over `segments[1]`; each owns a `handle<Resource>(ctx)` module under `apps/api/src/routes/` that implements every method and sub-path it handles. Read the dispatcher for the surface, then the matching route module for the authoritative behaviour. The machine-readable reference is `GET /api/openapi.json` ([API documentation (OpenAPI)](api-documentation.md)), built from `apps/api/src/openapi/manifest.ts`. `/api/auth/*` and `/api/internal/*` are answered before the caller is resolved. `/api/index/*` never reaches this worker: the router forwards it to liveworkspace's index ([Router app](../016-platform/router-app.md)).

It is the editor's autosave path: a request presented with an API token is refused `405 use_changesets`, naming the changeset route, since agents write through changesets. ### Design dates

A design's dates are its `createdAt` (shown as created) and `savedAt` (last
modified, the lists' order), both milliseconds since the epoch, as everywhere
on the wire. A create stamps both with the server's now, unless the body
carries its own: an Offline Mode sync carries the local record's `createdAt`
([Offline Mode](../006-design/offline-mode.md)), so it sits in the Explorer
where its age puts it.

- Each given date must be a whole number of milliseconds no earlier than
  `DESIGN_DATE_MIN` (1 January 2000, before any design a person could
  bring) and no later than the server's now plus `DESIGN_DATE_SKEW_MS`
  (one day, for a device clock that runs ahead), and `createdAt` must not be
  later than `savedAt`.
- A given `createdAt` alone keeps `savedAt` at now (or at `createdAt`, if a
  clock running ahead put that later); a given `savedAt` alone is refused (a
  design is never modified before it is created).
- Seeding the create's tabs leaves `savedAt` as given.
- Anything else is refused whole, 400 `bad_request` "invalid design dates";
  nothing is created.
- Only a genuine create takes them: re-committing an id the caller already
  owns keeps the stored `createdAt`.

### Marking a design used

The create body's `markUsed` (absent or `true`, or `false`) is read and validated: anything but a boolean is refused whole, 400 `bad_request` "invalid markUsed", and nothing is created. What Recent and Jump back in show is the index's record of opens ([Explorer Home](../013-workspace/explorer-home.md) "Making a design is a use"):

- For an API client's create (one the worker makes the index's item for), absent or `true`, the worker records the open at the index for the caller beside the create, never waited on, so the design joins their Jump Back In at once; `false` leaves it to join at its first open or edit.
- An editor's create (it sends the index's grant) is the editor's to record, as it records every open when it loads a design, and a re-commit of an id the index already holds is no making, so neither is recorded here.
- The create itself is the design's making, not an edit: the design's room records no editor for `POST /api/designs` ([Timeline](../013-workspace/timeline.md)), so its seeded tabs never count a use day that `markUsed: false` withheld.

### Designs in the Trash

A design's Trash state is the index's. A trashed design is reached only by its owner and team, so the index grants nobody else anything for it, and every door answers as for a design that is not there. The index keeps a design 30 days in the Trash, then deletes it for good and has the design's object drop its content ([Trash](../013-workspace/trash.md)); the index's own daily sweep also handles empty designs ([Empty design clean-up](../013-workspace/empty-design-cleanup.md)). livedesign runs no Trash cron and no empty-design sweep.

### Tab save

The whole-tab autosave (`PUT /api/designs/<id>/tabs/<tabId>`, about every 600 ms while someone edits) reads
only what it needs of the design, in one query (`getDesignForSave`: owner, team, name, created date and the tab
count). The owner's name and colour come from the profile cache (`apps/api/src/accounts/profiles.ts`), not from each
save. The stored tab, the changesets the editor had not seen and the realtime room's ledger are then read together;
the ledger is merged after the changesets. A denied save answers 403.

### Tab size

A tab is stored as one text value in one row of its design's SQLite (`tabs.data`, the tab's JSON without its id and
name), in the design's Durable Object, and a Durable Object's SQLite caps a string, a BLOB and a row at
**2,000,000 bytes**, the same figure as Cloudflare D1's ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)),
whose name the constants keep. Local `wrangler dev` does not enforce it, so the api enforces it itself:

- `D1_MAX_ROW_BYTES` = 2,000,000, the row cap. `MAX_TAB_BYTES` = `D1_MAX_ROW_BYTES` less
  `D1_ROW_HEADROOM_BYTES` (8 KiB) = 1,991,808 bytes of UTF-8 JSON. The
  headroom covers the row's other columns (the tab id, a UUID; the name, at
  most 60 characters, so at most 240 bytes; `updated_at`; SQLite's record
  header) many times over, so a tab under the cap always fits its row.
- All three live in `@livedesign/api-schema` (`../packages/api-schema/src/tab-size.ts`, with `tabDataBytes` and
  `tabTooLarge`), so the editor checks the same cap the worker does and the two cannot drift. A changeset part is
  capped the same (`CHANGESET_PART_MAX_BYTES` = `MAX_TAB_BYTES`).
- **Every write of a tab's data** is checked against it, at the storage layer
  (`upsertTab`, `seedTabs`, `swapTabData`), so no route can store what the row
  would refuse: design create, the tab save, a comment added or deleted
  through the api. A tab over the cap is refused with
  the named 413 (`payload_too_large`) and nothing is written; the worker logs
  `[tab-size] refused` with the write (`create`, `upsertTab`, `seedTabs`,
  `swapTabData`), the tab id, the bytes and the cap. The comment routes list
  413 among their answers in the OpenAPI manifest. The routes
  also check the request up front, so a create never leaves a design
  without its tabs.
- A photo page's pixels never count against it: they are blobs in `PHOTO_BLOBS`, and the tab holds their ids.
- The cap is not raised; storing a larger tab in chunks over several rows is a separate decision.

## Caching

Every JSON answer is the caller's live state, so it goes out `Cache-Control: no-cache` unless its
route chooses a policy of its own (the OpenAPI document, the public telemetry summary): a browser
may store it but asks the server again before reusing it. Without it a browser may reuse an answer
the server has since changed: Chromium holds a `410` with no explicit expiry indefinitely, so a
share-link visitor who once saw a design deleted would keep seeing it after the owner restored
it. Not `no-store`: the browser's cache drains a stored answer's body, and without it an answer
whose caller never reads the body holds its request open. Images and photo blobs set their own policies; previews are
liveworkspace's.

## Rate limiting

Six limiters, each a Cloudflare Workers Rate Limiting binding declared under `[[unsafe.bindings]]` in `apps/api/wrangler.toml` (where the ceilings live). Over-limit requests get `429` with `{ "error": "rate_limited" }`, except the telemetry ingest, which answers with its usual no-op `204` so a throttled beacon never surfaces as an error.

| Binding                       | Meters                                                                                                                                                                                                                      | Key                                                                                                                                         | Where              |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| `WRITE_RATE_LIMITER`          | every `POST` / `PUT` / `DELETE`, except `/api/events`; the room-ticket mint on its own key, `room-ticket:<network>`                                                                                                         | `token:<tokenId>` for an API token, `workbench:<sessionId>` for a workbench session, else the resolved owner id, else `anonymous:<network>` | `index.ts`         |
| `EVENTS_RATE_LIMITER`         | `POST /api/events`, the CLI's telemetry relay                                                                                                                                                                               | client IP                                                                                                                                   | `routes/events.ts` |
| `API_TOKEN_READ_RATE_LIMITER` | every `GET` made with an API token                                                                                                                                                                                          | `token:<tokenId>`                                                                                                                           | `index.ts`         |
| `SHARE_RATE_LIMITER`          | `GET /api/share/:code` (the unauthenticated share resolve; the live image and a link preview's `card` and `image.png` on their own key, `share-preview:<network>`), against blind guessing; password checks are the index's | client IP (IPv6 /64)                                                                                                                        | `index.ts`         |
| `UNFURL_RATE_LIMITER`         | `GET /api/unfurl` (an unauthenticated outbound page fetch)                                                                                                                                                                  | client IP                                                                                                                                   | `routes/unfurl.ts` |

Other reads (a signed-in or guest `GET`, and every `OPTIONS`) are unmetered. The write ceiling sits well above realistic editing traffic (autosave fires once per debounce window, comments are typed by humans) but low enough to stop a bot from spamming design creation, image uploads and photo blobs into storage quota exhaustion. The room-ticket mint keys on the caller's network rather than the owner because the per-owner budget is the autosave's, and a 429 there would cost a team member the whole session's realtime; `/api/events` is exempt so telemetry never competes with a user's real writes.

Before any limiter, a write whose `Content-Length` exceeds its body cap is refused with `413`: `MAX_BODY_BYTES` (8 MB), or `MAX_IMAGE_BYTES` for `/api/images`, or `PHOTO_BATCH_BYTES` (24 MB) for a photo blob batch (`limits.ts`).

Every limiter is optional. When a binding is absent its check short-circuits to "allow", so deployments without the feature still serve. The bindings are a Cloudflare paid-tier capability; the open-source path stays unaffected (per [Open source + distribution](../002-project-scope/open-source-and-business-model.md)).

## Storage

livedesign keeps no D1 database. Each design's content lives in its own SQLite-backed Durable Object, `DesignRoom`
(`apps/api/src/design-room/`), one per design id; workbench pairings, tickets and sessions are liveworkspace's; where a
design is and who may reach it is the index's; images and previews are the media service's; and photo pages' bytes
are R2's (`PHOTO_BLOBS`).

**What the design's object holds** (`design-schema.ts`, created on first use, never on construction, `CREATE ... IF
NOT EXISTS`, versioned by `_design_schema`):

- `design`: the design's own row: its name, owner, team and provenance as the grants and renames that reach it say,
  the creation intent (`opens_in`, `tab_kind`), `saved_at`, `created_at`, the comment email's throttle, and a
  `presentation` column that nothing reads, serves, writes or copies ([Presentation mode](../012-collaboration/presentation-mode.md)
  "Saved data"; schema steps are append-only, so the column and any stored value stay).
- `tabs` (the body, one JSON row per tab, with its `rev`, which a trigger only lets advance by one) and
  `design_tabs` (order and folder), with `tab_stats` (the Details view's numbers).
- `agent_changesets` and `agent_changeset_parts` (the changeset log).
- `image_refs` (which images each tab places), `image_grants` (placement grants) and `image_owners` (whose each
  image it places is): see **Images**.
- `photo_blob_refs`: the photo blobs each tab may read, with each blob's type and size.
- `tab_shares` and `share_outbox`: the other designs each shared tab is in, and what they are still to hear
  ([Tab ↔ design many-to-many](../006-design/tab-design-many-to-many.md)).
- `outbox`: what the design still owes the index and the media service (below).
- `notify_claims`: the once-only state of its notification emails.
- In the object's key-value storage: the order state (`epoch`, `seq`), the collaboration ledger, selections and
  agent presence.

A tab is one row, so the cap in **Tab size** stands.

**What each person's workbench holds** (their pairing requests, pairings, tickets, sessions and the rooms a workspace
session joined) is liveworkspace's, kept by its accounts Worker ([liveworkspace/docs/specs/011-workbench/workbench.md](../../../../liveworkspace/docs/specs/011-workbench/workbench.md)).

**Routing.** The worker authenticates the caller, applies its cross-cutting gates (rate limits, read-only tokens,
workbench confinement, body caps), settles the index's grant and hands every request under `/api/designs/:id/...`
(and a create) to the design's object, `designRoom(env, id).route(request, identity)` (typed RPC,
`design-client.ts`). The design list and the index's doors (delete, copy, share) are answered from the index, and the
room ticket and upgrade in the worker. The object rebuilds the route context from that identity and the grant and
runs the handlers against its own SQLite as `env.DESIGN_DB` (`@liveworkspace/index-app` `item-db.ts`, a D1-shaped
surface over `ctx.storage.sql`, so the content modules' SQL runs unchanged; it tells the room only of calls that
changed a row, so a read never counts as an edit). Other RPCs: `outline` (a design read's tab list),
`exportImage` (the export door's drawing for liveworkspace's previews, drawn where the content is), `hasTab`, `servesImage`, `heldBlobs`,
`exportCopy` / `importCopy` (a design copy), `revokeCodes`, `joined`, `anonymise` and `purge`.

**A save is one call and one transaction.** The tab `PUT` reaches the object in one RPC and writes the body, its
`design_tabs` row, its stats, `design.saved_at`, its image references and its placement grants in one transaction, with
no network round trip on its path. A read is one RPC.

**The outbox.** Triggers on the design's tables key every change in the same transaction as the write, so no write
path can forget one and a save makes no network call. The object's alarm drains it on idle and at most once a minute
(`FLUSH_MIN_GAP_MS`, `design-outbox.ts`): the design's summary to the index (`PUT /app/items/:id/summary`, the
Explorer's thumbnails and counts), each changed tab's comment threads and actions for the Inbox
(`PUT /app/items/:id/collab/:tabId`), who edited it for the Timeline and Most Used (`PUT /app/items/:id/events`), all
with this app's key ([one-explorer-contracts.md](../../../../liveworkspace/docs/specs/004-index/one-explorer-contracts.md) "What an
item pushes"); the images it places to the media service (`pushDesignMediaRefs`); and the owner's newest save to the
liveworkspace accounts Worker for its onboarding emails. A drain that fails keeps every key it did not push and
retries a minute later, so the Explorer and the Inbox lag a write by up to about a minute.

**Upkeep.** Each object runs its own daily upkeep from its alarm (`maintain`, every `MAINTENANCE_EVERY_MS`): photo
blob refs past their grace go, with their markers and any blob no design holds any more
(`sweepDesignPhotoBlobs`), and changesets past their 30-day retention go.

**Purge.** When the index deletes a design for good, its object ends every session, deletes all of its storage
(content, ledger, order state, selections, agent entries and alarm), releases its photo blobs' markers (and the blobs
no other design holds) and forgets its image references at the media service; the worker then asks the media service to drop its previews
(`purgeDesignPreviews`, best effort).

**Duration.** The object is billed while it runs a request or an alarm. Content requests and preview drawings run
there rather than in the worker, so a design under heavy API traffic keeps its object awake for that traffic; an idle
design costs nothing, and sockets hibernate.

## Realtime model

The `DesignRoom` Durable Object (`apps/api/src/design-room/design-room.ts`) is the realtime hub for one design id, and holds its content (see **Storage**). Clients connect via the `/ws` endpoint and immediately send a `hello`; the room broadcasts a `presence` snapshot whenever the set changes.

**Hibernation.** The room uses the Workers WebSocket Hibernation API (`state.acceptWebSocket` + class-level `webSocketMessage` / `webSocketClose` / `webSocketError` handlers) rather than in-memory `ws.accept()`, so the runtime can evict an idle room from memory between messages while every client's socket stays open, so an open-but-quiet session bills no DO duration. All per-session state that matters (the server-assigned ephemeral presence id, the `X-Verified-Role` trust-boundary role, and the `hello` presence including the remembered `tab-focus` tab) survives eviction in each socket's serialized attachment; only the per-session rate-cap window is in-memory and deliberately resets on a wake.

**Access is gated at the upgrade.** Browsers can't set headers on a WebSocket upgrade, so what admits a socket rides its URL: the index's grant itself, as `?t=` (`packages/index-app/src/room-ticket.ts` (repo root); a workbench session's ticket also seals its pairing and level cap with this app's key). A grant is short-lived (ten minutes) and names its design, so a logged one is soon useless. The worker checks it offline, **refuses the upgrade unless it admits this design**, and forwards what it says on headers only it sets, stamped on every path so a client can never supply them: `X-Verified-Role` (the grant's level, capped for a workbench session), `X-Verified-Person` (the person's tag, empty for a link visitor), `X-Verified-Tab-Scope` (the grant's `tab`, empty otherwise), `X-Verified-Share-Code` (the link a visitor came in by: the grant's `link:<code>`, or a person's `?s=`, which only ever closes sessions), `X-Verified-Workbench-Pairing`, `X-Verified-Adder` (a Participant's adder key), `X-Verified-Design` and `X-Verified-Grant-Exp`. The DO re-stamps the role onto presence in the `hello` handler, ignoring any role the client typed, so that header is the trust boundary, and confines a scoped session to its tab, live and in catch-up ([Tab-scoped share links](../013-workspace/tab-scoped-share-links.md)).

**Renewing the grant.** The room asks a session for a fresh grant (`{ kind: 'grant-renew', expiresAt }`) shortly before its grant lapses; the editor answers with a `grant` frame. A fresh grant saying the same moves the lapse on, and the design's owner and team are taken from it; one with another level or tab closes the socket (4005) so it reconnects as what it now is; a session still holding a lapsed grant is closed (`GRANT_LAPSED_CLOSE`, 4007) and its editor rejoins with a fresh one, or not at all ([one-explorer-contracts.md](../../../../liveworkspace/docs/specs/004-index/one-explorer-contracts.md) "Grants"). The decisions are @liveworkspace/index-app's `roomGrantStep`, `earliestRoomGrantDue` and `renewRoomGrant`, shared by every app's room.

**Room size.** A room admits at most `ROOM_MAX_CONNECTIONS` (100) connections at once, one constant for every product's room (`@liveworkspace/api-schema/room-capacity`). Every socket counts, a CLI's listening one too. Connection 101 is accepted only to be closed with `ROOM_FULL_CLOSE` (4008, reason `room-full`), because a browser hears nothing but an abnormal close for a refused upgrade; the room logs `[room] full` with the count. The editor shows "This room is full, so you can't join it live right now. We'll keep trying." once per spell of being turned away and tries again every minute (`ROOM_FULL_RETRY_MS`), and as soon as the tab is shown again, until a place frees up, never giving up; the page keeps working without the live room meanwhile. The CLI's room stream says "This room is full; waiting for a place…" once and retries at its longest backoff.

Edits and presence propagate as `op` messages. The room is **not** a stateless relay: it classifies every op, orders the ones that change the design, rewrites a few fields on the way through, keeps a small amount of collaboration state in its own storage, and stores the design's content in its own SQLite, the system of record for it ([Realtime conflict resolution](../012-collaboration/realtime-conflict-resolution.md), [Collaboration race hardening](../012-collaboration/collab-race-hardening.md)).

### Op classes

Every op kind belongs to exactly one of three lists in `@livedesign/api-schema` (`packages/api-schema/src/room-messages.ts`), and the class decides its ordering, its role gate, and whether a client may send it at all. The room reads `op.kind` to classify; the payload stays `op: unknown` on the wire.

- **Presence** (`PRESENCE_OP_KINDS`): ephemeral, mutate nothing. Relayed unordered (no `seq`), never logged, never replayed, from **any** connected session, so a view-only visitor still shows peers their cursor, selection, laser and tab.
- **Mutation** (`MUTATION_OP_KINDS`): change the design. Relayed **only from a session whose verified role is `edit`**; each gets a monotonic `seq` within the room's `epoch` and a slot in the catch-up log.
- **System** (`SYSTEM_OP_KINDS`): originated only by the api worker through the DO's internal endpoints, stamped `from: 'system'`. Dropped outright when a client sends one, so no peer can forge a revoke.

| `changeset`      | system   | the changeset's ops                                                | One write the api applied and recorded, sequenced through `/mutation` ([Agent changesets](../024-agents/agent-changesets.md#what-the-room-does)).                                                                                                                                                                                                                                                                        |

**Access changes end the sessions they affect.** A link turned off on the index ends its sessions at once: the index calls `POST /api/internal/items/:id/revoke` with the codes, and the room broadcasts `share-revoked` for each and closes the sockets that code admitted. Any other change (a password set, a team membership ended, a link's level or tab changed) takes effect when the session's grant is next renewed, within ten minutes. The room's internal `POST /close-sessions` (never reachable from outside, like `/broadcast`) closes matched sockets: a `workbench` match (a pairing whose access ended) with **4006** (`WORKBENCH_ENDED_CLOSE`), any other with **4005** (`ACCESS_CHANGED_CLOSE`, reason `access-changed`); nothing is broadcast, so no other session learns who left. The connector stops on 4005 and the editor reloads, which runs the ordinary access path again: a password prompt, a refusal page, or (when access remains another way) the editor.

Besides `op`, the room speaks a few non-op frames: `hello`, `sync` and `grant` from clients; `presence`, `catchup`, `cursor`, `grant-renew`, `selection-released` and `followers` from the room. `followers` (the presence ids following you) and `selection-released` go to one socket alone.

### What the room does to a frame

In order, for every inbound frame: a frame over 256 KiB is dropped; a per-session sliding-window rate cap (240 frames per second) drops a flood; an op from a session that hasn't said `hello` is dropped; a system-kind op from a client is dropped; a tab-scoped session may only touch its own tab and never the design's structure (`scopedSenderMayRelay`); a non-presence op from a session whose verified role isn't `edit` is dropped. Then:

- **Presence ops** relay to every other socket.
- **Mutation ops** are rewritten before they go anywhere: `opForTheWire` strips every comment `authorId` (a guest's credential), and `stampCommentAuthor` sets a posted comment's author name and colour to the sending session's presence, whatever the frame claimed. The rewritten op gets the next `seq`, lands in the catch-up log, relays to every other socket, is recorded in the ledger when it is an `el-delta`, and the sender receives a `cursor` frame naming the `seq` its own op took, echoing the op frame's `ref` when it carried one (a positive integer), so the sender knows that op is sequenced.
- Every outbound op frame to a tab-scoped session is filtered or redacted for its scope (`opForScope`), live and in catch-up.

On `hello` the room builds the session's presence itself (`helloPresence`): the id is a server-minted per-socket random (never the connector's owner id), the role is the verified one, and every claimed string is length-clamped. It then sends the joiner a `cursor` frame, and broadcasts presence (each socket gets the roster minus its own entry).

### Ordering and catch-up

Mutations are totally ordered by the single-threaded DO: a monotonic `seq` within an `epoch`. `epoch` and `seq` are persisted in DO storage (`order-state`) and restored on every wake, so hibernation does not strand reconnecting clients ([Resync without reloading the page](../012-collaboration/resync-without-reload.md)). The catch-up log (the last 256 mutations, `OP_LOG_LIMIT`) lives in memory only. On reconnect a client sends `{ kind: 'sync', epoch, lastSeq }`; `resolveCatchup` answers with the ops it missed, or `resync: true` when the gap is behind the log's floor or the epoch is foreign, and the client re-fetches its loaded tabs in place.

### What the room stores

Besides the design's content (**Storage**), its key-value storage holds:

- **`order-state`**: `{ epoch, seq }`, written on every mutation.
- **The collaboration ledger** (`RoomLedgerStore`, `apps/api/src/room-ledger-store.ts`; entries defined by the pure `collab-ledger.ts` in `@livedesign/design`): for every `el-delta` it sequences, the latest state of each checklist tick and comment, one key per element, tagged with the `seq` that set it. An entry that would pass the storage value limit stops growing. The api reads it back to merge a tab save (see the tab `PUT` above).

Per-session state (presence id, verified role, person tag, tab scope, admitting share code, workbench pairing, presence) lives in each socket's serialized attachment, so it survives hibernation; only the rate-cap windows and the catch-up log reset on a wake.

The room's other parts each have a module in `apps/api/src/`: the session attachment and the verified upgrade headers (`room-session.ts`), the role gate on client ops (`room-op-gate.ts`, the [Share roles](../013-workspace/share-roles.md) level ladder), the worker-only internal endpoints (`room-internal.ts`), the access-change closes (`../packages/api-kit/src/room-access.ts`) and the presence roster each socket is sent (`room-roster.ts`).

### What the room reports

- **One telemetry event**: the room counts a multiplayer session once (`Document·Used·Multiplayer`, `reportServerEvent`) into liveworkspace's telemetry, when `TELEMETRY_ENABLED` is on ([Telemetry + public transparency dashboard](../017-telemetry/telemetry.md)).

Every other design write is a REST call from a client (see the persistence boundary below).

### Internal endpoints

The api worker reaches the DO through its stub (`env.DESIGN_ROOM.get(...).fetch(...)`; content goes through the typed RPCs under **Storage**), which never traverses the public edge, so these paths are implicitly internal:

- **`POST /broadcast`** `{ op, ordered? }`: push a system op to every socket (`from: 'system'`), sequenced when `ordered` is true. A revoke from the index (`revokeCodes`) sends `share-revoked` (or `share-rescoped`) the same way, then closes the sockets that code admitted. Best-effort: a failure is logged (`[room-broadcast]`).
- **`POST /mutation`** `{ op }`: sequence a design change the worker made, as if a peer had sent it. `el-delta`, `changeset` and `tab-meta` are accepted (400 otherwise); the comment endpoints use `el-delta` so a view-role visitor's comment reaches connected editors (`relayElementDelta`), the changeset route uses `changeset` ([Agent changesets](../024-agents/agent-changesets.md#what-the-room-does)), and the tab rename route uses `tab-meta` (`relayTabRename`).
- **`POST /close-sessions`** `{ match, ... }`: close the sessions an access change ended (above).
- **`GET /selections?tab=<tabId>&person=<tag>`**: the elements each connected person has selected on a tab (every `select` is recorded in DO storage per session, pruned when the socket goes), each marked `mine` when the session's person tag is the one asked about. The changeset route reads it to find held elements.
- **`PUT /presence`**, **`DELETE /presence`**: an agent's presence entry with its expiry ([Agent presence](../024-agents/agent-presence.md#presence)).
- **`GET /ledger?tab=<tabId>&epoch=<epoch>`**: the tab's collaboration ledger, or an empty one when `epoch` isn't the room's current epoch (the saver's cursor can't be interpreted then).
- **Purging a room** (the `purge` RPC; `POST /purge` reaches the same code): the design was deleted for good, so the room closes every socket (`DESIGN_TRASHED_CLOSE`, reason `design-purged`), waits for the ledger's queued writes and deletes all of its storage, as **Purge** under **Storage** says. The index asks for it (`DELETE /api/internal/items/:id`) whenever a design leaves its Trash for good, by hand, by its daily sweep or by account deletion, and retries a design it could not reach.

### Conflict model

- **Different elements on one tab merge.** `el` ops apply by id, so concurrent edits to different elements survive on every peer.
- **The same element is last-writer-wins, over the whole element.** Two `el` updates to one element apply in room order and the later one replaces the earlier, whoever held the selection. The concurrent-selection lock ([Live app](../007-editor/live-app.md)) is advisory and client-only (`remoteSelectionsByElement`, built from `select` ops): it makes these collisions rare, and the room does not enforce it. `tab-meta` patches are last-writer-wins per field, and `design-meta` per whole tab list.
- **Multi-writer fields merge.** Checklist ticks and comments travel as `el-delta` deltas that commute, and whole-element or whole-tab ops don't overwrite a receiver's copy of them. A photo page's layers merge layer by layer (`photo`).

### The persistence boundary

The design's object holds both the content and the ordering and collaboration state. Tab content reaches its store through `PUT /api/designs/:id/tabs/:tabId`, fired by each editor's debounced autosave with the editor's whole copy of the tab. The store keeps the last save of a tab, with the room ledger merged in as described on that row. Each editor's copy already folds in the ops it has received, so the last save normally carries everyone's work; an element edit that reached the saver only after its snapshot can be missing from the store until a later save carries it, while live peers still hold it.

A tab `PUT` is not relayed to the room; it is the editor's autosave and nothing else's. Every other writer of tab content (the MCP server, the CLI, an API-token script) writes a [changeset](../024-agents/agent-changesets.md), which the api records in the design's store and relays to the room, and which every later editor save re-applies unless that editor has seen it. The comment endpoints also tell the room about their writes.

Every tab the api receives (design create, tab save) runs the stored-tab migration (`migrateStoredTab`) before `isValidTab`, as every tab read does, so an element in a former stored shape (for example freehand points before [Stroke points](../006-design/stroke-points.md)) from a browser loaded before a deploy or an API-token script is stored in the current shape rather than refused.

## Data model

livedesign has no D1 database, so it has no migrations. The schema is each design's own, in
`apps/api/src/design-room/design-schema.ts` (listed under **Storage**). Element content lives in each tab's `data` JSON: element-level SQL filtering isn't a use
case, so normalising element rows would buy nothing, and the editor already round-trips JSON for every save.

Where a design is filed, who it is shared with, its share links and password, whether it is in the Trash, its
favourites, placement defaults, the Timeline, the Inbox, and teams and their members are the index's and
liveworkspace's ([one-explorer-contracts.md](../../../../liveworkspace/docs/specs/004-index/one-explorer-contracts.md)).

### Owner-keyed data

This is the one list of columns that hold an owner id (a guest id or an account userId), and what **account deletion** (`deleteAccount` in `apps/api/src/db/account.ts`) does with each. There is no owner migration here: a guest's designs move to the account in the index when they sign in ([Auth + guest access → Guest → account](../014-identity/auth-and-guest-access.md#guest--account-migration)). A column holding an owner id is named `owner_id` (`author_id` on `agent_changesets`); `apps/api/src/db/account-owner-columns.test.ts` finds every such column in the schema, fails until it is listed there, and proves each against a real SQLite database.

| Column                       | Account deletion                                                                                                                          |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `design.owner_id`            | In each design's own store: the account's own designs are deleted for good through the index first, which purges each store               |
| `image_owners.owner_id`      | In each design's own store: the person's images themselves are deleted from the media service, so a design that placed one serves nothing |
| `agent_changesets.author_id` | In each design's own store: those on someone else's design stay until the 30-day changeset retention ages them out                        |

`deleteAccount` deletes the person's images from liveworkspace's media service, from every app (`forgetOwner`, first, so a failure leaves the account whole to delete again), . Their workbench pairings and sessions are liveworkspace's, which ends them when the account closes. Their name comes off other people's designs they worked in through the index's person purge (`anonymise`). Account deletion runs on `DELETE /api/account` and whenever the index says an account closed (`POST /api/internal/people/:id/purge`), wherever it was closed. `entitled` rows name people too, but only until their grant lapses, and go with the design.

**Kept by the accounts Worker, not here.** API tokens are the account's and close with it. A person's settings ([User preferences](../007-editor/user-preferences.md)), name and colour (`GET`/`PUT /api/participants`), sign-in sighting and email address live in the liveworkspace accounts database ([liveworkspace/docs/specs/003-accounts/accounts.md](../../../../liveworkspace/docs/specs/003-accounts/accounts.md)), under the account's user id or, for a guest, the `guest_<uuid>` id its guest token names. Closing an account deletes them there, and a guest's move to an account on sign-in is the accounts Worker's too.

A new owner-keyed column adds a row here, a statement to `deleteAccount`, and an entry in the test, in the same change.

## One-time setup

Before the first deploy:

1. Create the R2 bucket: `wrangler r2 bucket create livedesign-photo-blobs` (and its `-staging` twin).
2. Set the worker secrets: the accounts client (`ACCOUNTS_URL`, `API_RESOURCE`, `ACCOUNTS_CLIENT_ID`, `ACCOUNTS_CLIENT_SECRET`), `INDEX_KEY`, `MEDIA_KEY`, and optionally `TELEMETRY_KEY`. Email needs no secret: the `EMAIL` binding in `wrangler.toml` is the credential.

The Durable Object class (`DesignRoom`) is declared in `apps/api/wrangler.toml` and needs no setup. After that, the monorepo's root deploy workflows ship it ([Deployment](../016-platform/deployment.md#deploy)); the api deploys in the first tier, before the router that binds it.
