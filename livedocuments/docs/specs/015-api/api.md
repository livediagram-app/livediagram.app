# API app

The HTTP + WebSocket layer the live editor calls for document persistence and realtime collab.

- **Workspace:** `apps/api` (`@livedocuments/api`).
- **Worker name:** `livedocuments-api`.
- **Mount:** routed from the [router worker](../016-platform/router-app.md) at `/api/*`. The router forwards the request as-is: the api worker sees the full `/api/...` path.

## Why this exists

Realtime collaboration needs server state: a Durable Object per document holds the in-room participant list, orders and relays ops between connected clients, keeps the collaboration state that must outlive a socket, and holds the document's content in its own SQLite. The editor reaches it through one boundary, `apps/editor/lib/api-client.ts`; only Offline Mode documents stay in the browser ([Offline Mode](../006-document/offline-mode.md)).

## Tech

- **Runtime:** Cloudflare Workers.
- **No database of its own:** the api has no D1 binding and no SQL migrations. Content is each document's Durable Object; workbench pairings and sessions are liveworkspace's accounts Worker's; API tokens are checked with liveworkspace and never stored (see **Storage**).
- **Index:** where every document is, who may open it, its sharing, folders, favourites, Trash, Timeline and Inbox are liveworkspace's index ([one-explorer.md](../../../../liveworkspace/docs/specs/004-index/one-explorer.md), [one-explorer-contracts.md](../../../../liveworkspace/docs/specs/004-index/one-explorer-contracts.md)). The api reaches it at `INDEX_ORIGIN` (`apps/api/src/index-service.ts`).
- **Images:** the bytes are in liveworkspace's media service (`MEDIA_URL`, `MEDIA_KEY`, `apps/api/src/media.ts`). A document's previews (its Explorer thumbnail, live image and share card) are liveworkspace's too ([Previews](../../../../liveworkspace/docs/specs/006-media/previews.md)): the api only draws the document on request through the export door, and binds no bucket.
- **Documents:** one SQLite-backed Durable Object per document (`DocumentRoom`, binding `DOCUMENT_ROOM`, `new_sqlite_classes`), named by the document's id via `idFromName`. It holds the document's content, its image references and grants, and is its realtime room (see **Storage** and **Realtime model**).
- **Workbenches:** liveworkspace's, not this api's: a person's pairing requests, pairings, tickets, sessions and the rooms a workspace session joined live in the accounts Worker ([liveworkspace/docs/specs/011-workbench/workbench.md](../../../../liveworkspace/docs/specs/011-workbench/workbench.md)), and `/api/workbench/*` is forwarded there unchanged ([Workbench embeds](../013-workspace/workbench-embeds.md)).

## Wire-format types

The DTO shapes the api worker emits + the live editor consumes live in `packages/api-schema` (`@livedocuments/api-schema`): `LiveDoc` (published as `Document`), `TabSummary`, `TabRecord`, `Folder`, `ShareLink`, `ServerMessage` / `ClientMessage`, and the room op vocabulary (`RoomOp` / `RoomOutgoing` / `RoomIncoming`). Both apps import them; the api worker also re-exports them under `*DTO` aliases (`DocumentDTO`, `TabDTO`, `ShareLinkDTO`, ..., `apps/api/src/types.ts`) for its own call sites.

Defining the wire shapes once means server and client cannot drift: adding a field on one side without updating the other is a typechecker error. **Do not redefine these types inline in `apps/api/` or `apps/editor/`**; extend the schema package instead. Per AGENTS.md the reuse-over-duplication rule is non-negotiable.

## Auth

The api resolves who is calling through three identities, in this order of preference (see [Auth + guest access](../014-identity/auth-and-guest-access.md) and [Public API and API tokens](public-api-and-tokens.md)):

1. **A person's token**: `Authorization: Bearer <jwt>`, minted by the liveworkspace accounts Worker: an account's access token ([Auth + guest access → Signing in](../014-identity/auth-and-guest-access.md#signing-in)) or a guest's token (`kind: "guest"`, `sub: guest_<uuid>`, [Auth + guest access → Guests](../014-identity/auth-and-guest-access.md#guests)). Verified locally in `apps/api/src/auth/accounts.ts` (`getPersonIdentity`, via `@liveworkspace/auth-client`'s `createVerifier`) against `${ACCOUNTS_URL}/api/auth/jwks`, with issuer `${ACCOUNTS_URL}/api/auth` and audience `API_RESOURCE`, so a token minted for another liveworkspace app is refused here. No call to the accounts Worker per request; the key set is cached per isolate. The `sub` claim is the owner id; an account's `email` is trusted only when `email_verified` is true, and its `teams` claim lists its teams. Returns null on any failure (invalid signature, expired, wrong audience, malformed, `ACCOUNTS_URL` / `API_RESOURCE` unset), logged as `[auth] access_token_rejected`, never 401: the request goes on as a link visitor's. A bearer shaped as an API token (`lwt_…`) or a workbench session (`lvw_…`) is never handed to the verifier; the paths below resolve it.
2. **API token**: `Authorization: Bearer lwt_…`, consulted only when no person's token verified. `resolveApiToken` checks it with liveworkspace, which made it ([Public API and API tokens](public-api-and-tokens.md)), remembering the answer for a minute per isolate; the owner id is the token's account, so a token request flows through the same checks as a signed-in one. A token minted **read-only** is refused on every `POST` / `PUT` / `DELETE` with `403 read_only_token`, at one choke point in `index.ts`.
3. **Workbench session**: `Authorization: Bearer lvw_…`, consulted only when neither of the above resolved ([Workbench embeds](../013-workspace/workbench-embeds.md)). Sessions are liveworkspace's ([liveworkspace/docs/specs/011-workbench/workbench.md](../../../../liveworkspace/docs/specs/011-workbench/workbench.md)): `resolveWorkbenchSession` (`src/auth/workbench-session.ts`) asks the accounts Worker about the secret with the api's client credentials, and keeps the answer per isolate (a live one up to a minute, a refused one ten seconds); an unknown, expired or revoked one is refused `401 invalid_session`, and accounts unreachable answers `503`. `workbenchRefusal` confines it before any route runs, by its scope: a document session answers another document `404`, any route outside `WORKBENCH_ROUTES` `403 workbench_confined`, and an `X-Share-Code` or `X-Share-Password` beside it `403 workbench_confined`; a workspace session reaches the Explorer's routes (`WORKSPACE_ROUTES`), never the account's. A view session's write is `403 workbench_read_only`.

No Bearer at all is a **link visitor**: someone holding only a share code. There is no guest header and no self-minted guest id: a guest is a liveworkspace guest token.

`ACCOUNTS_URL`, `API_RESOURCE`, `ACCOUNTS_CLIENT_ID` and `ACCOUNTS_CLIENT_SECRET` are **worker secrets** (`wrangler secret put` on each worker and environment; a deploy never writes them, so they survive every deploy), not `[vars]` entries. Only the client secret is sensitive, but keeping every out-of-band value in one mechanism is simpler than reasoning about which ones are safe in the open ([Secrets policy](../002-project-scope/secrets-policy.md)). Leaving `ACCOUNTS_URL` or `API_RESOURCE` unset leaves every caller a link visitor, useful for local dev or for environments without an accounts client yet. The sign-in round trip itself (`/api/auth/sign-in`, `/callback`, `/token`, `/sign-out`) and the guest handoff (`/api/auth/guest`) live in `apps/api/src/routes/auth.ts`.

### Access

Who may open a document, and at what level (`view` < `participate` < `edit`, and a tab when a link opens only one), is the index's to say, in a **grant**: a ten-minute ES256 JWT naming the person (or `link:<code>`), the document, the level and the tab ([one-explorer-contracts.md](../../../../liveworkspace/docs/specs/004-index/one-explorer-contracts.md) "Grants"). The owner and every joined member of the document's team get `edit`; anyone else needs a live share link.

- **The editor fetches its own** (`POST /api/index/items/:id/grant`, through the router, `apps/editor/lib/api/document-grants.ts`) while the document's code loads, keeps it until a minute before it lapses, and sends it on every request about that document as `X-Index-Grant` (`INDEX_GRANT_HEADER`). The api checks it offline against the index's published keys (`indexService.verifyGrant`, `apps/api/src/index-service.ts`, through `@liveworkspace/index-app`'s request kit): its `aud` is livedocuments, its `item` the document in the path.
- **A caller without one** (an API token, a workbench session, a browser that sent none) gets one fetched here (`resolveDocumentGrant`, `routes/document-grant.ts`), cached until a minute before it lapses: as that account with this app's key, or with the browser's own Bearer and its share headers.
- **A share link** rides as `X-Share-Code` (and `X-Share-Password` when the document has one), which the index's grant endpoint reads. A password refusal comes back as the index's: 401 `password_required` or 403 `password_invalid` ([Share password](../013-workspace/share-password.md)).
- **The room** takes the grant as its ticket on the upgrade (`?t=`), since a socket cannot send headers ([Realtime model](#realtime-model)).

Every route about one document then gates on the grant's level: reads on `view`, a Participant's writes on `participate`, everything else on `edit`, and a grant with a `tab` reaches only that tab. No grant answers 404, never revealing that the document exists.

## Endpoints

All JSON unless stated. CORS allows any origin (the editor app is same-origin via the router; this is mostly a dev convenience). Routes are dispatched in `apps/api/src/index.ts`, a thin switch over `segments[1]`; each owns a `handle<Resource>(ctx)` module under `apps/api/src/routes/` that implements every method and sub-path it handles. Read the dispatcher for the surface, then the matching route module for the authoritative behaviour. The machine-readable reference is `GET /api/openapi.json` ([API documentation (OpenAPI)](api-documentation.md)). `/api/auth/*` and `/api/internal/*` are answered before the caller is resolved. `/api/index/*` never reaches this worker: the router forwards it to liveworkspace's index ([Router app](../016-platform/router-app.md)).

### Document dates

A document's dates are its `createdAt` (shown as created) and `savedAt` (last
modified, the lists' order), both milliseconds since the epoch, as everywhere
on the wire. A create stamps both with the server's now, unless the body
carries its own: an Offline Mode sync carries the local record's `createdAt`
([Offline Mode](../006-document/offline-mode.md)), so it sits in the Explorer
where its age puts it.

- Each given date must be a whole number of milliseconds no earlier than
  `DOCUMENT_DATE_MIN` (1 January 2000, before any document a person could
  bring) and no later than the server's now plus `DOCUMENT_DATE_SKEW_MS`
  (one day, for a device clock that runs ahead), and `createdAt` must not be
  later than `savedAt`.
- A given `createdAt` alone keeps `savedAt` at now (or at `createdAt`, if a
  clock running ahead put that later); a given `savedAt` alone is refused (a
  document is never modified before it is created).
- Seeding the create's tabs leaves `savedAt` as given.
- Anything else is refused whole, 400 `bad_request` "invalid document dates";
  nothing is created.
- Only a genuine create takes them: re-committing an id the caller already
  owns keeps the stored `createdAt`.

### Marking a document used

The create body's `markUsed` (absent or `true`, or `false`) is still read and validated: anything but a boolean is refused whole, 400 `bad_request` "invalid markUsed", and nothing is created. It changes no list: what Recent and Jump back in show is the index's record of opens, which the editor writes when it loads a document (`POST /items/:id/open`, [Explorer Home](../013-workspace/explorer-home.md)).

### Documents in the Trash

A document's Trash state is the index's. A trashed document is reached only by its owner and team, so the index grants nobody else anything for it, and every door answers as for a document that is not there. The index keeps a document 30 days in the Trash, then deletes it for good and has the document's object drop its content ([Trash](../013-workspace/trash.md)). There is no Trash cron and no empty-document sweep here.

### Tab save

The whole-tab autosave (`PUT /api/documents/<id>/tabs/<tabId>`, about every 600 ms while someone edits) reads
only what it needs of the document, in one query (`getDocumentForSave`: owner, team, name and the tab count),
where it ran the full document read (the row with its share-code subqueries, then the owner's participant and the
tab summaries) as two sequential round trips. The writer's name and colour come from the profile cache (one
batched accounts read a minute per person, `apps/api/src/person/profiles.ts`), not from each save. The stored
tab, the changesets the editor had not seen and the realtime room's ledger are then read together; the ledger is
merged after the changesets, as before. A denied save still answers 403.

### Tab size

A tab is stored as one text value in one row of its document's SQLite (`tabs.data`, the tab's
JSON without its id and name), and a Durable Object's SQLite caps a string, a BLOB and a
row at **2,000,000 bytes**, the same limit as D1's ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)), whose names the constants keep.
Local `wrangler dev` does not enforce it, so the api enforces it itself:

- `D1_MAX_ROW_BYTES` = 2,000,000. `MAX_TAB_BYTES` = `D1_MAX_ROW_BYTES` less
  `D1_ROW_HEADROOM_BYTES` (8 KiB) = 1,991,808 bytes of UTF-8 JSON. The
  headroom covers the row's other columns (the tab id, a UUID; the name, at
  most 60 characters, so at most 240 bytes; `updated_at`; SQLite's record
  header) many times over, so a tab under the cap always fits its row.
- Both numbers live in `@livedocuments/api-schema`, so the editor checks the same
  cap the worker does and the two cannot drift.
- **Every write of a tab's data** is checked against it, at the storage layer
  (`upsertTab`, `seedTabs`, `swapTabData`), so no route can store what SQLite
  would refuse: document create, the tab save, a comment added or deleted
  through the api. A tab over the cap is refused with
  the named 413 (`payload_too_large`) and nothing is written; the worker logs
  `[tab-size] refused` with the write (`create`, `upsertTab`, `seedTabs`,
  `swapTabData`), the tab id, the bytes and the cap. The comment routes list
  413 among their answers in the OpenAPI manifest. The routes
  also check the request up front, so a create never leaves a document
  without its tabs.
- The cap is not raised and the storage format is unchanged; a tab that needs
  more is a separate decision.

## Caching

Every JSON answer is the caller's live state, so it goes out `Cache-Control: no-cache` unless its
route chooses a policy of its own (the OpenAPI document, the public telemetry summary): a browser
may store it but asks the server again before reusing it. Without it a browser may reuse an answer
the server has since changed: Chromium holds a `410` with no explicit expiry indefinitely, so a
share-link visitor who once saw a document deleted would keep seeing it after the owner restored
it. Not `no-store`: the browser's cache drains a stored answer's body, and without it an answer
whose caller never reads the body holds its request open. Images and SVG snapshots set their own
policies.

## Rate limiting

Seven limiters, each a Cloudflare Workers Rate Limiting binding declared under `[[unsafe.bindings]]` in `apps/api/wrangler.toml` (where the ceilings live). Over-limit requests get `429` with `{ "error": "rate_limited" }`, except the telemetry ingest, which answers with its usual no-op `204` so a throttled beacon never surfaces as an error.

| Binding                       | Meters                                                                                                              | Key                                                                                                                                             | Where              |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| `WRITE_RATE_LIMITER`          | every `POST` / `PUT` / `DELETE`, except `/api/events` and the room-ticket mint                                      | `token:<tokenId>` for an API token, `workbench:<sessionId>` for a workbench session, else the resolved owner id, else the literal `"anonymous"` | `index.ts`         |
| `EVENTS_RATE_LIMITER`         | `POST /api/events`, the CLI's telemetry relay                                                                       | client IP                                                                                                                                       | `routes/events.ts` |
| `API_TOKEN_READ_RATE_LIMITER` | every `GET` made with an API token                                                                                  | `token:<tokenId>`                                                                                                                               | `index.ts`         |
| `SHARE_RATE_LIMITER`          | `GET /api/share/:code` (the unauthenticated share resolve), against blind guessing; password checks are the index's | client IP (IPv6 /64)                                                                                                                            | `index.ts`         |
| `UNFURL_RATE_LIMITER`         | `GET /api/unfurl` (an unauthenticated outbound page fetch)                                                          | client IP                                                                                                                                       | `routes/unfurl.ts` |

Other reads (a signed-in or guest `GET`, and every `OPTIONS`) are unmetered. The write ceiling sits well above realistic editing traffic (autosave fires once per debounce window, comments are typed by humans) but low enough to stop a bot from spamming document / image creation into Durable Object and media quota exhaustion. The room-ticket mint is exempt because it shares the per-owner budget with the autosave, and a 429 there would cost a team member the whole session's realtime; `/api/events` is exempt so telemetry never competes with a user's real writes.

Before any limiter, a write whose `Content-Length` exceeds the body cap (`MAX_BODY_BYTES`, or `MAX_IMAGE_BYTES` for `/api/images`, `limits.ts`) is refused with `413`.

Every limiter is optional. When a binding is absent its check short-circuits to "allow", so deployments without the feature still serve. The bindings are a Cloudflare paid-tier capability; the open-source path stays unaffected (per [Open source + distribution](../002-project-scope/open-source-and-business-model.md)).

## Storage

Each document's content lives in its own SQLite-backed Durable Object, `DocumentRoom` (`apps/api/src/document-room/`), one per
document id. Workbench pairings, tickets and sessions are liveworkspace's. The api has no D1 database; where a
document is and who may reach it is the index's.

**What the document's object holds** (`document-schema.ts`, created on first use, `CREATE ... IF NOT EXISTS`):

- `document`: the document's own row: the slide deck ([Presentation mode](../012-collaboration/presentation-mode.md)),
  `saved_at`, `created_at`.
- `tabs` (the body, one JSON row per tab: elements, articles, pages and the page flow) and `document_tabs` (order and
  folder), with `tab_stats` (the Details view's numbers).
- `image_refs`: which gallery images each tab places ([Images, Reference index](../009-elements/images.md#reference-index)),
  written in the same transaction as the body.
- `agent_changesets` and `agent_changeset_parts` (the changeset log).
- `tab_shares` and `share_outbox`: the other documents each shared tab is in, and what they are still to hear
  ([Tab ↔ document many-to-many](../006-document/tab-document-many-to-many.md)).
- `outbox`: what the index and the media service still have to hear (below).
- In the object's key-value storage, as before: the order state (`epoch`, `seq`), the collaboration ledger,
  selections and agent presence.

A tab is one row. A tab over 2 MB does not fit a SQLite row in a Durable Object either, so the cap in **Tab size**
stands; storing a large tab in chunks is the follow-up.

**Workbench** pairing requests, pairings, tickets and sessions are liveworkspace's
([liveworkspace/docs/specs/011-workbench/workbench.md](../../../../liveworkspace/docs/specs/011-workbench/workbench.md)). API tokens are liveworkspace's alone: the
api checks a presented token there (`apps/api/src/db/api-tokens.ts`) and keeps no copy. Nothing about folders,
sharing, teams, the Trash, the Timeline or the Inbox is kept here.

**Routing.** The worker authenticates the caller, applies its cross-cutting gates (rate limits, read-only tokens,
workbench confinement, body caps) and hands every request under `/api/documents/:id/...` to the document's object,
`documentRoom(env, id).route(request, identity)` (typed RPC, `document-client.ts`). The object rebuilds the route
context from that identity and the grant and runs the handlers against its own SQLite as `env.DOCUMENT_DB`
(`@liveworkspace/index-app` `item-db.ts`, the D1 surface over `ctx.storage.sql`, which tells the room only of calls that changed a row, so a read never counts as an edit). The editor's wire protocol is unchanged. Other RPCs:
`outline` (a document read's tab list and deck), `exportImage` (the export door's drawing, where the content is),
`hasTab`, `servesImage` (the image byte endpoint's share check), `exportCopy` / `importCopy` (a document copy),
`joined`, `anonymise`, `purge` and `revokeCodes`.

**A save is one call and one transaction.** The tab `PUT` reaches the object in one RPC and writes the body, its
`document_tabs` row, its stats, `document.saved_at` and its image references in one `transactionSync`, with no
network round trip on its path. A read is one RPC. Measured on a laptop (CPU time, node:sqlite standing in for the object's
SQLite; `document-room-store.test.ts` keeps budgets on them): a 1 MB tab saves in about 50 ms and reads in about
13 ms; a tab placing 500 images saves in about 7 ms, and saves again unchanged in about 3 ms; a 200-tab document's
read takes about 1.5 ms.

**Images.** The bytes live in liveworkspace's media service; the document keeps the rest in its own SQLite:
`image_refs` (which images each tab places, written in the same transaction as the tab), `image_owners` (each
placed image's owner, as the media service answered, so a read never asks it) and `image_grants` (the images it may
serve beyond its owner's own: one a collaborator placed, or one a copy brought from its source). The byte endpoint
(`GET /api/images/:id`) asks the document (`servesImage`) whether it places the image, on the visitor's tab for a
tab-scoped link, and may serve it: its owner owns the image, or a grant covers it. Snapshots and live images are
drawn in the object with the same filter.

**The outbox.** Triggers on the document's tables key every change in the same transaction as the write, so no
write path can forget one and a save makes no network call. The object's alarm drains it on idle and at most once a
minute (`document-outbox.ts`): the document's summary to the index (`PUT /app/items/:id/summary`, the Explorer's
thumbnails and counts), each changed tab's comment threads and actions for the Inbox (`PUT
/app/items/:id/collab/:tabId`) and who edited it for the Timeline (`PUT /app/items/:id/events`, an `edited` event),
all with this app's key ([one-explorer-contracts.md](../../../../liveworkspace/docs/specs/004-index/one-explorer-contracts.md)
"What an item pushes"); the document's whole set of placed images to the media service (`MEDIA_KEY`), with the
placement grants that set earns; and the owner's newest save to the accounts Worker for its onboarding emails.
Comments are not Timeline events: they reach the Inbox through the collab push. A drain that fails keeps every key it
did not push and retries a minute later, so the Explorer, the Inbox and the media service lag a write by up to about
a minute. A tab that has gone also drops its tab-scoped share links.

**Upkeep.** Each object runs its own daily upkeep from its alarm: changesets past their retention go. The worker has
no cron (no `[triggers]` in `wrangler.toml`): every sweep is a Durable Object's alarm.

**Duration.** The object is billed while it runs a request or an alarm. Content requests and preview drawings now
run there rather than in the worker, so a document under heavy API traffic keeps its object awake for that
traffic; an idle document costs nothing, and sockets still hibernate.

## Realtime model

The `DocumentRoom` Durable Object (`apps/api/src/document-room/document-room.ts`) is the realtime hub for one document id. Clients connect via the `/ws` endpoint and immediately send a `hello`; the room broadcasts a `presence` snapshot whenever the set changes.

**Hibernation.** The room uses the Workers WebSocket Hibernation API (`state.acceptWebSocket` + class-level `webSocketMessage` / `webSocketClose` / `webSocketError` handlers) rather than in-memory `ws.accept()`, so the runtime can evict an idle room from memory between messages while every client's socket stays open, and an open-but-quiet session bills no DO duration. All per-session state that matters (the server-assigned ephemeral presence id, the `X-Verified-Role` trust-boundary role, and the `hello` presence including the remembered `tab-focus` tab) survives eviction in each socket's serialized attachment; only the per-session rate-cap window is in-memory and deliberately resets on a wake.

**Access is gated at the upgrade.** Browsers can't set headers on a WebSocket upgrade, so what admits a socket rides its URL: the index's grant itself, as `?t=` (`@liveworkspace/index-app`'s `room-ticket.ts`; a workbench session's ticket also seals its pairing and level cap with this app's key). A grant is short-lived (ten minutes) and names its document, so a logged one is soon useless. The worker checks it offline, **refuses the upgrade unless it admits this document**, and forwards what it says on headers only it sets, stamped on every path so a client can never supply them: `X-Verified-Role` (the grant's level, capped for a workbench session), `X-Verified-Owner`, `X-Verified-Tab-Scope` (the grant's `tab`, empty otherwise) and `X-Verified-Share-Code` (the link a visitor came in by: the grant's `link:<code>`, or a person's `?s=`, which only ever closes sessions). The DO re-stamps the role onto presence in the `hello` handler, ignoring any role the client typed, so that header is the trust boundary, and confines a scoped session to its tab, live and in catch-up ([Tab-scoped share links](../013-workspace/tab-scoped-share-links.md)).

**Renewing the grant.** The room asks a session for a fresh grant (`{ kind: 'grant-renew', expiresAt }`) shortly before its grant lapses; the editor answers with a `grant` frame (and renews a minute early anyway). A fresh grant saying the same moves the lapse on; one with another level or tab closes the socket (4005) so it reconnects as what it now is; a session still holding a lapsed grant is closed (`GRANT_LAPSED_CLOSE`) and its editor rejoins with a fresh one, or not at all ([one-explorer-contracts.md](../../../../liveworkspace/docs/specs/004-index/one-explorer-contracts.md) "Grants").

**Room size.** A room admits at most `ROOM_MAX_CONNECTIONS` (100) connections at once, one constant for every product's room (`@liveworkspace/api-schema/room-capacity`). Every socket counts, a CLI's listening one too. Connection 101 is accepted only to be closed with `ROOM_FULL_CLOSE` (4008, reason `room-full`), because a browser hears nothing but an abnormal close for a refused upgrade; the room logs `[room] full` with the count. The editor shows "This room is full, so you can't join it live right now. We'll keep trying." once per spell of being turned away and tries again every minute (`ROOM_FULL_RETRY_MS`), and as soon as the tab is shown again, until a place frees up, never giving up; the page keeps working without the live room meanwhile. The CLI's room stream says "This room is full; waiting for a place…" once and retries at its longest backoff.

Edits and presence propagate as `op` messages. The room is **not** a stateless relay: it classifies every op, orders the ones that change the document, rewrites a few fields on the way through, keeps a small amount of collaboration state in its own storage, and writes one telemetry row itself. The same object's SQLite is the system of record for the document's content ([Realtime conflict resolution](../012-collaboration/realtime-conflict-resolution.md), [Collaboration race hardening](../012-collaboration/collab-race-hardening.md)).

### Op classes

Every op kind belongs to exactly one of three lists in `@livedocuments/api-schema` (`packages/api-schema/src/room-messages.ts`), and the class decides its ordering, its role gate, and whether a client may send it at all. The room reads `op.kind` to classify; the payload stays `op: unknown` on the wire.

- **Presence** (`PRESENCE_OP_KINDS`): ephemeral, mutate nothing. Relayed unordered (no `seq`), never logged, never replayed, from **any** connected session, so a view-only visitor still shows peers their cursor, selection, laser and tab.
- **Mutation** (`MUTATION_OP_KINDS`): change the document. Relayed **only from a session whose verified role is `edit`**; each gets a monotonic `seq` within the room's `epoch` and a slot in the catch-up log.
- **System** (`SYSTEM_OP_KINDS`): originated only by the api worker through the DO's internal endpoints, stamped `from: 'system'`. Dropped outright when a client sends one, so no peer can forge a revoke.

The `follow` op is presence the room keeps and never relays.

### What the room does to a frame

In order, for every inbound frame: a frame over 256 KiB is dropped; a per-session sliding-window rate cap (240 frames per second) drops a flood; an op from a session that hasn't said `hello` is dropped; a system-kind op from a client is dropped; a tab-scoped session may only touch its own tab and never the document's structure (`scopedSenderMayRelay`); a non-presence op from a session whose verified role isn't `edit` is dropped. Then:

- **Presence ops** relay to every other socket.
- **Mutation ops** are rewritten before they go anywhere: `opForTheWire` strips every comment `authorId` (a guest's credential), and `stampCommentAuthor` sets a posted comment's author name and colour to the sending session's presence, whatever the frame claimed. The rewritten op gets the next `seq`, lands in the catch-up log, relays to every other socket, is recorded in the ledger when it is an `el-delta`, and the sender receives a `cursor` frame naming the `seq` its own op took, echoing the op frame's `ref` when it carried one (a positive integer), so the sender knows that op is sequenced.
- Every outbound op frame to a tab-scoped session is filtered or redacted for its scope (`opForScope`), live and in catch-up.

On `hello` the room builds the session's presence itself (`helloPresence`): the id is a server-minted per-socket random (never the connector's owner id), the role is the verified one, and every claimed string is length-clamped. It then sends the joiner a `cursor` frame, and broadcasts presence (each socket gets the roster minus its own entry).

### Ordering and catch-up

Mutations are totally ordered by the single-threaded DO: a monotonic `seq` within an `epoch`. `epoch` and `seq` are persisted in DO storage (`order-state`) and restored on every wake, so hibernation does not strand reconnecting clients ([Resync without reloading the page](../012-collaboration/resync-without-reload.md)). The catch-up log (the last 256 mutations, `OP_LOG_LIMIT`) lives in memory only. On reconnect a client sends `{ kind: 'sync', epoch, lastSeq }`; `resolveCatchup` answers with the ops it missed, or `resync: true` when the gap is behind the log's floor or the epoch is foreign, and the client re-fetches its loaded tabs in place.

### What the room stores

Besides the document's content (**Storage**), its key-value storage holds:

- **`order-state`**: `{ epoch, seq }`, written on every mutation.
- **The collaboration ledger** (`RoomLedgerStore`, `room-ledger-store.ts`; entries defined by the pure `collab-ledger.ts` in `@livedocuments/document`): for every `el-delta` it sequences, the latest state of each checklist tick and comment, one key per element, tagged with the `seq` that set it. An entry that would pass the storage value limit stops growing. The api reads it back to merge a tab save (see the tab `PUT` above).

Per-session state (presence id, verified role, owner bit, tab scope, admitting share code, presence) lives in each socket's serialized attachment, so it survives hibernation; only the rate-cap windows and the catch-up log reset on a wake.

The room's other parts each have a module of their own in `apps/api/src/`, beside the room (`document-room/document-room.ts`): the session attachment and the verified upgrade headers (`room-session.ts`), the role gate on client ops (`room-op-gate.ts`, the [Share roles](../013-workspace/share-roles.md) level ladder), the worker-only internal endpoints (`room-internal.ts`) and the presence roster each socket is sent (`room-roster.ts`).

### What the room writes itself

- **One telemetry row**: the room counts a multiplayer session once (`Document·Used·Multiplayer`, `reportServerEvent`) into liveworkspace's telemetry, when `TELEMETRY_ENABLED` is on ([Telemetry + public transparency dashboard](../017-telemetry/telemetry.md)).

Every other document write is a REST call from a client (see the persistence boundary below).

### Internal endpoints

The api worker reaches the DO through its stub (`env.DOCUMENT_ROOM.get(...).fetch(...)`; content goes through the typed RPCs under **Storage**), which never traverses the public edge, so these paths are implicitly internal:

- **`POST /broadcast`** `{ op, ordered? }`: push a system op to every socket (`from: 'system'`), sequenced when `ordered` is true. A revoke from the index (`revokeCodes`) sends `share-revoked` the same way, then closes the sockets that code admitted. Best-effort: a failure is logged (`[room-broadcast]`).
- **`POST /mutation`** `{ op }`: sequence a document change the worker made, as if a peer had sent it. `el-delta`, `changeset` and `tab-meta` are accepted (400 otherwise); the comment endpoints use `el-delta` so a view-role visitor's comment reaches connected editors (`relayElementDelta`), the changeset route uses `changeset` ([Agent changesets](../024-agents/agent-changesets.md#what-the-room-does)), and the tab rename route uses `tab-meta` (`relayTabRename`).
- **`GET /selections?tab=<tabId>&person=<tag>`**: the elements each connected person has selected on a tab (every `select` is recorded in DO storage per session, pruned when the socket goes), each marked `mine` when the session's person tag is the one asked about. The changeset route reads it to find held elements.
- **`PUT /presence`**, **`DELETE /presence`**: an agent's presence entry with its expiry ([Agent presence](../024-agents/agent-presence.md#presence)).
- **`GET /ledger?tab=<tabId>&epoch=<epoch>`**: the tab's collaboration ledger, or an empty one when `epoch` isn't the room's current epoch (the saver's cursor can't be interpreted then).
- **Purging a room** (the `purge` RPC; `POST /purge` reaches the same code): the document was deleted for good, so the room closes every socket (`DOCUMENT_TRASHED_CLOSE`, reason `document-purged`), waits for the ledger's queued writes, drops its alarm and deletes all of its storage (`deleteAll`): the document's content with it, and the ledger with its comment text, the order state, selections and agent entries. The index asks for it (`DELETE /api/internal/items/:id`) whenever a document leaves its Trash for good, by hand, by its daily sweep or by account deletion, and retries a document it could not reach.

### Conflict model

- **Different elements on one tab merge.** `el` ops apply by id, so concurrent edits to different elements survive on every peer.
- **The same element is last-writer-wins, over the whole element.** Two `el` updates to one element apply in room order and the later one replaces the earlier, whoever held the selection. The concurrent-selection lock ([Editor app](../007-editor/editor-app.md)) is advisory and client-only (`remoteSelectionsByElement`, built from `select` ops): it makes these collisions rare, and the room does not enforce it. `tab-meta` patches are last-writer-wins per field, and `document-meta` per whole tab list.
- **Multi-writer fields merge.** Checklist ticks and comments travel as `el-delta` deltas that commute, and whole-element or whole-tab ops don't overwrite a receiver's copy of them.

### The persistence boundary

The document's object holds both the content and the ordering and collaboration state. Tab content reaches its store through `PUT /api/documents/:id/tabs/:tabId`, fired by each editor's debounced autosave with the editor's whole copy of the tab. The store keeps the last save of a tab, with the room ledger merged in as described on that row. Each editor's copy already folds in the ops it has received, so the last save normally carries everyone's work; an element edit that reached the saver only after its snapshot can be missing from the store until a later save carries it, while live peers still hold it.

A tab `PUT` is not relayed to the room; it is the editor's autosave and nothing else's. Every other writer of tab content (the MCP server, the CLI, an API-token script) writes a [changeset](../024-agents/agent-changesets.md), which the api records in the document's store and relays to the room, and which every later editor save re-applies unless that editor has seen it. The comment endpoints also tell the room about their writes.

Every tab the api receives (document create, tab save) runs the stored-tab migration (`migrateStoredTab`) before `isValidTab`, as every tab read does, so an element in a former stored shape (for example freehand points before [Stroke points](../006-document/stroke-points.md)) from a browser loaded before a deploy or an API-token script is stored in the current shape rather than refused.

## Data model

The api has no D1 database and no SQL migrations. Its data is in two kinds of SQLite-backed Durable Object, each
creating its schema on first use:

- **Document content** (`document`, `tabs`, `document_tabs`, `tab_stats`, `image_refs`, `image_owners`, `image_grants`, `notify_claims`, `agent_changesets`, `agent_changeset_parts`, `tab_shares`, `share_outbox`, `outbox`) is in each document's Durable Object, `apps/api/src/document-room/document-schema.ts`. The document's own row holds its name, owner and deck. A tab shared with other documents is a copy in each. See [Per-tab storage](../006-document/per-tab-storage.md) for why a tab is its own row.
- **A person's workbench** (pairing requests, pairings, tickets, sessions and the rooms a workspace session joined) is liveworkspace's ([liveworkspace/docs/specs/011-workbench/workbench.md](../../../../liveworkspace/docs/specs/011-workbench/workbench.md)), which keeps only hashes of tickets and session secrets.

API tokens are liveworkspace's alone ([Public API and API tokens](public-api-and-tokens.md)). Where a document is filed, who it is shared with and whether it is in the Trash are the index's ([one-explorer-contracts.md](../../../../liveworkspace/docs/specs/004-index/one-explorer-contracts.md)).

### Owner-keyed data

This is the one list of columns that hold an owner id (a guest id or an account userId), and what **account deletion** (`deleteAccount` in `apps/api/src/db/account.ts`) does with each. Account deletion runs on `DELETE /api/account` and whenever the index says an account closed (`POST /api/internal/people/:id/purge`, the `personClosed` door), wherever it was closed. A guest's items move to the account in the index when they sign in ([Auth + guest access → Guest → account](../014-identity/auth-and-guest-access.md#guest--account)), and the index's merge door (`POST /api/internal/people/:guest/merge`, `personMerged`) moves the guest's images to the account at the media service (`mergeOwner`). | Column                       | Account deletion                                                                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `document.owner_id`          | In each document's own store: the account's own documents are deleted for good through the index first, which purges each store                         |
| `agent_changesets.author_id` | In each document's own store: those on someone else's document stay until the 30-day changeset retention ages them out                                  |
| `image_owners.owner_id`      | In each document's own store, the media service's answer cached: the service deletes the account's images, and a document then serves nothing of theirs |

**The person's images** go first, at liveworkspace's media service (`forgetOwner`, every image the account uploaded, in any app), so a failure leaves the account whole to delete again. **The person's workbench** is liveworkspace's, which ends every pairing (closing the rooms its sessions had open) when the account closes ([liveworkspace/docs/specs/011-workbench/workbench.md](../../../../liveworkspace/docs/specs/011-workbench/workbench.md) "Ending access").

**Kept by the accounts Worker, not here.** API tokens are the account's and close with it. A person's settings ([User preferences](../007-editor/user-preferences.md)), name and colour (`GET`/`PUT /api/participants`), first sighting, milestone claims and email address live in the liveworkspace accounts database ([liveworkspace/docs/specs/003-accounts/accounts.md](../../../../liveworkspace/docs/specs/003-accounts/accounts.md)). Closing an account deletes them there. A guest's settings and profile stay under the guest id when they sign in.

A new owner-keyed table adds a row here, a statement to `deleteAccount`, and an entry in the test, in the same change.

## One-time setup

Before the first deploy:

There is no bucket and no database to create and no migration to apply: the Durable Object (`DocumentRoom`) is declared in `wrangler.toml` (`new_sqlite_classes`) and makes its own schema on first use.

After that, the monorepo's deploy ships it in its first tier, before the sites and the router whose service bindings name `livedocuments-api` ([Deployment](../016-platform/deployment.md) "Deploy").
