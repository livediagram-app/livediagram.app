# Architecture

A pnpm + Turborepo monorepo: six Cloudflare-deployed apps, one distributed command-line app and fifteen shared packages (with the `@liveworkspace/*` packages at the repo root). Everything runs on Cloudflare Workers (Static Assets for the Next.js apps); there's no Node-hosted backend.

```
apps/
  marketing/    static landing site (Next.js export, /)
  editor/       the document editor (Next.js export; clean routes); the router serves the shared Explorer beside it
  help/         help centre (Next.js export + MDX, /help)
  api/          REST + WebSocket worker (Durable Objects, /api)
  mcp/          MCP server for AI tools (OAuth + tools, mcp.livedocuments.app)
  router/       service-binding router stitching the apps under one hostname
  cli/          the livedocuments command line for agents and scripts (Node, one esbuild bundle)
packages/
  ui/             shared UI primitives + chrome icons (Brand, CloseIcon, etc.)
  document/       document data model (Tab, Element types + helpers)
  templates/      template catalogue + pure element builders (editor template starts + MCP)
  template-previews/ per-template preview SVGs (editor template starts + marketing template gallery)
  help-registry/  this product's help-centre articles + categories, bound to @liveworkspace/help-registry's lookups (help app + editor search)
  api-schema/     wire-format DTOs the api worker emits + the live editor consumes
  agent-verbs/    the verbs the CLI routes to: schemas, handlers, compact text, addressing, guides, the skill
  edit-operations/ the engine agent changesets run on: edit operations and replace into element ops
  document-views/ read-only text views of a tab (outline, pages, layout, ...) for agents and scripts
  diagram-lint/   checks how a tab is laid out: overlaps, crossings, arrows behind boxes, with a fix each
  telemetry-client/ this product's telemetry facts (app, preferences key, tokens) bound to @liveworkspace/telemetry-client
  licences/       this product's licence tables (apps, overrides, embedded works) for @liveworkspace/licences' generator
  tailwind-config/ this product's brand ramps (amber) over @liveworkspace/tailwind-config's theme
  (shared with every product, in the monorepo's packages/ as @liveworkspace/*: api-client, api-kit, mcp-kit,
  telemetry-client, render-png, source-ast, style-guards, page-background, help-registry, tailwind-config, icons, licences, and the oxlint, prettier, vitest, next configs)
docs/specs/          product source of truth, read these before adding features
scripts/        repo-wide dev tooling (next-dev.mjs: shared Next.js dev launcher)
marketing/      off-site copy + media for listings and promotion (see docs/specs/019-marketing/marketing-assets.md)
  copy/         taglines, descriptions, tags, the canonical fact sheet
  media/
    icons/      the brand mark as PNGs
    logo/       the mark and lockup as SVG
```

## The editor's shape

The editor route (`apps/editor/app/document/[id]/`) is split three ways so no file becomes a god component:

- `useEditorState.ts` is the orchestration hook: it calls each domain sub-hook, threads their dependencies, and assembles the return view-model.
- `EditorContext.tsx` carries that view-model as `EditorContextValue = ReturnType<typeof useEditorState>`.
- `EditorView.tsx` renders the JSX, leaving `editor-page.tsx` a thin page shell.

`useEditorState.ts` is large by design: what remains in it is wiring, not logic, so it is exempt from the ~400-line soft target ([AGENTS.md](../../AGENTS.md#core-principle-no-god-files-plan-placement-first)). New behaviour goes into its own sub-hook, not into it.

## The shared packages

Each app pulls these in via `workspace:*`:

- **`@livedocuments/document`** owns the document data model: `Tab`, every `Element` type (Shape / Text / Sticky / Image / Freehand / Table / Link card / Arrow), pages and articles, defaults, geometry helpers, snap math, layer ordering, the web components' layouts and the load-time migration of documents saved with groups. It also holds the authoring input every non-editor writer shares: raw elements made safe (`normaliseElement`), finished tabs built (`buildTab`), every stored field per element type (`ELEMENT_FIELD_NAMES`) and validation that names the field and rule it fails (`elementValidationIssue`). The single source of what a document IS.
- **`@livedocuments/api-schema`** owns the wire format between the api worker and the live editor: every request / response shape, plus the response envelopes (`DocumentResponse`, `TabResponse`, ...) the editor and the MCP server both read, the small shared pure helpers it backs (`sha256Hex` for image-upload dedupe, worker-safe `bytesToBase64` / `bytesToBase64Url`, `embedTabImages` which inlines a tab's uploads for the api snapshot and the MCP preview, `titleCase` for display-casing preset values across the editor + telemetry dashboard, and the page-view path normaliser + the editor app's route-segment list, shared by every frontend, the router and the dashboard, [Page view telemetry](../specs/017-telemetry/page-view-telemetry.md)). Adding a field on the server without updating the client used to be routine drift; the typechecker catches it now.
- **`@liveworkspace/explorer`** (`packages/explorer/src/lens/` at the repo root) owns the Explorer's one filter state: the lens string's grammar (`parseLens` / `serialiseLens`), matching, autocomplete and the chips' view models.
- **`@livedocuments/diagram-lint`** checks how a tab is laid out ([Diagram lint](../specs/024-agents/diagram-lint.md)): `lintTab` answers the measures (crossings, arrows behind boxes, overlaps, extent) and ten kinds of finding, each with the refs the views print and a fix as edit operations. Pure and deterministic, consumed by the api worker (`?view=lint`, every changeset's footer) and the MCP (the summary line).
- **`@livedocuments/document-views`** renders a tab as a [document view](../specs/024-agents/document-views.md): `renderView` builds one view model (refs, derived containment, reading order, edges) and answers the outline, `layout`, `comments`, `show` or `find` as text and JSON, fitted to a token budget with one closing line naming what it left out; `overviewView` summarises a document from per-tab header facts, and `diffView` compares two reads of a tab for the CLI. Refs, slug ids, kind words and containment themselves live in `@livedocuments/document` (`element-refs.ts`, `containment.ts`), so edit operations and the lint name elements the same way. Pure and deterministic, consumed by the api worker (`?view=`).
- **`@livedocuments/edit-operations`** is the engine an agent changeset runs on ([Edit operations](../specs/024-agents/edit-operations.md)): `parseEditOperations` reads the line form (JSON objects allowed on a line) and `validateEditOperations` the JSON form; `applyEditOperations` applies the eleven operations to a tab, resolving refs and selectors, placing new boxes beside what they name and making room on insert; and `applyReplace` builds a whole tab from a template or raw elements. Each answers the next tab, its element ops and their inverse, the result lines and the targets it resolved, or named refusals with nothing applied; `formatResultLines`, `formatResultFooter` and `formatRejections` print them. Its `pages` slice runs an agent's [Pages](../specs/024-agents/pages-for-agents.md) writes: `parsePagesRequest` reads the body, `applyPageChanges` adds, sets, lays out, moves and deletes pages and `applyArticleWrite` writes an article from Markdown, on the same pure page edits the editor's page panel uses (`packages/document/src/pages-edits.ts`). Containment and carrying (`containerContents`) and refs live in `@livedocuments/document`, shared with the views. Pure and deterministic, consumed by the api worker.
- **`@livedocuments/ui`** owns the cross-app UI primitives. The chrome (`Brand`, `SiteHeader`, `SiteFooter`, `SiteSwitcher`), the form + feedback controls (`Button`, `TextInput`, `Select`, `EmptyState`), the hover and focus hints (`Tooltip` for a name, `HoverCard` for a title and description; see [Tooltips, hover cards and popovers](../specs/004-interface-design/tooltips-hover-cards-popovers.md)), the shared behaviour hooks (`useMediaQuery`, `useCopiedFlash`, and the dismiss / focus trio `useClickOutside`, `useEscape`, `useFocusTrap` the editor's dialogs and the public sites' popovers share) plus the popover-clamping helpers. It also holds the public sites' shared plumbing: the site constants (`SITE_URL`, `SITE_NAME`, `REPO_URL`, the `BRAND_ICONS` favicon set, the `PUBLIC_VIEWPORT`), the SEO builders (`pageMetadata` for per-page metadata, `breadcrumbJsonLd`, rendered by `JsonLd`), and `PageViewBoot`, the page-view tracker wired to the shared `siteTrack` emitter. Reach for these before re-typing a class list: a control that exists here and is rebuilt in an app is the drift this package was made to stop. The package also owns the **chrome icons** (`src/icons/`): a `Glyph` base (square viewBox, `currentColor` stroke, round caps, `aria-hidden`) and named React icons (`CloseIcon`, `TrashIcon`, `ChevronDownIcon`, `SearchIcon`, `LinkIcon`, `SharedDotIcon`, ...) that take `size` / `strokeWidth` / `className` overrides, so a glyph the editor, marketing hero and telemetry dashboard all draw is one path, not a copy per file. These are app-chrome components; the canvas's own icon catalogue (SVG markup strings for canvas elements) is `@liveworkspace/icons`.
- **`@liveworkspace/icons`** (the monorepo's `packages/icons`, shared with every product) owns the catalogues (the line-art glyphs and the stickers of [Stickers](../specs/010-palette/stickers.md)) plus pure SVG-markup builders for them, and `xmlEscape`, the one XML escaper every SVG builder in the monorepo shares (`@livedocuments/document` re-exports it). The editor dynamic-imports the data modules through its icon registry so they stay out of its first-load JS; the api + mcp workers static-import `@liveworkspace/icons/resolve` so headless renders (the live image, Explorer thumbnails, MCP inline images) draw the real glyphs.
- **`@livedocuments/templates`** owns the template library: the catalogue (kinds, titles, categories, per-template canvas overrides) and the pure per-template element builders. Two callers: the editor's template starts (which layer its theme recolour on top in `apps/editor/lib/template-builders.ts`) and the mcp worker's `list_templates` / `template` tools ([MCP server](../specs/015-api/mcp-server.md)), so the scaffolds can't drift between them. `buildTemplateTab` makes a finished template tab for the MCP and a changeset's `replace` alike.
- **`@livedocuments/template-previews`** owns the per-template preview illustrations: one static SVG per `TemplateKind`, rendered by the editor's template picker and by the marketing site's template gallery, so a template's card looks the same wherever it is offered and a new kind gets its artwork in one place. Its tests assert every listed template has a preview and that each drawing stays inside its viewBox.
- **`@livedocuments/help-registry`** owns the help-centre article + category registry: slugs, titles, descriptions, and per-article search keywords. The pure href, grouping and search helpers over it are the monorepo's `@liveworkspace/help-registry`, which every product binds to its own catalogue. Two callers: the help app's browse + search (`apps/help/lib/articles.ts` re-exports it) and the live editor's search-panel Help group (`apps/editor/lib/help-search.ts`), so adding an article once makes it findable in both.
- **`@livedocuments/licences`** binds this product's tables (its apps, overrides and embedded works) to **`@liveworkspace/licences`** (the monorepo's `packages/licences`, one engine and one pool of texts for every product), which generates the third-party licences page ([Third-party licences](../specs/002-project-scope/third-party-licences.md)). The marketing build runs it after every other app has built: it reads what each Next app ships to the browser from `next experimental-analyze` and what each worker bundles from a `wrangler --dry-run` metafile, collects each package's licence and notice files (with reviewed overrides for packages that ship none, and a reviewed table for what sits inside WASM and fonts), and writes a manifest plus deduplicated plain-text files that `apps/marketing/app/licences` renders. A package with no licence text, an unrecognised licence, a disallowed one or an unreviewed binary fails the build with a named error.
- **`@liveworkspace/source-ast`** parses the repo's own TypeScript for the static guards that read code ([Source scanners](../specs/003-system-architecture/source-scanners.md)): `parseSourceFiles(paths)` opens the files as one in-memory project in TypeScript 7's native compiler (`typescript/unstable/sync`) and returns their syntax trees.
- **`@liveworkspace/oxlint-config`** / **`prettier-config`** / **`vitest-config`** / **`next-config`** / **`tailwind-config`** (the monorepo's `packages/`, shared with every product) own the lint / format / test / Next.js / theme configs so every workspace stays consistent. The shared theme also owns the motion tokens (`duration-micro` / `-short` / `-long`); their numbers and the static motion-budget guard every app runs in its tests are `@liveworkspace/style-guards` ([Motion](../specs/004-interface-design/motion.md)). This product's own **`tailwind-config`** is only its palette: the shared theme, then its brand ramps in amber.

## Tech stack

What's running:

- **Frontend**: Next.js 16 (Turbopack) with `output: 'export'`, React 19, TypeScript 7 (the Go compiler, see [contributing](contributing.md#typescript)), Tailwind CSS 4.
- **API**: Cloudflare Workers (vanilla `fetch` handlers, not Hono).
- **Database**: none of its own. Each document's content is in its own SQLite-backed Durable Object ([API app](../specs/015-api/api.md) "Storage"). Workbench pairings, tickets and sessions are liveworkspace's accounts Worker's. Where documents are filed, sharing, teams, the Trash, the Timeline and the Inbox are liveworkspace's index; API tokens, a person's settings, name and email are the liveworkspace account's; uploaded images are liveworkspace's media service.
- **Index** ([One Explorer](../../../liveworkspace/docs/one-explorer.md), [its contracts](../../../liveworkspace/docs/one-explorer-contracts.md)): where every document is filed, who may open it, its sharing, folders, favourites, Trash and Inbox are liveworkspace's index, shared by every liveworkspace app. The editor calls it on its own origin at `/api/index/*`, which the router forwards to liveworkspace.app; access is a short-lived grant the index signs, sent to the api as `X-Index-Grant` and to the room as its `?t=` ticket. `/explorer` renders the shared `@liveworkspace/explorer`, which lists every app's items.
- **Local persistence** (optional per document, [Offline Mode](../specs/006-document/offline-mode.md)): Offline Mode stores a document only in the browser's IndexedDB, never the api. It is opt-in at create time (or by taking a cloud document offline) and dispatched behind the single `apps/editor/lib/api-client.ts` persistence boundary on `isOfflineId(id)`, so the rest of the editor takes the same code path either way. They are listed on their own page, This Browser (`/offline`, `apps/editor/app/offline`), since the index never sees them. Convertible both directions: Sync Document uploads it to the account, Take Offline downloads it and deletes the server copy. See [Offline Mode](../specs/006-document/offline-mode.md).
- **Realtime**: Cloudflare Durable Objects, one room per document. Edits sync as granular, id-addressed element ops, so concurrent edits to _different_ elements merge instead of clobbering, and the room stamps each mutation with a per-`epoch` sequence so peers converge and a reconnecting client catches up from a bounded op log (see [Realtime conflict resolution](../specs/012-collaboration/realtime-conflict-resolution.md)). Two people editing the _same_ element at once is last-writer-wins; the advisory, client-only selection lock ([Editor app](../specs/007-editor/editor-app.md)) makes it rare, not impossible. The fields a whole room writes at once (checklist ticks, comments) instead travel as per-change deltas that commute, and the room keeps a small ledger of them which the api merges into each tab save, so a save snapshotted before somebody's tick can't erase it from the store (see [Collaboration race hardening](../specs/012-collaboration/collab-race-hardening.md)). Every server-stored document has a room, personal ones included: agents and API-token scripts change tabs with [changesets](../specs/024-agents/agent-changesets.md), which the api applies, records in the document's Durable Object (`agent_changesets`, with the tab's compare-and-swap revision `tabs.rev`) and relays to the room, and which every editor save re-applies unless that editor has seen it. The whole-tab `PUT` is the editor's autosave alone.
- **Articles** ([Article pages](../specs/007-editor/article-pages.md)): the writing on article pages is edited with ProseMirror (MIT, `prosemirror-*` in `apps/editor`), loaded only once a tab has an article. The writing is stored as flat, id-addressed blocks on the tab (`Tab.articles`, `packages/document/src/article-flow.ts`) and syncs as its own room op (`{ kind: 'article' }`, block by block: put, remove, style), never inside whole-tab ops. The editor glue lives in `apps/editor/lib/article/` and `apps/editor/components/canvas/article/`; the pure model (pages, zones, margin notes, conversion to Page elements) in `packages/document/src/article-*.ts`.
- **Image storage**: liveworkspace's media service ([liveworkspace/docs/media.md](../../../liveworkspace/docs/media.md)), deduped by SHA-256. Each document's Durable Object keeps the images it places (`image_refs`), a cache of their owners (`image_owners`) and its placement grants (`image_grants`), and its outbox tells the media service its whole set as it changes. The bytes are served only through this api: `GET /api/images/:id?d=<document>` resolves the index's grant for that document and checks the document may serve the image (see [Image element + per-owner gallery](../specs/009-elements/images.md)); `GET /api/images/usage` reads the media service's usage plus the index's names.
- **Auth** (optional): sign-in through the liveworkspace accounts Worker (`liveworkspace.app`, OAuth 2.1 authorization code + PKCE), with livedocuments as an OAuth client. The api worker runs the round trip (`/api/auth/*`, refresh token in an HttpOnly cookie), verifies access tokens and liveworkspace guest tokens locally against `${ACCOUNTS_URL}/api/auth/jwks`, and treats every caller as a link visitor when `ACCOUNTS_URL` / `API_RESOURCE` are unset. A returning visitor who has signed in before is signed in silently; a guest gets a liveworkspace guest token through the guest handoff.
- **Email** (optional): the api worker sends transactional email via Resend (`apps/api/src/email/`) — account-deleted messages, milestone notes, and opt-out notifications (someone joins your shared document, comments, mentions, assigned actions) configurable on the Explorer profile page. Gated on `RESEND_API_KEY`: no key, no sends. Addresses come from the liveworkspace accounts Worker, which also sends the onboarding series (see [Transactional email (Resend)](../specs/014-identity/transactional-email.md) and [Account settings & email notifications](../specs/014-identity/profile-and-email-notifications.md)).
- **Timeline** ([Timeline](../specs/013-workspace/timeline.md)): liveworkspace's, kept by its index and shown by the shared Explorer, with What Happened on Home. livedocuments sends it only who edited a document (`PUT /app/items/:id/events`, one key per person, from the room's outbox); comments are not Timeline events, and reach the Inbox through the collab push.
- **Inbox** ([Inbox](../specs/013-workspace/inbox.md)): liveworkspace's, one view in the shared Explorer across every app. A document's Durable Object pushes each changed tab's comment threads and actions to the index from its outbox, on idle and at most once a minute (`apps/api/src/document-room/document-outbox.ts`). A row links into the editor with `#t=<tab>&el=<element>`.
- **Explorer Home** ([Explorer Home](../specs/013-workspace/explorer-home.md)): the shared Explorer's Home view (Jump back in, Shared with you recently, What Happened), read from the index. The editor records an open with the index (`POST /items/:id/open`) when it loads a document. livedocuments' own `/api/home` is gone.
- **Trash** ([Trash](../specs/013-workspace/trash.md)): the index's. A deleted document stays 30 days in the Trash, restorable, then the index deletes it for good and asks the document's Durable Object to drop its content. The MCP server can bin and restore but never purge.
- **API tokens** (optional, [Public API and API tokens](../specs/015-api/public-api-and-tokens.md)): signed-in users make revocable liveworkspace account tokens (`lwt_…`) on liveworkspace.app to call the REST API from their own scripts; the api worker checks an `Authorization: Bearer lwt_…` with liveworkspace and caches the answer for a minute. Signed-in only (like teams), six-month expiry. Absent in pure-guest mode.
- **API description** ([API documentation (OpenAPI)](../specs/015-api/api-documentation.md)): `GET /api/openapi.json` serves a public OpenAPI 3.1 document of the whole `/api/*` surface, assembled (`apps/api/src/openapi/`) from a declarative route manifest plus component schemas generated from `@livedocuments/api-schema` (`pnpm --filter @livedocuments/api gen:openapi`). A drift test pins the manifest to the real dispatch and the committed schemas to the types. The human-facing companion is the help centre's **Developers** category (`apps/help`).
- **Routing edge**: a Cloudflare Worker stitching the apps under one hostname via service bindings.

## Hard constraints

The repo's shape isn't accidental. Three rules keep the stack honest:

- **Static-only frontends.** Next.js apps use `output: 'export'`. No SSR, no Node runtime, no Next.js API routes. Server logic goes in the api worker. Breaking this breaks Cloudflare Pages deploys.
- **Reuse over duplication.** Shared types, UI primitives, configs, and the document data model live in `packages/`, never copy-pasted across apps. If two apps need the same thing, it lives in `packages/` on first occurrence.
- **No secrets in source.** The repo is public; secrets travel via env vars (`.env.local`), `wrangler secret put`, and GitHub Actions repo secrets. See [Secrets policy](../specs/002-project-scope/secrets-policy.md).

## Auth model in one sentence

Every caller is a verified token: a liveworkspace account's access token, or a liveworkspace guest token (a year-long `guest_…` identity fetched once through the accounts site, the same in every app), sent as `Authorization: Bearer`, whose `sub` is the owner id; API tokens and workbench sessions have their own paths, and a share link alone admits a link visitor. The canvas always works without signing in. See [Auth + guest access](../specs/014-identity/auth-and-guest-access.md) for the full model and [API app](../specs/015-api/api.md) for how the api worker resolves the caller and checks the index's grant.

## Deployment

GitHub Actions → Cloudflare Workers. Build artefacts get uploaded once, then marketing / help / api ship in parallel; the editor and mcp deploy after `api` (mcp has a service binding to it), and the router deploys last because its service bindings need the others to exist.

Two environments run that same sequence, from one reusable workflow (`deploy-reusable.yml`) so they cannot drift:

|         | Production                   | Staging                                                      |
| ------- | ---------------------------- | ------------------------------------------------------------ |
| Host    | `livedocuments.app`          | `staging.livedocuments.app`                                  |
| Trigger | Manual, after a green CI run | Automatic, on every green CI run on `main`                   |
| Workers | `livedocuments-<app>`        | `livedocuments-<app>-staging` (wrangler `[env.staging]`)     |
| Data    | Durable Objects              | Its own Durable Objects and index — no production data, ever |

Staging exists so every change runs against real remote Workers, Durable Objects and liveworkspace's staging index one deploy before it reaches people's documents. It is public but `noindex` (the router stamps `X-Robots-Tag` when its `DEPLOY_ENV` is `staging`). See [Staging environment](../specs/016-platform/staging-environment.md).

Both environments also get the **hosted profile** (`apps/api/hosted-vars.json`: telemetry on, per-owner image caps), which the workflow adds with `wrangler deploy --var` only in livedocuments.app's own repository and then reads back off the live api worker. A fork deploys the committed config alone, so it is telemetry-off and uncapped. See [Deployment](../specs/016-platform/deployment.md) "Hosted profile".

See [Self-hosting](../operations/self-hosting.md) for the step-by-step, and [Deployment](../specs/016-platform/deployment.md) for the deeper deployment contract.
