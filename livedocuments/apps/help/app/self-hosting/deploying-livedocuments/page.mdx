livedocuments is not one application but a small set of apps that each deploy as their own Cloudflare Worker, stitched together at a single hostname. This page is a conceptual map of how the pieces fit so the deployment makes sense. For the exact commands and account setup, the repository and its self-hosting guide are the authoritative source.

## The apps

The product is split into focused apps, each deployed as a named Cloudflare Worker.

- **marketing** serves the public landing site at the root.
- **live** is the editor itself, served at clean routes such as `/new` and `/explorer`.
- **help** is the help centre you are reading now, at `/help`.
- **api** is the Worker that holds the REST and WebSocket layer. It has no database of its own: each document's content lives in that document's own Durable Object, and each person's workbench in theirs.
- **router** sits in front and forwards each request to the right app by URL path. It holds no business logic, only routing.
- **mcp** (optional) is the MCP server that lets people connect AI tools to their documents. It has its own hostname (`mcp.livedocuments.app` on the hosted service), needs sign-in configured, and talks to the api Worker directly.

The router is what makes the first four appear under one domain. The hosted service's public telemetry dashboard is not one of them: it belongs to liveworkspace, which counts usage for livedocuments and its sister apps, and `/telemetry` redirects there.

## How a request is routed

The router Worker inspects the path and forwards accordingly: `/api/*` to the api Worker, `/help` to the help centre, the editor's routes (`/document`, `/explorer`, `/new`, `/join`, `/sign-in`, `/get-started`, `/embed` and the like) to the editor app, and everything else to marketing. Because the router has service bindings to the four path-routed apps, they must exist before the router can be deployed.

## How it deploys

Deployments run through **GitHub Actions to Cloudflare Workers**. In broad strokes:

1. Continuous integration runs lint, format, typecheck, test, and build on every pull request and every push to `main`.
2. A separate, manually triggered deploy workflow builds everything, then deploys the apps.
3. The marketing, help and api Workers deploy in parallel. The live editor follows the api, so a new editor never calls an api that lacks its routes, and the mcp Worker follows the api too. The bundled workflow always deploys mcp, so a fork that does not want the MCP server removes the `deploy-mcp` job, or creates its KV namespace first. The router deploys last because its bindings depend on the four path-routed apps already existing.
4. There is no database migration step: each Durable Object sets up its own storage the first time it is used.

Deploying needs a Cloudflare API token and account id, supplied as repository secrets (`CF_API_TOKEN` and `CF_ACCOUNT_ID`), never committed to source. You can also deploy by hand: run `pnpm build`, then run `wrangler deploy` for each Worker in the same order. The repository also has a staging workflow that the hosted service uses for rehearsals. It runs automatically after every green CI on `main`, so a fork should delete it, or it fails on every merge.
