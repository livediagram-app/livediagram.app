A self-hosted livedocuments is configured through environment variables, secrets and each Worker's `wrangler.toml`, not application code. A few `wrangler.toml` values ship with livedocuments.app's own settings (the index's address `INDEX_ORIGIN`, the KV id, and the MCP issuer and consent URL), so a fork replaces those it changes. The most important thing to understand is that the optional features are genuinely optional: leave them unset and the editor still works perfectly, just in a simpler mode. This page covers how configuration is supplied and the main toggles you will care about.

## How configuration is supplied

Secrets and settings never live in source code, since the repository is public. Instead, each Worker reads them at runtime.

- **Local development** uses a gitignored `.env.local` file per frontend app and a gitignored `.dev.vars` file per Worker.
- **Workers** receive secret values via `wrangler secret put`, and non-secret settings as `[vars]` in the Worker's `wrangler.toml`. Set plain settings in the file rather than the Cloudflare dashboard: every deploy replaces them with what the file declares.
- **Static frontends** only ever bundle values explicitly marked as publishable, prefixed `NEXT_PUBLIC_` so it is obvious they are safe to ship to the browser, and baked in at build time. Server-only secrets stay on the Worker side and never reach client code.

Each app that needs configuration ships an example file documenting which variables it expects, so you can see at a glance what to set.

## Optional sign-in

Sign-in goes through a liveworkspace accounts Worker. The editor always offers it; whether it works depends on what you give the API.

1. **Hybrid**, the production setup: the API has the accounts Worker's address and your client's details (`ACCOUNTS_URL`, `API_RESOURCE`, `ACCOUNTS_CLIENT_ID`, `ACCOUNTS_CLIENT_SECRET`), so guests and signed-in users coexist.
2. **Guest-only**: leave those unset. There is no account system, and no guest identity either: nobody can finish signing in, and every visitor is left without an identity.

Guests are liveworkspace guest tokens, minted by the same accounts Worker as accounts are, so there is no separate guest secret to set, and without the accounts Worker there are no guests. A guest's documents become their account's when they sign in. Accounts unlock the features that need one: [teams](/help/collaboration/teams/), [API tokens](/help/account-and-data/api-tokens/), and, if you set them up, email and the MCP server.

## Without sign-in

The API identifies a person by a verified liveworkspace token: an account's, or a guest's from the same accounts Worker. When sign-in is not configured, nobody has a token, so every request is answered as a link visitor's. The editor still works: documents are kept in this browser ([This Browser](/help/privacy-and-security/offline-mode/)), and shared documents open, with real-time collaboration, through their links. Documents in the cloud are filed in liveworkspace's index (reached with `INDEX_KEY`), and making one needs a guest or an account, so without sign-in new documents are made in this browser only.

## Other optional features

Every other optional feature follows the same pattern: unset means off, and the editor hides what it cannot use.

| Feature                 | Turn it on with                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Image uploads           | `MEDIA_KEY` on the api Worker, its secret on liveworkspace's media service, which keeps the images and their limits (100 images and 100 MB per person). Set `MEDIA_URL` too when the service is not liveworkspace.app's                                                                                                                                                                                 |
| Thumbnails              | Create the `livedocuments-images` R2 bucket the api `wrangler.toml` already binds (or delete that binding to leave thumbnails off)                                                                                                                                                                                                                                                                      |
| Email                   | `RESEND_API_KEY` on the api Worker, plus `RESEND_FROM` on a domain verified in Resend and `APP_BASE_URL` set to your origin, since both default to livedocuments.app (needs sign-in)                                                                                                                                                                                                                    |
| MCP server for AI tools | Deploy the mcp Worker with its own KV namespace and hostname, then point `CONSENT_BASE_URL` (mcp Worker) at your editor's origin, and `NEXT_PUBLIC_MCP_ORIGIN` (live build) and `OAUTH_ISSUER` (api Worker) at your MCP host (needs sign-in). See [The MCP Server](/help/self-hosting/configuration/mcp-server/)                                                                                        |
| Telemetry               | `TELEMETRY_ENABLED` on the api Worker and `NEXT_PUBLIC_TELEMETRY_ENABLED` on every frontend build, plus a telemetry service of your own that takes the same batches: `TELEMETRY_URL` and the `TELEMETRY_KEY` secret on the api and mcp Workers, and `NEXT_PUBLIC_TELEMETRY_URL` on every frontend build. The hosted service only takes livedocuments.app's own events, so without one nothing is stored |
| Workbenches             | Nothing extra beyond sign-in, but set `APP_BASE_URL` on the api Worker to the origin that serves the app, or pairing and frame links point at livedocuments.app (needs sign-in)                                                                                                                                                                                                                         |

The `NEXT_PUBLIC_*` values above are baked in at build time. When you deploy through the bundled GitHub Actions workflow, add them to the workflow's build step (or set `mcp_origin` in `deploy.yml`); apart from the sign-in flag, which the workflow turns on when the `ACCOUNTS_CLIENT_ID` repository secret is set, they are not read from repository secrets.

  For every variable, where it lives and the steps around it (OAuth redirect URIs, KV namespaces),
  follow the repository's `docs/operations/self-hosting.md` and each app's `.env.example` file.
