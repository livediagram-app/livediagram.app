# Marketing site

The marketing app (`apps/marketing`) is the public landing site served at `/` (everything the router doesn't hand to the live editor's routes, `/api/*`, or `/telemetry`, see [08-router-app](../016-platform/router-app.md)). Static Next.js export, no SSR. It is the top of the acquisition funnel: its only job is to explain what livediagram is and send visitors to `/new`.

## Golden rule: claims map to shipped features

**Every feature claim on the marketing site must correspond to something a visitor can actually do today.** No aspirational copy, no roadmap dressed as present tense.

- If a feature is not built (teams/permissions, true concurrent/CRDT editing, see [02-prototype-scope](../005-project-roadmap/prototype-scope.md)), it does **not** appear on the landing page, even softened.
- When the editor gains or loses a feature, update the landing page in the same change. Drift between the page and the product is a bug.
- Counts (templates, themes, shapes) must match the source of truth ([09-canvas-and-palette](../008-canvas/canvas-and-palette.md), `packages/templates/src/templates.ts`, `apps/live/lib/themes.ts`). As of this spec: **81 templates** (11 default + 70 extra, three blanks leading Popular, one per editor mode, and Draw and Illustrate templates of their own ([Templates by mode](../007-editor/templates-by-mode.md)), grouped into Brainstorm / Flowcharts / Hierarchies / Agile / Projects / Strategy / Design / Technical categories in the picker, including three mind-map styles (radial / tree / bubble), four flowchart styles (basic / swimlane / decision tree / approval workflow) plus a data-flow diagram, Mobile / Laptop / Web-page wireframes that pair with the device-frame shapes, a Slide deck of 16:9 pages and a Storyboard frame grid, a Flywheel momentum loop, a Logo design starter on square pages, an Article to write on pages, Timeline + horizontal/vertical Milestone timelines + Gantt + Roadmap + RACI project-planning starters, a Group card the whole team signs, agile User story map + Affinity map boards, Lean Coffee + Town Hall Q&A live-session boards built on the Q&A board, strategy canvases (Business Model Canvas, Empathy map, Funnel), OKR tree + Sitemap hierarchies, and the technical System / Cloud architecture, Database schema, Sequence, Class and State machine diagrams and an Event storming board plus an Impact-vs-Effort Prioritization matrix, a to-scale Floor plan furnished with the top-down Furniture icons, four more retro formats (Start / Stop / Continue, Mad / Sad / Glad, 4Ls, Sailboat), an Incident postmortem, an Opportunity solution tree, Crazy 8s, a Stakeholder map, a Risk matrix, a User persona, a Meeting agenda and a personal Objectives planner), **26 themes** (12 default + 14 extra, the extras including a Dark category and five multi-colour "rainbow" schemes; see [Multi-colour (rainbow) themes](../011-theme/multicolour-themes.md)). Both counts are pinned by `apps/live/lib/templates.test.ts` + `themes.test.ts` so spec drift surfaces as a test failure.
- Be honest about trade-offs where it builds trust: realtime is **last-write-wins**, not CRDT, say so rather than implying conflict-free merging.

## Structure

Single landing page (`app/page.tsx`), in this order: a sticky header, the hero, the template gallery, **five story beats**, the privacy callout, a closing CTA, and a footer. The page tells one story (start fast, work together, present, make it yours, keep it yours) rather than listing every category.

**The landing page tells a story; the detail lives on a page per category.** The page used to run one advertising block per `LANDING_SECTIONS` entry, thirteen in a row, each the same shape (title, badges, showcase, Explore link). It measured about 12,500px on desktop and read as a checklist: by the fifth identical band nothing stood out. (Before that, every feature card rendered inline, 60+ of them, which was worse.) So the body is now **five story beats** (`LANDING_BEATS` in `lib/landing-beats.ts`, rendered by `components/StoryBeat.tsx`), each grouping two to four categories under one idea. A beat has its headline, with the beat's number in a badge to its left, vertically centred on the title so a two-line title stays balanced (no eyebrow word above it: it only repeated the title), a pitch of its own, a **link to every category it covers** (each a chip into that category's `/features/<id>` page, so all thirteen stay one click from home, led by that category's own glyph from `components/category-icons.tsx`, one per section id and none shared, pinned by `category-icons.test.tsx`), a primary "Explore" link into its lead category, and an animated showcase composed from the **first feature of each category it covers** (`components/Showcase.tsx`, which `SectionShowcase` also wraps for the category pages), so the art shows the beat's breadth, not just one category. Beats alternate the showcase side and the tinted background. `landing-beats.test.ts` pins that **every section id is in exactly one beat**, so adding a category without placing it on the home page fails. The full `FeatureGrid` of cards for each category still renders on its **`/features/<id>`** page (one per `LANDING_SECTIONS` entry), so no feature claim is lost. See "Feature category pages" below.

### The Start Blank menu

The header's **Start Blank** (`StartBlankMenu` in `packages/ui`) is a menu button, not a link: one blank per [editor mode](../007-editor/editor-modes.md), so a visitor who came to sketch or to make a poster lands in the right mode without the wizard.

- **Opens** on hover with a mouse (without moving focus, the same CSS hover the apps menu uses) and on a press, Enter, Space or an arrow key (focus on the first row, the [menu](../004-interface-design/menus.md) keyboard). A chevron beside the label turns when it is open. Escape, an outside press or a choice closes it.
- **Rows**, in mode order, each the editor mode switch's glyph (`EDITOR_MODE_ICON`: `FlowchartIcon`, `MarkerIcon`, `IllustrateIcon`), a name and one line under it:

| Row                | Opens                              | Line under it                       | Source               |
| ------------------ | ---------------------------------- | ----------------------------------- | -------------------- |
| Blank Diagram      | `/new?blank=1`                     | Shapes, connectors and structure    | `HeaderDraw`         |
| Blank Whiteboard   | `/new?template=whiteboard`         | Free drawing without distractions   | `HeaderWhiteboard`   |
| Blank Illustration | `/new?template=blank-illustration` | Pages for infographics and articles | `HeaderIllustration` |

- Each row carries its own [landing-funnel](landing-funnel.md) source, so the funnel tells the three blanks apart.
- Each line under a name stays on one line; the menu is as wide as its longest row.
- The menu drops from the button's right edge, so it never runs off the page beside the primary.
- Blank Illustration's kind (`blank-illustration`) arrives with [Templates by mode](../007-editor/templates-by-mode.md); until then an unknown kind opens the plain wizard, as any stale template link does.

**Every CTA is measured** ([Landing funnel](landing-funnel.md)). A link into the editor from a public page builds its `href` with `ctaHref(href, source)` from `@livediagram/api-schema`, which adds `via=<Surface>.<Slot>` (`Home.Hero`, `Home.Gallery`, `Feature.Closing`, ...). The header takes its surface as a prop (`<Header surface="Faq" />`, passed through to the shared `SiteHeader`'s `ctaSurface`), and `StartDrawingCta` takes `surface` too. A new CTA adds its slot to `CTA_SOURCES` first; a bare `href="/new"` on a public page is a CTA the funnel can't see.

Reusable building blocks: `Section` + `FeatureGrid` (`components/Section.tsx`), `StoryBeat` (`components/StoryBeat.tsx`), `Showcase` (`components/Showcase.tsx`), `Header`, `Footer`, `Brand` (from `@livediagram/ui`). The feature sections are data, not markup: they live in `lib/landing-content.tsx` as the `LANDING_SECTIONS` array (each entry an `id`, `title`, `description`, a hand-written `cta` button label, and `items`). That single array drives the `/features/<id>` detail pages and, through `LANDING_BEATS` (which only names section ids, never copies their text), the landing page's beats, so adding a feature card or a whole section is a one-place edit and the two surfaces can never drift. **`LANDING_SECTIONS` is the authoritative section list** (the numbered walkthrough above is illustrative and may lag); do not fork the grid or hard-code a section list anywhere else. The "AI tools & external connections" section (`id: connect`, "Connect your tools and AI") groups the MCP AI connection, the public API / token integration path, and the optional in-editor AI assistant; the API + MCP cards moved here out of `foundations`, and the AI-assistant card out of `assist`, so all the "open at the edges" capabilities sit together.

## Feature category pages

**Arriving on a page is animated, never a cut** (`app/page-motion.css`). Moving between two marketing pages (home to a category page and back) is a cross-document **view transition**: the pages crossfade and the sticky header (`view-transition-name: site-header` on the shared `SiteHeader`) holds still. The opt-in, `@view-transition { navigation: auto }`, is **inlined in the root layout's `<head>`** rather than left in the bundled stylesheet: the browser only runs the transition if the new page has opted in by its first paint, and from the stylesheet it sometimes arrived later, so the transition was skipped and the old page logged "Transition was skipped" (about half of navigations in testing; none since). A link out of the marketing site (into the editor at `/new`, the help centre, the dashboard) **skips the transition** as the page swaps: only the marketing pages opt in, so the browser would otherwise start one, find the editor declined, and report "Transition was aborted because of invalid state" as an uncaught error on every hero click. The marketing page decides by the destination's app, the router's own split (`pageViewApp`), in a small inline `pageswap` listener beside the opt-in. On arrival the category hero eases up piece by piece (`.enter`, staggered by `--enter-delay`), and the feature cards and the landing beats rise in as they scroll into view (`.enter-on-scroll`, a scroll-driven animation where supported, a load-time one elsewhere; on the cards it sits on a wrapper, because the card's hover lift is a transform the animation would pin). All of it is CSS over content already in the static HTML, so crawlers and no-JS visitors get the same page, a browser without these features shows the page as before, and reduced motion turns it all off.

Each `LANDING_SECTIONS` entry gets a static page at **`/features/<id>`** (`app/features/[slug]/page.tsx`, a single dynamic route with `generateStaticParams()` over the section ids and `dynamicParams = false`, so only known categories are generated and an unknown slug 404s at build, the same pattern as `/alternatives/[slug]`). The page opens with a rich hero (`components/FeatureCategoryHero.tsx`: eyebrow, title, positioning line, a "Start drawing" CTA, and the section showcase), then renders the section's full `FeatureGrid`, a breadcrumb (`components/Breadcrumb.tsx`, styled to match the help centre), and the shared closing CTA (`components/StartDrawingCta.tsx`) so a visitor who drills into a category can still convert without bouncing home.

The landing beats and the detail-page hero share one illustration component: `components/Showcase.tsx` stacks a few fixed-height `FeatureArt` scenes, captioned, animating one at a time. `SectionShowcase` feeds it a category's own first features (the detail-page hero); a beat feeds it the first feature of each category it covers. The showcase is **hidden below the two-column breakpoint** (`hidden lg:block`) on both surfaces: when the layout stacks on mobile it ate the screen and just restated the pitch beside it.

- **Source of truth:** the page reads the matching `LANDING_SECTIONS` entry by `id`; there is no second copy of the feature copy. The golden rule (claims map to shipped features) therefore holds automatically, the detail pages show exactly the cards the landing page used to.
- **Grouped sub-sections:** a category with many features (more than ~6) is hard to scan as one long grid, so its features carry a `group` label and the detail page renders captioned sub-sections (`groupSectionFeatures` builds the ordered groups). Categories without `group` tags render one flat grid. Today `collaboration`, `customise`, `refine` and `present` are grouped; the rest are flat. `present` has two groups: **Slide deck** (the four deck features) and **Presenting modes** (Spotlight, Laser pointer, Avatar mode, Isometric, Zen), which were five one-feature groups until they were merged so the page reads as two sub-sections rather than six.
- **SEO:** every `/features/<id>` declares its own `alternates.canonical`, emits a `BreadcrumbList` (`Home → <Category>`), and is listed in `app/sitemap.ts` (derived from the section ids so a new section is sitemapped automatically).
- **No `/features` hub index.** The landing page is the feature overview; the category pages are reached from each section's "Explore …" link, not from a hub. (An earlier `/features` index page was removed.) The footer links to the comparison hub + content pages, not a features index.
- **Routing:** these live on the marketing origin under `/features/*`, which the router already forwards to the marketing worker as the default (non-live/api/telemetry/help) path, so no `apps/router` change is needed.

## Social sharing

Word of mouth is part of the acquisition funnel, so the page lets a happy visitor pass it on in one click. `packages/ui/src/ShareRail.tsx` renders a **vertical rail pinned to the right edge of the page**: a rotated "Share" label above the share targets (X, LinkedIn, Facebook, WhatsApp, email) and a **Copy link** action.

It began as a "Share" popover in the header and moved out to the edge to give the header room to breathe. Two consequences of where it ended up:

- **It lives in `@livediagram/ui`, not in the marketing app**, because `SiteHeader` renders it. Surfaces that use the shared header carry the rail by default (the telemetry dashboard is just as worth passing on as the landing page); the help centre turns it off (`shareRail={false}`) because its pages run `max-w-7xl`, so the rail would cover the article sidebar ([Help app](../018-help/help-app.md)).
- **It renders as a _sibling_ of the header, not a descendant.** The header's `backdrop-filter` establishes a containing block that would trap the rail's `fixed` positioning against the header instead of the viewport.

Beyond that:

- **Wide desktop only (`xl`, 1280px).** Page content is `max-w-6xl` (1152px), so only past `xl` is there a real gutter for a fixed rail to sit in without overlapping the content. Below that it is hidden, and a page URL is inherently shareable anyway.
- **Share targets are plain anchor links** to each network's public share-intent URL (`twitter.com/intent/tweet`, `linkedin.com/sharing/share-offsite`, `facebook.com/sharer`, `wa.me`, `mailto:`). No SDKs, no tracking pixels (keeps the "no tracking pixels" claim honest under [03](../002-project-scope/open-source-and-business-model.md)). They open in a new tab (`target="_blank"` + `rel="noopener noreferrer"`).
- **The Appearance rail sits under it.** A second, separate rail of the same card, a gap below, holds the [Appearance](../004-interface-design/appearance.md) toggle, which leaves the header at the same breakpoint.
- **Copy link** uses the Clipboard API to copy the canonical URL and flips to a tick for a beat, via the shared `useCopiedFlash`, so a rapid second copy restarts its own countdown rather than inheriting the first one's remainder.
- The shared URL is the canonical production site, `SITE_URL` from the package's own `site.ts` (the one origin constant every app uses), and the share text mirrors the product's one-line description, a constant in the component; update it if the positioning copy changes.
- The icons are stored as raw `<path>` `d` strings rather than JSX, so the module evaluates no top-level JSX at import time and the shared barrel stays importable from non-React test transforms.
- On the landing page itself the `'use client'` boundaries are the `TemplateGallery` (search state over the template cards), the `HeroIllustration` (the click-to-centre six-window stage, whose launch window grows into the editor), and `ShowcaseStagger`; everything else stays a server component for static export. The rail is a client component too, but it now arrives via the shared header rather than the page.

**Feature-card illustrations.** Every feature card carries a small animated mock of the real editor surface it describes (`components/FeatureArt.tsx`), passed via the card's `art` slot. Like the hero, the motion is **pure CSS**, shared keyframe classes (`fa-*`) live in `app/globals.css`, so it works under static export with no JS and settles to a finished frame under `prefers-reduced-motion`. The mocks must stay faithful to how the feature actually looks (presence avatars, the explorer / share panels), and every diagram in them is drawn as the editor draws it on the **Default theme**: its canvas, grid and the ink of unpainted shapes, arrows and labels, in the light half or the dark half with the appearance ([Appearance](../004-interface-design/appearance.md)). Only identity colours (stickies, cursors, highlights, selection), elements the example deliberately painted (the editor keeps a user's paint on any theme) and art whose subject is colour keep other colours; when a feature's UI changes, update its art. This is part of the golden rule above, an illustration is a claim too.

## SEO and metadata

The marketing site is the indexable surface for the product, so its `<head>` carries the search and social signals. The editor's routes and the API at `/api/*` are not optimised for organic search (the editor lives behind client-side bootstraps and has nothing useful to index).

- **One rule for every subpage, shared with the help centre**: subpage metadata comes from `pageMetadata()` in `@livediagram/ui` (the help centre wraps the same function, [Help app](../018-help/help-app.md) "SEO"). The title passes through verbatim (no suffix added), `og:type` is `article`, and the card is the large brand card (`summary_large_image`, `/opengraph-image` + `/twitter-image` by absolute URL) unless the page ships its own route-level image (`ownOgImage`, the `/features/<id>` cards). The origin, site name, repo URL, favicon set (`BRAND_ICONS`) and public viewport (`PUBLIC_VIEWPORT`) are shared constants in the same package, used by every app.
- `metadataBase`: `https://livediagram.app`. Lets relative paths in metadata resolve into absolute URLs (the canonical, OG image, sitemap entries).
- `alternates.canonical`: every static page declares its own canonical (`/`, `/faq`, ...). Stops query-string variants and the `www` mirror from competing with the canonical form. The retired `/terms` and `/privacy` routes are the exception: they are noindex redirect stubs whose canonical points at the help-centre Policies articles they now forward to (see "Content pages" below).
- `<html lang="en-GB">` on the root layout. Matches the OG locale + JSON-LD `inLanguage` so every locale signal across the page agrees. The earlier broader `lang="en"` worked but reads inconsistent next to OG's specific `en_GB` declaration.
- `openGraph`: title, description, url, siteName, locale (`en_GB`), type (`website` for the landing page, `article` for FAQ/alternatives). Mirrors the page-level title/description so social cards match the actual head. Article-type subpages with a tracked revision date (`/alternatives` + `/alternatives/<slug>` via `ALTERNATIVES_LAST_UPDATED`) also emit `article:modified_time` via `pageMetadata({ modifiedTime })`, the OG meta tag Google + social previews read for the freshness signal on article pages. FAQ omits it because the content moves with product releases, not on a tracked schedule. (The Terms and Privacy Policy moved into the help centre and carry their own "Last updated" lines there.) Card image is generated by `apps/marketing/app/opengraph-image.tsx` via `next/og`'s `ImageResponse`; Next.js's file convention pre-renders it to a static 1200x630 PNG at build time and ships it in `out/`, so the asset has no runtime dependency.
- `twitter`: card `summary_large_image`, title, description, and the card image. `apps/marketing/app/twitter-image.tsx` re-exports the OG handler so the Twitter card and the OG card stay byte-identical. Copy is identical to the OG / page-level title and description.
- `robots`: explicit `{ index: true, follow: true }` on every page. The hosted product wants indexing; ambiguity about defaults is the kind of thing a future migration silently breaks.
- `app/sitemap.ts`: lists the indexable marketing URLs, `/` + `/faq` + `/alternatives` + one entry per `/alternatives/<slug>` competitor page (mapped from `ALTERNATIVE_SLUGS` so adding a competitor updates the sitemap automatically, see [21-comparison-pages](comparison-pages.md)). The two public operational surfaces, `/telemetry` (the anonymous-events dashboard) and `/status` (the service-status page), are also listed: both are public, indexable (each sets `robots` `index: true` and a self-canonical), and reachable from the footer, so sitemapping them lets crawlers discover them directly rather than depending on footer links. They sit at a lower priority (0.4) than the marketing content because they're transparency pages, not primary landing destinations. `/terms` and `/privacy` are deliberately not listed: both legal pages moved into the help centre (the help app's own sitemap lists the canonical Policies articles), and each marketing route is now a noindex redirect there. `lastModified` is per-page truth, not blanket build-time: `/` and `/faq` use `new Date()` because they change with product releases; `/telemetry` and `/status` also use `new Date()` (the dashboard reflects live event data, the status page reflects the latest deployed state, so both are "fresh as of this build"); `/alternatives` + the per-competitor pages share an `ALTERNATIVES_LAST_UPDATED` constant. Without that split, every build claims content changed today, which is misleading to crawlers and dilutes the change-frequency signal for pages that actually move. Next.js generates `/sitemap.xml` at the root from this file.
- `app/robots.ts`: allows the marketing routes, points at the sitemap, and `Disallow`s the live-app routes and `/api/`. The router worker stitches all three apps onto the same hostname, so an unconditional allow would let crawlers waste budget on the editor's auth-walled HTML and the API's JSON responses. The live app also declares `noindex, nofollow` at its root layout (see [07-live-app.md](../007-editor/live-app.md)) as the in-page complement; together the two signals tell crawlers to skip the live app entirely.
- **`viewport` export** (Next.js metadata API): the root layout exports a `Viewport` object carrying `themeColor: '#0EA5E9'` (brand-500, see [01-color-scheme](../004-interface-design/color-scheme.md)) and `colorScheme: 'light dark'`. The first tints mobile browser chrome (Android Chrome's URL bar, iOS PWA status bar) to the brand, the second says the pages paint both appearances; which one follows the reader's origin-wide [Appearance](../004-interface-design/appearance.md) (System by default, the header toggle to override), applied before first paint. Every page, illustrations included, has a dark appearance, and its editor mock-ups show the editor as it looks in dark. Both are head meta, not page content, so they don't conflict with the "claims map to shipped features" rule.
- **`app/manifest.ts`**: emits `/manifest.webmanifest` at build time with `name`, `short_name`, `start_url: '/'`, `display: 'standalone'`, the brand theme + background colours, and the existing `/icon.svg` as the icon (which `purpose: 'any'` covers since the SVG is monochrome on a single brand stroke). Surfaces the Android Chrome "Add to Home Screen" prompt + the iOS Safari "Add to Home Screen" landing icon, with no behaviour change for normal page loads. Same `export const dynamic = 'force-static'` opt-in as robots.ts / sitemap.ts so it round-trips through `output: 'export'`. Because `livediagram.app` is one origin (the router stitches the apps by path), this is the **origin's** manifest: the editor (live app) references it (and `/apple-icon`) by absolute path from its own layout metadata, so installing the PWA from the editor gets the same icon + name rather than nothing (see [07-live-app](../007-editor/live-app.md)).
- **JSON-LD structured data**: the root layout renders a single `<script type="application/ld+json">` carrying a `@graph` of two schema.org types: `WebSite` (so the brand-name search produces a rich result) and `SoftwareApplication` (so the product is categorised correctly in browse / category-style results). Both schemas restate facts already in the page (name, url, description) and the SoftwareApplication offer is `price: "0"` (truthful: the hosted product is free with no paid tier, see [03](../002-project-scope/open-source-and-business-model.md)). No claims that aren't already true on the surface. Each schema also carries an `image` field pointing at the same OG card (`/opengraph-image`) so Google can pair the brand card with a visual, an `inLanguage` field matching the OG locale (`en-GB`), and a `sameAs` array on the SoftwareApplication that links the canonical GitHub repo (already linked from the footer + the FAQ self-host answer) so the brand's open-source presence is connected to the same entity.
- **FAQ JSON-LD**: `/faq` emits an additional `<script type="application/ld+json">` with schema.org `FAQPage` + a `Question` / `Answer` pair per entry. Unlocks Google's "expandable FAQ" rich result for the page. The JSON-LD `acceptedAnswer.text` is the plain-text form of each answer; entries that render JSX (a link to the help-centre privacy policy in the data-storage question, for instance) carry a parallel `aText` field with the same sentence, sans markup. The FAQ component reuses the existing `FAQS` array as the source so the structured data can't drift from the visible content.
- **Breadcrumb JSON-LD**: every indexable subpage (`/faq`, `/alternatives`, `/alternatives/<slug>`) emits a `BreadcrumbList` script. (The retired `/terms` + `/privacy` redirect stubs don't, since they render no breadcrumb trail.) Two items for two-level pages (`Home → <Page>`), three items for the comparison detail pages (`Home → Alternatives → <competitor>`). Unlocks Google's SERP breadcrumb display so the search result shows `livediagram.app > FAQ` instead of the bare URL. Rendered via `components/BreadcrumbJsonLd.tsx` so the pages share one source of truth; the `BreadcrumbList` shape itself is the shared `breadcrumbJsonLd` builder in `@livediagram/ui`, which the help centre's breadcrumbs use too. The landing page (`/`) doesn't get a breadcrumb (it IS home, the trail would be a single entry).
- **ItemList JSON-LD**: the `/alternatives` hub page emits an `ItemList` script whose `itemListElement` array lists every `/alternatives/<slug>` URL in display order. This is the schema.org shape Google expects for a curated index of related pages: it tells crawlers the page is a hub (not a piece of editorial content in its own right), surfaces the linked comparisons as a coherent set rather than scattered backlinks, and can enable carousel-style rich results for the hub itself. Built from the same `ALTERNATIVES` array the visible list + sitemap consume, so adding a competitor updates all three together.

When a new public page lands, add it to both `app/sitemap.ts` and its own metadata block (with `alternates.canonical`). Updating one without the other is a regression.

## Content pages (FAQ)

The **Terms of Service** and **Privacy Policy** no longer live here: they moved into the help centre's **Policies** category (`/help/policies/terms/`, `/help/policies/privacy-policy/`, see [55-help-app](../018-help/help-app.md)).
