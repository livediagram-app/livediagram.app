# API app

The HTTP + WebSocket layer the live editor calls for document persistence and realtime collab.

- **Workspace:** `apps/api` (`@livediagram/api`).
- **Worker name:** `livediagram-api`.
- **Mount:** routed from the [router worker](../016-platform/router-app.md) at `/api/*`. The router forwards the request as-is — the api worker sees the full `/api/...` path.

## Why this exists

The first prototype phase ([spec 02](../005-project-roadmap/prototype-scope.md)) ran entirely client-side with `localStorage` persistence. Once realtime collaboration entered scope, server state became necessary: a Durable Object per document holds the in-room participant list, orders and relays ops between connected clients and keeps the collaboration state that must outlive a socket, and D1 owns the durable document snapshot. The live app no longer reads or writes `localStorage` for documents — `apps/live/lib/api-client.ts` is the single boundary.

## Tech

- **Runtime:** Cloudflare Workers.
- **DB:** Cloudflare D1 (binding `DB`). Schema lives in `apps/api/migrations/`; each numbered file is one applied change. Treat the migration log as the source of truth on the schema — features get a migration each, so the count grows.
- **Realtime:** Cloudflare Durable Objects (`DocumentRoom`, binding `DOCUMENT_ROOM`). One instance per document id, identified by the document's UUID via `idFromName`.

## Wire-format types

The DTO shapes the api worker emits + the live editor consumes live in `packages/api-schema` (`@livediagram/api-schema`) — `LiveDoc` (published as `Document`), `TabSummary`, `TabRecord`, `Folder`, `ShareLink`, `ServerMessage` / `ClientMessage`, and the room op vocabulary (`RoomOp` / `RoomOutgoing` / `RoomIncoming`). Both apps import them; the api worker also re-exports under historical `XxxDTO` aliases (`apps/api/src/types.ts`) for backward compatibility with its existing call sites.

Defining the wire shapes once means server and client cannot drift — adding a field on one side without updating the other is a typechecker error. **Do not redefine these types inline in `apps/api/` or `apps/live/`**; extend the schema package instead. Per AGENTS.md the reuse-over-duplication rule is non-negotiable.

## Auth

The api resolves the request owner through four identities, in this order of preference (see [Auth + guest access](../014-identity/auth-and-guest-access.md) and [Public API and API tokens](public-api-and-tokens.md)):

1. **Clerk Bearer JWT** — `Authorization: Bearer <jwt>`. Verified against `env.CLERK_JWKS_URL` in `apps/api/src/auth/clerk.ts` using `jose`'s `createRemoteJWKSet` + `jwtVerify`. The token's `sub` claim is the owner id. Returns null on any failure (invalid signature, expired, malformed, missing env var), logged as `[auth] clerk_jwt_rejected reason=<jose code>`, never 401, because the worker must still serve the other paths. `exp` / `nbf` allow 5 seconds of clock skew, matching Clerk's backend SDK. A bearer shaped as an API token (`isApiTokenFormat`, `lvd_…`) or a workbench session (`isWorkbenchSessionFormat`, `lvw_…`) is never handed to the verifier: it is no Clerk session token, so `getClerkIdentity` returns null for it at once and logs nothing, and the token paths below resolve it.
2. **API token** — `Authorization: Bearer lvd_…`, consulted only when no Clerk JWT verified. `resolveApiToken` hashes it and looks up a live (non-revoked, non-expired) `api_tokens` row; the owner id is that row's Clerk userId, so a token request flows through the same ownership and gate checks as a signed-in one. A token minted **read-only** is refused on every `POST` / `PUT` / `DELETE` with `403 read_only_token`, at one choke point in `index.ts`.
3. **Workbench session** — `Authorization: Bearer lvw_…`, consulted only when neither a Clerk JWT nor a token resolved ([Workbench embeds](../013-workspace/workbench-embeds.md)). `resolveWorkbenchSession` hashes it and looks up a live `workbench_sessions` row of a live token; an unknown, expired or revoked one is refused `401 invalid_session`, never read as a guest. The owner is the session's owner, `clerkUserId` and the token stay null (a person's editor, never an administrator or an agent), and `workbenchRefusal` confines it before any route runs: another document answers `404`, any route outside `WORKBENCH_ROUTES` `403 workbench_confined`, a view session's write `403 workbench_read_only`, and an `X-Share-Code`, `X-Owner-Id` or `X-Share-Password` beside it `403 workbench_confined`.
4. **Guest header** — `X-Owner-Id: <participant-id>`, used when no Bearer credential resolved. The participant id is server-minted by `POST /api/guest-id` and persisted in `localStorage` under `livediagram:v2:self-id`. On the owner-scoped segments (`OWNER_SCOPED_SEGMENTS` in `apps/api/src/auth/guest-rest.ts`: `documents`, `folders`, `images`, `custom-themes`, `shape-libraries`, `participants`, `preferences`, `shared`, `timeline`, `activity`, `favourites`, `trash`, `placement-defaults`) two guards run before any handler:
   - A header value shaped like a Clerk account id is refused unconditionally with `401 account_id_not_a_guest_credential` (`isClerkIdShape`): no real client ever sends one, so it can only be a replayed, harvested account id ([Public API and API tokens §4.1](public-api-and-tokens.md#41-a-clerk-account-id-in-x-owner-id-is-refused-unconditionally)).
   - Once enforcement is armed (`GUEST_ID_HMAC_SECRET` set **and** `GUEST_SIG_ENFORCE_AFTER` in the past, `guestSignatureEnforced`), the header must carry a matching HMAC in `X-Owner-Sig`, or the request gets `401 signature_required`. Until an operator arms it, an unsigned guest id is still accepted on REST; this is the legacy-guest grace window ([Public API and API tokens §4](public-api-and-tokens.md#4-x-owner-id-trust-change)).

The request handler computes the resolution once at the top of `fetch`:

```ts
const clerkIdentity = await getClerkIdentity(env, request);
const clerkUserId = clerkIdentity?.userId ?? null;
// tokenAuth: { ownerId, tokenId, readOnly } | null, only when clerkUserId is null
const resolveOwner = (): string | null =>
  clerkUserId ?? tokenAuth?.ownerId ?? request.headers.get('X-Owner-Id');
const verifiedUserId = clerkUserId ?? tokenAuth?.ownerId ?? null;
```

Every endpoint uses `resolveOwner()` instead of reading the header directly, so adding new endpoints inherits the hybrid behaviour automatically. `verifiedUserId` (a server-verified account id from either Bearer credential, never the header) feeds the team-membership gates; account administration (teams mutations, `/api/tokens`, `/api/account`, `/api/migrate` flow 1) reads `clerkUserId` alone, so a token can't reach it.

`CLERK_JWKS_URL` is a **worker secret** (`wrangler secret put`, synced from a GitHub repo secret on deploy), not a `[vars]` entry — the JWKS itself is public, but the URL names the tenant, and keeping every out-of-band value in one mechanism is simpler than reasoning about which ones are safe in the open ([Secrets policy](../002-project-scope/secrets-policy.md)). Leaving it unset puts the api in pure-guest mode — useful for local dev or for environments where Clerk hasn't been provisioned yet.

Visitor-edit endpoints (`PUT /api/documents/:id/tabs/:tabId`) still also accept `X-Share-Code` for share-link auth — that header is checked via `canEditDocument()` and is orthogonal to the Clerk-vs-guest choice. A visitor following a share link is a guest who provides a code, regardless of whether they're separately signed in. When the document has a **share password** ([Share password](../013-workspace/share-password.md)), the same `canEditDocument()` / `canReadDocument()` checks also require a matching `X-Share-Password` header, so every share-code read and write is gated, not just the initial resolve. The owner identity short-circuits the password check. The realtime room upgrade carries the password as the `p` query param (browsers can't set headers on a WS upgrade) and refuses to open the room for a non-owner without it.

It is the editor's autosave path: a request presented with an API token is refused `405 use_changesets`, naming the changeset route, since agents write through changesets. ### Document dates

A document's dates are its `createdAt` (shown as created) and `savedAt` (last
modified, the lists' order), both milliseconds since the epoch, as everywhere
on the wire. A create stamps both with the server's now, unless the body
carries its own: an Offline Mode sync carries the local record's `createdAt`
([Offline Mode](../006-document/offline-mode.md)), and an imported board
carries the board's own created and last-modified dates
([Microsoft Whiteboard import](../020-import-export/whiteboard-import.md)), so
it sits in the Explorer where its age puts it.

- Each given date must be a whole number of milliseconds no earlier than
  `DOCUMENT_DATE_MIN` (1 January 2000, before any document a person could
  bring) and no later than the server's now plus `DOCUMENT_DATE_SKEW_MS`
  (one day, for a device clock that runs ahead), and `createdAt` must not be
  later than `savedAt`.
- A given `createdAt` alone keeps `savedAt` at now (or at `createdAt`, if a
  clock running ahead put that later); a given `savedAt` alone is refused (a
  document is never modified before it is created).
- Seeding the create's tabs leaves `savedAt` as given.
- Anything else is refused whole, 400 `bad_request` "invalid document dates";
  nothing is created.
- Only a genuine create takes them: re-committing an id the caller already
  owns keeps the stored `createdAt`.

### Marking a document used

Making a document is a use of it for whoever makes it: a use day and their latest use, the measures
[Explorer Home](../013-workspace/explorer-home.md#making-a-document)'s Jump back in reads. The create body's
`markUsed` decides it.

- Absent or `true`: the making counts, at the server's now. A create that carries dates of its own (an imported
  board) still counts on the day it is made.
- `false`: the document is made and filed as ever, and its creation is in the Timeline as ever, but it is no use:
  it joins Jump back in at its first open or edit. The editor sends it for every document of an import that makes
  more than one in one go; any client that makes many documents at once should too.
- Anything but a boolean is refused whole, 400 `bad_request` "invalid markUsed"; nothing is created.
- A re-commit of an id the caller already owns, and an Offline Mode sync (`X-Document-Conversion: sync`), are
  not makings of a document, so neither is a use, whatever `markUsed` says.
- `POST /api/documents/:id/copy` (a duplicate, or a copy of a shared document) always counts: one document, made
  on purpose.

### Documents in the Trash

Every document read (`getDocument`, `getDocumentMeta`, the lists, Shared with
you, Favourites, Activity, the Timeline) sees live documents only, so a door
nobody remembered fails closed with a 404. The doors that owe a person the
deleted state (every `/api/documents/:id/*` route, `/api/share/:code` and its
`image.svg`, the room ticket) ask `missingDocument` on a miss: 410
`document_trashed` when the document is in the Trash and the caller could have
opened it (owner, joined team member, share-code holder), else 404. The room's
WebSocket upgrade refuses a trashed document with a plain 404, whatever the
ticket or code. `POST /api/documents` over a trashed id answers 410 to its
owner and 403 to anyone else. The daily `0 3 * * *` cron purges documents 30
days in the Trash (`purgeExpiredTrash`, at most 2,000 a run, oldest first).
The same run moves live documents with no element on any tab, unsaved for 30
days, into the Trash with `reason: 'empty'` (`trashEmptyDocuments`, at most
2,000 a run; [Empty document clean-up](../013-workspace/empty-document-cleanup.md)).

### Tab size

A tab is stored as one text value in one D1 row (`tabs.data`, the tab's
JSON without its id and name), and Cloudflare D1 caps a string, a BLOB and a
row at **2,000,000 bytes** ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)).
Local `wrangler dev` does not enforce it, so the api enforces it itself:

- `D1_MAX_ROW_BYTES` = 2,000,000. `MAX_TAB_BYTES` = `D1_MAX_ROW_BYTES` less
  `D1_ROW_HEADROOM_BYTES` (8 KiB) = 1,991,808 bytes of UTF-8 JSON. The
  headroom covers the row's other columns (the tab id, a UUID; the name, at
  most 60 characters, so at most 240 bytes; `updated_at`; SQLite's record
  header) many times over, so a tab under the cap always fits its row.
- Both numbers live in `@livediagram/api-schema`, so the editor checks the same
  cap the worker does and the two cannot drift.
- **Every write of a tab's data** is checked against it, at the storage layer
  (`upsertTab`, `seedTabs`, `swapTabData`), so no route can store what D1
  would refuse: document create, the tab save, a comment added or deleted
  through the api, and a Q&A board write. A tab over the cap is refused with
  the named 413 (`payload_too_large`) and nothing is written; the worker logs
  `[tab-size] refused` with the write (`create`, `upsertTab`, `seedTabs`,
  `swapTabData`), the tab id, the bytes and the cap. The comment routes list
  413 among their answers in the OpenAPI manifest. The routes
  also check the request up front, so a create never leaves a document
  without its tabs.
- The cap is not raised and the storage format is unchanged; a tab that needs
  more is a separate decision.

## Caching

Every JSON answer is the caller's live state, so it goes out `Cache-Control: no-cache` unless its
route chooses a policy of its own (the OpenAPI document, the public telemetry summary): a browser
may store it but asks the server again before reusing it. Without it a browser may reuse an answer
the server has since changed: Chromium holds a `410` with no explicit expiry indefinitely, so a
share-link visitor who once saw a document deleted would keep seeing it after the owner restored
it. Not `no-store`: the browser's cache drains a stored answer's body, and without it an answer
whose caller never reads the body holds its request open. Images and SVG snapshots set their own
policies.

## Rate limiting

Seven limiters, each a Cloudflare Workers Rate Limiting binding declared under `[[unsafe.bindings]]` in `apps/api/wrangler.toml` (where the ceilings live). Over-limit requests get `429` with `{ "error": "rate_limited" }`, except the telemetry ingest, which answers with its usual no-op `204` so a throttled beacon never surfaces as an error.

| Binding                         | Meters                                                                                                                                                                                                 | Key                                                                                                                                             | Where                              |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `WRITE_RATE_LIMITER`            | every `POST` / `PUT` / `DELETE`, except `/api/events` and the room-ticket mint                                                                                                                         | `token:<tokenId>` for an API token, `workbench:<sessionId>` for a workbench session, else the resolved owner id, else the literal `"anonymous"` | `index.ts`                         |
| `API_TOKEN_READ_RATE_LIMITER`   | every `GET` made with an API token                                                                                                                                                                     | `token:<tokenId>`                                                                                                                               | `index.ts`                         |
| `SHARE_RATE_LIMITER`            | `GET /api/share/:code` (the unauthenticated share resolve), and every share-password check the verified cache cannot answer, on any share-code door (key `share-pw:<network>`), against blind guessing | client IP (IPv6 /64)                                                                                                                            | `index.ts`                         |
| `AI_RATE_LIMITER`               | `POST /api/ai` and `POST /api/ai/read-notes`, after the rest of the AI gate                                                                                                                            | client IP                                                                                                                                       | `routes/ai-gate.ts`                |

Other reads (a signed-in or guest `GET`, and every `OPTIONS`) are unmetered. The write ceiling sits well above realistic editing traffic (autosave fires once per debounce window, comments are typed by humans) but low enough to stop a bot from spamming document / image creation into D1 + R2 quota exhaustion. The room-ticket mint is exempt because it shares the per-owner budget with the autosave, and a 429 there would cost a team member the whole session's realtime; `/api/events` is exempt so telemetry never competes with a user's real writes.

Before any limiter, a write whose `Content-Length` exceeds the body cap (`MAX_BODY_BYTES`, or `MAX_IMAGE_BYTES` for `/api/images`, `limits.ts`) is refused with `413`.

Self-host: every limiter is optional. When a binding is absent its check short-circuits to "allow", so deployments without the feature still serve. The bindings are a Cloudflare paid-tier capability; the open-source path stays unaffected (per [Open source + distribution](../002-project-scope/open-source-and-business-model.md)).

## Realtime model

The `DocumentRoom` Durable Object (`apps/api/src/document-room.ts`) is the realtime hub for one document id. Clients connect via the `/ws` endpoint and immediately send a `hello`; the room broadcasts a `presence` snapshot whenever the set changes.

**Hibernation.** The room uses the Workers WebSocket Hibernation API (`state.acceptWebSocket` + class-level `webSocketMessage` / `webSocketClose` / `webSocketError` handlers) rather than in-memory `ws.accept()`, so the runtime can evict an idle room from memory between messages while every client's socket stays open — an open-but-quiet session no longer bills DO duration. All per-session state that matters (the server-assigned ephemeral presence id, the `X-Verified-Role` trust-boundary role, and the `hello` presence including the remembered `tab-focus` tab) survives eviction in each socket's serialized attachment; only the per-session rate-cap window is in-memory and deliberately resets on a wake.

**Access is gated at the upgrade.** Browsers can't set headers on a WebSocket upgrade, so the client passes a one-time ticket / owner id / share code / share password as `?t=` / `?o=` / `?s=` / `?p=` query params. The api worker resolves a role there — the ticket's server-resolved role (see `POST /room-ticket` above; consuming a ticket also satisfies the password gate, since the mint already enforced it), else `edit` for the owner (PERSONAL documents only, and never for an account id, which a signed-in owner presents through the ticket instead — a team document's owner id is visible to every teammate, so it is not accepted as a bare `?o=`; team owners ride the ticket), else the link's role for a valid share code for _this_ document, otherwise none — and **refuses the upgrade outright unless a role resolved** (and, for a password-protected non-ticket non-owner, unless the password matches via a constant-time compare). Team membership is ONLY honoured via the ticket: member ids are Clerk ids deliberately visible to teammates, so a bare `?o=` matching a member must not grant edit (a removed member could otherwise keep joining the room). The resolved role is forwarded to the DO as the `X-Verified-Role` header; the DO re-stamps it onto presence in the `hello` handler, ignoring any role the client typed into its own payload, so that header is the trust boundary. Three more headers ride with it, set on every path so a client can never supply them: `X-Verified-Owner` (`1` when the upgrade resolved as the document's owner, else `0`; a bit, never an id, which the facilitator baton needs so the owner can always take it back), `X-Verified-Tab-Scope` (a tab-scoped link's tab, empty otherwise) and `X-Verified-Share-Code` (the code that admitted a share visitor, empty otherwise). A room ticket carries the scope and the code from the mint. The DO pins them on the session and confines a scoped session to its tab, live and in catch-up ([Tab-scoped share links](../013-workspace/tab-scoped-share-links.md)).

Edits and presence propagate as `op` messages. The room is **not** a stateless relay: it classifies every op, orders the ones that change the document, rewrites a few fields on the way through, keeps a small amount of collaboration state in its own storage, and performs one kind of document write in D1 itself. D1 stays the system of record for document content ([Realtime conflict resolution](../012-collaboration/realtime-conflict-resolution.md), [Collaboration race hardening](../012-collaboration/collab-race-hardening.md)).

### Op classes

Every op kind belongs to exactly one of three lists in `@livediagram/api-schema` (`packages/api-schema/src/room-messages.ts`), and the class decides its ordering, its role gate, and whether a client may send it at all. The room reads `op.kind` to classify; the payload stays `op: unknown` on the wire.

- **Presence** (`PRESENCE_OP_KINDS`): ephemeral, mutate nothing. Relayed unordered (no `seq`), never logged, never replayed, from **any** connected session, so a view-only visitor still shows peers their cursor, selection, laser, walking character and tab, and can answer a poll.
- **Mutation** (`MUTATION_OP_KINDS`): change the document. Relayed **only from a session whose verified role is `edit`**; each gets a monotonic `seq` within the room's `epoch` and a slot in the catch-up log.
- **System** (`SYSTEM_OP_KINDS`): originated only by the api worker through the DO's internal endpoints, stamped `from: 'system'`. Dropped outright when a client sends one, so no peer can forge a revoke or rewrite a Q&A board.

Matched sockets close with **4005** (`ACCESS_CHANGED_CLOSE`, reason `access-changed`); nothing is broadcast, so no other session learns who left. The connector stops on 4005 and the editor reloads, which runs the ordinary access path again: a password prompt, a refusal page, or (when access remains another way) the editor. Besides `op`, the room speaks a few non-op frames: `hello`, `sync` and `facilitator` from clients; `presence`, `catchup`, `cursor`, `facilitator` and `selection-released` from the room.

### What the room does to a frame

In order, for every inbound frame: a frame over 256 KiB is dropped; a per-session sliding-window rate cap (240 frames per second) drops a flood; an op from a session that hasn't said `hello` is dropped; a system-kind op from a client is dropped; a tab-scoped session may only touch its own tab and never the document's structure (`scopedSenderMayRelay`); a non-presence op from a session whose verified role isn't `edit` is dropped; `poll-start` / `poll-end` must come from the baton holder when one is held. Then:

- **Presence ops** relay to every other socket (or, for `avatar-push`, to the one addressed socket).
- **Mutation ops** are rewritten before they go anywhere: `opForTheWire` strips every comment `authorId` (a guest's credential), and `stampCommentAuthor` sets a posted comment's author name and colour to the sending session's presence, whatever the frame claimed. The rewritten op gets the next `seq`, lands in the catch-up log, relays to every other socket, is recorded in the ledger when it is an `el-delta` or `vote`, and the sender receives a `cursor` frame naming the `seq` its own op took, echoing the op frame's `ref` when it carried one (a positive integer), so the sender knows that op is sequenced.
- Every outbound op frame to a tab-scoped session is filtered or redacted for its scope (`opForScope`), live and in catch-up.

On `hello` the room builds the session's presence itself (`helloPresence`): the id is a server-minted per-socket random (never the connector's owner id), the role is the verified one, and every claimed string is length-clamped. It then sends the joiner a `cursor` frame, replays the running poll and its answers, broadcasts presence (each socket gets the roster minus its own entry), and tells the joiner who holds the facilitator baton.

### Ordering and catch-up

Mutations are totally ordered by the single-threaded DO: a monotonic `seq` within an `epoch`. `epoch` and `seq` are persisted in DO storage (`order-state`) and restored on every wake, so hibernation does not strand reconnecting clients ([Resync without reloading the page](../012-collaboration/resync-without-reload.md)). The catch-up log (the last 256 mutations, `OP_LOG_LIMIT`) lives in memory only. On reconnect a client sends `{ kind: 'sync', epoch, lastSeq }`; `resolveCatchup` answers with the ops it missed, or `resync: true` when the gap is behind the log's floor or the epoch is foreign, and the client re-fetches its loaded tabs from D1 in place.

### What the room stores

Durable Object storage, never D1, and none of it a copy of the document:

- **`order-state`**: `{ epoch, seq }`, written on every mutation.
- **The collaboration ledger** (`RoomLedgerStore`, `room-ledger-store.ts`; entries defined by the pure `collab-ledger.ts` in `@livediagram/document`): for every `el-delta` and `vote` it sequences, the latest state of each answer, idea, checklist tick, comment and the round's dots, one key per element (plus the tab's vote), tagged with the `seq` that set it. An entry that would pass the storage value limit stops growing. The api reads it back to merge a tab save (see the tab `PUT` above).
- **The live poll** (`RoomLivePoll`, `room-live-poll.ts`, key `live-poll`): the running poll and every answer, replayed on `hello`, dropped on `poll-end`.
- **The facilitator baton** (key `facilitator`, `facilitator.ts`): who holds it, the token only the holder was sent, and a grace deadline enforced by a DO alarm when the holder's socket goes away ([Facilitator](../012-collaboration/facilitator.md)).

Per-session state (presence id, verified role, owner bit, tab scope, admitting share code, presence) lives in each socket's serialized attachment, so it survives hibernation; only the rate-cap windows and the catch-up log reset on a wake.

### What the room writes to D1

- **Q&A board writes.** `POST /api/documents/:id/tabs/:tabId/qa` hands each board action to the room's internal `POST /qa`; `handleQaWrite` runs them one at a time through an in-memory queue and calls `writeQaAction` (`qa-board-write.ts`), which reads the tab row, applies `applyQaAction`, bumps `qaRev` and compare-and-swaps the row. The result goes out as a sequenced `qa` system op. This is the one document write that happens inside the room.
- **One telemetry row**: the room counts a multiplayer session once (`Document·Used·Multiplayer`, `reportServerEvent`) into the telemetry events table, when `TELEMETRY_ENABLED` is on ([Telemetry + public transparency dashboard](../017-telemetry/telemetry.md)).

Every other document write is a REST call from a client (see the persistence boundary below).

### Internal endpoints

The api worker reaches the DO through its stub (`env.DOCUMENT_ROOM.get(...).fetch(...)`), which never traverses the public edge, so these paths are implicitly internal:

- **`POST /broadcast`** `{ op, ordered? }`: push a system op to every socket (`from: 'system'`), sequenced when `ordered` is true. Used by share-link revoke (`DELETE /api/documents/:id/share/:code`), a tab delete that takes scoped links with it (both `share-revoked`) and a rescope (`share-rescoped`), via `broadcastShareOp` in `room-client.ts`; after relaying either the room closes the sockets that code admitted. Best-effort: a failure is logged (`[room-broadcast]`), never fails the request, since the D1 write is authoritative.
- **`POST /mutation`** `{ op }`: sequence a document change the worker made, as if a peer had sent it. `el-delta`, `changeset` and `tab-meta` are accepted (400 otherwise); the comment endpoints use `el-delta` so a view-role visitor's comment reaches connected editors (`relayElementDelta`), the changeset route uses `changeset` ([Agent changesets](../024-agents/agent-changesets.md#what-the-room-does)), and the tab rename route uses `tab-meta` (`relayTabRename`).
- **`GET /selections?tab=<tabId>&person=<tag>`**: the elements each connected person has selected on a tab (every `select` is recorded in DO storage per session, pruned when the socket goes), each marked `mine` when the session's person tag is the one asked about. The changeset route reads it to find held elements.
- **`PUT /presence`**, **`DELETE /presence`**: an agent's presence entry with its expiry ([Agent presence](../024-agents/agent-presence.md#presence)).
- **`POST /qa`**: one Q&A board write, above.
- **`GET /ledger?tab=<tabId>&epoch=<epoch>`**: the tab's collaboration ledger, or an empty one when `epoch` isn't the room's current epoch (the saver's cursor can't be interpreted then).

### Conflict model

- **Different elements on one tab merge.** `el` ops apply by id, so concurrent edits to different elements survive on every peer.
- **The same element is last-writer-wins, over the whole element.** Two `el` updates to one element apply in room order and the later one replaces the earlier, whoever held the selection. The concurrent-selection lock ([Live app](../007-editor/live-app.md)) is advisory and client-only (`remoteSelectionsByElement`, built from `select` ops): it makes these collisions rare, and the room does not enforce it. `tab-meta` patches are last-writer-wins per field, and `document-meta` per whole tab list.
- **Multi-writer fields merge.** Answers, ideas, checklist ticks, comments and dots travel as `el-delta` / `vote` deltas that commute, and whole-element or whole-tab ops don't overwrite a receiver's copy of them.
- **Q&A boards are server-owned** and ordered by `qaRev`.

### The persistence boundary

D1 holds the document; the room holds ordering and collaboration state. Tab content reaches D1 through `PUT /api/documents/:id/tabs/:tabId`, fired by each editor's debounced autosave with the editor's whole copy of the tab. D1 keeps the last save of a tab, with the room ledger and `qaRev` merged in as described on that row. Each editor's copy already folds in the ops it has received, so the last save normally carries everyone's work; an element edit that reached the saver only after its snapshot can be missing from D1 until a later save carries it, while live peers still hold it.

A tab `PUT` is not relayed to the room; it is the editor's autosave and nothing else's. Every other writer of tab content (the MCP server, the CLI, an API-token script) writes a [changeset](../024-agents/agent-changesets.md), which the api records in D1 and relays to the room, and which every later editor save re-applies unless that editor has seen it. The comment and Q&A endpoints also tell the room about their writes.

Every tab the api receives (document create, tab save) runs the stored-tab migration (`migrateStoredTab`) before `isValidTab`, as every tab read does, so an element in a former stored shape (for example freehand points before [Stroke points](../006-document/stroke-points.md)) from a browser loaded before a deploy, an API-token script or a Google Drive copy is stored in the current shape rather than refused.

## Data model

The schema starts at `0001_init.sql` and evolves migration-by-migration; the migration files double as commit history of the shape. Today, in broad strokes:

- **`documents`** — id, owner, name, share flag, folder fk, timestamps. The original `data` JSON column was dropped in migration 0006 once tabs moved to their own rows.
- **`tabs`** — one row per tab keyed on `(id)`: the body only, in a `data` JSON blob (elements + per-tab settings — theme, background, lock). No column points at a document, so nothing cascades from `documents`; the delete paths drop a tab once no document links it. See [13-per-tab-storage.md](../006-document/per-tab-storage.md) for why.
- **`document_tabs`** — the many-to-many link: `(document_id, tab_id)` with the tab's `order_index` and `folder` in that document, cascading from both sides. See [Tab ↔ document many-to-many](../006-document/tab-document-many-to-many.md).
- **`image_refs`** (migration 0050) — `(tab_id, image_id)`: which gallery images each tab places, a projection of `tabs.data` written in the same batch as every body write, with no foreign keys. Read by image retention, the usage map and share-visitor image reads; `image_refs_backfill` tracks the one-off indexing of older tabs. See [Images, Reference index](../009-elements/images.md#reference-index).
- **`participants`** — id, name, color. Volatile presence/status state stays on the wire.
- **`share_links`** — code → documentId + role. Multiple links per document are supported; revoking a link is a row delete.
- **`folders`** — id, owner, name, optional self-referential `parent_id`. Documents reference a folder via `documents.folder_id`. Both FKs `ON DELETE SET NULL` so deleting a folder promotes its children. Cycle prevention is enforced in the API layer (D1 can't declaratively).
- **`shared_with`** (migration 0010) — `(owner_id, document_id, role, last_seen)`, primary key on `(owner_id, document_id)`. Tracks which documents a non-owner has accessed via a share link so the Explorer can render a "Shared with you" accordion. FK to `documents` with `ON DELETE CASCADE` so deleting / revoking a document drops every visitor's reference for free.

Document-store hybrid: meta + folder + share state lives in real columns; element content lives in tab `data` JSON. Element-level SQL filtering isn't a use case today, so normalising element rows would buy nothing — and the editor already round-trips JSON for every save.

## One-time setup

Before the first deploy:

1. `pnpm --filter @livediagram/api exec wrangler d1 create livediagram`
2. Copy the printed `database_id` into the `[[d1_databases]]` block in `apps/api/wrangler.toml`. The block is already there with its binding name (`DB`) — only the id changes. What is committed is livediagram.app's own database id, so a self-hoster is replacing a real value rather than filling in a blank.
3. `pnpm --filter @livediagram/api run db:migrate:remote` to apply migrations.

After that, GitHub Actions handles deploys via `deploy.yml` (`deploy-api` step). The router's service binding to `livediagram-api` means the API must deploy before the router.
