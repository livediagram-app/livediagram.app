livediagram is not one application but a small set of apps that each deploy as their own Cloudflare Worker, stitched together at a single hostname. This page is a conceptual map of how the pieces fit so the deployment makes sense. For the exact commands and account setup, the repository and its self-hosting guide are the authoritative source.

## The apps

The product is split into focused apps, each deployed as a named Cloudflare Worker.

- **marketing** serves the public landing site at the root.
- **live** is the diagram editor itself, served at clean routes such as `/new` and `/explorer`.
- **telemetry** is the public, read-only analytics dashboard at `/telemetry`.
- **community** is the Community, the public gallery of documents people share, at `/community`.
- **help** is the help centre you are reading now, at `/help`.
- **api** is the Worker that holds the REST and WebSocket layer, backed by the D1 database and the per-document Durable Object.
- **router** sits in front and forwards each request to the right app by URL path. It holds no business logic, only routing.
- **mcp** (optional) is the MCP server that lets people connect AI tools to their documents. It has its own hostname (`mcp.livediagram.app` on the hosted service), needs sign-in configured, and talks to the api Worker directly.

The router is what makes the first six appear under one domain.

## How a request is routed

The router Worker inspects the path and forwards accordingly: `/api/*` to the api Worker, `/telemetry` to the dashboard, `/help` to the help centre, `/community` to the Community, the editor's routes (`/document`, `/explorer`, `/new`, `/join`, `/sign-in`, `/get-started`, `/embed` and the like) to the live app, and everything else to marketing. Because the router has service bindings to the six path-routed apps, they must exist before the router can be deployed.

## How it deploys

Deployments run through **GitHub Actions to Cloudflare Workers**. In broad strokes:

1. Continuous integration runs lint, format, typecheck, test, and build on every pull request and push.
2. A separate, manually triggered deploy workflow builds everything, then deploys the apps.
3. The marketing, telemetry, help, community, and api Workers deploy in parallel. The live editor follows the api, so a new editor never calls an api that lacks its routes, and the optional mcp Worker follows the api too. The router deploys last because its bindings depend on the six path-routed apps already existing.
4. Database migrations are applied to D1 as part of the api deploy, before the new Worker code goes live.

Deploying needs a Cloudflare API token and account id, supplied as repository secrets (`CF_API_TOKEN` and `CF_ACCOUNT_ID`), never committed to source. You can also deploy each Worker by hand with `wrangler deploy` in the same order. The repository also has a staging workflow that the hosted service uses for rehearsals; a fork can delete it.
